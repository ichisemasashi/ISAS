## 1. 開発方針（プロジェクトを貫く原則）

要求定義フェーズで確立し、以降の全フェーズに適用する原則。

1. **反復＋敵対的レビュー**：成果物は「作成→敵対的レビュー（矛盾・欠落・非現実性の摘出）→修正」を反復して確定する。各レビューは記録票に残し、指摘を追跡IDで管理する。
2. **UXを第一級要求**：既存システム（KSAS等）の「機能はあるが使い辛い」を回避し、UXを機能と同格に扱う（要求仕様 4.11／5.1）。設計・実装でも実ユーザー参加型の検証を行う。
3. **技術リスク先行（リスクファースト）**：不確実性の高い部分（オフライン同期・地図性能・RLS×規模）は、本実装前にスパイク（技術検証）で潰す。
4. **食品安全・法令遵守を優先**：農薬記録・トレーサビリティ・GDPr等に関わる要件は優先度Mustとし、フェーズを前倒しする。
5. **段階リリース（フェーズ制）**：MVP（Phase 1）で現場入力の核を最速で価値化し、以降段階的に拡張する。

## 3. 各工程の詳細

### 工程1：要求定義（✅ 完了）

「何を作るか（What）」を合意する工程。**本プロジェクトでは反復＋敵対的レビューで実施した。**

- **進め方**：ドラフト作成 → 未決事項を順次確定（対象作物・農機連携・GAP・オフライン・規模・テナント・多言語・海外対応 等）→ 各版で**敵対的レビュー**を実施し、指摘を全件処置。
- **敵対的レビューの運用**：
  - 「この仕様のまま設計に進むと破綻・紛糾する箇所」を、擁護ではなく攻撃の視点で摘出。
  - 指摘を重大度（Critical/High/Medium/Low）と追跡ID（C-1、R2-M3 等）で管理し、記録票に残す。
  - ユーザーの意思決定で対策方針を確定 → 仕様へ反映 → 再レビュー、を収束するまで反復。
- **結果**：
  - 版：v0.1 → **v1.0**（確定）
  - レビュー：**全11回**、**累計72件**を処置（Critical 3／High 8／Medium 27／Low 34）
  - 収束の証跡：**High指摘が7回連続ゼロ**、指摘が基本設計の粒度に収束
- **成果物**：
  - [要求仕様書 v1.0](農業営農支援システム_要求仕様書.md)
  - レビュー記録票 [第1回](要求仕様書_敵対的レビュー記録票_v0.9.md)／[第2回](要求仕様書_敵対的レビュー記録票_第2回_v0.13.md)／[第3回](要求仕様書_敵対的レビュー記録票_第3回_v0.15.md)／[第4回](要求仕様書_敵対的レビュー記録票_第4回_v0.16.md)／[第5回](要求仕様書_敵対的レビュー記録票_第5回_v0.17.md)／[第6回](要求仕様書_敵対的レビュー記録票_第6回_v0.18.md)／[第7回](要求仕様書_敵対的レビュー記録票_第7回_v0.19.md)／[第8回](要求仕様書_敵対的レビュー記録票_第8回_v0.21.md)／[第9回](要求仕様書_敵対的レビュー記録票_第9回_v0.22.md)／[第10回](要求仕様書_敵対的レビュー記録票_第10回_v0.23.md)／[第11回](要求仕様書_敵対的レビュー記録票_第11回_v0.24.md)

### 工程2：基本設計（🟡 進行中）

「どう作るか（How）」の骨格を決める工程。要求仕様の依存関係とリスクから、**データモデルを土台に据え、高リスク項目をスパイクで並行検証**する。

#### 2-0. アーキテクチャ決定記録（ADR）
- **目的**：要求仕様7章の「たたき台」を確定し、以降の判断基準を明文化する。
- **決めること**：フロント（React＋PWA/Service Worker）／地図（MapLibre＋PostGIS、背景衛星の役割分離）／バックエンド（REST or GraphQL・認証・RBAC）／DB（PostgreSQL＋PostGIS）／マルチテナント分離（行レベル＋RLS・セッション変数方式）／1システム=1DB=1国の配備モデル／i18n（ICU/CLDR）。
- **成果物**：`docs/design/ADR/`（決定ごとに1ファイル）
- **完了基準**：主要な技術選定が根拠付きで確定し、レビュー済み。

#### 2-1. データモデル設計＋マルチテナント/RLS権限設計（★最優先の土台）
- **目的**：全機能が乗るスキーマと権限モデルを固める。
- **設計する内容**：
  - 論理ERD → 物理テーブル定義（`tenant_id`・更新時刻・更新者・バージョン番号・deleted_at）
  - **RLSポリシー**：3.2ロール表のDB表現／グループ管理者の横断／**本人起点の横断（user_idベース、労務サマリ限定）**／**個人データ（位置ログ・打刻・労務サマリ）の最小権限**
  - **追記型イベント**（StockEvent・打刻Punch・位置ログ）と競合解決（5.1.1）のテーブル設計
  - **論理削除・版履歴**（復元用、F-D06②）、**監査ログ**（改ざん耐性・仮名化）
  - PostGIS（圃場ポリゴン・メッシュ・GPSログ）、i18n（I18nLabel）
- **成果物**：`docs/design/データモデル設計書.md`＋ERD
- **完了基準**：Phase 1機能を満たすスキーマ確定／RLSポリシー方針確定／敵対的レビュー通過。

#### 2-2. オフライン同期方式設計（技術リスク：高）
- **目的**：5.1.1のデータ分類別ルールを実装可能な同期方式に落とす。
- **設計する内容**：PWA＋Service Worker＋ローカルストレージ／同期プロトコル（差分・追記型）／競合解決（追記型・前進優先マージ・楽観ロック）／端末時刻とサーバー受理時刻の二本立て／端末キャッシュ対象（農薬マスタ・使用履歴・作業リスト・地図タイル・**テンプレート/前回値**）／許容遅延（5.3.1）。
- **成果物**：`docs/design/オフライン同期設計書.md`＋**スパイク結果**
- **完了基準**：競合シナリオが方式で解決できることをスパイクで実証。

#### 2-3. UXデザインシステム＋情報アーキテクチャ（第一級要求）
- **目的**：F-D01（デザインシステム）・F-D11（IA/ナビ）等、Phase 1のUX土台を設計する。
- **設計する内容**：デザイントークン（色・タイポ・余白）／コンポーネント／アイコン・ピクトグラム／状態表示（同期/保存/エラー）／主要タスクのIA・ナビ／多言語・RTL・アクセシビリティ（WCAG 2.1 AA）／現場最適化（手袋・直射日光）。
- **プロセス**：プロトタイプ → **実ユーザー参加型ユーザビリティテスト**（作業員・高齢者・実習生）で検証。
- **成果物**：`docs/design/UXデザインシステム.md`＋プロトタイプ＋UT計画（UX目標：タスク成功率90%・SUS75等）
- **完了基準**：主要タスク（作業確認・日誌・農薬記録）のUXがUT初期目標を満たす見込み。

#### 2-4. 農機共通データモデル（ISOBUS/ADAPT）
- **目的**：ベンダー非依存の共通データモデル＋アダプタ層を設計する（主軸＝ファイル取込）。
- **設計する内容**：共通データモデル（ISOBUS/ISO-XML・ADAPT参照）／アダプタIF（ファイル取込を中核、農機OpenAPI・DataConnectを補助）／日次バッチ取込＋自前永続化。
- **成果物**：`docs/design/農機連携設計書.md`
- **完了基準**：初回アダプタ（ファイル取込＋農機OpenAPI補助）の設計確定。

### 工程5：リリース・運用・改善

- **段階リリース**：Phase 1（MVP）を優先リリースし、現場に定着させてから拡張。
- **継続改善**：利用データ（離脱・エラー・タスク時間）でUX・性能を継続改善（5.1の反復）。
- **運用者責任の明確化**：OSS（MIT）として、サービス実施範囲・データレジデンシー・法令遵守は運用者責任（要求仕様#13）。

## 4. 横断的活動（全工程に適用）

- **品質保証（敵対的レビュー）**：要求定義で確立した「作成→敵対的レビュー→修正」を、設計書・実装にも継続適用する。
- **UX検証**：プロトタイプ段階から実ユーザー参加型テストを行い、リリース後も継続。
- **セキュリティ／プライバシー**：保存時暗号化・RLS・監査ログ・GDPR権利対応・位置情報の最小権限を全工程で担保。
- **データ移行**：既存Excel/CSV・農薬使用履歴・旧MITサービスデータの回収と取込（清算期限に留意）。
- **国際化基盤**：i18n・UTC・単位/通貨はPhase 1から組み込む（海外はPhase 4だが基盤は先行）。

### 6.3 レビューから得た運用上の教訓

> **教訓1（ADR-0008 第8回）**：設計者＝査読者では自分の前提を疑えず、7巡＋3軸チェックでもHigh（IND-H1）を見落とした。**接合の多い重要ADRは、自己巡回に加えて独立レビュー（別セッション/別エージェント）を1回入れる**を標準手順とする。入れるタイミングは「N回ごと」ではなく**自己レビューが全緑（Medium 0）に達した版**——そこが自己判断の最も信用できない瞬間。
>
> **教訓2（ADR-0002 第5回）**：**クローズ済みADRへ波及追記したら、その版に対して1回レビューを回す**。ADR-0002 v6 は「決定を1箇所に4行足した」だけで、構成要素一覧・帰結・未解決事項・関連する既存決定（A2b-M2）の射程が更新されず、High 2 を生んだ。**追記は本文全体に行き渡らせる**。
>
> **教訓3（ADR-0002 第6回）**：**同じ版で複数の指摘を処置したら、処置どうしを突き合わせる**。v7 は第5回の8件に個別に正しく答えたが、**A2f-H1 の答え（索引を全シャードに複製）と A2f-M2 の答え（加入は同期反映）を合成すると分散トランザクションになる**という High を生んだ。個別最適の合成は壊れる——**「処置の合成」をレビューの検査項目に加える**。
>
> **教訓4（ADR-0001 第6回）**：**「〜と同じ扱いにする」という書き方は危険信号**。ADR-0001 v8 は特権経路専用テーブルを「A1e-M1 と同じ扱い」と書いたが、**A1e-M1 が"何を避けるために"そうなっているか（フェイルクローズの自己ブロック）を引き継がなかったため、形だけ真似て逆の結果（認証の自己ブロック）を招いた**。ADR-0002 v6 が「中央IDと同じ」と書いて IND-H1 を生んだのと同じ構造。**既存決定を参照するときは、その決定の"回避目的"まで確認する**。あわせて、**追記が使う道具（今回はRLS）がそのADRの既存決定と技術的に噛み合うかを検査する**。
>
> **教訓5（ADR-0001 第7回）**：**処置で「何を失ったか」を検査する**。v9 は守り方を RLS から `GRANT` へ替えて自己ブロックを解消したが、**RLSが暗黙に提供していた「テーブルを列挙せず網羅検査できる」性質**（`pg_class.relrowsecurity` 走査）を失ったことに気づいていなかった。**道具を替えると、目的は達しても副次的性質が落ちる**。教訓3（処置の合成を検査）の裏返しとして、レビューの検査項目に加える。
>
> **教訓6（ADR-0001 第7回・プロセス）**：**追記は必ず「6箇所」に行き渡らせる**。「追記が本文全体に届いていない」という同型の指摘が**3回連続で再発**した（ADR-0002 A2f-L3 → ADR-0001 A1f-M1 → A1g-M2）。個別に直しても止まらないため、追記のたびに **①§1背景の前提／②§2の総論的な決定文／③§3選択肢（裁定なら記録）／④§4帰結／⑤§5未解決事項／⑥関連する既存決定の射程** を確認することを運用ルールとし、レビューの検査項目にする。
>
> **教訓7（ADR-0002 第7回）**：**上流ADRの整理が進んだら、その処置が下流に作らせた負債を回収する**。ADR-0002 v8 は「索引は性能最適化」という良い整理に到達したが、**その整理が示す当然の帰結（＝ならばテーブルとして持つ必要すらない）を辿らず**、既に ADR-0001 に作らせた「RLSの防波堤の外」の枠を前提として残した——結果、**任意コンポーネント1つのためにP0土台に恒久的な例外**が残った。教訓5（処置で何を失ったか）の裏返しとして、**「処置で下流に何を余計に背負わせたか」「上流が改善したら下流の負債を戻して回収できないか」**を検査項目に加える。
>
> **教訓8（ADR-0002 第7回）**：**却下する選択肢は、その選択肢の最良の形で書く**。ADR-0002 §3.2 は (iv)「索引を持たない構成」を「**IdPに所属を持たせる**」と定式化したが、それは真実源を二重化する不利な形であり、正しい (iv) は「各シャードのメンバーシップから導出する」だった。**選択肢の記述バイアスが裁定を誤らせる**——選択肢表を書いたら、却下する側を**その案の擁護者ならどう書くか**で見直す。
>
> **教訓9（ADR-0002 第8回）**：**教訓5は「失った機能」ではなく「失った保証」を検査する**。ADR-0002 v9 は物理索引を捨てて整合・鮮度・侵害面の問題群を消したが、**索引の複製が暗黙に支えていた「対象シャード集合を知れる」という保証**を失い、**complete が構造的に常に真になる**High を生んだ。**機能一覧を見ても出てこない——"その仕組みが何を保証していたか" を辿らないと見つからない。**
>
> **教訓10（ADR-0002 第8回・プロセス）**：**教訓はチェックリスト化し、版ごとに適用結果を記録する**。v9 は教訓6（6箇所）を明示的に適用したので5/6箇所を守れたが、**明示しなかった教訓（A2h-L3の「範疇を超えた規定」・教訓7の「下流への逆流」）は同じ版で破っていた**。**教訓は書いただけでは守られない**——処置結果に「各教訓の適用結果」を1行ずつ記録する運用にする。
>
> **教訓11（ADR-0002 第9回・独立レビュー）**：**「未処置ゼロ＝収束」は成り立たない**。ADR-0002 は v10 時点で未処置ゼロだったが、独立レビューが **High 4件**（FORCE RLS の実挙動／restrictive の AND 合成／監査チェーンの移送／要求仕様の用語破り）を検出した。**未処置ゼロは「これまでに当てた角度では見つからない」ことしか意味しない。** また **「指摘が周縁化・メタ化している」ことを収束の証拠にしてはならない**——角度が固定されていれば、土台側に未検査の穴が残ったまま指摘だけが外側へ移動する。**独立レビューの投入条件は「全緑に達した版」だけでなく「High が連続する版」も含める。**
>
> **教訓12（ADR-0002 第9回）**：**同じ判断規則を、対象を変えて総当たりで適用したかを検査する**。IND2-H1 も IND2-H3 も、**必要な知識はリポジトリ内に既にあった**——「FORCE RLS 下では SECURITY DEFINER でも0行」はデータモデル設計書 §6 の `audit_writer（BYPASSRLS）` に、「restrictive は AND だから permissive を足しても通らない」はデータモデル設計書 §4 の④除外規定に、それぞれ**正しく書かれていた**。それなのに**メンバーシップと横断経路には適用されなかった**。**知識の欠如ではなく適用の網羅性の欠如**であり、レビューでは「**この規則が当てはまる対象を全列挙したか**」を明示的に問う必要がある。
>
> **教訓13（ADR-0001 第8回）**：**同じ版の中で思想が一貫しているかを検査する**。ADR-0001 v13 は A1g-H1 で「**強制力を人手の一覧からスキーマとテストへ移す**」と正しく述べながら、同じ版の (β) では「**検査が唯一の防御**」に戻っていた（A1h-H1）。**教訓を1箇所に適用しても、同じ版の別の箇所には適用されていない**——教訓10（版ごとに各教訓の適用結果を記録する）を、**処置を入れた全文書に対して**行う（ADR-0002 v10 では実践したが ADR-0001 v13 では記録がなかった）。
>
> **教訓14（ADR-0001 第8回）**：**「列挙の網羅性」は列挙の対象を機械的に洗い出す手順まで落とす**。教訓12 を立てた直後の版で、**③共有＋上書きの漏れ（A1h-M2）と「作業時間」の漏れ（A1h-L1）が2件同時に発生**した。「全列挙したか」と問うだけでは守れない——**分類表の全行／並記された語の全項目／表の全列に機械的に当てはめる**という手順にする。
>
> **教訓15（PostgreSQL実挙動検証）**：**外部技術に依存する設計は「単一機能の性質」と「包含関係を跨いだときの挙動」を別に検証する**。20項目の単一機能の記述はすべて正確だったのに、誤りは**すべて包含を跨ぐ場所**に集中した——親→パーティション子／テーブル→ビュー／セッション→トランザクション／ポリシー→実行プラン／述語→カタログ表現／ロール属性→メンバーシップ／USING→WITH CHECK。**「自動で効く」と仮定した場所を機械的に洗い出す**。
>
> **教訓16（PostgreSQL実挙動検証）**：**スパイクのSQLと文書のポリシー/DDL本文は同一でなければならない。** 別物なら PASS は設計を検証していない（今回、差異15件・述語形5種のうち3種は一度も実行されていなかった）。**検証成果物（EXPLAIN 全文・実行ログ）をリポジトリに保存する**——要約数値だけでは再現性がなく、後から「Index Cond に何が入ったか」を判定できない。**スパイクは最も内側の1経路だけを通しても PASS するので、包含の外側を明示的に試験項目に含める。**
