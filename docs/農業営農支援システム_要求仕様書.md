## 1. 背景・目的

### 1.1 背景
- 圃場の集約・大規模化が進み、紙・Excelでの管理が限界に達している。
- 複数の従業員・作業受託先が広範囲の圃場で作業するため、「誰が・いつ・どこで・何を」の共有が困難。
- 収量・品質・コストのデータが分散し、経営判断（PDCA）に活かせていない。

### 1.2 目的
- 圃場・作付・作業・資材・収穫データを一元管理し「見える化」する。
- 現場（スマホ）と管理（PC）をつなぎ、作業指示と記録を効率化する。
- 蓄積データを分析し、収量・品質の向上とコスト最適化を支援する。
- 外部システム（農機・会計・気象・センシング等）と連携できる基盤とする。

### 1.3 スコープ
- **対象**：大規模・法人経営（従業員複数・作業受託あり）を主想定。ただし極小規模から最大規模まで同一システムで対応する。
- **対象作物**：水稲・畑作・野菜・果樹のすべてを対象とする（作物種別に依存しない汎用データモデルとする）。
- **対象地域**：日本国内および**海外圃場**を対象とする。**対象国は固定せず**（農作業が行われる地域すべてを想定）、圃場に**国コード**を持たせ、国別プロファイル（規制・地図・言語・単位/通貨）を段階的に整備するアダプタ的方式で対応する。国内制度に依存する機能（筆ポリゴン取込 F-06／WAGRI農機連携 F-56／JGAP・環境保全型農業直接支払 F-81〜83 等）は国内圃場向けとし、海外圃場は各国の規制・認証（GLOBALG.A.P.等）への対応を段階的に行う（**国内先行**）。データモデル・i18n・単位/通貨/タイムゾーンは海外圃場を前提に国・地域非依存で設計する。
- **配布形態／ライセンス**：本システムは**MITライセンスのオープンソースソフトウェア（OSS）**として配布する。
- **利用形態**：運用形態は配備者（デプロイする主体）の自由とし、**自社利用・複数法人のグループ/連合利用・第三者へのサービス提供（SaaS運用等）のいずれも許容**する。複数組織の同居を前提にマルチテナント構成とする。
- **想定規模**：圃場枚数は極小〜巨大。**ユーザー数の上限は「1DB（1システム＝1国）あたり最大5万人」**を性能設計の基準とする。全体規模はシステム（＝国別のDB）の増設で水平に拡張し、総数に上限を設けない。
- **今回の整理範囲**：ソフト機能全体＋農機/IoT/API連携までの全体像。
- **重視点**：①スマホ現場入力のしやすさ ②地図・GIS ③外部連携・API ④データ分析・可視化。

> 補足：OSSとして誰でも運用でき、1配備あたり複数法人のグループ/連合利用（1DBあたり最大5万ユーザー）を前提とするため、組織（テナント）単位のデータ分離・権限管理を設計の基本に置く。個々の運用者がどの範囲・どの地域でサービスを実施するか、データレジデンシーや法令遵守（GDPR等）をどう満たすかは**運用者の責任**であり、本仕様はそれを可能にする機能を提供する立場をとる。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 圃場（ほじょう） | 田・畑・果樹園など作物を育てる区画。枚数で数える。 |
| 作付（さくづけ） | ある圃場・シーズンに、どの作物・品種を栽培するかの割当。 |
| 作業日誌 | 「いつ・どこで・誰が・何の作業をしたか」の記録単位。 |
| メッシュ | 圃場を格子（例：5〜20m四方）で区切った単位。可変施肥や収量マップに使う。 |
| 可変施肥 | 圃場内の生育ムラに応じて施肥量を場所ごとに変えること。 |
| トレーサビリティ | 農薬・肥料の使用履歴を追跡・証明できる状態。GAP等で必要。 |
| 組織（Organization） | 権限・データ分離の単位となる法人・団体。「テナント」とほぼ同義で用いる。 |
| テナント | マルチテナントにおけるデータ分離の単位。本仕様では組織＝テナントとして扱う。複数組織をまとめる親を「グループ/連合」と呼ぶ。 |
| メンバーシップ（Membership） | ユーザーと組織を結ぶ多対多の関連。組織ごとにロール・権限を個別付与する。受託作業者が複数組織にまたがる場合の受託リレーションを表す。 |
| システム（1稼働単位／配備単位） | 本ソフトウェアの1つの稼働単位＝配備単位。**1システム＝1DB＝原則1国**を対象とし、データ所在・地図・規制の境界となる（複数国は国ごとに別システムを配備）。※旧「リージョン」に相当。用語の重複を避けるため本仕様では「システム」または「国」を用い、「リージョン」は用いない。 |
| 国コード | 圃場・組織が属する国を表す識別子（ISO 3166等）。地図・規制・言語・単位の切替に用いる。 |
| 国別プロファイル | 国ごとに異なる規制・地図ソース・言語・単位/通貨などの設定の束。対応国の追加時に整備する。 |
| RLS（行レベルセキュリティ） | DBの行単位でアクセス制御する仕組み（PostgreSQL Row Level Security）。テナント分離の基盤。 |
| DWH（データウェアハウス） | 分析用にデータを集約する基盤。本システムでは国またぎ集計を行う場合にシステム外へ任意で設ける（PIIフリー/仮名化推奨）。 |
| SLO | サービス品質の目標値（応答時間・稼働率等）。5.2の数値目標を指す。 |
| RPO/RTO | RPO＝障害時に許容する最大データ損失（目標復旧時点）、RTO＝復旧までの最大時間（目標復旧時間）。 |
| LWW（最終更新優先） | 競合時に更新時刻の新しい方を採用する解決方式（last-write-wins）。 |

> **グループ管理者の横断範囲**：グループ管理者の「全組織○」は、**単一システム（＝1DB＝単一国）内の組織群に限定**する（1システム＝1DB＝1国のため）。**多国籍グループ（例：国内本社＋海外子会社）の統括は1システム内では完結しない**。この場合は各国システムのエクスポートを**システム外の統合レポートで束ねる**（本システムの1稼働単位の責務外。7章・9章#11と整合）。

> **クロステナント（受託作業者等）**：受託作業者のように複数の組織にまたがって働くユーザーは、ユーザーと組織を**多対多のメンバーシップ**で結び、**組織ごとに個別のロール・権限を付与**する（テナントAでは受託作業者、テナントBでは別権限、というように独立に設定）。1ユーザーが複数テナントに所属できるが、各テナント内で見えるのは付与された範囲のみで、テナント間のデータは既定で分離される。上表の各ロールは「あるテナント内での」権限を表す。

> **本人起点の横断ビュー（テナント分離の明示的例外）**：受託作業者**本人**（およびその**雇用主テナントの管理者**）は、テナント分離の例外として、**本人の全メンバーシップにまたがる自分の稼働実績を横断参照・集計できる**（労務・給与の基礎：F-70〜72）。これはグループ管理者の横断とは別の、**本人起点の限定的横断**であり、参照できるのは当該本人の稼働に関する情報のみ（他者・他組織の業務データは含まない）。同一システム（1DB）内で成立し、システム（国）をまたぐ場合はシステム外で束ねる。

## 4. 機能要求

各機能に優先度を付す（**M**=Must / **S**=Should / **C**=Could）。

### 4.1 圃場管理・GIS（重点）
- **F-01（M）** 電子地図上で圃場をポリゴンとして登録・編集・削除できる。
- **F-02（M）** 圃場に属性（圃場名／住所／面積／所有者／地目／メモ）を登録できる。
- **F-03（M）** 作物・所有者・状態などで圃場を色分け表示できる。
- **F-04（S）** 面積を地図から自動計算できる（手入力も可）。
- **F-05（S）** 圃場をグループ・エリア・団地単位で束ねて管理できる。
- **F-06（S）** 筆ポリゴン（農水省公開データ、国内のみ）等の外部地図データを取り込める。
- **F-07（C）** メッシュ（格子）単位で圃場内を区切って管理できる。
- **F-08（M）** スマホのGPSで現在地から近い圃場を特定できる。
- **F-08a（M／Phase 2）** 作業員の位置ログを記録し、**作業実績の裏取り・可視化**（軌跡・在圃時間）に活用する（**F-73**）。将来的には進捗率の自動推定（F-73a）や作業計画の見直し（F-12/4.3.1ガント）にも用い得る。位置ログは**作業中のみ記録（ON）し、休憩中は記録を停止（OFF）**する。**OFF判定は打刻（F-74・Must）への連動を既定**とし（作業開始/完了・休憩の打刻に連動）、作業員の明示操作を補助手段とする。
  - **同意前提・グレースフル縮退**：位置ログの記録は**事前同意した作業員についてのみ行う**（5.4.1）。**同意しない作業員には位置ログを記録せず、その場合でも他機能（作業日誌・打刻等）は支障なく動作する**。したがってF-08aは「収集機能としてはMust」だが、個々の作業員の記録は同意を前提条件とする。
  - **フェーズ**：位置ログの収集は消費機能（F-73）と同じ**Phase 2**で導入する（Phase 1で消費先のないPIIを収集しないため）。打刻（F-74）とそのOFF制御はPhase 1で先行する。取得はプライバシー要件（5.4.1）に従い、常時監視・行動追跡を目的としない。
- **F-09（M）** 地図基盤は**ベクタ地図エンジン（MapLibre＋OpenStreetMap系）でポリゴン描画・オフライン**を担う。背景の衛星画像は用途で役割を分ける：
  - **ポリゴン描画用の背景＝高精細衛星画像（MapTiler／Esri World Imagery(for Export)等の有償ソース）を既定**とする（畦・小区画・果樹列の境界をトレースするにはメートル級の高精細が必須。無償で全機能を賄う前提はとらない）。
  - **Sentinel-2（無償・10m）は生育解析用**（NDVI等、F-52/F-61）に用い、ポリゴン描画の主背景としては用いない。
  - 国・地域非依存の地図ソースを用いる。Google Earth/Google Maps は利用規約で「衛星画像からのポリゴントレース（digitize）」および「タイル/衛星画像のオフライン保存」を禁止しており、F-01・F-34と両立しないため採用しない。
- **F-09a（M）** オフライン地図タイルは、**全世界を1配備に保持しない**。1配備（1DB）は**原則1国を対象**とし、**その国分のオフラインタイルのみを対象**とする。端末側は担当圃場周辺（バウンディングボックス＋バッファ）を事前ダウンロードして保持し、端末容量の破綻を避ける。

### 4.2 作付計画
- **F-10（M）** 年度・シーズン単位で作付計画（圃場×作物×品種）を作成できる。作物は水稲・畑作・野菜・果樹すべてに対応し、作物種別を設定で追加できる。
- **F-11（S）** 農薬・肥料の使用量・単価を設定し、栽培面積と掛け合わせて資材費をシミュレーションできる。
- **F-12（S）** 作物ごとの標準作業暦（テンプレート）から、開始日・工期・依存関係付きの作業タスク群（4.3.1のガント）を自動生成できる。
- **F-13（C）** 輪作・連作の履歴を参照して警告できる。

### 4.3 作業指示・タスク管理（大規模法人で重要）
- **F-20（M）** 管理者・責任者が作業（圃場・作業種別・開始予定日・終了予定日／工期・担当者）を指示できる。
- **F-21（M）** 作業員はスマホで自分に割り当てられた作業リストを確認できる。
- **F-22（M）** 他メンバーの作業状況（未着手／進行中／完了）も共有・可視化できる。
- **F-23（S）** 天候・優先度による作業の並べ替え・再割当ができる。
- **F-24（C）** 作業指示に施肥量・散布量などのパラメータを付与できる。

### 4.3.1 スケジュール・工程管理（ガントチャート）（重点）
> 開始日〜終了日を持つタスクを時間軸で管理し、ガントチャート形式で全体工程を計画・追跡する。

- **F-25（M）** 各作業タスクに「開始予定日・終了予定日（または工期日数）」を設定できる。
- **F-26（M）** タスク群を横軸＝日付のバーで表示するガントチャート（タイムライン）を提供する。
- **F-27（S）** タスク間の依存関係（先行→後続、例：代掻き→田植え）を設定し、チャート上に表示できる。
- **F-28（S）** 依存関係のある先行タスクの日程を変更すると、後続タスクの予定日を自動でずらせる（連動）。
- **F-29（S）** マイルストーン（田植え開始日・出荷締切など重要期日）を設定・表示できる。
- **F-2A（S）** バー上に進捗率（%）を表示し、計画（ベースライン）と実績を対比できる。
- **F-2B（S）** 圃場グループ・作物・作業種別・担当者でガントチャートを絞り込み／並べ替えできる。
- **F-2C（S）** 担当者・農機ごとの割当を時間軸で表示し、負荷の重なり（オーバーアロケーション）を検知・警告できる（リソースビュー）。
- **F-2D（C）** チャート上でバーのドラッグ操作により日程・工期を直接変更できる。
- **F-2E（C）** 作物ごとの作業適期ウィンドウ（例：田植えは4/20〜5/10）を背景帯として表示し、逸脱を警告できる。
- **F-2F（C）** 天候予報（4.10 F-91）と連動し、雨天予定日に屋外作業が重なる場合に警告できる。
- **F-2G（C）** クリティカルパス（遅延が全体遅延に直結する経路）を強調表示できる。
- **F-2H（S）** ガント上の予定を、作業員のスマホ作業リスト（F-21）および作業日誌（F-30）と同一データで連動させる。

### 4.4 作業記録（日誌）（現場入力の要）
- **F-30（M）** スマホ・PCから数タップで作業日誌を作成できる（圃場・作業種別・日時・作業者）。**日時は打刻（F-74）から自動補完できる**（手修正も可）。
- **F-31（M）** 写真・メモを日誌に添付できる。
- **F-32（M）** 使用した農薬・肥料を記録できる。**農薬記録の必須項目**は、散布月日・圃場・作物・薬剤名・希釈倍率・散布量・対象病害虫・作業者・使用器具とする（JGAP／農薬取締法省令の記帳事項に準拠）。
- **F-33（S）** 作業時間・使用機械・投入資材を記録し、原価計算に連携できる。
- **F-34（M）** オフラインで入力し、通信回復時に同期できる（圏外圃場が多いため必須）。入力・写真添付・作業リスト参照・資材の出庫記録（F-42）・**農薬使用基準の事前警告（F-41）**がオフラインで動作すること。そのため農薬マスタ・使用履歴・作業リスト・担当圃場周辺の地図タイル等を端末にキャッシュする。競合解決は5.1.1のデータ分類別ルールに従う。
- **F-35（S）** よく使う入力パターンを定型化して入力を省略できる。
- **F-36（S）** 農機連携により作業を自動記録できる（4.6参照）。
- **F-37（M）** 既存のExcel/CSV（圃場台帳・作業記録等）を取り込み、初期データとして移行できる（マッピング指定・重複チェックを含む）。移行対象には、F-41（M・使用回数/収穫前日数チェック）が初年度から正しく機能するよう、**過去の農薬使用履歴**を含める。移行粒度は、**最低限は薬剤別の使用回数・最終散布日のサマリ**を取り込む。**F-41の使用回数・収穫前日数チェックはこのサマリで充足する**（使用回数＝件数、収穫前日数＝最終散布日からの経過で判定できるため）。**個々の散布レコード（散布日・薬剤・圃場・作物）は監査・トレーサビリティ（F-43）の遡及に有用**なので、可能なら併せて取り込む。移行しない場合は初年度の使用回数チェックが不完全になる旨を利用者に明示する。

### 4.5 資材・在庫・トレーサビリティ
- **F-40（M）** 農薬・肥料マスタ（登録番号・成分・希釈倍率・使用回数制限等）を管理できる。
- **F-41（M）** 農薬の使用基準（適用作物・回数・収穫前日数）をチェックし、違反を警告できる。**農薬マスタおよび当該圃場・作物の使用履歴を端末にキャッシュし、オフラインでも散布記録の入力時点で事前警告できる**こと（圏外での違反散布→同期後発覚という食品安全リスクを回避）。オンライン同期時にサーバ側で再チェックし、齟齬があれば通知する。（食品安全に直結し、F-34/F-41aのオフライン必須要件が依存するためMust。v0.16でSから格上げ。）
- **F-41a（M）** オフラインキャッシュした農薬マスタの**鮮度管理**を行う（失効農薬の誤判定を防ぐ）：①キャッシュに**バージョン／有効期限**を持たせ、**オンライン時に強制更新**する。②一定期間更新がない場合は「**マスタが古い可能性**」を警告する。③**失効農薬は失効日を保持**し、オフラインでも失効判定・警告できる。
- **F-42（M）** 資材の入出庫・在庫の**コア機能**：在庫残高は直接編集せず、**入出庫イベントの追記**から導出する（オフライン同期時の消失防止：5.1.1）。**出庫記録は現場からオフラインで入力できる**（F-34/F-41の農薬記録・基準チェックの基礎となり食品安全に関わるためMust）。同期後にマイナス在庫が生じた場合の**是正フロー**：①**管理者へ通知**する、②管理者が実棚を確認し、残高を直接書き換えるのではなく**棚卸し調整イベント（差分の入出庫イベント）を追記**して整合させる（追記型を維持し監査証跡を残す）。農薬は使用量が法規制対象のため、是正は記録として追跡可能とする。
- **F-42x（S）** 在庫管理の**高度機能**（発注点管理・棚卸し支援・在庫評価等）。コア（F-42）とは別要件とし、Phase 2以降で対応する。
- **F-43（S）** 圃場・作物単位で農薬/肥料使用履歴を出力し、GAP・出荷証明に使える。

### 4.6 農機・IoT・センシング連携（重点：外部連携）
> 方針：特定メーカー/機種に固定せず、ベンダー非依存で連携する。**主軸はISOBUS/ISO-XML等のファイル取込（CSV/SDカード等を含む）**とし、メーカー個社のクラウドAPI（WAGRI/農機OpenAPI・海外のDataConnect等）は**「利用できる場合に使う補助的手段」**と位置づける。これは、特定メーカーのAPI提供停止・事業撤退（例：三菱マヒンドラ農機のMITサービス終了）によっても中核機能が失われないようにするため。

- **F-50（S）** 対応農機の稼働情報（位置・稼働時間・エラー）を収集・表示できる。
- **F-51（S）** 食味・収量センサ付き収穫機のデータ（水分・タンパク・収量）を圃場/メッシュ単位で取り込める。
- **F-52（C）** ドローン/衛星のセンシングから生育マップを生成できる。
- **F-53（C）** 生育マップを基に可変施肥マップを作成し、対応農機へ送信できる。
- **F-54（M）** メーカー・機種を問わず連携できるよう、標準化した取込フォーマット（共通データモデル）と変換層（アダプタ）を設ける。**ファイル取込（ISOBUS/ISO-XML・CSV等）を主軸の連携経路**とし、メーカーAPI連携は補助経路としてアダプタで追加する。共通データモデルは**ISOBUS（ISO 11783）/ISO-XML および AgGateway ADAPT** を参照規格とし、国内の農機OpenAPI・海外のクラウド間APIの双方をアダプタで吸収できる設計とする。
- **F-55（S）** 新しいメーカー/機種の追加を、アダプタ追加のみで対応でき、本体改修を最小化できる。
- **F-56（M）** **初回対応の主軸はISOBUS/ISO-XML等のファイル取込アダプタ**とし、これを中核機能とする。**補助的に**農機OpenAPI（WAGRI）準拠アダプタを用意し、その実証パートナー第一候補＝クボタ（API数最多、植付・収穫等の状態データが充実）、第二候補＝井関農機（収量・散布レートを明示提供）とする。ヤンマーはWAGRI外の「営農API」直接契約ルートとして後続で対応する。メーカーAPIはあくまで"利用できる場合の補助"であり、提供停止・撤退時もファイル取込で中核機能を維持する。以降、他メーカー・他方式をアダプタ追加で順次拡張する。
  > 注：当初想定していた三菱マヒンドラ農機は2026年3月に解散（農機事業撤退）を発表し、IoT基盤「MITサービス」の外部連携も2026年3月末で終了したため、初回対象から除外した。共通データモデル（F-54）は農機OpenAPIのスキーマを参考に設計する。
- **F-57（M）** 農機OpenAPIのデータ保持期間（クボタで12ヶ月等）を踏まえ、**日次バッチで取込み自前DBへ永続化**する。長期の分析（F-51、F-60〜63）はISAS側の永続データを基礎とする。
- **F-58（C）** 海外圃場向けの農機連携は、初回＝**DataConnect**（John Deere・CLAAS・CNH（Case IH/New Holland/Steyr）等の主要ブランドが参画するメーカー横断のクラウド間データ交換IF）を対象とし、1接続で複数ブランドの機械データを取得する。第2＝**John Deere Operations Center API**。いずれもF-54の共通データモデルにアダプタで接続する（Phase 4）。

### 4.7 データ分析・可視化（重点）
- **F-60（M）** 収量・食味・コストを圃場/作物/年度で集計・グラフ表示できる。
- **F-61（M）** 収量メッシュマップ・食味メッシュマップを地図上に可視化できる。
- **F-62（S）** 経営ダッシュボード（面積・進捗・原価・収量）を提供する。
- **F-63（S）** 年度間・圃場間で比較分析できる。
- **F-64（C）** 蓄積データを基に改善提案（AIによる施策推奨・病害虫診断等）を行う。

### 4.8 労務・従業員管理（大規模法人向け）
- **F-70（S）** 従業員の作業時間・作業実績を集計できる。
- **F-71（C）** 作業実績を勤怠・給与計算の基礎データとして出力できる。
- **F-72（S）** 受託作業の実績を受託先別に集計し、請求根拠にできる。
- **F-73（S）** 位置ログ（F-08a）を**作業実績の裏取り・可視化**（圃場ごとの軌跡表示・在圃時間の集計等）に用いる。これが位置ログを取得する主目的であり（5.4.1）、位置ログはこの機能で消費される（目的なきPII収集を避ける）。※測位誤差・圃場境界の重なりがあるため、位置は「実績の裏取り」に留め、判断は作業記録（F-30）・打刻（F-74）を一次情報とする。
  > **在圃時間と作業時間の区別**：F-73の「在圃時間」は位置ログ由来の**参考値**（圃場に居た時間）、F-70/打刻（F-74）由来の「作業時間」が**正**（労務・給与の基礎）。両者は別指標であり、労務集計は作業時間を用い、在圃時間は実績の裏取り・突合にのみ用いる。
- **F-73a（C）** 位置ログ・打刻・作業記録を組み合わせ、**圃場ごとの進捗率を自動推定**してガント（F-2A）へ反映することを将来検討する（推定精度の課題があるため、当面は手入力/ステータスベースのF-2Aを一次とする）。
- **F-74（M）** 作業員が**作業の開始/完了・休憩の開始/終了を打刻**できる。この打刻に連動して位置ログのON/OFF（F-08a）および作業時間集計（F-70）が動作する。**位置ログの休憩中OFF（F-08a）というプライバシー安全装置を成立させる基盤であるため、F-08aと同じくMust**（v0.17でSから格上げ）。打刻はオフラインでも可能とし、追記型イベントとして扱う（5.1.1）。
  - **Phase 1の消費先**：打刻は**作業日誌（F-30）の開始/終了時刻を自動補完**し、**当日の作業時間（開始〜終了−休憩）を簡易表示**する（本格的な労務集計F-70はPhase 3）。これによりF-74はPhase 1の段階から消費先を持ち、単独で価値を提供する（位置ログ連携F-08a・労務集計F-70は後続フェーズ）。
  > 労務・給与（F-70〜72）の集計範囲：**集計は1システム（＝1DB＝1国）内で行う**。受託作業者が同一システム内の複数組織（テナント）にまたがる場合、その本人の稼働は**本人起点の横断ビュー（3.2、テナント分離の明示的例外）により、本人およびその雇用主テナントの管理者が横断集計できる**（独立した受託先どうしでも、本人の稼働に限って参照可能）。参照先は**専用の労務サマリ（LaborSummary：打刻・作業時間のみ、業務内容は含まない）**に限定し、他者・他組織の業務データは露出しない（7章RLS）。**システム（国）をまたいだ本人単位の集計は行わない**（各システムで別集計）。多国籍で働く個人の総稼働が必要な場合はシステム外で束ねる（R2-H3と同じ責務分界）。

### 4.9 帳票・出力
> 方針：出力は**CSV形式を基本**とする（汎用性・他システム移行性を優先）。GAPはJGAP準拠を基本とし、公式様式への完全準拠はスコープ外。必要な様式のみ個別にテンプレート化する。

- **F-80（M）** 作業日誌・圃場台帳・農薬使用記録をCSVで出力できる。
- **F-81（S）** JGAPに準拠した農薬使用記録（F-32の必須項目）をCSVで出力し、GAP対応・出荷証明に使える。
- **F-82（C）** 補助金・行政提出用の帳票は、対象が確定した様式のみテンプレート化して出力する（PDF/Excelは必要に応じ追加）。
- **F-83（C）** JGAP以外への将来対応は、**国際水準GAPガイドライン（農水省2022年策定）の記録項目**を保持基準とする。都道府県GAPは同ガイドライン準拠への収斂が進んでいるため、**県版GAPの個別様式対応は行わない**（記録項目の包含で対応）。**環境保全型農業直接支払の様式テンプレート化はスコープ外**とする（行政提出様式は完全準拠が必要で、4.9の「公式様式の完全準拠はスコープ外」方針と整合しないため。必要な運用者は様式非依存で保持した記録データからCSV/独自出力で対応する）。記録データは引き続き様式非依存で保持する。
- **F-84（C）** 海外圃場向けには**GLOBALG.A.P.等の国際認証**への対応を将来検討する。記録項目は国際水準GAPガイドライン（GLOBALG.A.P.を参照して策定）を基準とするため、大部分を流用できる想定。

### 4.10 外部連携・API（重点）
- **F-90（S）** REST APIを公開し、外部システムからデータ取得・登録ができる。
- **F-91（S）** 会計システム・販売管理・市況情報・気象データと連携できる。
- **F-92（C）** 農水省のオープンAPI（農業データ連携基盤 WAGRI 等）に準拠する。
- **F-93（S）** Webhook等でイベント通知（作業完了・エラー等）ができる。

## 5. 非機能要求

### 5.1 使いやすさ（UX）
- 現場作業員が手袋・屋外・電波不安定な環境でも数タップで入力できること。
- スマホ・タブレット・PCに対応（レスポンシブ／PWAまたはネイティブアプリ）。
- 高齢の作業者でも迷わない、文字大きめ・操作の少ないUI。

### 5.1.1 オフライン対応（必須要件）
- 圏外圃場が多いことを前提に、オフラインでの作業リスト参照・作業日誌入力・写真添付・**資材の出庫記録**を**必須**とする。
- 通信回復時に自動同期し、競合（同一データの複数端末編集）を検知・解決できること。
- オフライン中のデータは端末側に安全に保持し、消失しないこと。

#### 競合解決ルール（データ分類別・v0.8確定）

| 分類 | 対象データ | ルール |
|---|---|---|
| 追記型（イベント） | 作業日誌・写真・収穫データ・**資材入出庫イベント**・**打刻（F-74）**・位置ログ | 新規作成は別レコードのため競合しない。同一レコードの別フィールド編集はフィールド単位で共存。**同一フィールドを2人が別内容で編集した場合は自動で上書きせず、両方の値を保持して管理者へ報告し、管理者権限で採用値を確定する**（静かなデータ消失を防ぐ） |
| 状態遷移型 | 作業指示のステータス・進捗率 | **前進優先マージ**（完了＞進行中＞未着手。進んだ状態を採用）。巻き戻しは明示操作（理由入力必須）のみ |
| 残高・集計型 | 資材在庫 | **残高の直接編集を禁止**し、入出庫イベントの追記から残高を導出する。同期後にマイナス在庫が生じた場合は警告表示し、**是正はF-42（管理者通知＋棚卸し調整イベントの追記）**による |
| 導出型 | 原価・集計値・ダッシュボード数値 | 編集可能な形で保存せず、元データ（作業時間・資材使用・単価マスタ）から**常に再計算** |
| 計画・マスタ型 | 圃場ポリゴン・作付計画・ガント日程・作業の**再割当**・各種マスタ | **オフライン編集対象外（オンライン専用）**。オンライン同時編集は**楽観ロック**（バージョン番号）で検知し、上書きせず差分提示・マージ操作 |
| 権限・組織型 | ユーザー・ロール・テナント設定 | **オフライン編集禁止＋オンライン専用＋楽観ロック**（権限の巻き戻りはセキュリティ事故のため） |

- LWWの判定時刻は**端末申告時刻を無条件に信用しない**。編集時の端末時刻とサーバー受理時刻を両方記録し、競合判定・監査に用いる（詳細は基本設計）。
- いずれの分類でも、上書き・マージが発生した場合は上書き前の値を監査ログ（5.4）に残し、追跡可能とする。

### 5.2 性能・可用性
- 想定規模は圃場枚数が極小〜巨大、**ユーザー数は1DB（1システム＝1国）あたり最大5万人**。全体規模はシステム増設で水平拡張する。
- 大量圃場（数万枚規模）でも地図・空間検索が破綻しないアーキテクチャ（タイル化・空間インデックス等）とする。
- 農繁期のアクセス集中に耐える水平スケーラビリティを確保する。
- **可用性目標の適用対象**：稼働率・RTOの目標は**管理系（オンライン機能：PC管理画面・分析・同期サーバ等）**に適用する。**現場のスマホ入力はオフライン前提（5.1.1）で、サーバ障害中も継続動作**するため、可用性目標の直接対象外とする（回復後に同期）。したがって「サーバ稼働率」と「現場業務の継続性」は分離して考える。

#### 5.2.1 性能SLO（初期目標・負荷試験で検証する叩き台）
| 画面/操作 | 条件 | 初期目標 |
|---|---|---|
| 地図初期表示 | 圃場1,000枚を含む画面 | 2秒以内（p95） |
| 地図パン/ズーム | 同上 | 200ms以内で追従 |
| 圃場一覧表示 | 10,000件・ページング | 1.5秒以内（p95） |
| ガント表示 | 500タスク | 3秒以内（p95） |
| 作業日誌の保存（オンライン） | 写真1枚添付 | 1秒以内（p95） |
| API応答（一般GET） | — | 500ms以内（p95） |

#### 5.2.2 可用性・復旧目標（初期目標）
| 指標 | 意味 | 初期目標 |
|---|---|---|
| 稼働率 | 管理系（オンライン機能） | 99.5%以上 |
| RPO（目標復旧時点） | 障害時に許容する最大データ損失 | 15分以内 |
| RTO（目標復旧時間） | 障害から復旧までの最大時間 | 4時間以内 |
| バックアップ保持 | 世代保持 | 日次30世代＋週次12世代（目安） |

> オフライン必須（5.1.1）のため、サーバ障害中も現場のスマホ入力は継続可能。RTO/稼働率は主に管理系（PC・分析）に効く。

### 5.3 信頼性・データ保全
- 入力データのバックアップと、**他システムへ移行可能なエクスポート**を保証する（囲い込み回避）。
- **第三者データの再配布制約**：エクスポート対象は原則として利用者が入力・生成したデータとする。**第三者から取得したデータ（WAGRI/農機OpenAPI由来の農機データ、外部の農薬マスタ等）は、提供元のライセンス・利用規約により再配布・再エクスポートが制限される場合がある**ため、エクスポート時は当該データを**除外、または利用者自身の記録に加工した派生データのみを対象**とする。取り扱い可否は提供元規約と運用者が確認する。
- オフライン入力データの同期整合性を担保する。

#### 5.3.1 オフライン同期の許容遅延（初期目標）
| 指標 | 初期目標 |
|---|---|
| 電波回復後の自動同期開始 | 回復検知から60秒以内 |
| 1日分の日誌（写真含む数十件）の同期完了 | 5分以内 |
| 同期対象データのオフライン保持 | 端末に14日分以上を保持可能 |

### 5.4 セキュリティ
- ロールベースのアクセス制御（テナント×ロール×圃場グループ）、通信の暗号化（TLS）、認証（多要素認証を選択可）。
- 個人情報・経営情報の適切な取り扱い。
- 監査ログ（誰がいつ何を変更したか）。改ざん耐性を持たせ、保持期間を設定する。**監査ログの実施者は仮名化ID（仮名マップ経由）で参照**し、GDPR等の本人削除要求時は**仮名マップのみを切断**する（ログ本体＝証跡は保持しつつ、本人特定性を除去）。これにより「改ざん耐性（不変）」と「削除要求（忘れられる権利）」を両立する。
- **保存時暗号化（encryption at rest）**：DB・バックアップ・添付ファイル（写真等）を保存時に暗号化し、鍵管理（ローテーション含む）を行う。
- **データ保持/削除ポリシー**：データ種別ごとに保持期間を設定し、期間経過後は自動削除または匿名化する（監査ログ・位置ログ・作業記録等）。
- **GDPR等の権利対応**：本人データの開示・訂正・削除（忘れられる権利）・エクスポート（データポータビリティ）に応じる機能を提供する。適法性の判断・運用は運用者の責任（9章#13）。
- **法令保持義務とGDPR削除の優先関係**：**法令で保持が義務づけられた記録（農薬使用記録の「作業者」（F-32）、その他トレーサビリティ・税務等の法定記録）は、GDPR削除（忘れられる権利）の対象外**とし、法的保持義務を優先して保持する。本人削除要求時は、**当該法定記録は保持しつつ、それ以外のPII（アカウント情報・任意の個人データ等）を削除または仮名化**する（監査ログは仮名マップ切断で対応）。削除対象/保持対象の区分と法的根拠は運用者が定める。
- 脆弱性対応（依存ライブラリの更新・定期的なセキュリティ点検）を運用に組み込む。

#### 5.4.1 位置情報・労働者プライバシー
- 作業員の位置ログは**作業中のみ取得**し、**休憩中は取得しない**（F-08a、OFF判定は作業ステータス連動を既定）。**取得目的は「作業進捗の把握と作業計画策定の基礎データ」および圃場特定・作業記録の補助**に限定し、常時監視・行動追跡を目的としない（目的を明示することでデータ最小化原則に適合させる）。
- 位置情報の取得にあたり、作業員から**事前同意**を取得できる仕組みを持つ（多言語で提示）。同意状況を記録する。**同意は拒否でき、拒否した作業員には位置ログを記録しない**。その場合でも**作業日誌・打刻など位置ログに依存しない機能は通常どおり利用できる**（グレースフル縮退。F-08a）。同意を雇用条件として強制しない。
- 位置ログには**保持期間**を設定し、期間経過後は自動削除または匿名化する（保持期間は運用者が設定可能）。
- 位置情報・個人データの取り扱いは、配備先の国の労働者監視・個人情報規制（GDPR等）に運用者が適合できるよう、同意・保持・削除・エクスポートの各機能を提供する（法令遵守の責任は運用者。9章#13）。

### 5.5 保守・拡張性
- 作物・作業種別・帳票様式を設定で追加できる（コード改修なしを目指す）。
- **多言語対応（必須）**：海外圃場を対象に含むため、**全世界の言語を扱えるi18n基盤**とする。具体的には：
  - **任意の言語をデータ追加のみで追加**できる（コード改修なし）。Unicode全面対応、RTL（右書き：アラビア語等）レイアウト、言語ごとの複数形規則、ロケール別の日付・数値・単位表示に対応する。
  - **初期リリース言語は日本語＋英語**。以降、現場の作業員構成に応じて順次追加する（国内はベトナム語・インドネシア語等を想定。農業分野の外国人材の主要国籍に基づく）。
  - 作業員が自分の言語を選択でき、マスタ（作業種別等）も多言語表示できる。
  - **翻訳運用（ハイブリッド方式）**：UI固定文言＝機械翻訳一次訳＋ネイティブレビュー（農業用語グロッサリを先に整備）／マスタ＝登録時に機械翻訳を自動付与し「未レビュー」フラグで後日確定／自由入力（日誌メモ等）＝原文保持＋オンデマンド機械翻訳／**農薬名・圃場名等の固有名詞は翻訳しない**（誤訳の法令リスク回避）。
  - 翻訳に依存しない補助策として、アイコン・ピクトグラム中心のUI、作業指示への写真・定型文活用（F-31/F-35）、日本語UIの「やさしい日本語」基準を併用する。
- マルチテナント構成として、組織（テナント）の追加・分離を運用で行えること。

```
圃場 1--* 収穫データ(Harvest)   … 収量, 食味(水分/タンパク), メッシュ値
農機(Machine) 1--* 稼働ログ(MachineLog)
ユーザー(User) 1--* 労務サマリ(LaborSummary) … 打刻・作業時間の集約（業務内容は含まない）
                                 ※本人起点の横断ビュー（3.2）の参照先。稼働のみを保持
ユーザー(User) 1--* 打刻(Punch)  … 作業/休憩の開始・終了（作業員ロールのユーザーが打刻。F-74、追記型）
作物マスタ 1--* 作業適期(CropWindow) … 作業種別, 適期開始日, 適期終了日
マスタ各種(作物/作業種別等) 1--* 多言語ラベル(I18nLabel) … 言語コード, 表示名, レビュー状態
全エンティティ 1--* 監査ログ(AuditLog) … 対象, 変更前値, 変更後値, 実施者,
                                 端末時刻, サーバー受理時刻（改ざん耐性・保持期間あり）
```

- 全レコードはテナント（組織）IDを持ち、既定でテナント単位に分離する（横断できるのはグループ管理者のみ。例外として、**本人は労務サマリ（LaborSummary）に限り、自分の稼働を組織横断で参照できる**：3.2の本人起点横断）。
- 同期の競合解決（5.1.1）のため、更新のあるエンティティは更新時刻（端末編集時刻・サーバー受理時刻）と更新者、楽観ロック用のバージョン番号を保持する。在庫・原価は残高/導出値を直接保持せず、イベント（StockEvent）や元データから導出する。

- 位置情報は圃場ポリゴン・メッシュ・GPSログを地理空間データ（GeoJSON / PostGIS等）で保持。
- ガントチャートは **WorkOrder（日程・進捗・ベースライン）＋依存関係＋作業適期（CropWindow）** を基礎データとし、専用テーブルを追加せずこれらから描画する。

## 7. 技術構成（たたき台・要検討）

> 要求段階のため確定ではなく選択肢の提示。ただし確定した前提（オフライン必須／ベンダー非依存連携／1DBあたり最大5万ユーザー／MITライセンスのOSS・運用者自由）を反映する。

- **フロント**：Web（React等）＋モバイル。オフライン必須のため**PWA（Service Worker＋ローカルストレージ）またはオフライン対応ネイティブ**を採用し、同期・競合解決機構を持つ。
- **地図/GIS**：**ベクタ地図エンジン（MapLibre GL＋OpenStreetMap系）でポリゴン描画・オフラインタイル**、PostGISで空間検索。背景衛星画像は**用途で役割分離**：ポリゴン描画用は**高精細（MapTiler／Esri World Imagery(for Export)等の有償ソース）を既定**、Sentinel-2（無償・10m）は**生育解析（NDVI等）専用**（無償で全機能を賄う前提はとらない）。**Google Earth/Mapsは規約上ポリゴントレース・オフライン保存が不可のため不採用**。**オフラインタイルは全世界を保持せず、1配備（1DB＝原則1国）が対象国分のみ**を扱い、端末は担当圃場周辺のみ事前DLする。数万圃場規模を前提にタイル化・空間インデックスを設計。
- **バックエンド**：REST/GraphQL API、認証基盤、RBAC（ユーザー↔組織の多対多メンバーシップに対応）。1DBあたり最大5万ユーザー＋インスタンス増設を見据えた水平スケール構成。
- **DB**：RDB（PostgreSQL＋PostGIS）を中核、時系列・稼働ログは別途検討。
- **連携**：農機/センサはベンダー非依存の**共通データモデル＋アダプタ層**（F-54〜58）で連携する。**主軸はISOBUS/ISO-XML等のファイル取込アダプタ（中核機能）**、メーカー個社のクラウドAPIは**補助経路**とする（提供停止・撤退時も中核機能を維持）。共通データモデルは**ISOBUS（ISO 11783）/ISO-XML および AgGateway ADAPT を参照規格**とし、国内の農機OpenAPI・海外のクラウド間API（DataConnect等）の双方をアダプタで吸収する。補助APIの初回は農機OpenAPI（WAGRI）準拠（実証第一候補＝クボタ、第二＝井関。ヤンマーは営農API直接契約で後続）、WAGRI準拠（F-92）と整合。取込は日次バッチ＋自前永続化（F-57）。
  - **WAGRI契約方針**：設計・検証段階は**お試し会員（無料・1年・100回/月）**でAPI仕様とデータ品質を検証し、Phase 1 実装時に**データ利用・提供会員（40,000円/月・クライアント、転送20GB/月込み）**へ移行。**農業法人割引の適用可否を申請時に確認**する。食味データの提供可否・認証/同意フロー・更新頻度は利用申請時に照会する。
- **インフラ**：クラウド（可用性・スケール・バックアップ前提）。グループ/連合利用のため**マルチテナント**を基本とし、分離方式は**行レベル分離（共有スキーマ＋tenant_id＋PostgreSQL RLS）**とする。
  - RLS設計の留意点：接続プール維持のためテナント別DBロールではなく**セッション変数（例：`SET app.tenant_id`）＋ポリシー参照方式**とする／グループ管理者の横断アクセスはRLSポリシーで宣言的に許可する／`tenant_id`を複合インデックスの先頭に置く／横断ダッシュボード等の集計系は集計テーブル・マテリアライズドビューを別途設計する／オフライン同期APIの同期対象絞り込みにもtenant_idを必ず通す。
  - **本人起点の横断ビュー（3.2）の実装**：受託作業者本人（＋雇用主テナント管理者）が全メンバーシップの自分の稼働のみ横断参照できるよう、テナント分離ポリシーとは別に**`user_id`（本人）を条件とするRLSポリシー**を設ける。**参照先は専用の労務サマリ（LaborSummary：打刻・作業時間の集約。業務内容＝圃場・作業種別等は含まない）に限定**し、作業日誌（WorkLog）等の業務テーブルを本人起点で他テナント分まで露出させない（業務データの越境露出を防ぐ）。労務サマリは打刻（Punch）・作業日誌から**当該テナント内で集約**して生成し、本人横断ビューはそのサマリのみを束ねる。グループ管理者の横断（tenant_idベース）とは別経路として設計する。
- **国際化**：**全世界の言語を扱えるi18n基盤**を初期から組み込む（初期リリースは日英）。RTLレイアウト・複数形規則・ロケール別の日付/数値/単位に対応するi18nフレームワーク（ICU/CLDR準拠）を採用。**タイムゾーン**は全時刻をUTC保存＋表示時にローカル変換、**通貨・単位系**（原価・面積等）はテナント/圃場ごとに設定可能とする（海外圃場対応）。**原価等の金額集計（F-60〜63）は同一通貨内に限定**し、通貨をまたぐ単純合算は行わない（異通貨の横断集計が必要な場合の換算・基準日は本仕様の対象外とする）。
- **1システム＝1DB**：本システムの1稼働単位（1システム）は**1つのDB**に対応し、**原則1国を対象**とする（1DBあたり最大5万人）。これによりデータは対象国内に留まり、データ所在規制（GDPR等）に素直に適合する。オフライン地図タイルも対象国分のみ（F-09a）。**グループ管理者の横断アクセスは、この単一DB内のテナント間をRLSで制御する**ため、権限判定とデータアクセスが同一DBに閉じ、複数DB分散との不整合（旧M-6）は生じない。
- **複数国展開・横断分析**：同一運用者が複数国で展開する場合は**国ごとに独立した1システム（＝1DB）を分けて配備**する。国をまたいだ集計が必要なら、各システムからエクスポートしたデータを**システム外の別基盤（DWH等）で集約**する（本システムの1稼働単位の責務外）。その際も**個人識別情報（PII）は含めず仮名化・集計値のみ**を推奨し、越境移転の適法性は運用者が確保する。
  > 注：本システムはOSSとして「国別分離（1システム＝1DB）」「任意のDWH集約」の機能を提供するに留まり、両者を同時に用いる際のコンプライアンス（越境移転の適法性等）は運用者が確保する。C-2（データレジデンシー分離とDWH集約の衝突）は、DWHをPIIフリー/仮名化に限定し、集約可否を運用者判断とすることで解消する。
- **海外対応の考慮**：海外圃場向けの地図データソース（筆ポリゴンは国内のみ／背景はSentinel-2等）、海外からのアクセスレイテンシ（配備先の地理的配置）を設計時に考慮する。国内制度依存の連携（WAGRI等）は国内圃場に限定して適用する。海外農機はISOBUS/ADAPT準拠の共通モデルにDataConnect等をアダプタ接続する（F-58）。
- **データ移行**：既存Excel/CSVの取込パイプライン（F-37）を用意する。
