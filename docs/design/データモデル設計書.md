## 1. 設計原則（P0からの継承）

このデータモデルは以下を貫く（各ADRの決定）：

- **テナント分離**：全テナント固有テーブルに `tenant_id`、RLS（USING＋WITH CHECK・FORCE RLS・フェイルクローズ）（ADR-0001）。
- **テーブル4分類**：①テナント固有／②システム共有／③共有＋テナント上書き／④ユーザー所有。migrationの`COMMENT ON TABLE ... IS 'isas.table_class=<value>'`完全一致を機械可読な正とし、タグ欠落・列NULL性・RLS形の不一致をCIで拒否する（ADR-0001 v19）。
- **不変性3層**：①イベント（①-a＝確認済み法定根拠あり／①-b＝PII）／②可逆確定／③下書き（ADR-0003）。第4の操作は移送。労務サマリは横断用の最小化された**不変な確定投影**として実体化するが、①-a法定区分は `retention_basis` が確認済みの場合だけ適用する（ADR-0002 v13／IND3-M8）。
- **型の区別**：時点＝`timestamptz`（UTC）／暦日＝`date`（圃場ローカル・圃場TZ基準）（ADR-0015）。
- **PK＝UUID（非連番）**、FKは同一テナント内（ADR-0001 A1e-L1/L2）。
- **時系列は時間主軸パーティション＋サブパーティション**（ADR-0004）。
- **単位＝原値権威＋正規化導出**、金額＝同一通貨内集計（ADR-0015）。

## 2. 論理ERD（概念→論理）

```
System/法域デプロイ(1以上のDBシャード)
  └─* Tenant/Group ─* Organization ─┐
                                     ├─* Field(圃場) ─* Cropping(作付) ─* WorkOrder(作業指示)
User *─┬─* Membership(role,perm,scope) ┘                                   │
       ├─* Punch(打刻)                                                     ├─* WorkLog(作業日誌)  ← 複合(①-a農薬記録/①-b PII)
       ├─* LaborSummary(労務サマリ)                                        │      └─* PesticideRecord(農薬使用記録①-a法定)
       └─* Draft(下書き④・テナント非帰属)                                │            └─ actor_ref → WorkActor(作業者·法的根拠フラグ)
Crop(作物マスタ) ─* Variety(品種)                                          │      └─* Photo(写真①-a/①-b)
AgroChemical(農薬肥料マスタ②/③) ─* Material(資材使用)                      └─* Harvest(収穫)
  └─* I18nLabel(多言語:共有/テナント上書き)                          StockEvent(入出庫①-a) ← 在庫は導出
Machine(農機) ─* MachineLog(稼働ログ・時系列)
<各テナント固有テーブル> ─* *_history(版履歴·層②)       ← 確定データの更新前スナップショット
AuditLog(監査①-a・追記型・ハッシュチェーン)   ← 全エンティティの変更を記録（越境参照は特権別経路）
```

### エンティティ分類（4分類 × 3層）

| エンティティ | テーブル分類 | 不変性層 | 主な型 |
|---|---|---|---|
| Organization / Field / Cropping / WorkOrder | ①テナント固有 | ②可逆確定 | id:uuid, tenant_id, deleted_at, version, geom(Field) |
| WorkLog（作業日誌） | ①テナント固有 | **フィールド単位**（①-a法定列/①-b PII列） | 実施日:date, 作業内容:①-a, 個人メモ/写真:①-b, 更新時刻:timestamptz |
| PesticideRecord（農薬使用記録） | ①テナント固有 | ①-a法定（散布内容） | 散布月日:**date**, 収穫前日数計算, 作業者は`actor_ref`で分離 |
| WorkActor（作業者） | ①テナント固有 | **フィールド単位**（法定名:①-a法的根拠保持/連絡先等:①-b削除可） | actor_id, legal_name(法的根拠), user_id参照(NULL化可), retention_basis |
| StockEvent / Punch / MachineLog / 位置ログ | ①テナント固有 | ①-a(在庫)/①-b(打刻位置) | event_ts(採番時点):timestamptz, occurred_at(業務時点), 時系列パーティション |
| LaborSummary | ①テナント固有（**本人起点 restrictive 例外**＝§4） | **追記型・不変の確定投影**。確認済み `retention_basis` があるレコードだけ①-a法定区分 | user_id, 期間, 稼働のみ, 確定時刻, 訂正チェーン, 保持区分／根拠 |
| AgroChemical / Crop / 作業種別 | ②共有 or ③共有+上書き | ②可逆確定 | 共有(tenant_id NULL)＋テナント上書き（部分一意索引） |
| I18nLabel | ③共有+上書き | ②可逆確定 | (対象, 言語, 表示名, レビュー状態, 安全フラグ) |
| Draft（下書き） | ④ユーザー所有（**テナント非帰属**） | ③下書き | user_id, tenant_id NULL可, 確定でtenant固有へ移送 |
| *_history（版履歴） | ①テナント固有（親に追随） | ②の更新前スナップショット | 親PK, version, valid_from/to, 変更者 |
| AuditLog | ①テナント固有（書込は監査トリガのみ・越境は特権別経路） | ①-a追記 | 変更前後, 実施者:仮名化ID, ハッシュチェーン |

## 3. 型の適用ルール（ADR-0015：暦日/瞬間）

| 用途 | 型 | 根拠 |
|---|---|---|
| イベント発生時刻・ログ・監査・打刻・同期時刻 | `timestamptz`（UTC保存・表示時変換） | 時点。DST/多TZに頑健 |
| 散布月日・収穫日・作業適期・作付年度 | `date`（圃場TZ基準の暦日） | 収穫前日数（法定）を日跨ぎでずらさない |
| 暦日の確定 | 端末の瞬間 → **圃場属性のTZ** → その暦日 | 越境作業者・深夜でもずれない |
| 金額 | `numeric` ＋ 通貨コード（テナント/圃場設定） | 同一通貨内集計 |
| 単位付き数量（面積等） | 原値＋原単位（権威）＋正規化値（生成列） | 往復丸め防止 |

## 4. RLSポリシー設計（ADR-0001/0005）

**接続前提**：全DBアクセスは明示トランザクション＋`SET LOCAL app.tenant_id`／`app.user_id`／`app.allowed_tenants[]`／`app.scope_field_groups[]`（**すべてサーバ側で導出・注入時検証**）。トランザクションプーリング。アプリは非所有者・非BYPASSRLSロール。全テーブル `FORCE ROW LEVEL SECURITY`。

#### ポリシー結合の設計（**v8全面改訂**：IND3-H2 の裁定＝(a) を反映）

PostgreSQL の RLS は、**restrictive を AND、permissive を OR** で結合する。**かつ permissive が1本も無いテーブルは誰にも0行**（OR が空集合＝偽）。この2つの性質から、役割を次のとおり固定する（ADR-0001 v15 §2.9）：

| ポリシー種別 | 役割 | 述語 | `TO` |
|---|---|---|---|
| **permissive** | **経路を開くだけ** | **`USING (true)` / `WITH CHECK (true)` 固定**（**条件を書いてはならない**——OR で吸収され絞りとして機能しないか、他の permissive を無効化する） | **`TO` でロールを明示列挙**（漏れれば見えない＝安全側） |
| **restrictive** | **絞りはすべてここ** | 下記7形のいずれか | **`TO` を付けない（全ロール）** |

> **【v8】v7 までの誤り（IND3-H2）**：v7 は「作成者／個人データの最小権限」を **permissive** に置いていたが、**同じテーブルに基本 permissive `USING(true)` を必須化した時点でそれらは OR で吸収され無効**になっていた。**絞りは permissive では表現できない。**

**注入変数（すべてサーバ側で導出し、注入時にDB側で検証する）**：`app.allowed_tenants`（uuid[]・**リクエスト単位の許可集合**）／`app.tenant_id`（uuid・書込先）／`app.user_id`（uuid・**リクエスト主体。対象者を入れる用途に流用しない**）／`app.scope_field_groups`（uuid[]）／**`app.caps`（text[]・v8新設）**／**`app.employer_subject_users`（uuid[]・v8新設）**／`app.bootstrap_claimed_user`（uuid・`auth_role` のみ）。

**capability 一覧**：`view_others_tracks`／`view_others_punch`／`scope_all`。

**【v8】セッション変数の参照は必ず正規化する（PG-H1・実測確認）**：`SET LOCAL` を一度使った接続では「未設定」が **NULL ではなく `''`** になり、素のキャストは**プラン時例外**になる。以下を略記として用いる：

- `AT` ＝ `ANY(COALESCE(NULLIF(current_setting('app.allowed_tenants', true), ''), '{}')::uuid[])`（`SFG`＝`app.scope_field_groups`／`ESU`＝`app.employer_subject_users` も同形）
- `TID` ＝ `NULLIF(current_setting('app.tenant_id', true), '')::uuid`（`UID`＝`app.user_id`／`BCU`＝`app.bootstrap_claimed_user` も同形）
- `CAP(x)` ＝ `x = ANY(COALESCE(NULLIF(current_setting('app.caps', true), ''), '{}')::text[])`

**正規化しても不正値は例外のまま**（`'garbage'::uuid` はエラー）。正しくは「**未設定・空は非通過（0行）／不正値は例外（22P02）**」であり「不正は偽」ではない。**不正値は注入時にDB側で弾く。例外の握り潰しは禁止（フェイルオープンへの反転）。関数にラップしない**（qual から `current_setting` が消えて検査が偽陰性になる）。

#### restrictive の述語形（7形。**USING と WITH CHECK の対**で定義する）

**PostgreSQL は `WITH CHECK` を省略すると `USING` を書込検査に流用する**（v7 までこれを見落とし、`labor_summary` で他テナント名義の①-a追記が可能だった＝IND3-H3／PG-M3）。**すべての restrictive で両方を明示する。**

| # | 対象 | USING（読取） | WITH CHECK（書込） |
|---|---|---|---|
| (a) | ①一般 | `tenant_id = AT` | `tenant_id = TID` |
| (b) | **`labor_summary` のみ** | `tenant_id = AT OR user_id = UID OR user_id = ESU` | **`tenant_id = TID`**（読取の集合を書込に流用しない） |
| (c) | 圃場スコープ対象 | `field_group_id IS NULL OR field_group_id = SFG OR CAP('scope_all')` | 同左 |
| (d) | **個人データ**（`location_log` 軌跡・`punch`）**v8新設** | `user_id = UID OR CAP('view_others_tracks')`（打刻は `view_others_punch`） | `user_id = UID`（**本人のみ追記**） |
| (e) | ③共有＋上書き | `tenant_id IS NULL OR tenant_id = AT` | **`tenant_id = TID`**（**`tenant_id IS NULL` の書込を拒否＝共有汚染の防止**） |
| (f) | **`membership` のみ** | `tenant_id = AT OR (current_user = '<bootstrap_owner>' AND user_id = BCU)` | `tenant_id = TID`（ブートストラップ例外は `FOR SELECT` のみ。`auth_role` は関数EXECUTEだけ） |
| (g) | **④ユーザー所有**（`draft`） | **テナント分離の対象外**。独立ポリシー `user_id = UID` | 同左（確定時に①へ移送） |

> **【v13】検査（ADR-0001 v19 §5 と同一）**：`isas.table_class`タグと列NULL性／RLS形が一致する／restrictiveに`TO`無し／正当な全主体にpermissiveあり／permissive述語は`true`のみ／全restrictiveに形ごとの`WITH CHECK`あり／read集合`AT`・`ESU`・`tenant_id IS NULL`をwriteへ流用しない／セッション変数は正規化形で関数ラップしない／`current_user`例外はmembershipのみ／`UID`は(b)(d)(g)のみ／`app.caps`は(c)の`scope_all`と(d)の個人データだけ／`ESU`はlabor_summaryのみ。
>
> **【v8】振る舞いテストは読取・書込・capability の3面**：遮断／**横断が通ること**（グループ管理者・本人起点・③共有行）／**書込側**（他テナント名義の INSERT・行移送・共有行の書込がすべて拒否されること）／**capability の有無で個人データの可視性が変わること**／**`SET LOCAL` を使った接続の2回目のトランザクション**での注入漏れ挙動。


> **【v8】④下書き確定時の越境FK検証（R2-M3／R3-L2。IND3-M4 により方式を変更）**：WITH CHECK は挿入先自表の `tenant_id` しか見ないため、下書きが参照する `field_id`／`chemical_id` 等が現テナントに帰属するかを別途検証する必要がある。**v7 までは「特権経路で参照先の実 `tenant_id` を取得して越境と不存在を区別する」としていたが、それは restrictive の床を越える手段（BYPASSRLS の追加／`current_user` 例外の追加）を要し、いずれも v15 の検査（迂回主体の一覧・述語形の限定）に反する**（IND3-M4）。よって方式を改める：
> - **アプリが参照先の `tenant_id` を明示的に渡し、DB側は「自テナント一致」のみを検証する**（不一致は一般化したエラー）。**「越境」と「不存在」をDBで区別しない。**
> - 区別が業務上どうしても必要なら、**検証専用の SECURITY DEFINER 関数所有ロールを述語形に正式追加（第8形）し、対象表を一覧化して検査対象に載せる**——**黙って例外を作らない**。
> - 入力値の妥当性検査とレート制限（存在推測の防止）は ADR-0009／ADR-0017。

> **NULL不可視化の回避**（M3-M4）：未グループ化圃場（`field_group_id IS NULL`）は担当者から恒久不可視になる事故を避けるため、上式で `IS NULL` を許容する。運用上は**新規圃場を既定グループへ強制所属**させ、`IS NULL` はセーフティネットとして残す。
>
> **スコープの子テーブル適用**（R2-M2／R3-M1）：`field_group_id` を持つのは `field` のみ。子・関連テーブルにスコープを効かせる方式を**テーブル種別で分ける**（①-a不変テーブルへの同期UPDATEは①-a違反になるため一律の非正規化はしない）：
> - **不変（①-a）・法定の関連レコード**（`pesticide_record` 等）：スコープ列を**持たせず、親 `field` の可視性に従属**させる。解決は **SECURITY DEFINER のセキュリティバリア関数**で「現在の圃場グループ」を1回解決（結果キャッシュ）し、`field_id` の親がスコープ可視なら可視とする（再帰RLSと高頻度サブクエリの性能問題を回避）。
> - **可変・運用テーブル**（作業指示・下書き由来の確定前後の運用データ等）：**`field_group_id` を非正規化保持**（圃場のグループ変更時に同期UPDATE可）し、restrictive 述語を単純列比較にする。
> - **業務ルールの確認事項**：担当替え・組織改編の後、**過去の記録を旧担当に見せ続けるか／新担当に見せるか**（＝スコープを「記録時点」で見るか「現在」で見るか）は業務判断。要求仕様/E系のエスカレーションに上げる。既定は「**現在の圃場グループ**で解決」（親従属方式がこれに合致）。
> - 非正規化 vs セキュリティバリア関数の性能・整合は **S4** のPoCで両者を比較して確定する。
>
> **ロール別の有効ポリシー集合**は S4（RLS×規模）のPoCで表形式のポリシーテストとして固定・検証する。テナント分離(restrictive)＋スコープ(restrictive) を常時土台にし、横断/本人/作成者は permissive でアクセス経路を付与する構成をスパイクで確認（ADR-0001 A1-M2）。

## 5. パーティション設計（ADR-0004）

**対象**：時系列・高頻度追記（位置ログ・打刻・MachineLog・StockEvent・AuditLog）。

- **主軸＝時間レンジ**（月/週）：retention（古いパーティションをドロップ/アーカイブ）を成立させる（ADR-0003 A3-L1）。パーティション振り分けには **`event_ts`（採番時点）** を使う（下記）。
- **副軸（サブパーティション）＝tenant_id のハッシュ/リスト**：RLSプルーニング・空間性能（各サブパーティション内は単一テナント寄り）。物理DDLは各時間パーティションを `PARTITION BY LIST/HASH (tenant_id)` でサブパーティション化する（§6）。
- **パーティションキー包含の徹底**（M3-H1）：PostgreSQLは**全パーティションキー列をPK/一意制約に含める**必要がある。主軸`event_ts`＋副軸`tenant_id`を採るため、**PKは `(tenant_id, event_ts, event_uuid)`**（両キー包含）。tenant_id未包含のPKはサブパーティション時にエラーになるため採らない。
- **冪等dedupの時刻分離＋決定性の固定**（M3-H2／R2-H1）：業務上の時点 `occurred_at`（クライアント生成・クロックずれあり）を**パーティション振り分けに使わない**。`event_uuid` は **UUIDv7 に固定**し、振り分け軸 `event_ts` は **`event_uuid` から抽出**する（決定的。**「サーバ受理時刻」の選択肢は採らない**＝再送で値が変わり非決定になるため）。これにより同一 `event_uuid` は必ず同一 `event_ts` パーティションに入る。
- **決定性をDBで束縛**（R3-M2／スパイクS1で検証済）：`event_ts` は**クライアントの自由入力を信頼しない**。**スパイクS1で判明した2つのPostgreSQL制約**により経路を確定した：
  - **① 生成列はパーティションキーにできない**（`cannot use generated column in partition key`）。
  - **② BEFORE ROW トリガはタプルルーティングの「後」に走る**ため、トリガで `event_ts` を設定してもルーティングはトリガ前の値（NULL/生値）で行われ、`no partition found` になる。
  - → **【v9までの採用経路・v10で撤回】**：`event_ts` をアプリ層で `uuidv7_time(event_uuid)` から計算して供給し、`CHECK (event_ts = uuidv7_time(event_uuid))` で束縛していた。**下記【v10】で撤回。**

- **【v10全面改訂】冪等・物理配置・端末申告時刻を3つの別機構に分ける（IND3-H5）**：v9 までは **`event_ts` を `event_uuid`（UUIDv7）から抽出**し CHECK で強制していた。**しかし UUIDv7 の埋め込み時刻は端末の壁時計であり、「決定的」は再送間の決定性しか与えず、クロックずれを打ち消さない**——**ADR-0004 A4b-M1 が掲げた目的（端末クロックずれで別パーティションに入らないこと）は達成されておらず、ADR-0007 §2.8「時刻の権威はサーバ」とも正面衝突していた**。しかも **CHECK がサーバ側での補正を禁止**していた。

  > **実測で確認**：範囲外の時刻は **`ERROR: no partition of relation ... found for row`** で **INSERT が失敗する**。電池切れ後に 1970 へリセットされた端末、数年進んだ端末——いずれも**①-a法定記録（農薬使用記録）を1件も受理できない**。`event_uuid` を変えない限り永久に受理できず、変えれば冪等キーが変わり二重計上になる。逆に未来時刻の位置ログは「未来のパーティション」に入り、**retention で期限が来ても削除されない**（保持期間超過）。

  | 機構 | 担うもの | 実装 |
  |---|---|---|
  | **① 冪等** | 再送で二重計上しない | **受理台帳 `event_receipt`** が権威。**イベント表の一意制約に依存しない** |
  | **② 物理配置** | パーティション・retention・プルーニング | **`event_ts`＝サーバが検証・クランプした業務時点**（意味を再定義） |
  | **③ 端末申告時刻** | 監査・是正・乖離検出 | **`occurred_at`（生・詐称可能）**を保持し、乖離は **ADR-0007 §2.8** の枠組み（`pending`／監査）へ |

  - **① 受理台帳が冪等の権威**：`event_receipt(tenant_id, event_uuid) PRIMARY KEY, event_ts, received_at`。**push の受理は台帳への `INSERT ... ON CONFLICT DO NOTHING` と同一トランザクション**で行う。**再送は台帳が弾き、台帳に記録済みの `event_ts` を返す**——**これにより「サーバが決める値は再送で変わる」という v9 の却下理由が解消する**（決定性は台帳が与える）。
    - 台帳は **非パーティション**とする。保持期間は**端末アウトボックスの最大保持（14日・要求 5.3.1）に十分な余裕**を足した値（既定：1年）とし、`received_at` 索引を使った小分け削除で運用する。パーティション化すると一意制約に `received_at` が必要になり、冪等キーの保証を失うため採用しない。
    - **保持期間を超える再送は業務キーの一意制約で最終防護**する（ADR-0008 IND-L4 と同じ思想。台帳のTTLに正しさを預けない）。
    - **副産物**：台帳は `event_ts` でパーティション化されないため **`(tenant_id, event_uuid)` の一意制約をそのまま張れる**——ADR-0007 が書いてきた冪等キー表記が**そのまま成立する**（IND3-L3 の解消）。
  - **② `event_ts` の意味を再定義**：「採番時点（UUIDv7由来）」→ **「サーバが検証・クランプした業務時点」**。サーバは端末申告の `occurred_at` を**許容ウィンドウにクランプ**する（既定：`received_at - 400日 〜 received_at + 1日`。要求 5.3.1 の14日に十分な余裕を見た値で、法域・運用で調整可）。**`CHECK (event_ts BETWEEN received_at - INTERVAL '400 days' AND received_at + INTERVAL '1 day')` でDB側でも強制**する。
    - **これで `event_ts` が範囲外になることが構造的に起きない＝受理は必ず成功する**。**「どんな端末時計でも①-aは受理できる」を不変条件とする。**
    - **【v11・S1 再実行で発見】クランプ窓の下限は「常に存在する最古のパーティションの開始」以上でなければならない**。さもないとクランプしても該当パーティションが無く `no partition ... found for row` になり、**上記の不変条件が達成されない**（S1 で実際に落ちた）。**retention でパーティションをドロップする際は、クランプ窓の下限も同時に繰り上げる**。すなわち **クランプ窓と retention 窓は同一の設定から導出する**（別々に決めてはならない）。
    - **`CHECK (event_ts = uuidv7_time(event_uuid))` は撤回**。**`event_uuid` の UUIDv7 固定は維持**（ソート性・時系列局所性・`uuidv7_time` による診断）だが、**パーティションキーの導出には使わない**。副産物として **PG-L4（PG18 の組込み `uuidv7()` へ差し替える際に CHECK の DROP/ADD＝全件再検証が要る）の負担も消える**。
    - **クランプが発生したら乖離として記録**し、ADR-0007 §2.8（善意のずれと詐称を動機で判別せず一律に「乖離」とする）に従って `pending`／監査へ載せる。
    - **アプリ供給の制約は維持**：①生成列はパーティションキーにできない／②BEFORE ROW トリガはルーティングの後に走る——ため、**`event_ts` はアプリ/リポジトリ層が算出して INSERT 時に明示供給**する（算出の入力が `uuidv7_time` から「クランプ済み `occurred_at`」に変わっただけ）。
  - **`DEFAULT` パーティションは置かない（実測で確認した罠）**：未来日付の行が DEFAULT に入ると、**後から当該月のパーティションを作成できなくなる**（`ERROR: updated partition constraint for default partition ... would be violated by some row`）。**②により範囲外が起きないので DEFAULT は不要**であり、置くと運用の罠になる。**パーティションは自動作成ジョブで常に先行作成する。**
  - **retention の起算点**：`event_ts` でのパーティションドロップは**粗い削除**であり、**保持期間の厳密な適用は `occurred_at` ベースの精密削除**と二段で行う。**起算点（業務時点か受理時点か）は法域別＝E2**（ADR-0003 A3b-L1）。
  - **S1 の合格基準に追加**：**「端末時計が ±1年ずれた端末の①-aイベントが1件も失われないこと」**／**「再送が台帳で弾かれ、台帳に記録済みの `event_ts` が返ること」**。
- **パーティション跨ぎ一意はDBが保証しない前提**（R2-H1）：宣言的パーティションの一意制約は**パーティションキー（`event_ts`）を含む**必要があるため、`UNIQUE(tenant_id, event_uuid, event_ts)` は**パーティションローカル一意**でしかない（`event_ts` が違えば同一 `event_uuid` を許す）。上記の決定的抽出で「同一 `event_uuid`→同一 `event_ts`」を成立させることで初めて重複排除が効く。加えて冪等は**受理時のUPSERT（ON CONFLICT）＋アプリ側デデュープ**で二重に担保する（DB制約単独に依存しない）。
- **RLS（v9全面改訂・PG-H6）**：**`ENABLE`／`FORCE ROW LEVEL SECURITY` とポリシーはパーティション子に伝播しない**（v8 までの「S1 で確認」は事実に反する。**S1 は親経由しか試験していない**）。**実測**：子は `relrowsecurity=f`・ポリシー0本で、**子を直接参照すると RLS が完全に無効**（親経由50件／子直接100件）。**対策＝子を専用スキーマ `part` に置き、通常ロールに `USAGE` を与えない**（親は `public`、アクセスは親経由のみ。**実測：子直接は `permission denied for schema part`**）。**スキーマ `USAGE` が無ければ個別 `GRANT` の事故にも耐える**（`priv` と同じ二重防御）。**パーティション自動作成ジョブは `part` に作成し子に `GRANT` しない**（`ALTER DEFAULT PRIVILEGES` も設定しない）。**検査＝`part` に通常ロールの権限が無いこと／`relispartition` のテーブルが `part` 以外に無いこと。S1 に「子直接参照の拒否」を合格項目として追加。**
- **監査ハッシュチェーン**：パーティション/期間単位のチェーン＋**期間末尾ハッシュのアンカ署名を外部保存**（ドロップ後も改ざん証明）。

```sql
-- ①テナント固有・②可逆確定：圃場
CREATE TABLE field (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL,
  field_group_id uuid,                       -- スコープ（担当エリア）
  name          text NOT NULL,
  geom          geometry(MultiPolygon, 4326) NOT NULL,  -- PostGIS(4326保持)
  -- 面積の権威を分離（M3-M3）：登記/申告面積が計算の権威、GIS実測は参考/検証用
  registered_area numeric,                   -- 原値（権威・希釈量/収量計算の既定）
  registered_area_unit text,                 -- 原単位（権威）
  gis_area_sqm  numeric GENERATED ALWAYS AS  -- geom導出（参考・検証用。権威ではない）
                  (ST_Area(geom::geography)) STORED,  -- 生成列は式のIMMUTABLE性が前提（R2-L1）
                  -- ST_Area(geography)が非IMMUTABLEな環境ではトリガ計算/ビュー導出に切替（S2で確認）
  timezone      text NOT NULL,                -- 圃場TZ(IANA)（暦日確定用・ADR-0015 A15c-L1）
  deleted_at    timestamptz,                  -- ソフトデリート
  version       bigint NOT NULL DEFAULT 1,    -- 楽観ロック
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz

-- timezone は移行時、圃場代表点の緯度経度→IANA TZ を一括解決（境界データはL2/§8）
-- 計算の使い分け：法定・希釈・収量/10a=registered_area、地図表示・逸脱検知=gis_area_sqm
CREATE INDEX ON field (tenant_id, field_group_id);
CREATE INDEX ON field USING gist (tenant_id, geom);  -- btree_gist（要スパイクS2）
ALTER TABLE field ENABLE ROW LEVEL SECURITY;
ALTER TABLE field FORCE ROW LEVEL SECURITY;
-- USING/WITH CHECK ポリシーは §4 のとおり

-- ①テナント固有：作業者（PIIをフィールド単位で分離・M3-M2）
CREATE TABLE work_actor (
  actor_id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL,
  employee_no   text,                        -- テナント内の自然キー（あれば・重複防止）
  legal_name    text NOT NULL,               -- ①-a：法定記録の作業者名（法的根拠で保持）
  contact       text,                        -- ①-b：連絡先等PII（GDPR削除は列NULL化=tombstone）
  user_id       uuid,                        -- 参照（アカウント削除でNULL化・legal_nameは残る）
  retention_basis text NOT NULL,             -- 保持根拠（法令保持/同意 等・E3の線引き）

CREATE UNIQUE INDEX ON work_actor (tenant_id, employee_no) WHERE employee_no IS NOT NULL;

-- ①-a法定：農薬使用記録（散布内容。作業者は actor_ref で分離）
CREATE TABLE pesticide_record (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL,
  worklog_id    uuid NOT NULL,
  field_id      uuid NOT NULL,
  applied_on    date NOT NULL,               -- 散布月日（圃場ローカル暦日）
  chemical_id   uuid NOT NULL,
  dilution      text, amount numeric, target_pest text, tool text,
  -- 作業者はPII分離。ON DELETE RESTRICT で法定記録の参照整合を守る（R2-M1）
  actor_ref     uuid NOT NULL REFERENCES work_actor(actor_id) ON DELETE RESTRICT,
  created_at    timestamptz NOT NULL DEFAULT now()
);  -- 散布内容は①-aのため更新/削除しない（訂正は訂正イベント追記）
-- GDPR消去は work_actor 行の物理削除ではなく contact/user_id の NULL化(tombstone)で行う。
-- actor行・legal_name は法定保持期間中は保持し、期間満了で pesticide_record と連動して消去（E3）。

-- ③共有+上書き：農薬肥料マスタ（部分一意索引・M3-L1）
CREATE TABLE agro_chemical (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid,                        -- NULL=システム共有／非NULL=テナント上書き
  reg_key       text NOT NULL,               -- 登録番号等の自然キー
  name          text NOT NULL, active_ingredient text, ...
);
-- 共有は key で全体一意、上書きは (key,tenant) で一意（ADR-0001 ③）
CREATE UNIQUE INDEX ON agro_chemical (reg_key) WHERE tenant_id IS NULL;
CREATE UNIQUE INDEX ON agro_chemical (reg_key, tenant_id) WHERE tenant_id IS NOT NULL;
-- 解決ビュー：テナント上書きがあればそれ、なければ共有
-- 【v9】ビューは security_invoker 必須（PG-H4／IND3-M6）：通常のビューは基底表のRLSを
--   「ビュー所有者」の文脈で評価するため、TO で列挙した permissive が適用されず
--   FORCE RLS 下では誰が読んでも0行になる。しかもビューは pg_policies にも
--   relrowsecurity にも現れないため検査に引っかからない。
--   → RLS有効な表を参照する業務ビューは WITH (security_invoker = true) で作成する
--     （PostgreSQL 15 以降が必須。最低要求バージョンを実質 PG15 に固定＝ADR-0004）。
--   → 絞り込み条件はポリシーと同じ変数を使う（app.tenant_id 単一ではなく
--     app.allowed_tenants 集合。単一だとグループ管理者の横断がビュー経由で通らない）。
--   → current_setting は §4 の正規化形を用いる。
CREATE VIEW agro_chemical_effective WITH (security_invoker = true) AS
  SELECT DISTINCT ON (reg_key) id, tenant_id, reg_key, name, active_ingredient
  FROM agro_chemical
  WHERE tenant_id IS NULL OR tenant_id = ANY(COALESCE(NULLIF(current_setting('app.allowed_tenants', true), ''), '{}')::uuid[])
  ORDER BY reg_key, (tenant_id IS NOT NULL) DESC;  -- 上書き優先

-- 【v10】受理台帳：冪等の権威（IND3-H5）。イベント表の一意制約に依存しない。
--   push の受理は本表への INSERT ... ON CONFLICT DO NOTHING と同一トランザクションで行う。
--   再送は本表が弾き、記録済みの event_ts を返す（サーバ採番でも決定性が保たれる）。
--   event_ts でパーティション化しないため (tenant_id, event_uuid) の一意をそのまま張れる。
CREATE TABLE event_receipt (
  tenant_id   uuid NOT NULL,
  event_uuid  uuid NOT NULL,
  event_ts    timestamptz NOT NULL,        -- サーバが検証・クランプした業務時点（採番結果）
  received_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, event_uuid)
);
CREATE INDEX event_receipt_received_at_idx ON event_receipt(received_at);
-- 保持期間：端末アウトボックス最大14日（要求5.3.1）に十分な余裕を足した既定1年。
--   received_at 索引で小分け削除し、超過分の再送は業務キーの一意制約で最終防護する
--   （ADR-0008 IND-L4 と同じ思想）。台帳自体は冪等二列PKを守るため非パーティション。
-- RLS：①テナント固有として §4 の形(a) を適用。子は part スキーマ（§5 PG-H6）。

-- 時系列・追記：位置ログ（時間×tenantサブパーティション・M3-H1/H2）
CREATE TABLE location_log (
  event_uuid    uuid NOT NULL,               -- クライアント生成 UUIDv7（冪等dedup・時刻内包）
  tenant_id     uuid NOT NULL,
  user_id       uuid NOT NULL,
  -- event_ts はサーバがoccurred_atを検証・クランプした決定的な振り分け軸。
  -- アプリ/リポジトリ層で算出し、受理台帳と同一トランザクションで明示供給する（§5【v10】）。
  event_ts      timestamptz NOT NULL,
  occurred_at   timestamptz NOT NULL,        -- 業務上の時点(UTC)。振り分けには使わない
  geom          geometry(Point, 4326),
  PRIMARY KEY (tenant_id, event_ts, event_uuid),     -- 全パーティションキー包含
  received_at   timestamptz NOT NULL DEFAULT now(),   -- 【v10】サーバ受理時刻
  CONSTRAINT event_ts_window CHECK (                    -- 【v10】クランプ窓をDBで強制（IND3-H5）
    event_ts BETWEEN received_at - INTERVAL '400 days' AND received_at + INTERVAL '1 day')
  -- 【v10撤回】CHECK (event_ts = uuidv7_time(event_uuid)) はサーバ側の補正を禁止していたため撤回。
  --   event_ts は「サーバが検証・クランプした業務時点」に再定義（§5）。UUIDv7 固定は維持するが
  --   パーティションキーの導出には使わない。
) PARTITION BY RANGE (event_ts);                      -- 主軸=サーバ検証済み業務時点

-- 版履歴（層②・M3-L3）：確定データの更新前スナップショット
CREATE TABLE field_history (

-- *_history にも親と同じ tenant restrictive/permissive を明示的に作る。
-- PostgreSQLに「親のRLSへ自動追随」する仕組みはないため、DDL生成とカタログ検査で全履歴表を網羅する。

-- 【v11】追記型・不変の確定投影：労務サマリ（法定区分は根拠確認済みの場合のみ）
--   v4 は「導出/②相当」としていたが、(1) 元データの打刻(Punch)は①-bで削除・匿名化され得るため
--   再計算できない、(2) 確認済み法域根拠がある場合だけ法定区分を適用する、(3) 本人起点横断は「打刻・作業日誌を
--   他テナント分まで露出させない」ことを目的としており（要求#18/3.2/7章）、都度導出にすると
--   横断参照のたびに他テナントの打刻を読む経路が要る——の3点により、実体化が必須。
CREATE TABLE labor_summary (
  summary_uuid   uuid PRIMARY KEY,               -- UUIDv7
  tenant_id      uuid NOT NULL,                  -- ①テナント固有（生成元テナント）
  user_id        uuid NOT NULL,                  -- 本人起点 restrictive 例外の条件列（§4）
  period_start   date NOT NULL,                  -- 対象期間（圃場ローカル暦日＝ADR-0015）
  period_end     date NOT NULL,
  work_minutes   integer NOT NULL,               -- 稼働（打刻・作業時間の集約）。業務内容は持たない
  confirmed_at   timestamptz NOT NULL,           -- 不変な確定投影への追記時刻
  corrects       uuid,                             -- 訂正チェーン（NULL=原本／非NULL=同一tenantの訂正元）
  correction_reason text,                        -- 訂正理由（corrects が非NULL のとき必須）
  retention_class text NOT NULL CHECK (retention_class IN ('operational','statutory')),
  retention_basis text,                          -- statutory のとき確認済み根拠IDが必須
  created_at     timestamptz NOT NULL DEFAULT now()
  ,CONSTRAINT statutory_basis_required CHECK
     (retention_class <> 'statutory' OR NULLIF(retention_basis, '') IS NOT NULL)
  ,CONSTRAINT labor_summary_tenant_summary_unique UNIQUE (tenant_id, summary_uuid)
  ,CONSTRAINT labor_summary_corrects_same_tenant_fk
     FOREIGN KEY (tenant_id, corrects) REFERENCES labor_summary(tenant_id, summary_uuid)
);
-- 不変条件：確定後は UPDATE しない。訂正は corrects を張った新レコードの追記。
--   有効値＝同一 (tenant_id, user_id, period) の訂正チェーン末尾（ビューで解決＝ADR-0003 A3-M2）。
-- 未確定期間はこの表に入れない：テナント内で打刻から導出して表示する（参考値・越境しない）。
--   横断参照では各シャードが自テナント内で導出した最小化サマリを返す（PIIは越境しない）。
--   権威確定（給与）に使えるのは本表の確定済みレコードのみ（ADR-0002 §3.1／§3.1.1）。
-- RLS（§4）：restrictive は本人起点例外形
--   `tenant_id = ANY(AT) OR user_id = UID OR user_id = ANY(ESU)`
--   WITH CHECK は `tenant_id = TID`（自テナントのみ追記）。各変数はADR-0001 §2.9.5の正規化形。
-- 保持・削除：statutory は確認済み根拠の期間を優先、operational は運用者設定の保持／削除方針に従う。
-- 根拠未設定のレコードを statutory として受理しない。削除時も訂正・削除証跡を監査する。

CREATE VIEW labor_summary_effective WITH (security_invoker = true) AS
  SELECT ls.*
  FROM labor_summary ls
  WHERE NOT EXISTS (
    SELECT 1 FROM labor_summary newer
    WHERE newer.tenant_id = ls.tenant_id AND newer.corrects = ls.summary_uuid
  );
-- 末尾だけを有効値として返す。訂正履歴は基底表で保持し、給与等へ既出なら差分訂正イベントを別途追記する。
-- 未確定値は tenant 内の punch/work_log から導出する別ビューとし、confirmed/effective と型・APIを分ける。

-- 監査（①-a追記・ハッシュチェーン・M3-L3/L4）
CREATE TABLE audit_log (
  event_uuid    uuid NOT NULL,
  tenant_id     uuid NOT NULL,
  event_ts      timestamptz NOT NULL,
  entity        text NOT NULL, entity_id uuid NOT NULL, op text NOT NULL,
  before        jsonb, after jsonb,
  actor_pseudonym text NOT NULL,             -- 仮名化ID（セキュリティ最小化）
  prev_hash     bytea, row_hash bytea NOT NULL,  -- 【v5】(tenant_id, 期間) 単位ハッシュチェーン（下記）
  PRIMARY KEY (tenant_id, event_ts, event_uuid)
) PARTITION BY RANGE (event_ts);
-- 書込（R2-L2／R3-L1）：audit_log も FORCE RLS 対象。SECURITY DEFINER トリガは所有者権限でも
--   FORCE RLS が効くため、書込は専用ロール audit_writer（BYPASSRLS）で行う。
--   BYPASSRLSは権限を持つ全表でRLSを迂回するため、属性自体をスコープ境界とはみなさない。
--   NOLOGIN・非委譲・audit_log INSERT-only ACL・固定search_path関数で最小化する：
--     ・audit_writer は INSERT のみ（UPDATE/DELETE/SELECT 不可＝append-only）
--     ・SECURITY DEFINER 関数は search_path を固定（ADR-0001 の注意点と同様）
--     ・tenant_id は監査対象行から導出し、クライアント設定(app.tenant_id)に依存しない
-- 【v5】チェーン単位＝(tenant_id, 期間)（ADR-0002 IND2-H4／ADR-0004 A4b-M2 の再裁定）：
--   v4 は「パーティション単位」だったが、シャード分割（1国=複数DB化）は必ず一度起き、その実体は
--   「テナント単位のデータ移送」である。パーティション単位チェーンだと1テナント分の行を別DBへ移した
--   瞬間に、移出元は鎖の途中が抜けて検証不能・移入先は他テナントの鎖に異物が入り、外部保存済みの
--   アンカ署名が実データと一致しなくなる（＝要求#17 の改ざん耐性が失われる）。
--   よってチェーンを (tenant_id, 期間) 単位に分割し、アンカ署名も (tenant_id, 期間) 単位で外部保存する。
--     ・テナント移送＝チェーン丸ごとの移送になり、鎖もアンカも無傷（移送後も検証可能）
--     ・prev_hash は同一 (tenant_id, 期間) 内の直前行を指す
--     ・副次的な利点：テナント間でチェーンが独立するため、A4b-M2 が懸念した直列化ボトルネックが
--       パーティション単位よりさらに緩和される（並行挿入がテナント境界で分かれる）
--     ・代償：チェーン数とアンカ署名数が (テナント数 × 期間数) に増える。署名のバッチ化・保管方式は ADR-0017
-- 【v7】「期間」の粒度（A1h-L3）：既定は audit_log のパーティション境界と同一（月）。
--   見積り例＝テナント1000 × 月12 = 12,000 チェーン/年（＝アンカ署名 12,000/年）。
--   同一テナント内の直列化が S5 でSLOを侵す場合は粒度を細分化する（日/時間）が、署名数が比例して
--   増えるトレードオフになる（A1h-M3/L3）。粒度と署名方式は S5 の実測後に ADR-0017 で確定。
-- 【v7】移送時のチェーン閉鎖（A1h-M3／ADR-0003 §2.9）：移送は期間境界で行うことを原則とし、
--   期間途中に移送する場合は移送時点でチェーンを閉じて末尾ハッシュをアンカ署名し、
--   移入先で新しいチェーンを開始する（鎖を2つに割らない）。
--   ＋ハッシュチェーンで改ざん耐性を担保。
-- 期間末尾ハッシュのアンカ署名を外部保存。越境監査（システム管理操作・法域跨ぎ）は
--   audit_reader（NOLOGIN・BYPASSRLS・audit_log SELECT-only）が固定search_path関数で最小化readし、
--   呼出主体・法域・期間・目的コードを権威情報へ照合する。成功／拒否はaudit_writer経路で再監査する。
--   audit_reader/audit_writerは相互・ログインロールへGRANTせず、PUBLIC EXECUTEも許可しない（ADR-0001 v19）。
```

> **仮名化 vs 実値の使い分け**（M3-L4）：`audit_log.actor_pseudonym` は**セキュリティ監査**目的でデータ最小化（①-b相当）。`work_actor.legal_name` は**法定の作業者記録**（①-a・法的根拠で保持）。目的が異なるため扱いを分ける（ADR-0003 の①-a/①-b に対応）。

**スパイクで確定した設計事項（本文へ反映済）**：
- **event_ts の導出はアプリ層＋CHECK**：生成列はパーティションキー不可、BEFOREトリガはルーティング後に走るため使えない（§5/§6）。
- **R4-L1 解決**：`uuidv7_time` は IMMUTABLE で作成でき時刻復元一致。`ST_Area(geography)` 生成列も可（IMMUTABLE）。
- **R4-L2 は一部解決**：`event_ts` レンジのプルーニングとスコープrestrictiveの索引利用は成立。空間は合成10万行でSLO内だが、bboxの非leakproof空間条件が `Filter` に落ちるため「tenant絞り→空間」の構造的合格には未達。本番規模・並行負荷での再測に加え、PG-M2／PG-M8の設計処置が必要。

**【v11】S2 の設計処置（PG-M2／PG-M8）**：空間APIはRLSだけにtenant絞りを委ねず、サーバが検証済み `tenant_id` の等値をSQLへ冗長に明示し、`btree_gist` の `(tenant_id, geom)` 複合GiSTを使う。複数tenant横断はtenantごとのサブクエリで候補を絞ってからマージし、KNNの全tenant候補読み捨てを避ける。RLSは最終防波堤として残す。S2で等値明示KNN 0.137msを確認済みで、bbox・並行負荷は本番相当データで再測する。再測不合格時はtenant hashパーティションまたは法域内読取投影を別ADRで裁定し、非leakproof演算子を安易に `LEAKPROOF` ラップしない。

- **未実行**：S3（冪等×パーティションの独立検証はS1に統合済）、S5（監査ハッシュチェーン並行性）は実装フェーズで。
- **成果物**：本結果をADR-0004/0001の未解決事項へも反映する。
