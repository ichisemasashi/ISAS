## 1. 背景・課題（Context）

本システムは複数法人による**グループ/連合利用**を前提とするマルチテナント構成であり、**組織（テナント）単位でデータを分離**しつつ、**グループ管理者のみが横断アクセス**できる必要がある（要求仕様3.2）。加えて以下の制約がある：

- **規模**：1DB（＝1システム＝1国、ADR-0002）あたり最大5万ユーザー。
- **グループ管理者の横断**：同一システム内の全組織を横断参照できる（テナント間分離の例外）。
- **本人起点の横断**：受託作業者本人（＋雇用主）が、自分の稼働（労務サマリ）に限りテナントをまたいで参照できる（要求仕様#18）。
- **個人データの最小権限**：位置ログ・打刻・労務サマリは最小権限で制御（要求仕様3.2）。
- **オフライン同期**：同期対象を確実にテナントで絞り込む必要がある（漏えい防止）。
- **アプリ層のバグ耐性**：WHERE句の付け忘れ等でも他テナントのデータが漏れない「最後の防波堤」が欲しい。

どのマルチテナント分離方式を採るかは、権限・性能・運用・セキュリティに広く影響するため、最初に決定する。

## 2. 決定（Decision）

**行レベル分離（共有スキーマ＋全テーブルの `tenant_id`＋PostgreSQL Row Level Security（RLS））** を採用する。

- 全業務テーブルに `tenant_id` 列を持たせ、既定でテナント単位に行を分離する。
- **RLSポリシー**でDB層のアクセス制御を強制する（アプリ層のWHERE句に依存しない最後の防波堤）。

**RLSを実際に効かせるための必須条件（A1-H1・A1-H2）**：RLSは以下を満たさないとサイレントに無効化される。実装の前提条件として決定に含める。

- **テナント文脈は `SET LOCAL app.tenant_id`（トランザクション境界）で設定**する。セッションレベルの `SET` は接続プールで使い回した際に**前のテナント文脈が次のリクエストへリークする**ため用いない。全クエリを「テナント設定済みトランザクション」内で実行する共通機構（ミドルウェア／コネクションラッパ）を必須とし、接続返却時のリセットも担保する（A1-H1）。
  - **前提（A1b-L1／A1c-L3）**：`SET LOCAL` はトランザクション内でのみ有効なため、**単純な読取を含む全DBアクセスを明示トランザクションで包む**。コネクションプーラ（PgBouncer等）は**トランザクションプーリングモード**を用いる（セッションプーリングは前提が崩れるため不可）。トランザクションプーリングでは**セッション単位のprepared statements・LISTEN/NOTIFY・advisory lock**が期待通り動かない既知制約があるため、ドライバ/ORMはこれらに依存しない設定（サーバサイドprepared statementの扱い・LISTEN/NOTIFY非依存）とする。
- **全業務テーブルに `FORCE ROW LEVEL SECURITY` を設定**する。これがないとテーブル所有者はRLSをバイパスする（A1-H2）。**【v9】対象は業務テーブル（下記①〜④分類）に限る**——分類外の**特権経路専用テーブル**はRLSではなく `GRANT/REVOKE` で守るため FORCE RLS の対象外である（**FORCE RLS を付けると特権経路自身が自己ブロックする**：A1f-H1）。
- **ポリシーはフェイルクローズ**：`app.tenant_id` が未設定/NULLのときは**全拒否**（`current_setting('app.tenant_id', true)` が NULL の場合に真とならないポリシー式）とする。未設定でフェイルオープン（全件参照）にしない（A1-H2）。**未設定・空文字列・不正値はすべて安全側（全拒否）で扱う**（空文字列の `''::uuid` はエラーになるため、キャスト前に正規化するか、不正値は拒否として扱う実装ルールとする：A1b-L2）。
- **読取と書込の両方を定義（A1d-M1）**：各RLSポリシーは**USING（読取・可視性）と WITH CHECK（書込＝INSERT/UPDATE）の両方**を定義する。WITH CHECK がないと、**INSERT時のtenant_id詐称**（他テナントのtenant_idで行を作る）や**UPDATEでのtenant_id書き換え（別テナントへの行移送）**を防げない。テナント固有テーブルは `WITH CHECK (tenant_id = current)` を必須とし、自テナント以外への書込・移送を拒否する。
- **アプリの接続ロールは非所有者・非スーパーユーザー・非BYPASSRLS**とする。マイグレーション等の特権操作は別ロールで実行し、常用しない（A1-H2）。
- **認証・ブートストラップの特権経路（A1e-M1）**：フェイルクローズにより `app.tenant_id` 設定前は何も読めないため、「どのテナントを設定すべきか」を知るための**認証・所属解決（ユーザー→メンバーシップ→許可tenant_id集合）は、RLS対象外の特権経路で行う**。具体には認証・所属解決を**SECURITY DEFINER関数**（集合検証関数と同系、search_path固定・最小権限）または**認証用の専用ロール/スキーマ**で実行し、テナント確定後に `SET LOCAL app.tenant_id` して以降の業務クエリに入る二段構えとする（ADR-0009 認証と連携）。これがないと**ログイン/セッション確立自体がフェイルクローズで自己ブロックされる**。

- テナントの識別は、接続プールを維持するため**テナント別DBロールではなく、セッション変数方式**とする（上記のとおり `SET LOCAL` を用いる）。
- **横断アクセスは別ポリシーで宣言的に許可**する（相互作用に注意：A1-M2）：
  - **グループ管理者**：同一システム（同一DB）内の配下組織を横断参照。行単位サブクエリの性能劣化を避けるため、**許可tenant_id集合をセッション変数（配列）に事前解決して注入**し、ポリシーはその集合との包含判定で済ませる（A1-M1）。
    - **防波堤性と性能の両立（A1b-M1／A1c-M1）**：注入集合を**アプリが計算する**と、その計算バグが誤った横断アクセスを生み、「RLS＝アプリバグへの最後の防波堤」性が横断経路で弱まる。これを緩和するため注入集合をDB側で検証するが、**検証を行単位（ポリシー内 EXISTS）で行うと、行単位サブクエリの性能問題（A1-M1で回避したもの）が復活する（循環）**。したがって検証は**「集合注入時に1回」**に限定する：リクエスト冒頭で `SET LOCAL` する前に、注入予定のtenant_id集合が当該user_idのグループ管理者メンバーシップに包含されることを**1クエリ（SECURITY DEFINER関数等）で検証**し、**検証済みの集合のみ**をセッション変数に注入する。**SECURITY DEFINER関数は`search_path`を固定し最小権限で定義する**（関数注入・権限昇格の攻撃面を避ける：A1d-L1）。**ポリシー本体は注入済み集合との包含判定のみ（サブクエリなし）**に保つ。これで防波堤性（注入は必ず検証済み）と性能（ポリシーはサブクエリなし）を両立する。
  - **本人起点横断**：`user_id` を条件とするRLSポリシーで、**労務サマリ（LaborSummary）テーブルに限定**し「当該user_idの稼働」のみ許可（業務テーブルWorkLog等は越境露出させない。ADR-0005・要求仕様#18）。複数ポリシーのOR結合で範囲が意図せず広がらないよう、対象テーブルごとに適用ポリシーを明示し、必要に応じ restrictive ポリシーで絞る（A1-M2）。
- **テーブルの分類（A1-M3）とポリシー**：業務テーブルを4種に分類し、それぞれ専用のRLSポリシーを当てる（加えて分類外の**特権経路専用テーブル**を下記に定義する）。
  - **① テナント固有**（tenant_id必須・RLS対象）：`USING (tenant_id = current)`（読取）＋`WITH CHECK (tenant_id = current)`（書込：詐称・越境移送を拒否）のフェイルクローズ・ポリシー。「全業務テーブルにtenant_id」はこの分類に適用。
  - **② システム共有**（tenant_idなし、全員読取のみ・例：国レベルの共有マスタ候補）：読取は全テナント可、書込は特権ロールのみ。**書込の運用（A1c-L2）**：アプリの通常接続は非所有者・非BYPASSRLSロール（A1-H2）で共有マスタを書けない。共有マスタの書込は**管理用の別接続/別ロール**（テナント通常接続とは別経路）で行い、通常のテナント操作からは書けないようにする。
  - **③ 共有＋テナント上書き可能**（tenant_id NULL=共有の既定行、非NULL=テナント上書き）：**フェイルクローズの単純ポリシー（`tenant_id = current`）ではNULL共有行が誰にも見えなくなり機能破綻するため（A1b-M2）、専用ポリシー `tenant_id IS NULL（共有）OR tenant_id = current（自テナント上書き）` を用いる**。
    - **責務分離（A1c-L1）**：RLSは**行の可視性のみ**を制御する（共有行と自テナント上書き行の両方が可視になる）。「同一キーで上書き行を優先して採用する」解決は**RLSではなくビュー/クエリ側のロジック**（自テナント行があればそれ、なければ共有行）で行う。
    - **一意制約（A1c-L1／A1d-L2）**：共有行（tenant_id NULL）と自テナント上書き行の重複を防ぐ制約設計を行う。**sentinel（`COALESCE(tenant_id, 既定値)`）方式は既定値が実tenant_idと衝突するリスクがあるため、部分一意インデックスを推奨**：共有行用 `UNIQUE(key) WHERE tenant_id IS NULL` ＋ テナント行用 `UNIQUE(key, tenant_id) WHERE tenant_id IS NOT NULL`。
    - **書込制御（WITH CHECK：A1d-M1）**：一般テナント接続には `WITH CHECK (tenant_id = current)` を課し、**tenant_id IS NULL（共有）行の書込を拒否**する（共有汚染の防止）。**共有行への書込は特権ロールのみ**（②と同じ別接続/別ロール運用：下記A1c-L2）。一般テナントは自テナント上書き行のみ作成・編集できる。
  - **④ ユーザー所有**（tenant非依存・`user_id`でアクセス制御。例：下書き/未確定データ＝ADR-0003層③）：**`USING/WITH CHECK (user_id = 現在のユーザー)`** のポリシーで本人のみ参照・書込可とする（tenant_idベースではない）。**確定時にtenant固有（①）または可逆確定（②相当）へ移送**し、tenant_idを付与する。下書きは本人以外・他テナントから見えない。（ADR-0003 A3b-M1で追加。v7）
- **【v8／v9改訂】分類外＝特権経路専用テーブル（ADR-0002 v8 A2g-M3 波及。v9で第6回レビューを反映）**：上記4分類は**業務テーブル**の分類であり、**通常ロールに一切見せてはならない基盤テーブルは4分類のいずれにも属さない**。代表例は **ADR-0002 の法域ローカル `user→shard` ルーティング索引**——`tenant_id` を持たないので①③ではなく、②システム共有にすると**全ユーザーの所属関係が全テナントから読める**（機密性の破綻）、④ユーザー所有では**入口層が"他人の `user_id`"で引く用途**（そのユーザーのシャードを解決する）に機能しない。よって次の枠を定義する：

  - **【v9】定義は「通常ロールに `GRANT` しないテーブル」（A1f-M2）**：v8 は「A1e-M1 と同じ扱い」と書いたが、**A1e-M1 は"アクセス経路"の決定であって"テーブル分類"ではない**（メンバーシップテーブルは①テナント固有のまま、特権経路からも通常経路からも読まれる）。この2つを混同すると一覧化の基準が判定不能になるため、**軸を分離**する：
    - **軸1＝アクセス経路（A1e-M1）**：SECURITY DEFINER関数／認証専用ロールから読む、という経路の話。**①のテーブルもこれに該当し得る**（メンバーシップ）。**該当してもテーブルの分類は①のまま**であり、本枠には含めない。
    - **軸2＝テーブル分類（本枠）**：**通常ロールに `GRANT` しない**＝通常経路からは存在しないに等しいテーブル。判定基準は経路ではなく**権限**で定める。
  - **【v9】守り方は `GRANT/REVOKE`。RLSでは守らない（A1f-H1。v8の記述を撤回）**：v8 は「デフォルト拒否のポリシーを置く」「FORCE RLS の対象外にする例外ではない」と書いたが、**これを実装すると認証が自己ブロックする**——`ENABLE RLS` でマッチするポリシーが無ければ0行、そして `FORCE RLS` は**テーブル所有者のバイパスも止める**（A1-H2 の目的）。SECURITY DEFINER 関数は**関数所有者の権限で実行される**ため、**特権経路自身が0行しか得られずログイン不能**になる（A1e-M1 が「これがないと自己ブロックされる」と警告したまさにその失敗）。
    - **RLSは行の可視性の仕組み**であり、「**テーブル全体を特権ロール以外に見せない**」のは**テーブル単位の権限**の問題である。よって正しい道具は `GRANT/REVOKE`：
      - `REVOKE ALL ON <テーブル> FROM <アプリ通常ロール>;`
      - `GRANT SELECT ON <テーブル> TO <認証専用ロール>;`（またはSECURITY DEFINER関数の所有者のみ）
    - **RLS／FORCE RLS は設定しない**（設定しても得るものがなく、自己ブロックの罠だけが残る）。**この枠は本ADRの「RLSが最後の防波堤」の外にあることを正直に認め、代わりに権限で担保する**（帰結は §4）。
  - **【v9】書込も SECURITY DEFINER 関数経由（A1f-L3）**：ADR-0002 v8 は索引の書込を「**メンバーシップ付与と同一トランザクション**（加入先シャードのローカルTX）」と決めた。通常ロールに直接 `INSERT/DELETE` を与えると遮断の意味が薄れるため、**通常ロールは書込権限を持たず、同一トランザクション内で SECURITY DEFINER 関数を呼んで索引行を更新する**。関数は `search_path` 固定・最小権限（A1d-L1 と同じ規律）とし、**自シャードの行しか書けないことを関数内で検証**する。
  - **【v9】参照の監査（A1f-M3）**：**行レベルトリガは `INSERT/UPDATE/DELETE` にしか設定できず、`SELECT` を捕捉できない**（本プロジェクトの監査はトリガ＋ハッシュチェーン＝ADR-0004）。したがって参照監査は**SECURITY DEFINER 関数内で明示的に監査行を追記する**方式とする（または `pgaudit` 等の拡張。選択は ADR-0017 で確定）。
    - **認証前の参照は actor が確定していない**（相手が主張した `user_id` にすぎない）。よって**「主張された `user_id` ＋ 接続元 ＋ リクエストID」として記録し、認証済みの actor とは種別を分けて保存**する（未認証の主張を認証済み行為と同じ列に混ぜない）。
    - 監査の粒度・保持期間・**ログイン数に比例する量に耐えるか**は ADR-0017／ADR-0020 と一体で確定する（§5）。
  - **【v9】バックアップ・レプリカ・環境コピー（A1f-L1）**：本枠のテーブルは各DB内にあるため**バックアップ・リードレプリカ・開発/検証環境へのダンプにも当然含まれる**。本番の権限で遮断しても、**ダンプを開発環境へ復元した時点で誰でも読める**——ADR-0002 が「侵害時は全件が一度に漏れる機密資産」と警告した内容の実務上の主経路である。**開発/検証環境へのコピー時はマスキングまたは除外の対象**とし、ADR-0017（データ保護）／ADR-0019（環境運用）へ申し送る。
  - **【v9】テストの期待値は「権限エラー」（A1f-H1）**：ポリシーテスト（§5）には「特権経路専用テーブルが通常ロールから読めないこと」を含めるが、**期待するのは0行ではなく `permission denied`** である（0行を期待するテストは、誤って `GRANT` を与えたときに合格してしまう）。
  - 該当テーブルは**一覧化して管理**する（無自覚に増えると多層防御の穴になるため。§5）。
- **性能**：`tenant_id` を**複合インデックスの先頭**に置く。横断ダッシュボード等の重い集計は、RLSを通した実行時集計ではなく**集計テーブル／マテリアライズドビュー**を別途用意する。
- **主キー・識別子（A1e-L2）**：PK・外部公開IDは**UUID等の非連番**を用いる（連番PKは行数・クロステナントの規模を漏らし、URL露出時の列挙も容易なため。監査ログ等の追記型を含む）。
- **外部キー（A1e-L1）**：PostgreSQLのFK制約チェックはRLSをバイパスして評価されるため、**FKは原則同一テナント内に閉じる**設計とする。テナント跨ぎFK（共有マスタ参照等）は、FK違反エラー/タイミングによる他テナント行の存在推測（情報漏れ）を踏まえたエラーハンドリングを設計フェーズで検討する。
- **オフライン同期API**：同期対象の絞り込みにも必ず `tenant_id`（＋権限）を通す。**端末（オフライン）側にはRLSがない**ため、複数テナントに所属するユーザーの端末データ分離・暗号化は [ADR-0007（オフライン同期）] と連携して設計する（A1-L2）。

## 3. 検討した選択肢（Options）

前提：本システムは**1配備＝1DB＝1国**（ADR-0002）で、1DB内のテナント数は数個〜数百のオーダー（数万テナントのSaaSではない）。

> **前提の境界（A1-L1）**：要求仕様#13でOSS運用者は第三者へのサービス提供（SaaS）も許容される。SaaS運用者が1DBに**数千テナント**を収容する運用では、この「数百」前提が崩れ、DB分離却下の根拠も弱まる。その場合は**ハイブリッド（D案）＝大口テナントのみDB/スキーマ分離、またはテナント群のシャーディング**で対応する（本ADRの決定は、規模が本前提を超えたら D案へ拡張できる余地を残す）。

| 方式 | 概要 | 長所 | 短所 | 本件評価 |
|---|---|---|---|---|
| **A. DB分離** | テナントごとに物理DB | 分離が最強・障害影響も個別・個別バックアップ | **グループ管理者の横断集計がDBをまたぎ困難**／運用コスト×テナント数／マイグレーションが全DB分 | ✕ 横断要件と衝突、テナント数分の運用が重い |
| **B. スキーマ分離** | 同一DB内にテナント毎スキーマ | 分離は明確・単一DB運用 | 横断クエリが煩雑／スキーマ数増で接続プール・マイグレーションが劣化／PostGIS等も個別 | △ 中途半端になりやすい |
| **C. 行レベル分離＋RLS（採用）** | 共有スキーマ＋tenant_id＋RLS | **横断集計が容易**（ポリシーで宣言的に許可）／マイグレーション1回／規模に十分／要求仕様のデータモデル（全レコードにtenant_id）と一致／**アプリのバグに対しDB層が防波堤** | 物理分離ほどの隔離ではない／全テーブルへのtenant_id列とインデックス設計が必須／ポリシー設計を誤ると穴 | ◎ 横断要件・規模・データモデルに最適 |
| D. ハイブリッド | 基本は行レベル、大口のみDB/スキーマ分離 | 柔軟 | 最初から二重の運用系統を持つ | ○ 将来の外販SaaS化まで不要 |

**却下理由**：Aは「グループ管理者の横断」という中核要件と正面衝突し、1DB内のテナント数が限定的な本件では運用コストに見合わない。Bは横断が煩雑で、スキーマ数増による運用劣化が読みにくい。Cは横断要件・規模・既存データモデル（全レコードがtenant_idを持つ）と最も整合し、DB層での防波堤も得られる。

## 4. 帰結（Consequences）

**良い影響**
- グループ管理者の横断・本人起点横断を、**RLSポリシーで宣言的**に表現できる。
- マイグレーションが1系統で済み、運用がシンプル。
- アプリ層のWHERE句漏れに対して**DB層（RLS）が最後の防波堤**になり、監査要件（5.4）と相性が良い。
- 要求仕様6章のデータモデル（全レコードにtenant_id）をそのまま実装でき、仕様変更が不要。

**注意すべき影響・制約（以降の設計に生じる制約）**
- **全業務テーブルに `tenant_id` を必須化**し、複合インデックス先頭に置く設計規約を全体に適用する。
- **RLSポリシー設計が権限の正しさを左右する**ため、ポリシーはテスト（他テナント参照の遮断・横断許可の範囲）を必須とする。
- セッション変数（`app.tenant_id` 等）の**設定漏れ＝分離破綻**になるため、接続取得時に確実に設定する共通機構（ミドルウェア／コネクションラッパ）を用意する。
- 集計系はRLS越しの実行時集計だと重くなるため、**集計テーブル／マテビュー**の設計・更新方式を別途必要とする。
- 物理隔離ではないため、**保存時暗号化・鍵管理・監査ログ**（ADR-0017）で機微データ保護を補完する。
- **【v9】特権経路専用テーブルはRLSの防波堤の外にある（A1f-M1）**：認証・所属解決はテナント文脈が確定する**前**に参照する必要があるため、この枠のテーブルは **RLSではなく `GRANT/REVOKE` で守る**（A1f-H1）。したがって**この枠に限り「アプリバグに対するDB層の防波堤」は存在せず、権限付与の誤りが直接漏えいになる**——本ADRの中核主張（RLSが最後の防波堤）に対する**明示的な例外**である。よって、①該当テーブルは**最小限に保つ**（追加には明示的な判断を要する＝§5の一覧化）、②**ADR-0017 の脅威モデルで個別に評価する**（RLSが全テーブルを覆っている前提で設計してはならない）。**ADR-0002 の `user→shard` 索引は、法域内全ユーザーの取引関係グラフという機密資産**であり、この例外の下に置かれる最初の対象である。

## 5. 未解決事項（設計フェーズで詰める → 9.1へ）

- RLSポリシーの具体設計（3.2ロール表のDB表現、グループ管理者の許可tenant_id集合の事前解決＋**DB側検証（EXISTS/SECURITY DEFINER）**の実装、本人起点横断の労務サマリ限定ポリシー、permissive/restrictiveの使い分け、③共有＋上書き可能テーブルの専用ポリシーと上書き優先解決：A1-M1/M2/A1b-M1/M2）。
- `SET LOCAL app.tenant_id` を全クエリのトランザクション境界で確実に設定・解除する共通機構の実装（ミドルウェア／コネクションラッパ）とテスト（A1-H1）。
- RLSの有効性テスト（他テナント参照の遮断、未設定時のフェイルクローズ、FORCE RLS〔対象＝業務テーブル①〜④〕、非所有者ロールでの動作）を自動テスト化（A1-H2）。**【v9】あわせて「特権経路専用テーブルが通常ロールから読めないこと」を、期待値＝`permission denied`（0行ではない）としてテストする**（A1f-H1）。**特権経路（SECURITY DEFINER関数）からは正しく読めること**も同時にテストし、自己ブロックの再発を検出できるようにする。
- テーブル分類（テナント固有／システム共有／共有＋上書き可能／ユーザー所有）の一覧化と、共有マスタの具体対象（農薬肥料マスタ・作物マスタ・多言語ラベル等）の確定（A1-M3）。
- **【v8／v9改訂】特権経路専用テーブルの一覧化（A1f-M2）**：一覧化の基準は「**通常ロールに `GRANT` しないテーブル**」とする（アクセス経路ではなく権限で判定）。**特権経路から読まれるが通常経路でも使うテーブル（メンバーシップ等）は①テナント固有のままであり、この一覧には含めない**。現時点の該当は **ADR-0002 の `user→shard` ルーティング索引**のみ。**無自覚に増えると多層防御の穴になる**ため、追加には明示的な判断を要するものとする（ADR-0002 A2g-M3／ADR-0009／ADR-0017）。
- **【v9】特権経路専用テーブルの参照監査の実装方式（A1f-M3）**：SECURITY DEFINER関数内での明示追記か `pgaudit` かの選択、**認証前の「主張された `user_id`」と認証済み actor の種別分離**、ログイン数に比例する監査量の保持・性能を **ADR-0017／ADR-0020** で確定する。
- **【v9】特権経路専用テーブルの環境コピー時の扱い（A1f-L1）**：バックアップ・レプリカ・開発/検証環境ダンプに含まれるため、**マスキングまたは除外**の運用を **ADR-0017／ADR-0019** で確定する。
- 集計テーブル／マテビューの対象・更新頻度・整合性（横断ダッシュボードF-60〜63）。
- テナント削除・移設（オフボーディング）の運用。
- 規模が「1DB数百テナント」前提を超えた場合のハイブリッド/シャーディング移行計画（A1-L1）。
- 端末側データ分離・暗号化はADR-0007と連携（A1-L2）。

> 関連：テナントの物理境界（1DB=1国）は [ADR-0002](ADR-0002-配備モデル-1DB-1国.md)、権限の詳細は [ADR-0005](ADR-0005-権限モデル-RBAC-メンバーシップ.md)、暗号化・監査は [ADR-0017] で扱う。
