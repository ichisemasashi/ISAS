## 1. 背景・課題（Context）

本システムは複数法人による**グループ/連合利用**を前提とするマルチテナント構成であり、**組織（テナント）単位でデータを分離**しつつ、**グループ管理者のみが横断アクセス**できる必要がある（要求仕様3.2）。加えて以下の制約がある：

- **規模**：1DB（＝1システム＝1国、ADR-0002）あたり最大5万ユーザー。
- **グループ管理者の横断**：同一システム内の全組織を横断参照できる（テナント間分離の例外）。
- **本人起点の横断**：受託作業者本人（＋雇用主）が、自分の稼働（労務サマリ）に限りテナントをまたいで参照できる（要求仕様#18）。
- **個人データの最小権限**：位置ログ・打刻・労務サマリは最小権限で制御（要求仕様3.2）。
- **オフライン同期**：同期対象を確実にテナントで絞り込む必要がある（漏えい防止）。
- **アプリ層のバグ耐性**：WHERE句の付け忘れ等でも他テナントのデータが漏れない「最後の防波堤」が欲しい。**【v10／v11】テナント文脈が確定する前に参照が必要な認証・所属解決の経路は、原理的にこの防波堤の外になる**（フェイルクローズが自己ブロックするため）。ただし**その経路が読むのは①テナント固有テーブル（メンバーシップ等）であり、テーブル自体はRLS配下に留まる**（A1e-M1 の軸1）——**RLSの外に置く専用テーブルは、v11時点で存在しない**（§2【v11】・§3.1・§4）。

どのマルチテナント分離方式を採るかは、権限・性能・運用・セキュリティに広く影響するため、最初に決定する。

## 2. 決定（Decision）

**行レベル分離（共有スキーマ＋全テーブルの `tenant_id`＋PostgreSQL Row Level Security（RLS））** を採用する。

- 全業務テーブルに `tenant_id` 列を持たせ、既定でテナント単位に行を分離する。
- **RLSポリシー**でDB層のアクセス制御を強制する（アプリ層のWHERE句に依存しない最後の防波堤）。**【v11】現時点で例外はない**——ADR-0002 v9 が索引の物理化を撤回したため、**全テーブルがRLS配下（①〜④）に収まっている**。将来マテリアライズドキャッシュ等を導入する場合に備え、**「特権経路専用テーブル」の枠を条件付きで用意してある**（専用スキーマ＋テーブル権限＋網羅検査。下記【v11】【v9】【v10】・§3.1・§4）。**例外を作るときは、スキーマという物理的な区画に閉じ込め、網羅検査で増殖を検出する。**

**RLSを実際に効かせるための必須条件（A1-H1・A1-H2）**：RLSは以下を満たさないとサイレントに無効化される。実装の前提条件として決定に含める。

- **テナント文脈は `SET LOCAL app.tenant_id`（トランザクション境界）で設定**する。セッションレベルの `SET` は接続プールで使い回した際に**前のテナント文脈が次のリクエストへリークする**ため用いない。全クエリを「テナント設定済みトランザクション」内で実行する共通機構（ミドルウェア／コネクションラッパ）を必須とし、接続返却時のリセットも担保する（A1-H1）。
  - **前提（A1b-L1／A1c-L3）**：`SET LOCAL` はトランザクション内でのみ有効なため、**単純な読取を含む全DBアクセスを明示トランザクションで包む**。コネクションプーラ（PgBouncer等）は**トランザクションプーリングモード**を用いる（セッションプーリングは前提が崩れるため不可）。トランザクションプーリングでは**セッション単位のprepared statements・LISTEN/NOTIFY・advisory lock**が期待通り動かない既知制約があるため、ドライバ/ORMはこれらに依存しない設定（サーバサイドprepared statementの扱い・LISTEN/NOTIFY非依存）とする。
- **全業務テーブルに `FORCE ROW LEVEL SECURITY` を設定**する。これがないとテーブル所有者はRLSをバイパスする（A1-H2）。**【v9】対象は業務テーブル（下記①〜④分類）に限る**——分類外の**特権経路専用テーブル**はRLSではなく `GRANT/REVOKE` で守るため FORCE RLS の対象外である（**FORCE RLS を付けると特権経路自身が自己ブロックする**：A1f-H1）。
- **ポリシーはフェイルクローズ**：`app.tenant_id` が未設定/NULLのときは**全拒否**（`current_setting('app.tenant_id', true)` が NULL の場合に真とならないポリシー式）とする。未設定でフェイルオープン（全件参照）にしない（A1-H2）。**未設定・空文字列・不正値はすべて安全側（全拒否）で扱う**（空文字列の `''::uuid` はエラーになるため、キャスト前に正規化するか、不正値は拒否として扱う実装ルールとする：A1b-L2）。
- **読取と書込の両方を定義（A1d-M1）**：各RLSポリシーは**USING（読取・可視性）と WITH CHECK（書込＝INSERT/UPDATE）の両方**を定義する。WITH CHECK がないと、**INSERT時のtenant_id詐称**（他テナントのtenant_idで行を作る）や**UPDATEでのtenant_id書き換え（別テナントへの行移送）**を防げない。テナント固有テーブルは `WITH CHECK (tenant_id = current)` を必須とし、自テナント以外への書込・移送を拒否する。
- **アプリの接続ロールは非所有者・非スーパーユーザー・非BYPASSRLS**とする。マイグレーション等の特権操作は別ロールで実行し、常用しない（A1-H2）。
- **認証・ブートストラップの経路（A1e-M1。**v13で機構を是正**）**：フェイルクローズにより `app.tenant_id` 設定前は何も読めないため、「どのテナントを設定すべきか」を知るための**認証・所属解決（ユーザー→メンバーシップ→許可tenant_id集合）**を、テナント文脈の確定前に行う経路が必要である。テナント確定後に `SET LOCAL app.tenant_id` して業務クエリに入る二段構えは維持する（ADR-0009 認証と連携）。これがないと**ログイン/セッション確立自体がフェイルクローズで自己ブロックされる**。

  - **【v13】「SECURITY DEFINER なら RLS を回避できる」は誤りだった（ADR-0002 第9回 IND2-H1）**：v6 の A1e-M1 は「SECURITY DEFINER関数で実行する」と定めていたが、**PostgreSQL では SECURITY DEFINER 関数内の RLS 判定は `current_user`＝関数所有者で行われ、`FORCE ROW LEVEL SECURITY` は所有者のバイパスも止める**（A1-H2 がまさにその目的で導入した）。メンバーシップは①テナント固有＝**FORCE RLS ＋ フェイルクローズ**の対象なので、**ログイン時（`app.tenant_id` 未設定）に SECURITY DEFINER から読んでも0行**になる。**A1e-M1 は A1-H2 と当初から矛盾していた**（同じ論理は A1f-H1 で `priv` テーブルについて、データモデル設計書 §6 で `audit_log` の `audit_writer（BYPASSRLS）` について、既に正しく適用されていた——**規則を知っていたのに、メンバーシップに適用していなかった**＝教訓12）。
  - **【v13／v14改訂】採用する機構＝ブートストラップ例外を restrictive の述語に埋め込む**：**認証専用ロール `auth_role`** を設ける。**BYPASSRLS も SECURITY DEFINER によるRLS回避も用いない。**

    - **【v14】`TO` の使い分けを原則として定める（A1h-H1 の是正）**：v13 は「restrictive を `TO app_role` に限定する」としたが、**これは穴が開く方向に倒れる**——本ADRは既に **A1c-L2（共有マスタ書込の管理用別ロール）／A1-H2（マイグレーション用の別ロール）／`audit_writer`／`auth_role`** と**複数のロール**を持ち、**`TO` への追記を忘れたロールには restrictive が適用されない**（何もしなければ安全側、ではない）。**列挙漏れの倒れる方向が permissive と restrictive で逆**であることを原則にする：

      | ポリシー種別 | `TO` の扱い | 列挙漏れが起きたとき | 
      |---|---|---|
      | **restrictive**（絞る） | **`TO` 指定を付けない（全ロールに適用）** | ——（列挙しないので漏れが起きない） |
      | **permissive**（経路を開く） | **`TO` でロールを明示列挙** | **そのロールは何も見えない＝フェイルクローズ**（安全側） |

      **restrictive をロール限定にしてはならない。** 例外が必要なら**述語の中に書く**（下記2）。

    - **【v17】permissive の `TO` には「そのテーブルに正当にアクセスするすべてのロール」を列挙する（PG-H3・S1 再実行で実地確認）**：v14〜v16 は `TO app_role, auth_role` と書いていたが、**S1 を文書どおりに実行したところ、共有マスタ（③）の共有行を投入できなかった**——**テーブル所有者も FORCE RLS 下では permissive の対象外**であり、`TO` に無いロールは何もできない。**A1c-L2 が言う「管理用の別接続/別ロール」を `admin_role` として実体化**し、③の permissive の `TO` に列挙した。あわせて **③の restrictive の WITH CHECK に `admin_role` の共有行書込例外**（`OR (current_user = '<admin_role>' AND tenant_id IS NULL)`）を加える（一般ロールの共有汚染は引き続き拒否＝A1d-M1）。
  - **列挙漏れの倒れる方向は安全側**（そのロールが何もできない＝フェイルクローズ）だが、**「所有者・トリガ・バッチ経路は permissive の対象外」であることを設計として明示**しないと、実装時に「なぜか書けない」で FORCE RLS を外す方向へ倒れる。**`*_history` の版履歴トリガ・監査トリガ・一括投入の書込主体も、同じ枠で明示する**（未着手＝§5）。
- **【v14】① には「基本 permissive」が必須である（処置中に判明した PostgreSQL の性質）**：PostgreSQL では行が可視になるのは **「すべての restrictive を満たし、かつ**少なくとも1つの permissive を満たす**」**場合であり、**permissive が1本も無いテーブルは誰にも0行**になる（permissive の OR が空集合＝偽）。したがって **restrictive テナント分離だけを置いた①テーブルは、正しいテナント文脈でも何も見えない**。**①③には「経路を開く基本 permissive」を必ず置く**：`FOR ALL TO app_role, auth_role USING (true) WITH CHECK (true)`（**絞りは restrictive が行う**ので `true` でよい）。**検査に「permissive が1本も無い①③テーブルが存在しないこと」を含める**（§5）。
      > これは v13 までの記述（「①＝restrictive のみ」）では**全①テーブルが0行になる**という欠陥であり、**IND2-H3（restrictive/permissive の結合意味論）と同じ根**である。教訓14（列挙対象を機械的に洗い出す）を **restrictive/permissive の全組合せ**に当てて発見した。

    1. **restrictive テナント分離ポリシーは全ロールに適用する**（`TO` 指定なし）。述語は §2.9.5 の**正規化形**を用いる（**未設定・空は非通過／不正値は例外**）。
    2. **【v16】ブートストラップ例外のキーは `auth_role` ではなく専用の関数所有者ロール `bootstrap_owner` にする（IND3-H1／PG-H5 の是正）**：v14/v15 は述語を `current_user = '<auth_role>'` としていたが、**これは `auth_role` 自身が membership に `SELECT` を持つ場合しか真にならない**——ところが §2 3b／§5 検査／ADR-0002 A2i-M1 は「**`auth_role` はテーブル権限ゼロ・`EXECUTE` のみ**」を要求しており、**SECURITY DEFINER 経由では `current_user` が関数所有者になるため第2項が常に偽→0行→自己ブロック**になる（IND2-H1 の再演）。**どちらを採っても成立しない自己矛盾**だった。よって：

       | ロール | 属性 | 権限 |
       |---|---|---|
       | **`auth_role`** | LOGIN | **いかなるテーブルにも直接権限を持たない**。**ブートストラップ関数の `EXECUTE` のみ** |
       | **`bootstrap_owner`**（v16新設） | **NOLOGIN・非BYPASSRLS・非superuser** | **membership（および所属解決に必要な最小限の表）の `SELECT` のみ**。**ブートストラップ関数の所有者** |

       - membership の restrictive 述語（形(f)）：`tenant_id = AT OR (current_user = '<bootstrap_owner>' AND user_id = BCU)`
       - membership の permissive の `TO` に **`bootstrap_owner` を含める**（含めないと **permissive が無い＝0行**＝PG-H3 の型を踏む）。**`auth_role` は直接読まないので含めない。**
       - **`bootstrap_owner` をいかなるロールにも `GRANT` しない**（`SET ROLE` で例外を得られないようにする＝PG-L7）。**NOLOGIN** で直接ログインも不可。
       - **実測で検証済み**：`auth_role` が関数経由で**テナント跨ぎ2件を解決**でき、**`auth_role` の membership 直接参照は `permission denied`**、**主張（`app.bootstrap_claimed_user`）と引数が一致しない場合は0件**。
    3. **`auth_role` の GRANT は「ブートストラップ関数の `EXECUTE`」のみ**。**テーブル権限はゼロ**（§5 検査で担保）。所属解決に必要な読取は **`bootstrap_owner` 所有の SECURITY DEFINER 関数の中に閉じる**。
    4. **`auth_role` では `app.allowed_tenants`／`app.tenant_id` を設定しない／業務クエリを実行しない**。テナント確定後は**業務ロールの接続に切り替える**（接続・ロールの分離＝ADR-0002 A2h-M2）。
    5. **解決結果を認証完了前にクライアントへ返さない**（主張された `user_id` の所属関係が未認証の相手に漏れないようにする）。レート制限は ADR-0009、負荷の増幅は ADR-0002 §5。
    6. **【v14】変数名は役割が明白なものにする（A1h-L2）**：v13 の `app.auth_subject` は業務側の `app.user_id` と紛らわしいため **`app.bootstrap_claimed_user`**（＝**未認証で主張された**ユーザー）に改める。**`auth_role` の接続を握られた場合、1接続で本変数を順に変えて総当たりできる**（入口層のレート制限が効かない経路）ため、**ADR-0017 の脅威項目**として明記し、**解決の監査記録による事後検知**（下記 参照の監査）と接合する。
  - **【v14】この機構を守る検査（A1h-H1／M1。§5 に実装方法まで定める）**：**restrictive を全ロール適用に戻したため、「(テーブル, ロール) の全組合せ」を列挙する必要がなくなった**——検査は「**restrictive に `TO` 指定が付いていないこと**」を見るだけでよく、**テーブルもロールも列挙しない**（A1g-H1 の思想と一致）。詳細は §5。

- テナントの識別は、接続プールを維持するため**テナント別DBロールではなく、セッション変数方式**とする（上記のとおり `SET LOCAL` を用いる）。
- **横断アクセスは別ポリシーで宣言的に許可**する（相互作用に注意：A1-M2）：
  - **【v13】横断は permissive を足すだけでは成立しない——restrictive の述語を横断可能な形にする（ADR-0002 第9回 IND2-H3）**：PostgreSQL の RLS は **restrictive を AND、permissive を OR** で結合するため、**restrictive テナント分離が `tenant_id = current` である限り、permissive で横断経路を足しても他テナント行は可視にならない**（AND で切られる）。v6〜v12 は「横断は別ポリシーで宣言的に許可する」と書いていたが、**その許可は restrictive の内側でしか効かない**。データモデル設計書 §4 は④について同じ論理で除外規定を置いていたが、**横断経路には置いていなかった**（＝規則の適用漏れ・教訓12）。よって次のとおり改める：
    1. **restrictive テナント分離の述語を `tenant_id = ANY(current_setting('app.allowed_tenants'))` に統一する**（未設定/空は全拒否＝フェイルクローズ維持）。
       - **【v14】`allowed_tenants` の定義（A1h-M4）**：**「そのリクエストで許可されるテナント集合」であり、ユーザーの所属テナント集合ではない。** v13 の「通常ユーザーは自テナント1要素」は**リクエスト単位の話**である（ADR-0005 の多対多メンバーシップと矛盾しない）。
         - **通常ユーザー＝選択中の1テナント**（コンテキスト）。**グループ管理者＝配下組織集合**（注入時にDB側で検証＝A1b-M1）。
         - **複数テナントに所属する受託者は、テナントごとに別リクエスト（per-tenant コンテキスト）**になる。横断read のファンアウトは **ADR-0008 §2.6.2 の per-shard/per-tenant 権限注入**がこれを行う。
         - **「所属集合」と誤読してはならない**——誤読すると**受託者の restrictive の床が全所属テナントに広がり、要求#18 が「本人の稼働に限る」と定めた例外が業務データ全体への越境になる**。
         - **本人起点横断だけが例外**であり、`allowed_tenants` の外を読むために**restrictive の述語自体に例外を持つ**（下記2）。
    2. **本人起点横断は真の例外**（`allowed_tenants` に含まれないテナントの行を読む必要がある）。**対象テーブル（労務サマリ）に限り**、restrictive を **`tenant_id = ANY(app.allowed_tenants) OR user_id = current_setting('app.user_id')::uuid`** とする。**この形の restrictive を持つテーブルを明示的に列挙**し、他テーブルには絶対に付けない。
    3. **④ユーザー所有**は従来どおり restrictive テナント分離の**対象外**（`tenant_id` を持たないため）。
    4. **【v14】restrictive の述語形を次の5種に限定する（A1h-M2）**。**それ以外の形の restrictive が存在しないこと／①③テーブルに restrictive が無いものが存在しないこと**をカタログ走査で検査する（§5）：
       | # | 形 | 対象 |
       |---|---|---|
       | (a) | **標準** `tenant_id = ANY(app.allowed_tenants)` | ①テナント固有（下記の例外を除く） |
       | (b) | **本人起点例外** `(a) OR user_id = current_setting('app.user_id')::uuid` | **`labor_summary` のみ**（一覧化） |
       | (c) | **スコープ** `field_group_id IS NULL OR field_group_id = ANY(app.scope_field_groups)` | 圃場スコープ対象 |
       | (e) | **【v14新設】③共有＋上書き** `tenant_id IS NULL OR tenant_id = ANY(app.allowed_tenants)` | ③共有＋テナント上書き |
       | (f) | **【v14新設】ブートストラップ例外** `(a) OR (current_user = '<auth_role>' AND user_id = current_setting('app.bootstrap_claimed_user', true)::uuid)` | **membership のみ**（一覧化） |
       （(d) **④ユーザー所有は restrictive テナント分離の対象外**＝形を持たない）
       - **【v14】(e) を新設した理由（A1h-M2）**：v13 は述語形を3種に限定したが、**③共有＋上書きの形が列挙から漏れていた**。しかも③の述語は `tenant_id = current` のままで `allowed_tenants` に更新されておらず、**③テーブル（農薬肥料マスタ・作物マスタ・I18nLabel）でグループ管理者横断が動かなかった**。**`NULL = ANY(array)` は NULL（偽扱い）**なので、③を (a) に揃えると **A1b-M2「共有行が誰にも見えなくなる」破綻が再発する**——**`tenant_id IS NULL` を先に許容する独自の形が必要**である。
    5. **失ったもの（教訓5/9の適用）**：restrictive の床が `tenant_id = current`（絶対）から `allowed_tenants`（アプリが計算した集合）へ上がったため、**集合計算のバグの影響範囲が横断経路だけでなく全テーブルへ広がった**。**この床を守る唯一の機構が A1b-M1 の「注入時のDB側検証」になる**ため、その検証の厳密さが要求水準になる。あわせて**通常ユーザー（横断権限なし）では `allowed_tenants` が `{app.tenant_id}` の1要素であることを注入時に検証**する。
  - **グループ管理者**：同一システム（同一DB）内の配下組織を横断参照。行単位サブクエリの性能劣化を避けるため、**許可tenant_id集合をセッション変数（配列）に事前解決して注入**し、**restrictive の述語がその集合との包含判定で済む**（上記【v13】1／A1-M1）。
    - **防波堤性と性能の両立（A1b-M1／A1c-M1）**：注入集合を**アプリが計算する**と、その計算バグが誤った横断アクセスを生み、「RLS＝アプリバグへの最後の防波堤」性が横断経路で弱まる。これを緩和するため注入集合をDB側で検証するが、**検証を行単位（ポリシー内 EXISTS）で行うと、行単位サブクエリの性能問題（A1-M1で回避したもの）が復活する（循環）**。したがって検証は**「集合注入時に1回」**に限定する：リクエスト冒頭で `SET LOCAL` する前に、注入予定のtenant_id集合が当該user_idのグループ管理者メンバーシップに包含されることを**1クエリ（SECURITY DEFINER関数等）で検証**し、**検証済みの集合のみ**をセッション変数に注入する。**SECURITY DEFINER関数は`search_path`を固定し最小権限で定義する**（関数注入・権限昇格の攻撃面を避ける：A1d-L1）。**ポリシー本体は注入済み集合との包含判定のみ（サブクエリなし）**に保つ。これで防波堤性（注入は必ず検証済み）と性能（ポリシーはサブクエリなし）を両立する。
  - **本人起点横断**：**労務サマリ（LaborSummary）テーブルに限定**し「当該user_idの稼働」のみ許可（業務テーブルWorkLog等は越境露出させない。ADR-0005・要求仕様#18）。**【v13】これは permissive では実現できない**——`allowed_tenants` の外のテナントの行を読むため、**当該テーブルの restrictive 述語自体に `OR user_id = app.user_id` を含める**（上記【v13】2）。**この例外を持つテーブルを一覧化し、一覧外のテーブルが同形の restrictive を持たないことを検査する**（範囲が意図せず広がらないための担保。A1-M2）。
- **テーブルの分類（A1-M3）とポリシー**：業務テーブルを4種に分類し、それぞれ専用のRLSポリシーを当てる（加えて分類外の**特権経路専用テーブル**を下記に定義する）。
  - **① テナント固有**（tenant_id必須・RLS対象）：`USING (tenant_id = current)`（読取）＋`WITH CHECK (tenant_id = current)`（書込：詐称・越境移送を拒否）のフェイルクローズ・ポリシー。「全業務テーブルにtenant_id」はこの分類に適用。
  - **② システム共有**（tenant_idなし、全員読取のみ・例：国レベルの共有マスタ候補）：読取は全テナント可、書込は特権ロールのみ。**書込の運用（A1c-L2）**：アプリの通常接続は非所有者・非BYPASSRLSロール（A1-H2）で共有マスタを書けない。共有マスタの書込は**管理用の別接続/別ロール**（テナント通常接続とは別経路）で行い、通常のテナント操作からは書けないようにする。
  - **③ 共有＋テナント上書き可能**（tenant_id NULL=共有の既定行、非NULL=テナント上書き）：**フェイルクローズの単純ポリシー（`tenant_id = current`）ではNULL共有行が誰にも見えなくなり機能破綻するため（A1b-M2）、専用ポリシー `tenant_id IS NULL（共有）OR tenant_id = current（自テナント上書き）` を用いる**。
    - **責務分離（A1c-L1）**：RLSは**行の可視性のみ**を制御する（共有行と自テナント上書き行の両方が可視になる）。「同一キーで上書き行を優先して採用する」解決は**RLSではなくビュー/クエリ側のロジック**（自テナント行があればそれ、なければ共有行）で行う。
    - **一意制約（A1c-L1／A1d-L2）**：共有行（tenant_id NULL）と自テナント上書き行の重複を防ぐ制約設計を行う。**sentinel（`COALESCE(tenant_id, 既定値)`）方式は既定値が実tenant_idと衝突するリスクがあるため、部分一意インデックスを推奨**：共有行用 `UNIQUE(key) WHERE tenant_id IS NULL` ＋ テナント行用 `UNIQUE(key, tenant_id) WHERE tenant_id IS NOT NULL`。
    - **書込制御（WITH CHECK：A1d-M1）**：一般テナント接続には `WITH CHECK (tenant_id = current)` を課し、**tenant_id IS NULL（共有）行の書込を拒否**する（共有汚染の防止）。**共有行への書込は特権ロールのみ**（②と同じ別接続/別ロール運用：下記A1c-L2）。一般テナントは自テナント上書き行のみ作成・編集できる。
  - **④ ユーザー所有**（tenant非依存・`user_id`でアクセス制御。例：下書き/未確定データ＝ADR-0003層③）：**`USING/WITH CHECK (user_id = 現在のユーザー)`** のポリシーで本人のみ参照・書込可とする（tenant_idベースではない）。**確定時にtenant固有（①）または可逆確定（②相当）へ移送**し、tenant_idを付与する。下書きは本人以外・他テナントから見えない。（ADR-0003 A3b-M1で追加。v7）
- **【v11】この枠は現時点で対象0件＝条件付きの枠である（ADR-0002 v9 A2h-H1 の逆流）**：本枠は ADR-0002 v8 の波及として設けたが、**ADR-0002 v9 が方針を改め、`user→シャード集合` は各シャードの①メンバーシップから導出する（物理的な索引テーブルを持たない）ことを既定とした**（ADR-0002 §3.2(iv')）。**導出は A1e-M1（①のテーブルを特権経路で読む／テーブルの分類は①のまま）の既存の扱いで足るため、本枠に該当するテーブルは現時点で存在しない。**
  - したがって **本ADRは「RLSが最後の防波堤」という中核主張を、実際には例外なく保っている**（§4）。
  - 本枠は **ADR-0002 が導出のコストを実測し、性能上どうしてもマテリアライズドキャッシュ（物理索引）を後付けすると裁定した場合にのみ発効する**「**条件付きの枠**」として維持する。枠の設計（下記【v9】【v10】）はそのまま使える状態で保存しておく。
  - **新たにこの枠へテーブルを置こうとするときは、まず「①のまま特権経路で読めないか（A1e-M1 の軸1で足りないか）」を検討する**——ADR-0002 v6〜v9 の経緯は、**その検討を飛ばして枠を新設すると土台に不要な例外が残る**ことを示した実例である（開発工程 教訓7）。
- **【v8／v9改訂】分類外＝特権経路専用テーブル（ADR-0002 v8 A2g-M3 波及。v9で第6回レビューを反映。**v11で条件付きの枠に格下げ**）**：上記4分類は**業務テーブル**の分類であり、**通常ロールに一切見せてはならない基盤テーブルは4分類のいずれにも属さない**。代表例は **ADR-0002 の法域ローカル `user→shard` ルーティング索引**——`tenant_id` を持たないので①③ではなく、②システム共有にすると**全ユーザーの所属関係が全テナントから読める**（機密性の破綻）、④ユーザー所有では**入口層が"他人の `user_id`"で引く用途**（そのユーザーのシャードを解決する）に機能しない。よって次の枠を定義する：

  - **【v9】定義は「通常ロールに `GRANT` しないテーブル」（A1f-M2）**：v8 は「A1e-M1 と同じ扱い」と書いたが、**A1e-M1 は"アクセス経路"の決定であって"テーブル分類"ではない**（メンバーシップテーブルは①テナント固有のまま、特権経路からも通常経路からも読まれる）。この2つを混同すると一覧化の基準が判定不能になるため、**軸を分離**する：
    - **軸1＝アクセス経路（A1e-M1）**：SECURITY DEFINER関数／認証専用ロールから読む、という経路の話。**①のテーブルもこれに該当し得る**（メンバーシップ）。**該当してもテーブルの分類は①のまま**であり、本枠には含めない。
    - **軸2＝テーブル分類（本枠）**：**通常ロールに `GRANT` しない**＝通常経路からは存在しないに等しいテーブル。判定基準は経路ではなく**権限**で定める。
  - **【v9】守り方は `GRANT/REVOKE`。RLSでは守らない（A1f-H1。v8の記述を撤回）**：v8 は「デフォルト拒否のポリシーを置く」「FORCE RLS の対象外にする例外ではない」と書いたが、**これを実装すると認証が自己ブロックする**——`ENABLE RLS` でマッチするポリシーが無ければ0行、そして `FORCE RLS` は**テーブル所有者のバイパスも止める**（A1-H2 の目的）。SECURITY DEFINER 関数は**関数所有者の権限で実行される**ため、**特権経路自身が0行しか得られずログイン不能**になる（A1e-M1 が「これがないと自己ブロックされる」と警告したまさにその失敗）。**RLSは行の可視性の仕組み**であり、「**テーブル全体を特権ロール以外に見せない**」のは**テーブル単位の権限**の問題である。**RLS／FORCE RLS は設定しない**（設定しても得るものがなく、自己ブロックの罠だけが残る）。

  - **【v10】専用スキーマ＋網羅検査で守る（A1g-H1。v9の「個別テーブルのGRANT管理」を強化）**：v9 は `REVOKE`/`GRANT` を個別テーブルに当てる形だったが、**RLSが暗黙に持っていた「テーブルを列挙せずに網羅検査できる」性質（`pg_class.relrowsecurity` の走査）を失っていた**。GRANTの世界で同等の網羅性を再構成する（裁定の記録は §3.1）：
    1. **特権経路専用テーブルは専用スキーマ `priv` に置く**。**通常ロールに `priv` の `USAGE` を与えない**——スキーマ `USAGE` が無ければ、**個別テーブルに誤って `GRANT` が付いていてもアクセスできない**（個別GRANT漏れに耐える二重の防御）。
    2. **マイグレーション規約**：`priv` スキーマには **`ALTER DEFAULT PRIVILEGES` を設定しない**、かつ **`GRANT ... ON ALL TABLES IN SCHEMA` の対象から `priv` を除外**する。これがないと、**運用の一括付与が「GRANTしない」という既定を静かに上書きする**（RLSは付け忘れれば拒否側に倒れるが、GRANTは一括付与で許可側に倒れる——安全性の向きが逆であることに注意）。
    3. **網羅検査を自動テスト化（列挙しない）**：`information_schema.role_table_grants` と `has_schema_privilege` を走査し、**「通常ロールが `priv` の `USAGE` を持たないこと」「`priv` のオブジェクトに通常ロールの権限が1件も無いこと」**を検査する。**テーブル名を列挙しないため、新規テーブルが増えても自動的に検査対象になる**（＝`relrowsecurity` 走査と同等の強度）。
    3b. **【v11／v12改訂】認証専用ロールは「テーブル権限ゼロ＋`EXECUTE` のみ」——これを検査する（ADR-0002 v9 A2h-M2／v10 A2i-M1 の逆流）**：認証専用ロールは A1e-M1 により**RLSの外**で所属解決を行い、かつ**法域内の全シャードDBへ接続できる**——**RLSが最終防波堤として効かない唯一の主体**である。v11 は「業務テーブルに権限を持たないこと（メンバーシップ等の最小限の読取のみ）」と書いたが、**メンバーシップは①テナント固有＝業務テーブル**なので自己矛盾しており、**検査を実装できなかった**。かつ A1e-M1 は SECURITY DEFINER でRLSを回避する方式であり、テーブル権限を直接与えるのは方式違い（フェイルクローズで0行になる）。よって：
      - **認証専用ロールは、いかなるテーブルにも直接権限を持たない**。所属解決は **SECURITY DEFINER 関数の `EXECUTE` 権限のみ**で行う（関数の所有者権限で①メンバーシップを読み、RLSを回避する＝A1e-M1 の方式そのまま）。
      - **検査は例外なしで書ける**：①**認証専用ロールがいかなるテーブルにも直接権限を持たないこと**（カタログ走査で網羅可能）、②**与えられた `EXECUTE` が一覧化された SECURITY DEFINER 関数に限ること**（A1g-L2 の `prosecdef` 走査と接合）。
      - **「接続できること」と「業務データを読めること」の分離は関数の返り値で制御**する（関数は `user_id → シャード集合` のみを返し、業務データを返さない）。
      - **認証接続と業務接続はロール・接続プールの両面で分け、認証接続から `SET LOCAL app.tenant_id` 後の業務クエリを実行できないようにする**。**「認証層＝RLSの外側の侵害」は ADR-0017 の独立した脅威項目**として扱う。
    4. **逆向きの検査も置く**：**`priv` 以外のスキーマに、通常ロールから読めない業務テーブルが存在しないこと**（分類を誤って業務テーブルを `priv` に置き、業務が動かなくなる事故の検出。A1f-M2 の一覧化基準と対応）。
    5. **強制力はスキーマとテストに持たせる**：§5 の「一覧化」は文書化のために残すが、**人手の台帳に依存しない**（一覧から漏れても 1〜4 で守られる）。
    6. **全シャードに一律適用（A1g-L1）**：ADR-0002 v8 により索引は**法域内の全シャードに複製**されるため、**同名テーブルが各シャードDBに存在する**。上記の権限設定・網羅検査・ダンプマスキングは**全シャードに対して一律に適用**し、**シャード追加時の手順に権限設定と検査を含める**（1シャードのGRANT誤りで法域内全ユーザーの関係グラフが漏れる＝ADR-0002 A2g-M1 の「侵害面 N 倍」の実務上の姿）。ADR-0019 の配備手順へ申し送る。
  - **【v9／v10改訂】書込は「メンバーシップから収束させる」SECURITY DEFINER 関数（A1f-L3／A1g-M1）**：ADR-0002 v8 は索引の書込を「**メンバーシップ付与と同一トランザクション**（加入先シャードのローカルTX）」と決めたため、**通常ロールから `EXECUTE` できる、所有者権限で動く関数**が必要になる——これは権限昇格の踏み台になり得るので、**引数を信用しない設計にする**。
    - v9 は「自シャードの行しか書けないことを検証」としたが、**それは接続先DBから自明であり、本質的な検証条件ではない**。かつ**引数に任意の `user_id` を渡して他人の索引行を削除できると、ADR-0002 の上位集合保証（漏れは許さない）を外部から破れる**（＝他人のデータを横断readから静かに欠落させる攻撃。**RLSは漏洩を防ぐが欠落は防げない**）。
    - よって関数は **`refresh_user_shard_index(user_id)`** の形とし、**「どう書くか」を引数で受け取らない**。関数は**同一DBのメンバーシップテーブルを見て、当該 `user_id` の索引行を「あるべき状態」へ収束させる**（メンバーシップがあれば行を保証、無ければ削除）。**冪等・宣言的**であり、他人の `user_id` を渡してもメンバーシップに従って収束するだけなので**状態を誤らせられない**。
    - 関数は `search_path` 固定・最小権限（A1d-L1 と同じ規律）。**`EXECUTE` を通常ロールに与えてよいのは、上記の導出設計によって安全が担保されているから**であると明記する。
    - **索引の変更は「書込」なのでトリガで捕捉できる**（SELECTと異なる）。**追加/削除はハッシュチェーン監査の対象に含める**（ADR-0004）。
  - **【v9／v10改訂】参照の監査＝未認証は監査本体に書かない（A1f-M3／A1g-M3）**：**行レベルトリガは `INSERT/UPDATE/DELETE` にしか設定できず、`SELECT` を捕捉できない**（本プロジェクトの監査はトリガ＋ハッシュチェーン＝ADR-0004）。したがって参照監査は**SECURITY DEFINER 関数内で明示的に監査行を追記する**方式とする（または `pgaudit`。選択は ADR-0017）。ただし**認証前の参照をそのまま監査本体へ書くと、攻撃者が任意の `user_id` を主張してログインを試みるだけで監査を膨らませられる**（＝改ざん耐性のある領域に、信頼できない入力を無制限に書き込ませる）。よって記録先を分ける：
    - **認証に成功した解決のみ**を**監査本体（ハッシュチェーン）**へ記録する（改ざん耐性が必要なのは「実際に誰が誰の所属を解決したか」）。
    - **未認証の試行は別系統の運用ログ**（改ざん耐性不要・短期保持・**レート制限後**・存在しない `user_id` の主張は**個別行ではなく集約カウント**）に記録する（ADR-0020 可観測性・ADR-0009 レート制限）。
    - **量の見積り基準は「ログイン数」ではなく「ログイン試行数（＝攻撃者が制御できる量）」**である。ADR-0004 のハッシュチェーンは**並行挿入の直列化がS5で未検証**であり、そこへ未認証の大量書込を流すと**正規のログインまで遅くなる**。
  - **【v9】バックアップ・レプリカ・環境コピー（A1f-L1）**：本枠のテーブルは各DB内にあるため**バックアップ・リードレプリカ・開発/検証環境へのダンプにも当然含まれる**。本番の権限で遮断しても、**ダンプを開発環境へ復元した時点で誰でも読める**——ADR-0002 が「侵害時は全件が一度に漏れる機密資産」と警告した内容の実務上の主経路である。**開発/検証環境へのコピー時はマスキングまたは除外の対象**とし、ADR-0017（データ保護）／ADR-0019（環境運用）へ申し送る。
  - **【v9】テストの期待値は「権限エラー」（A1f-H1）**：テスト（§5）には「特権経路専用テーブルが通常ロールから読めないこと」を含めるが、**期待するのは0行ではなく `permission denied`** である（0行を期待するテストは、誤って `GRANT` を与えたときに合格してしまう）。あわせて**特権経路からは正しく読めること**も検査し、自己ブロックの再発を検出する。
  - 該当テーブルは一覧化して文書化する（§5）。ただし**強制力は上記【v10】のスキーマ分離と網羅検査に持たせる**。
- **性能**：`tenant_id` を**複合インデックスの先頭**に置く。横断ダッシュボード等の重い集計は、RLSを通した実行時集計ではなく**集計テーブル／マテリアライズドビュー**を別途用意する。
- **主キー・識別子（A1e-L2）**：PK・外部公開IDは**UUID等の非連番**を用いる（連番PKは行数・クロステナントの規模を漏らし、URL露出時の列挙も容易なため。監査ログ等の追記型を含む）。
- **外部キー（A1e-L1）**：PostgreSQLのFK制約チェックはRLSをバイパスして評価されるため、**FKは原則同一テナント内に閉じる**設計とする。テナント跨ぎFK（共有マスタ参照等）は、FK違反エラー/タイミングによる他テナント行の存在推測（情報漏れ）を踏まえたエラーハンドリングを設計フェーズで検討する。
- **オフライン同期API**：同期対象の絞り込みにも必ず `tenant_id`（＋権限）を通す。**端末（オフライン）側にはRLSがない**ため、複数テナントに所属するユーザーの端末データ分離・暗号化は [ADR-0007（オフライン同期）] と連携して設計する（A1-L2）。

### 2.9 【v15】権限は注入変数（capability）で表現し、絞りはすべて restrictive で強制する（IND3-H2 の裁定＝(a)）

**問題**：v14 までの設計では、**要求 3.2 のロール別権限と #21 の個人データ最小権限が RLS へ写像されていなかった**。業務ロールはDB上1つ（`app_role`）なので `TO` では差別化できず、注入変数（`allowed_tenants`／`user_id`／`scope_field_groups`）にも**権限を表す項が無い**。さらに **v14 で必須化した基本 permissive `USING (true)` が、permissive で表現するとされた最小権限（`created_by = current` 等）を OR で吸収して無効化していた**。結果、**「RLSが最後の防波堤」はテナント次元では真だがロール次元では偽**だった。

**裁定：(a) 注入変数に権限（capability）を追加し、restrictive で強制する。**

#### 2.9.1 原則：permissive は経路を開くだけ・絞りはすべて restrictive

| ポリシー種別 | 役割 | 述語 | `TO` |
|---|---|---|---|
| **permissive** | **経路を開くだけ** | **`USING (true)` / `WITH CHECK (true)` 固定** | **`TO` でロールを明示列挙**（漏れれば見えない＝安全側） |
| **restrictive** | **絞りはすべてここ** | 下記の述語形のいずれか | **`TO` を付けない（全ロール）** |

- **permissive に条件を書いてはならない**。書いても **OR で他の permissive に吸収されるか、他の permissive を無効化する**だけで、絞りとしては機能しない（IND3-H2 の根）。
- **検査**：**`permissive` の述語が `true` 以外のものが存在しないこと**（絞りが permissive に紛れ込んでいないことの検出）。

#### 2.9.2 注入変数（すべてサーバ側で導出し、注入時にDB側で検証する＝A1b-M1 と同方式）

| 変数 | 型 | 意味 | 注入時のDB側検証 |
|---|---|---|---|
| `app.allowed_tenants` | `uuid[]` | **そのリクエストで許可されるテナント集合**（所属集合ではない＝A1h-M4） | メンバーシップに包含されること／横断権限が無ければ1要素であること |
| `app.user_id` | `uuid` | **リクエスト主体**（不変。対象者を入れる用途に流用しない＝IND3-H4） | 認証済みの主体と一致 |
| `app.scope_field_groups` | `uuid[]` | 担当圃場グループ | メンバーシップのスコープに包含 |
| **`app.caps`**（v15新設） | `text[]` | **そのリクエストで許可される権限（capability）集合** | **そのユーザーのロール・メンバーシップから導出できる capability の部分集合であること** |
| **`app.employer_subject_users`**（v15新設） | `uuid[]` | **雇用主横断の対象従業員集合**（IND3-H4） | **双方向確認済みの雇用関係**にある従業員であること |
| `app.bootstrap_claimed_user` | `uuid` | 未認証で主張されたユーザー（`auth_role` のみ） | — |

**capability の一覧（要求 3.2／#21 からの写像。増やすときは本表と述語形の両方を更新する）**：
`view_others_tracks`（他者の位置ログ軌跡）／`view_others_punch`（他者の打刻・作業実績）／`scope_all`（テナント内全域＝スコープ制限なし・IND3-M7）。

#### 2.9.3 【v15】この裁定で RLS が守る範囲と、守らない範囲（正直な限定）

**(a) を採ってもなお、RLS が強制できるのは「行の可視性・書込可否」だけ**である。**操作の可否は RLS の対象外**。

| 次元 | RLS が強制する | 根拠 |
|---|---|---|
| テナント境界 | ✅ | restrictive (a)(e) |
| スコープ（担当圃場グループ） | ✅ | restrictive (c)＋`scope_all` |
| 本人性・個人データの可視性 | ✅ **（v15で追加）** | restrictive (d)＋`app.caps` |
| 雇用主横断の対象範囲 | ✅ **（v15で追加）** | restrictive (b)＋`app.employer_subject_users` |
| **操作の可否**（権限管理・承認・設定変更など、行の可視性で表せないもの） | ❌ **アプリ層が唯一の防御** | RLS は行フィルタであり操作の認可機構ではない |

**この限定を §4 帰結にも明記する**（「RLSが最後の防波堤」を無条件に主張しない）。**操作の可否についてはアプリ層の認可が唯一の防御である**ため、ADR-0017 の脅威モデルで別途扱う。

#### 2.9.4 【v15】述語形は「USING と WITH CHECK の対」で定義する（IND3-H3／PG-M3）

**PostgreSQL は `WITH CHECK` を省略すると `USING` 式を書込検査に流用する**。v14 までは述語形を USING だけで定義し、検査も USING しか見ていなかったため、**`labor_summary`（「WITH CHECK なし」と明記）で他テナント名義の①-a追記が可能**だった（権威確定が拾う＝給与の過大請求経路）。**すべての restrictive は USING と WITH CHECK の両方を明示する。**

| # | 対象 | USING（読取） | WITH CHECK（書込） |
|---|---|---|---|
| (a) | ①一般 | `tenant_id = ANY(AT)` | `tenant_id = TID` |
| (b) | **`labor_summary` のみ** | `tenant_id = ANY(AT) OR user_id = UID OR user_id = ANY(ESU)` | **`tenant_id = TID`**（追記は自テナントのみ。**読取の集合を書込に流用しない**） |
| (c) | 圃場スコープ対象 | `field_group_id IS NULL OR field_group_id = ANY(SFG) OR CAP('scope_all')` | 同左 |
| (d) | **個人データ**（位置ログ軌跡・打刻）**v15新設** | `user_id = UID OR CAP('view_others_tracks')`（打刻は `view_others_punch`） | `user_id = UID`（**本人のみ追記**） |
| (e) | ③共有＋上書き | `tenant_id IS NULL OR tenant_id = ANY(AT)` | **`tenant_id = TID`**（**`tenant_id IS NULL` の書込を拒否＝共有汚染の防止**。`USING` を流用してはならない） |
| (f) | `membership` のみ | `tenant_id = ANY(AT) OR (current_user = '<bootstrap_owner>' AND user_id = BCU)`（**v16：キーは `auth_role` ではなく関数所有者ロール**） | `tenant_id = TID`（ブートストラップ経路は `FOR SELECT` のみ） |
| — | ④ユーザー所有 | restrictive テナント分離の**対象外**。独立ポリシー `user_id = UID` | 同左（確定時に①へ移送） |

#### 2.9.5 【v15】セッション変数の参照は必ず正規化する（PG-H1・実測で確認）

**`SET LOCAL` を一度使った接続では、以後「未設定」が NULL ではなく `''` になる**（カスタムGUCの reset 値）。素の `current_setting('x', true)::uuid[]` は **`''` でプラン時例外**になるため、**「未設定は全拒否」は成立しない**。**すべての参照を次の形に正規化する**（実測で検証済み）：

- 配列：`AT` ＝ `ANY(COALESCE(NULLIF(current_setting('app.allowed_tenants', true), ''), '{}')::uuid[])`（`SFG`／`ESU`／`CAP()` の `app.caps` も同形）
- スカラー：`UID` ＝ `NULLIF(current_setting('app.user_id', true), '')::uuid`（`TID`／`BCU` も同形）
- `CAP(x)` ＝ `x = ANY(COALESCE(NULLIF(current_setting('app.caps', true), ''), '{}')::text[])`

**正規化しても「不正値」は例外のまま**である（実測：`'garbage'::uuid` はエラー）。したがって：
- **正しい記述は「未設定・空は非通過（0行）／不正値は例外（22P02）」**であり、「不正は偽」ではない。
- **不正値は注入時にDB側で検証して弾く**（ポリシー述語は正規化済みを前提とする）。
- **この例外を握り潰して空配列にフォールバックする実装を禁じる**（フェイルクローズがフェイルオープンに反転するため）。**規約としてCIで検出する。**
- **関数にラップしない**（`pg_policies.qual` から `current_setting` が消えて検査4/5が偽陰性になる＝PG-M4）。正規化はインラインで書く。

### 2.10 【v16】RLS が「自動で効かない」3つの境界（PG-H6／PG-H4 の是正）

**PostgreSQL 実挙動の検証**（[PostgreSQL実挙動検証記録](../PostgreSQL実挙動検証記録.md)）で、**単一機能の記述は20項目すべて正確だった一方、誤りはすべて「包含関係を跨いだときに規則が自動で効く」と仮定した場所に集中**していた。**RLS が自動では効かない境界**を明示し、それぞれに構造的な対策と検査を置く。

#### 2.10.1 パーティション親 → 子（PG-H6・実測で確認）

**`ENABLE`／`FORCE ROW LEVEL SECURITY` とポリシーは、パーティション子に伝播しない。** 親経由の参照では親のポリシーが全パーティション行に適用されるが、**子を名指しした参照では子自身のポリシー（＝無い）が使われ、RLS は完全に無効**になる。

> **実測**：子は `relrowsecurity=f, relforcerowsecurity=f`・ポリシー0本。**親経由＝50件（自テナントのみ）／子を直接参照＝100件（全テナント）**。
> **データモデル設計書 §5 の「全パーティション/サブパーティションに FORCE RLS が伝播することを S1 で確認」は事実に反する**（ADR-0004「子への非伝播に注意」が正しかった）。**S1 は親経由しか試験していない。**

**対策（構造で塞ぐ）**：
1. **パーティション子は専用スキーマ `part` に作成し、通常ロールに `USAGE` を与えない**。**親は `public` に置き、アクセスは親経由のみ**とする。**実測で確認**：親経由は通り（50件）、**子直接は `permission denied for schema part`**。
2. **スキーマ `USAGE` が無ければ、個別テーブルに誤って `GRANT` が付いていてもアクセスできない**——`GRANT … ON ALL TABLES IN SCHEMA` や `ALTER DEFAULT PRIVILEGES` の事故に耐える（`priv` スキーマと同じ二重防御の型）。
3. **パーティション自動作成ジョブ**は `part` スキーマに作成し、**子に `GRANT` しない**。`ALTER DEFAULT PRIVILEGES` を `part` に設定しない。
4. **検査**：**`part` スキーマに通常ロールの `USAGE`／権限が1件も無いこと**／**`relispartition = true` のテーブルが `part` 以外のスキーマに存在しないこと**（＝子の置き場所の逸脱検出）。**列挙しないカタログ走査で判定できる。**
5. **振る舞いテスト**：**子テーブルの直接参照が拒否されること**を合格項目に加える（S1 の再実行項目）。

#### 2.10.2 テーブル → ビュー（PG-H4／IND3-M6・実測で確認）

**通常のビューは、基底表の RLS を「ビュー所有者」の文脈で評価する。** ビュー所有者には `TO` で列挙した permissive が適用されないため、**FORCE RLS 下では誰が読んでも0行**になる。**しかもビューは `pg_policies` にも `relrowsecurity` にも現れないため、§5 の検査のどれにも引っかからない**。

**対策**：
1. **RLS 有効な表を参照する業務ビューは `WITH (security_invoker = true)` で作成する**（呼び出し元の文脈で RLS を評価する）。**これは PostgreSQL 15 以降の機能であり、本設計の最低要求バージョンを実質 PG15 に固定する**（ADR-0004 に明記）。
2. **ビュー本文の絞り込み条件は、ポリシーと同じ変数を使う**——`app.tenant_id`（単一）ではなく **`app.allowed_tenants`（集合）**。単一だと**グループ管理者の横断がビュー経由で通らない**（形(e) で直した意図が潰れる）。**`current_setting` は §2.9.5 の正規化形**を用いる。
3. **検査**：**RLS 有効な表に依存するビューが `security_invoker` であること**（`pg_class.reloptions` ＋ `pg_depend`）。**v15 までの検査はビューを一切見ていなかった。**
4. **振る舞いテスト**：**主要ビュー経由で正しい行が見えること**（現行の項目は素のテーブルしか見ていない）。

#### 2.10.3 セッション → トランザクション（PG-H1・§2.9.5 で処置済み）

**`SET LOCAL` を一度使った接続では「未設定」が NULL ではなく `''` になる**（カスタムGUC の reset 値）。§2.9.5 の正規化形で処置済み。**テストは「`SET LOCAL` を使った接続の2回目のトランザクション」で行う**（1回目だけでは NULL 経路しか通らない）。

> **【v16】この3境界は「規則が自動で効く」と仮定した典型である。** 新しい機構を導入するときは、**それが包含の外側（子・ビュー・プール返却後・実行プラン・カタログ表現・ロール継承）でも成立するかを機械的に確認する**（開発工程 教訓15）。

## 3. 検討した選択肢（Options）

前提：本システムは**1配備＝1DB＝1国**（ADR-0002）で、1DB内のテナント数は数個〜数百のオーダー（数万テナントのSaaSではない）。

> **前提の境界（A1-L1）**：要求仕様#13でOSS運用者は第三者へのサービス提供（SaaS）も許容される。SaaS運用者が1DBに**数千テナント**を収容する運用では、この「数百」前提が崩れ、DB分離却下の根拠も弱まる。その場合は**ハイブリッド（D案）＝大口テナントのみDB/スキーマ分離、またはテナント群のシャーディング**で対応する（本ADRの決定は、規模が本前提を超えたら D案へ拡張できる余地を残す）。

| 方式 | 概要 | 長所 | 短所 | 本件評価 |
|---|---|---|---|---|
| **A. DB分離** | テナントごとに物理DB | 分離が最強・障害影響も個別・個別バックアップ | **グループ管理者の横断集計がDBをまたぎ困難**／運用コスト×テナント数／マイグレーションが全DB分 | ✕ 横断要件と衝突、テナント数分の運用が重い |
| **B. スキーマ分離** | 同一DB内にテナント毎スキーマ | 分離は明確・単一DB運用 | 横断クエリが煩雑／スキーマ数増で接続プール・マイグレーションが劣化／PostGIS等も個別 | △ 中途半端になりやすい |
| **C. 行レベル分離＋RLS（採用）** | 共有スキーマ＋tenant_id＋RLS | **横断集計が容易**（ポリシーで宣言的に許可）／マイグレーション1回／規模に十分／要求仕様のデータモデル（全レコードにtenant_id）と一致／**アプリのバグに対しDB層が防波堤** | 物理分離ほどの隔離ではない／全テーブルへのtenant_id列とインデックス設計が必須／ポリシー設計を誤ると穴 | ◎ 横断要件・規模・データモデルに最適 |
| D. ハイブリッド | 基本は行レベル、大口のみDB/スキーマ分離 | 柔軟 | 最初から二重の運用系統を持つ | ○ 将来の外販SaaS化まで不要 |

**却下理由**：Aは「グループ管理者の横断」という中核要件と正面衝突し、1DB内のテナント数が限定的な本件では運用コストに見合わない。Bは横断が煩雑で、スキーマ数増による運用劣化が読みにくい。Cは横断要件・規模・既存データモデル（全レコードがtenant_idを持つ）と最も整合し、DB層での防波堤も得られる。

### 3.1 【v10】特権経路専用テーブルの守り方の裁定（A1f-H1／A1g-H1）

認証・所属解決が使うテーブル（現時点＝ADR-0002 の `user→shard` 索引）は、**テナント文脈が確定する前に参照する必要がある**ため RLS のフェイルクローズと両立しない。その守り方を3案から裁定した経緯を記録する（v8→v9→v10 で2度改めているため）。

| 方式 | 自己ブロックしないか | 網羅検査（列挙せず検出できるか） | 一括付与への耐性 | 評価 |
|---|---|---|---|---|
| (i) RLS＋デフォルト拒否ポリシー＋FORCE RLS（**v8案・撤回**） | ✕ **SECURITY DEFINER 関数（＝特権経路そのもの）も0行になり認証が自己ブロック**（A1e-M1 が警告した失敗） | ◎ `relrowsecurity` 走査で可能 | ◎ RLSは付け忘れれば拒否側に倒れる | ✕ **実装すると認証が壊れる**（A1f-H1） |
| (ii) 個別テーブルへの `REVOKE`/`GRANT`（**v9案・強化して継続**） | ◎ 問題なし | ✕ **一覧に載ったテーブルの個別テストのみ**——新規テーブルが漏れる | ✕ **`ALTER DEFAULT PRIVILEGES`／`GRANT ON ALL TABLES` が既定を静かに上書き** | △ 方向は正しいが、**RLSが持っていた網羅性を失う**（A1g-H1） |
| **(iii) 専用スキーマ `priv`＋通常ロールへの `USAGE` 不付与＋網羅検査（採用）** | ◎ 問題なし | ◎ **`role_table_grants`／`has_schema_privilege` の走査で、テーブルを列挙せず検査できる** | ◎ **`priv` を `ALTER DEFAULT PRIVILEGES`／一括GRANTの対象から除外**＋スキーマ `USAGE` が無ければ個別GRANT漏れにも耐える | ◎ **(ii)の正しさに(i)の網羅性を取り戻した形** |

**却下理由**：(i) は目的（テーブル全体の遮断）に対して道具（行可視性の制御）が誤っており、実装すると認証が自己ブロックする。(ii) は道具は正しいが、**RLSが暗黙に提供していた「列挙せず網羅検査できる」という性質**が要件だったことを見落としていた——**この枠には §4 のとおりRLSの防波堤が無く、検出こそが唯一の防御**であるため、網羅性の欠落は致命的。(iii) は遮断をスキーマという**物理的な区画**に持たせ、検査を**カタログ走査**にすることで、人手の一覧に強制力を依存させない。

> **教訓（本ADR固有）**：**道具を替えるときは、元の道具が暗黙に提供していた性質を棚卸しする**。v8→v9 は「自己ブロックを解消する」目的は達したが、失ったもの（網羅検査）を評価していなかった（開発工程 教訓5）。

### 3.2 【v13】テナント文脈確定前に①メンバーシップを読む機構の裁定（IND2-H1）

A1e-M1 は v6 で「SECURITY DEFINER 関数で実行する」と定めたが、**A1-H2（全業務テーブルに FORCE RLS）の下では0行になる**ことが独立レビューで判明した。**FORCE RLS を維持したまま認証前に①を読む方法**を裁定する。

| 方式 | RLSを迂回する主体が増えるか | 侵害時の影響範囲 | フェイルクローズの維持 | 検査可能性 | 評価 |
|---|---|---|---|---|---|
| (γ) メンバーシップを FORCE RLS 対象外にする | ✕ 所有者がRLSをバイパス可能に戻る | 当該テーブル全件（全テナント） | ✕ 所有者経路で崩れる | ○ | ✕ **A1-H2 と正面衝突。却下** |
| (α) 所属解決関数の所有者を `BYPASSRLS` ロールにする | ✕ **増える**（`rolbypassrls` 主体が1つ増える） | `GRANT` された表に限る（BYPASSRLSは表権限を与えない）ので**メンバーシップ全件** | ○ 関数外は影響なし | △ **`rolbypassrls` の棚卸しが必須**（増殖しやすい） | △ 実装は最短。データモデル設計書 §6 の `audit_writer` と同型で前例もあるが、**RLSを迂回する主体を増やす** |
| **(β) ロール限定ポリシーによるブートストラップ経路（採用）** | ◎ **増えない**（`auth_role` は非BYPASSRLS・非所有者） | **主張された1ユーザー分のメンバーシップ行のみ**（`app.auth_subject` で絞る） | ◎ 未設定なら NULL 比較で偽＝全拒否 | ◎ **(テーブル,ロール) の全組合せをカタログ走査で検査できる** | ◎ **採用**。最小権限が最も強く、RLSの枠内に留まる |

**却下理由**：(γ) は A1-H2 の目的（所有者バイパスの封じ込め）を破壊する。(α) は動くが **`rolbypassrls` 主体を1つ増やす**——`audit_writer` に続き2つ目になり、「RLSを迂回できる主体」の管理が本設計の弱点（A1f-M1 が認めた「防波堤の外」）に近づく。しかも影響範囲が**メンバーシップ全件**であり、(β) の「1ユーザー分」に対して桁が違う。**(β) は RLS の枠内に留まったまま目的を達する**ので、これを採る。

**【v14】(β) の実装形を改めた（A1h-H1）**：v13 は (β) を「**restrictive をロール限定（`TO app_role`）にする**」形で実装したが、**それは「restrictive が適用されないロールが存在する」状態を作り、ロールが増えるたびに `TO` の追記漏れ＝穴になる**（本ADRは既に A1c-L2 の管理用ロール・A1-H2 のマイグレーションロール・`audit_writer`・`auth_role` を持つ）。**しかも同じ版の A1g-H1 で「強制力を人手の一覧からスキーマとテストへ移す」と述べた思想に反していた**（教訓13）。v14 では：

- **restrictive は全ロールに適用（`TO` 指定なし）**、**例外は述語の中に書く**（`current_user = '<auth_role>' AND user_id = app.bootstrap_claimed_user`）。**新しいロールを追加しても restrictive は効き続ける**（穴が開かない）。
- **`TO` の使い分けを原則化**：**restrictive は `TO` なし（列挙しないので漏れない）／permissive は `TO` で列挙（漏れれば見えない＝フェイルクローズ）**。**列挙漏れの倒れる方向が逆**であることが根拠。
- **検査が単純化した**：「**restrictive に `TO` 指定が付いていないこと**」を見るだけでよく、**(テーブル, ロール) の全組合せを列挙する必要がなくなった**（§5 一段目 2）。
- したがって **v13 の「検査が無いなら (β) を採ってはならない」という条件は緩和された**——検査は依然必要だが、**検査の失敗が即座に穴になる構造ではなくなった**。**下表の (β) の「検査可能性◎」は v13 時点では過大評価だった**（教訓8）ので、v14 の形を前提とした評価に読み替える。

> **教訓（本ADR固有）**：**既存の決定を参照するときは、その決定が前提としている他の決定との整合を実際に確認する**。A1e-M1（v6）は A1-H2（v2で導入）と矛盾していたが、**両者は同じADRの同じ節にあった**。「同じ文書の中だから整合しているはず」という思い込みが6版にわたって残った（開発工程 教訓4/12）。

## 4. 帰結（Consequences）

**良い影響**
- グループ管理者の横断・本人起点横断を、**RLSポリシーで宣言的**に表現できる。
- マイグレーションが1系統で済み、運用がシンプル。
- アプリ層のWHERE句漏れに対して**DB層（RLS）が最後の防波堤**になり、監査要件（5.4）と相性が良い。
- 要求仕様6章のデータモデル（全レコードにtenant_id）をそのまま実装でき、仕様変更が不要。

**注意すべき影響・制約（以降の設計に生じる制約）**
- **全業務テーブルに `tenant_id` を必須化**し、複合インデックス先頭に置く設計規約を全体に適用する。
- **RLSポリシー設計が権限の正しさを左右する**ため、ポリシーはテスト（他テナント参照の遮断・横断許可の範囲）を必須とする。
- セッション変数（`app.tenant_id` 等）の**設定漏れ＝分離破綻**になるため、接続取得時に確実に設定する共通機構（ミドルウェア／コネクションラッパ）を用意する。
- 集計系はRLS越しの実行時集計だと重くなるため、**集計テーブル／マテビュー**の設計・更新方式を別途必要とする。
- 物理隔離ではないため、**保存時暗号化・鍵管理・監査ログ**（ADR-0017）で機微データ保護を補完する。
- **【v15】RLS が守る範囲を限定して明記する（IND3-H2 の裁定＝(a)）**：**capability を注入変数に加えたことで、ロール別の「行の可視性」と「個人データの最小権限」は RLS で強制できるようになった**（§2.9）。**しかし RLS は行フィルタであり操作の認可機構ではない**——**権限管理・承認・設定変更のような「行の可視性で表せない操作の可否」はアプリ層が唯一の防御**である。**したがって §4 の「RLS が最後の防波堤」は、テナント境界・スコープ・本人性・個人データの可視性についての主張であり、操作の可否には及ばない**。無条件の主張はしない。ADR-0017 の脅威モデルは**アプリ層の認可を独立の保護対象**として扱うこと。
- **【v15】絞りを restrictive に集約した代償**：**permissive は `USING (true)` 固定**になったため、**すべての絞りが restrictive の述語形に集中する**——述語形が増えれば検査項目も増え、**述語形の管理そのものが防波堤の一部**になる。現在7形（(a)〜(f)＋④の独立ポリシー）。**増やすときは注入変数表・述語形表・検査項目・振る舞いテストの4箇所を同時に更新する**（教訓6の6箇所に準じる）。
- **【v15】注入時のDB側検証の責務が増えた**：`allowed_tenants` に加えて **`app.caps`（ロール由来の部分集合であること）と `app.employer_subject_users`（双方向確認済みの雇用関係であること）** も注入時に検証する必要がある。**この検証がテナント分離だけでなく個人データ保護の床にもなった**ため、A1b-M1 の「集合注入時に1回」の検証がさらに重い責務を負う。
- **【v13／v14改訂】restrictive の述語統一により、`allowed_tenants` の注入検証が防波堤の一部になった（IND2-H1／H3／A1h-H1）**：認証経路を RLS の枠内に留めた（BYPASSRLS を増やさない）代償として、**「restrictive の床がアプリ計算の `allowed_tenants` である」**状態が生まれた。**A1b-M1 の注入時DB側検証がこの床を守る唯一の機構**であり、**ポリシーだけでは分離が完結しない**。ADR-0017 の脅威モデルはこれを保護対象に含めること。
  - **【v14】ただし「restrictive が適用されないロール」は作らない**（A1h-H1 の是正）。restrictive は全ロールに適用し、例外は述語に書く。**`TO` はrestrictiveには付けない／permissiveにのみ付ける**という原則により、**ロールが増えても穴が開かない**。
  - **【v14】①③には基本 permissive が必須**（permissive が1本も無いテーブルは誰にも0行になる）。**これは「restrictive だけ置けば安全」という直感が誤りである**ことを意味し、**検査項目（permissive の存在）が機能そのものを守る**。
- **【v13】「横断は宣言的に許可できる」という当初の主張は不正確だった（IND2-H3）**：restrictive/permissive の結合意味論により、**横断は「permissive を足す」ではなく「restrictive の述語を横断可能な形にする」**必要がある。§4「良い影響」の「横断をRLSポリシーで宣言的に表現できる」は成立するが、**その表現は restrictive 側にある**。
- **【v11】現時点でRLSの防波堤に例外はない（ADR-0002 v9 A2h-H1 の逆流）**：ADR-0002 v9 が「索引は各シャードの①メンバーシップから導出する（物理テーブルを持たない）」を既定としたため、**「特権経路専用テーブル」の枠は対象0件**となった。**本ADRの中核主張（RLSがアプリバグへの最後の防波堤）は、実際には例外なく成立している。** 下記の記述は**将来物理化する場合に発効する条件付きの設計**として保持する。**上流ADRの整理が進んだことで、下流に作った負債を回収できた例**である（開発工程 教訓7）。
- **【v9／v10改訂・v11で条件付き】特権経路専用テーブルはRLSの防波堤の外にある（A1f-M1／A1g-H1）**：認証・所属解決はテナント文脈が確定する**前**に参照する必要があるため、この枠のテーブルは **RLSではなく専用スキーマ＋テーブル権限で守る**（§3.1）。したがって**この枠に限り「アプリバグに対するDB層の防波堤」は存在せず、権限付与の誤りが直接漏えいになる**——本ADRの中核主張（RLSが最後の防波堤）に対する**明示的な例外**である。よって：
  - **検出が唯一の防御**である。**`priv` スキーマの `USAGE`／権限の網羅検査（列挙しないカタログ走査）を自動テストに常設する**ことが、この例外を許容する条件になる（検査が無いなら例外を認めない）。
  - **該当テーブルは最小限に保つ**（追加には明示的な判断を要する＝§5）。増殖は網羅検査では防げず（検査は「通常ロールから見えない」ことしか保証しない）、**「RLSの外に置いてよいか」の判断は人が行う**。
  - **ADR-0017 の脅威モデルで個別に評価する**（RLSが全テーブルを覆っている前提で設計してはならない）。**ADR-0002 の `user→shard` 索引は、法域内全ユーザーの取引関係グラフという機密資産**であり、この例外の下に置かれる最初の対象。
- **【v10】スキーマ分離の運用コストが増える（A1g-H1）**：`priv` スキーマの権限管理・`ALTER DEFAULT PRIVILEGES` の対象除外・カタログ走査テストの常設・**全シャードへの一律適用とシャード追加時の手順**（ADR-0002 v8 の複製配置）が運用項目として加わる。マイグレーション規約に反する一括付与が入ると静かに穴が開くため、**規約違反をCIで検出する**必要がある。
- **【v10】通常ロールから `EXECUTE` できる SECURITY DEFINER 関数が増える（A1g-M1／A1g-L2）**：索引の更新（`refresh_user_shard_index`）と監査追記のために、**通常ロールから呼べて所有者権限で動く関数**が存在する。安全性は「**引数で"どう書くか"を指示させず、メンバーシップから収束させる**」という設計に依存しており、**この設計規律が崩れると権限昇格の踏み台になる**。関数群は一覧化し `pg_proc.prosecdef` 走査で棚卸しする（§5）。

## 5. 未解決事項（設計フェーズで詰める → 9.1へ）

- RLSポリシーの具体設計（3.2ロール表のDB表現、グループ管理者の許可tenant_id集合の事前解決＋**DB側検証（EXISTS/SECURITY DEFINER）**の実装、本人起点横断の労務サマリ限定ポリシー、permissive/restrictiveの使い分け、③共有＋上書き可能テーブルの専用ポリシーと上書き優先解決：A1-M1/M2/A1b-M1/M2）。
- `SET LOCAL app.tenant_id` を全クエリのトランザクション境界で確実に設定・解除する共通機構の実装（ミドルウェア／コネクションラッパ）とテスト（A1-H1）。
- RLSの有効性テスト（他テナント参照の遮断、未設定時のフェイルクローズ、FORCE RLS〔対象＝業務テーブル①〜④〕、非所有者ロールでの動作）を自動テスト化（A1-H2）。
- **【v13／v14改訂】RLS・権限の網羅検査は「カタログでの構造検査」＋「自動生成した振る舞いテスト」の二段とする（IND2-H3／A1h-M1／教訓12）**。**v13 は検査の内容だけを書き、判定方法を書いていなかった**——`pg_policies.qual` は PostgreSQL が正規化して再構成したテキストであり、**キャスト・括弧・スキーマ修飾の書き方の揺れで文字列一致が壊れる**（正しいポリシーが弾かれる／誤ったポリシーが通る、の両方が起きる）。**述語の文字列比較に依存しない検査**にする。

  **一段目：カタログでの構造検査（テーブルもロールも列挙しない）**——`pg_policies`／`pg_class`／`pg_roles`／`information_schema.role_table_grants` の走査のみで判定でき、**述語の内容を比較しない**：
  1. **`tenant_id` 列を持つ全テーブルに RESTRICTIVE ポリシーが存在すること**（欠落＝分離消失）。
  2. **RESTRICTIVE ポリシーに `TO` 指定（ロール限定）が付いていないこと**（`pg_policies.roles = {public}`）。**これが A1h-H1 の再発防止であり、ロールの列挙を不要にする**。
  3. **①③テーブルに PERMISSIVE ポリシーが1本以上あること**（**permissive が無いと誰にも0行**＝上記【v14】の性質）。
  4. **述語に `current_user` が現れる RESTRICTIVE を持つテーブルが、例外一覧（現時点では `membership` のみ）に限ること**（ブートストラップ例外の増殖検出）。
  5. **`app.user_id` を参照する RESTRICTIVE を持つテーブルが、本人起点例外の一覧（`labor_summary` のみ）に限ること**。
  6. **`FORCE ROW LEVEL SECURITY` が未設定の業務テーブルが存在しないこと**（対象＝①〜④）。
  7. **`rolbypassrls` を持つロールが一覧（現時点では `audit_writer` のみ）に限ること**、**`auth_role` がいかなるテーブルにも直接権限を持たないこと**、**`auth_role` の `EXECUTE` が一覧化された SECURITY DEFINER 関数に限ること**、**`pg_proc.prosecdef` の関数が一覧外に存在しないこと**。
  8. **ポリシー名規約**（例 `<table>_tenant_isolation`）の違反をCIで検出する（**述語比較の代替ではなく、1〜7 の補助**）。

  9. **【v15】permissive の述語が `true` 以外のものが存在しないこと**（絞りが permissive に紛れ込んでいないことの検出＝IND3-H2 の再発防止）。
  10. **【v15】restrictive に `WITH CHECK` が明示されていること**（省略＝`USING` の流用＝IND3-H3／PG-M3）。かつ **`WITH CHECK` 述語に `app.allowed_tenants`／`app.user_id`／`app.employer_subject_users`／`tenant_id IS NULL` が現れないこと**（読取の集合を書込に流用していないこと）。
  11. **【v15】セッション変数の参照がすべて正規化形（`COALESCE(NULLIF(...), '{}')` ／ `NULLIF(..., '')`）であること**、かつ**関数にラップされていないこと**（PG-H1／PG-M4）。**素の `current_setting('app.*', true)::` が qual に現れたら違反**。
  12. **【v15】`app.caps` を参照する restrictive を持つテーブルが、個人データ一覧に限ること**／**`app.employer_subject_users` を参照する restrictive が `labor_summary` のみであること**（例外の増殖検出）。

  13. **【v16】`part` スキーマ（パーティション子の置き場）に通常ロールの `USAGE`／権限が1件も無いこと**、かつ **`relispartition = true` のテーブルが `part` 以外に存在しないこと**（PG-H6）。
  14. **【v16】RLS 有効な表に依存するビューが `security_invoker` であること**（`pg_class.reloptions` ＋ `pg_depend`。PG-H4／IND3-M6）。**v15 までの検査はビューを一切見ていなかった。**
  15. **【v16】`bootstrap_owner` の権限が一覧化された表の `SELECT` に限ること**／**`bootstrap_owner` が NOLOGIN・非BYPASSRLS・非superuser であること**／**`bootstrap_owner` がいかなるロールにも `GRANT` されていないこと**（`SET ROLE` で例外を得られないようにする＝PG-L7）。**`auth_role` はテーブル権限ゼロ・ブートストラップ関数の `EXECUTE` のみ**（IND3-H1／PG-H5）。

  **二段目：自動生成した振る舞いテスト（実データで確認・テーブルを人手で列挙しない）**——カタログからテーブル一覧を取り、**2テナント分＋2ユーザー分のダミー行を投入して、各ロール・各コンテキストで実際に読む**：
  1. **遮断**：他テナント行が見えないこと（未設定時のフェイルクローズを含む）。
  2. **横断が通ること（IND2-H3 の再発防止）**：**グループ管理者が `allowed_tenants` 内の他テナント行を読める**／**本人起点で `allowed_tenants` 外の自分の `labor_summary` 行を読める**／**③の共有行（`tenant_id IS NULL`）が読める＋グループ管理者が配下の上書き行を読める**。**「遮断」だけを検査すると、横断が動かない状態でも全部緑になる**（IND2-H3 が見逃された理由／A1h-M2 の③も同型）。
  3. **特権経路が動くこと**：`auth_role` が `app.bootstrap_claimed_user` の設定下で当該ユーザーの membership を**テナント跨ぎで読めること**（自己ブロックの再発検出＝A1f-H1）、かつ**業務テーブルは読めないこと**。
  4. **通常ユーザーの `allowed_tenants` が1要素であること**を注入時検証のテストで担保する（restrictive の床が集合になった代償＝A1h-M4）。
  5. **【v15】書込側のテスト（IND3-H3／PG-M3）**：**他テナントの `tenant_id` を指定した INSERT が拒否されること**／**UPDATE による行移送が拒否されること**／**`labor_summary` に他テナント名義の追記ができないこと**／**一般ロールが `tenant_id IS NULL`（③共有行）を INSERT・UPDATE できないこと**。**「遮断（読取）」だけを検査すると書込側の穴が全部緑になる。**
  6. **【v15】capability のテスト**：`app.caps` に該当 capability が**無いときに他者の個人データ（位置ログ軌跡・打刻）が見えないこと**、**あるときに見えること**、**注入時のDB側検証がロール由来でない capability を弾くこと**。
  8. **【v16】パーティション子テーブルの直接参照が拒否されること**（PG-H6）。
  9. **【v16】主要ビュー経由で正しい行が見えること**（③解決ビュー・訂正チェーンの有効値ビュー・未確定期間の導出ビュー。PG-H4）。**グループ管理者がビュー経由で配下テナントの上書き行を見られること**も含める。
  10. **【v16】ブートストラップ経路のテスト**：`auth_role` が関数経由で**テナント跨ぎに解決できること**／**`auth_role` の membership 直接参照が `permission denied` になること**／**主張（`app.bootstrap_claimed_user`）と引数が一致しない場合に0件になること**（いずれも実測で成立を確認済み）。
  7. **【v15】注入漏れの挙動を「`SET LOCAL` を使った接続の2回目のトランザクション」で確認する**（1回目だけでは NULL 経路しか通らず、`''` 経路のバグが緑になる＝PG-H1）。
- テーブル分類（テナント固有／システム共有／共有＋上書き可能／ユーザー所有）の一覧化と、共有マスタの具体対象（農薬肥料マスタ・作物マスタ・多言語ラベル等）の確定（A1-M3）。
- **【v8／v9／v10改訂】特権経路専用テーブルの管理（A1f-M2／A1g-H1）**：判定基準は「**通常ロールに `GRANT` しないテーブル**」（アクセス経路ではなく権限で判定）。**特権経路から読まれるが通常経路でも使うテーブル（メンバーシップ等）は①テナント固有のままであり、本枠には含めない**。現時点の該当は **ADR-0002 の `user→shard` ルーティング索引**のみ。**【v10】強制力は専用スキーマ `priv` と網羅検査に持たせ、一覧は文書化のためにのみ維持する**（人手の台帳に依存しない）。ただし**「RLSの外に置いてよいか」の判断は人が行う**ため、追加には明示的な判断を要する（ADR-0002 A2g-M3／ADR-0009／ADR-0017）。
- **【v10】`priv` スキーマのマイグレーション規約とCI検出（A1g-H1）**：`ALTER DEFAULT PRIVILEGES` を `priv` に設定しない／`GRANT ... ON ALL TABLES IN SCHEMA` の対象から `priv` を除外する、という規約を定め、**規約違反のマイグレーションをCIで検出**する仕組み（静的検査＋適用後のカタログ走査）を確定する（ADR-0021 CI/CD）。
- **【v9／v10改訂】特権経路専用テーブルの参照監査の実装方式（A1f-M3／A1g-M3）**：SECURITY DEFINER関数内での明示追記か `pgaudit` かの選択を **ADR-0017** で確定する。**認証成功した解決のみ監査本体（ハッシュチェーン）へ、未認証の試行は別系統の運用ログ（短期・レート制限後・集約カウント）へ**という分離を前提とし、**量の見積り基準は「ログイン試行数（攻撃者制御下）」**とする。レート制限は **ADR-0009**、運用ログは **ADR-0020**、ハッシュチェーンの並行性は **S5** で検証する。
- **【v9】特権経路専用テーブルの環境コピー時の扱い（A1f-L1）**：バックアップ・レプリカ・開発/検証環境ダンプに含まれるため、**マスキングまたは除外**の運用を **ADR-0017／ADR-0019** で確定する。**【v10】法域内の全シャードに一律適用**し、**シャード追加時の手順に権限設定・網羅検査・マスキング設定を含める**（ADR-0002 v8 の複製配置／A1g-L1）。
- **【v10】SECURITY DEFINER 関数の一覧化と棚卸し（A1g-L2）**：現時点の該当＝所属解決（A1e-M1）・許可集合の検証（A1b-M1）・索引の読取／**更新 `refresh_user_shard_index`（A1g-M1）**・監査追記（A1f-M3）。各関数の**目的・引数の信頼可否・`EXECUTE` を与えるロール・関数内の検証条件**を設計フェーズで確定し、**`pg_proc.prosecdef` を走査して一覧外の SECURITY DEFINER 関数が存在しないことを自動テスト**する（テーブル側の網羅検査と同じ思想）。関数は**権限昇格の主要な攻撃面**であり、テーブルと同格に管理する。
- **【v11／v12】認証専用ロールの権限（ADR-0002 v9 A2h-M2／v10 A2i-M1）**：**テーブル権限ゼロ＋SECURITY DEFINER 関数の `EXECUTE` のみ**という形を実装し、**①いかなるテーブルにも直接権限を持たないこと／②`EXECUTE` が一覧化された関数に限ること**をカタログ走査で検査する。**認証接続/業務接続の分離**も実装する。**「認証層＝RLSの外側の侵害」の脅威評価**を ADR-0017 の独立項目として立てる（ADR-0009／ADR-0019）。
- **【v10】権限・RLSテストのロール構成要件（A1g-L3）**：RLS/権限テストは**本番と同一のロール構成**（所有者・アプリ通常ロール・認証専用ロール・管理ロール）で実行する。**ロール構成自体をマイグレーションで管理**し、テスト専用に緩めた構成では検査しない（構成が違えば結果が本番を反映しない）。
- 集計テーブル／マテビューの対象・更新頻度・整合性（横断ダッシュボードF-60〜63）。
- テナント削除・移設（オフボーディング）の運用。
- 規模が「1DB数百テナント」前提を超えた場合のハイブリッド/シャーディング移行計画（A1-L1）。
- 端末側データ分離・暗号化はADR-0007と連携（A1-L2）。
