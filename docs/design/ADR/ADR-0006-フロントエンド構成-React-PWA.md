## 1. 背景・課題（Context）

フロントエンドは、本システムの最大の技術リスク（現場のオフライン利用）とUX目標（KSASより使いやすく）を同時に満たす必要がある。満たすべき要件：

- **現場＝モバイルでオフライン利用**（要求仕様5.1.1）：圏外の圃場で作業日誌・農薬使用基準チェック・在庫出庫・打刻・位置ログを行い、復帰時に同期。オフライン中も**事前警告**（農薬使用基準 F-41）が要る。
- **UX目標**（5.1／4.11）：作業日誌入力30秒、タスク成功率90%、SUS 75。片手・手袋・屋外日光下でも使える。
- **2つの利用文脈**：**現場（スマホ・オフライン・素早い入力）**と**オフィス（PC・大画面・計画/分析/管理）**。
- **地図/GIS**（4.1／ADR-0010）：圃場ポリゴン描画・オフラインタイル。
- **多言語・多地域**（ADR-0015）：全世界の言語、圃場ローカル暦日、通貨/単位。
- **配信＝MITのOSS**（1.3）：運用者が自前ホスト可能な構成。
- **大量データ**：圃場数万・位置ログ多数を端末側に持ち得る（同期＝ADR-0007）。

これらを、**単一コードベースで保守可能**かつ**現場のオフライン要件を破綻させない**形にする。

## 2. 決定（Decision）

**React＋TypeScript の単一コードベースを、PWA を既定として構築する。** モバイル（現場）とデスクトップ（オフィス）を**レスポンシブな単一コードベース**で提供する。**offline-first は「現場の運用サブセット」に限定**し、オフィスの分析/一覧は**オンライン・サーバ集計**とする（A6-M1）。**PWA を既定・ネイティブ（Capacitor）は端末能力が要る場合のオプション**と位置づけ、どこまでをPWAで賄うかは端末能力スパイクS6で確定する（A6-H1）。

> **用語の正確化（A6-H1）**：本ADRは「PWA中心」ではなく「**PWAを既定、ネイティブは能力要件があるときのオプション**」を採る。「純PWAで全要件を満たす」とは主張しない。

### 2.0 データ種別で決める真実源（A6-M1／M2／R2-M1／R2-M2）

**層は「画面単位」でなく「データ種別単位」で決める**（画面は実務で重なるため・R2-M1）。3区分：

| データ種別 | 例 | 真実源 | オフライン |
|---|---|---|---|
| **①運用データ**（書込を伴う） | 作業日誌・在庫出庫・打刻・位置ログ | **端末IndexedDB が真実源**（同期エンジンがIndexedDBを更新） | 読み書き可（圏外可） |
| **②共有参照キャッシュ** | agro_chemical(③)・作物マスタ・**安全基準(F-41)** | **サーバが原本、IndexedDBに版・鮮度契約つきでキャッシュ** | 参照可（鮮度契約でfail-safe） |
| **③分析データ**（読取専用の集計/大量一覧） | 計画・帳票・集計（数万件） | **サーバが真実源**（Queryキャッシュは揮発） | 不可（縮退表示） |

- **混在画面**（例：今日の未同期入力＋サーバ傾向）は、**各データ種別を別々の真実源から読んで合成**する。オフライン時は③の集計部分を「**オフラインにつき最新でない**」ラベル＋**最終同期時刻**を明示して**縮退表示**し（F-D系・R3-L2）、①②は通常どおり動く。
- **②参照キャッシュの範囲（R3-L2）**：agro_chemical等を**全世界分は持たず、対象国/実際に使う薬剤・作物に絞ってキャッシュ**し端末容量を抑える（ADR-0011のタイル「必要分のみ」と同型）。
- 二層UIはコンポーネント/デザインを共有するが、**データパスは種別で分離**する。②の更新は優先同期対象（H2の鮮度契約と一体）。

- **言語/型**：**TypeScript**（型安全・大規模保守）。
- **UIライブラリ**：**React**。代替（Vue/Svelte/SolidJS）と比較のうえ採用（A6-L1）：**地図（MapLibreのReactバインディング）・i18n（ICU系）・オフライン/Query（TanStack）・Capacitor連携のエコシステム成熟と採用実績**が最も厚く、多人数・長期保守の人材確保にも有利。Svelte/Solidはバンドル/性能で魅力だがライブラリ成熟でReactに劣後、Vueは有力だが本要件での優位が決定的でない。具体のコンポーネント体系は **ADR-0016（UXデザインシステム）** で確定。
- **レンダリング＝クライアントサイドSPA**：オフライン起動が必須のため、**アプリシェルを端末にキャッシュして起動をサーバ非依存にする**。SSR/SSGは初期表示に有利だが、**オフライン起動・端末ローカルデータ駆動**の要件と噛み合わないため主軸にしない（マーケ用公開ページ等が必要なら別建て）。
- **PWA**：
  - **Service Worker**（**Workbox** で生成）＝アプリシェル（HTML/JS/CSS）と静的資産の**プリキャッシュ**、実行時キャッシュ戦略（地図タイル等）。
  - **インストール可能**（ホーム画面追加）。オフラインでも起動・入力可能。
  - **更新戦略**：SWの更新は**明示的な更新通知＋リロード**（勝手に画面が変わらない）。**リロードは「未確定入力なし」の安全なタイミングに限る／未確定入力は下書き（④）へ退避してからリロード**（A6-L3）。破壊的スキーマ変更時のバージョン整合はADR-0007と連携。
- **オフラインファーストのデータ層（現場・運用UI）**：
  - 端末ローカルの一次ストア＝**IndexedDB**（作業日誌・在庫イベント・位置ログ・マスタキャッシュ・**農薬使用基準の事前キャッシュ**）。**現場・運用UIは IndexedDB を真実源として読む**（オンライン/オフラインでコードパスを分けない）。オフィス・分析UIはこの限りでない（§2.0）。
  - サーバとの**差分同期は ADR-0007** に委譲。フロントは「ローカルに書く→同期エンジンが送る」を前提に設計（楽観的更新）。冪等キー＝**UUIDv7**（データモデル設計書§5：`event_uuid`）をクライアントで採番し、`event_ts` も `uuidv7_time` 相当をクライアントで算出して送る（スパイクS1で確定した経路）。
  - **未同期データの保護（A6-H3／R2-L1）**：**「未同期の書込は消えてはいけない」を不変条件**とする。保護の**主軸は「早期同期＋永続化」**：(a) **接続が一瞬でも回復したら未同期キューを最優先で送る**（滞留を最小化）、(b) `navigator.storage.persist()` を要求し**インストールPWA/ネイティブで永続性を確保**（各OSの実効性はS6で実測。**同一端末内の別ストレージ冗長化は端末全体のeviction/紛失に無力なので主軸にしない／任意エクスポートは補助**）、(c) **未同期件数・最終同期時刻をUIで常時可視化**し長期未同期を警告（F-D系）、(d) 冪等（UUIDv7）は**重複を防ぐが消失は防げない**ため、エビクション耐性が不足する運用者はネイティブ（下記(b)）へ。保持責務はADR-0007と接合。
  - **安全criticalデータの鮮度契約（A6-H2／R2-M3）**：F-41の安全/法令基準キャッシュは**版・有効期限・最終同期時刻**を持つ。**オフライン有効期間は運用者が設定可能**（法域/通信事情に合わせる）とし：
    - **有効期間内**＝通常運用（オフラインでも警告判定を行う）。
    - **有効期間超過**＝**「基準が古い可能性」を明示し、判定をfail-safe側に強める**が、**「保留＝実施不能」を既定にはしない**。**明示的承認（「基準が古い可能性を了解して実施」を記録＝監査）で継続可能**にする（数日〜数週間圏外が常態の海外/僻地でも運用が死なないように）。
    - **承認のガードレール（R3-M1・承認の形骸化と権限逸脱を防ぐ）**：(a) **チェック種別で承認可否を分ける**——**登録失効・使用禁止など最重要チェックは承認でも実施不可（保留）**、希釈上限・使用回数等は承認で継続可。(b) 承認は**役割で制限**（例：現場責任者以上）＋**監査記録**（誰が/いつ/どの基準版で）＋**乱発の可視化**（連続承認を検知）。(c) 承認は**オフライン有効期間超過時のみ**（オンライン時は通常のfail-safe）。承認権限者・対象チェックの線引きは運用者の法域に委ね、**E系/ADR-0017**と接合。
    - **登録失効・回収は復帰時に最優先同期**。オフライン警告は**参考**、**最終確定はオンライン再検証を要する機微操作**（ADR-0015「安全ラベルはレビュー済みのみ」と整合）。安全と運用継続のバランスは運用者の法域/実態に委ね、E系と接合。
  - **オフライン認証の継続（R2-M4）**：現場は**トークン失効後もオフラインで運用継続できねばならない**（数日圏外）。**「最後に検証したセッション＋権限スナップショット」で運用継続**（①運用データの読み書きはローカル、機微操作は不可）、**オンライン復帰時に再認証・再検証**し、失効時は**未同期分の送信のみ許して以降をロック**する。
  - **失効の反映遅れへの対処（R3-M2・ADR-0005の即時失効との両立）**：オフライン権限スナップショットは**オフライン中の失効（解雇/剥奪）を反映できない**ため：(a) **オフライン猶予に上限**（運用者設定・既定は短め）を設け、超過で**「読み書き可」→「読取のみ」→「機微ロック」→「運用ロック（未同期送信のみ）」と段階縮退**。(b) スナップショットで許すのは**①運用データの最小操作のみ**（原価・個人データ・エクスポート等の機微は常にオンライン検証）。(c) 復帰時に失効が判明したら**未同期分の受理可否をサーバが最終判断**（作成時刻・スナップショット署名で検証）。猶予上限・段階縮退・署名の具体は**ADR-0009/0005**で確定（0006は要件を規定）。
  - **端末側データ保護（R3-M3・紛失/盗難）**：オフラインファーストは端末に**運用データ＋作業者PII＋参照**を蓄積するため、露出面の保護を0006の要件として規定（実装は**ADR-0017**）：(a) **端末保存データの暗号化**（ネイティブはOSキーストア、ブラウザPWAは暗号化保証が弱い旨と対策・限界を明記）、(b) **失効/オフライン猶予超過/明示ログアウトで端末キャッシュを自動パージ**（未同期は送信後に消去、送信不能なら保持し警告）、(c) **リモートワイプ**（ネイティブ/MDM経路）。ブラウザPWAの暗号化限界が要件を満たさない運用者はネイティブ（(b)経路）へ。
- **地図**：**MapLibre GL JS**（ADR-0010）。オフラインタイルは対象国分＋端末は圃場周辺のみ（ADR-0011）。
- **国際化**：**ICU MessageFormat（CLDR）** ベースのi18n（ADR-0015）。日付は「時点=UTC表示変換／暦日=圃場TZ」をフロントでも遵守。
- **状態管理（真実源は§2.0のデータ種別で固定）**：**運用データ＝永続ローカル（IndexedDB・真実源、同期エンジン経由で更新）**、**分析データ＝サーバ状態（TanStack Query 等・揮発キャッシュ）**、**共有参照＝サーバ原本＋IndexedDBキャッシュ（鮮度契約）**、**UI状態＝軽量ストア**。運用データと分析データのパスを混在させない（A6-M2）。
- **位置ログの取得方式（A6-M3／R2-L2）**：**打刻（F-74）連動を既定**（作業開始打刻→位置ログON、休憩/終了打刻→OFF）で「作業中ON/休憩中OFF」を実現。取得は**適応間隔**（移動時は密・静止時は疎）でバッテリ/データ量を抑制。**打刻忘れ検知**（作業中のはずが位置更新が無い→リマインド）を設ける。ただしON後の**継続取得はiOSでバックグラウンド実行に依存**するため、背景実行の可否はS6/ネイティブ（(b)）依存であり「打刻連動で解決」とはしない。バッテリ・IndexedDB書込量の目安はS6で実測。
- **バンドル分割（A6-M4）**：**文脈単位のコード分割（現場・運用UI／オフィス・分析UI）**と、**地図・i18n・分析の遅延読込**。現場UIは最小構成で起動し、初期JS上限＝**性能予算**を定義・計測（ADR-0020）。
- **ビルド/ツール**：**Vite**（高速・PWAプラグイン）。E2E/単体テストの土台も用意（ADR-0021）。
- **アクセシビリティ/現場UX**：大きいタップ標的・高コントラスト・片手操作・オフライン状態の明示（F-D系）。
- **native は「能力オプション」＋配布の条件分岐（A6-H1）**：**iOS Safari の PWA 制約**（バックグラウンド位置取得が実質不可、ストレージのエビクション、Background Sync 非対応、プッシュ制約）により、**F-08a の継続位置ログ等がブラウザPWAだけでは満たせない可能性**がある。対応を**配布経路とセット**で分岐する：
  - **(a) PWAで賄える範囲**（オフィス全般＋現場のフォアグラウンド操作）＝**運用者が自前ホストするPWA**（MIT・1.3に適合）。
  - **(b) バックグラウンド位置ログ等ネイティブ必須機能**が要る運用者向け＝**同一Reactコードを Capacitor で薄くネイティブ化**。ただし**ネイティブ配布は App Store/Play・コード署名・開発者登録が必要で「サーバに置くだけ」では配れない**。かつ**本プロジェクトは中央publisherを持たない自前ホストOSS**のため「公式アプリ1本」では各運用者の自前バックエンドに接続できない（A6/R2-H1）。よって**ネイティブ配布モデルを次の選択肢から選ぶ**（S6で必須範囲確定後）：
    - **(b-2) 運用者による自己署名公開（既定）**：各運用者が**フォークして自分の開発者アカウントで署名・配布**（ストア/MDM/エンタープライズ）。公式は**ビルド手順・CIテンプレ**を提供。※自律的だが運用者負担大。**中央組織を持たないOSSでも成立する現実解**のため既定とする（R3-L1）。
    - **(b-1) 設定可能backendの汎用アプリ（担い手が現れた場合のオプション）**：「**接続先バックエンドURLを実行時設定できる**汎用クライアント」を1本ストア公開（各運用者はサーバのみ用意）。※任意URL接続の**セキュリティ（接続先検証・証明書ピンニング等）はADR-0017**と接合。**Apple/Google開発者登録・審査対応・鍵管理・継続保守の担い手（財団/主要スポンサ/運用者連合）が要る**ため、担い手が確立した場合のオプションとする（R3-L1）。
    - **(b-3) 併用**：担い手があれば小規模は(b-1)、規制の厳しい/大規模運用者は(b-2)。
    - 鍵管理・審査・任意backend接続のセキュリティは**ADR-0017**、必須範囲の確定は**S6**へ接続。
  - **単一コードベースは維持**（能力差はプラグイン層で吸収）。「PWAで全部」とは主張しない。

## 3. 検討した選択肢（Options）

| 観点 | 選択肢 | 評価 |
|---|---|---|
| 配布形態 | **PWA既定＋ネイティブは能力オプション（採用）** ／ フルネイティブ（iOS/Android別） ／ React Native | ◎ PWAは単一コード・自前ホスト（MIT）・即時配信。ただし**ネイティブが要る範囲は自前ホストで配れない**ため配布を条件分岐（A6-H1）。フルネイティブは2文脈×2OSで工数肥大。RNはオフィスWebと二重管理 |
| ラッパ | **Capacitor（必要時のみ・採用）** ／ ラッパなし ／ 最初からRN | ◎ 同一Reactコードを必要時のみネイティブ化。ラッパ無しだとiOS制約でF-08aが破綻。ただしネイティブ配布は署名/審査が要る（A6-H1）。最初からRNはオフィスWebと乖離 |
| レンダリング | **CSR/SPA（採用）** ／ SSR（Next.js等） | ◎ オフライン起動・ローカルデータ駆動にはCSRが自然。SSRはサーバ依存で圏外起動と相性が悪い |
| 言語 | **TypeScript（採用）** ／ JavaScript | ◎ 大規模・多人数・長期保守で型が効く |
| ローカル永続 | **IndexedDB（採用）** ／ localStorage ／ SQLite(wasm) | ◎ IndexedDBは大容量・構造化・非同期。localStorageは容量/同期API不足。SQLite-wasmは有力だがまず標準のIndexedDBで、必要ならADR-0007で再評価 |
| 状態 | **層分離（サーバ/永続/UI）（採用）** ／ 単一グローバルストアに全部 | ◎ オフライン同期を単一ストアに混ぜると複雑化。関心を分離 |

**却下理由**：フルネイティブ2OSは工数と二重保守。純SSRはオフライン起動に不向き。ラッパ無しPWAはiOSの位置ログ制約で現場要件（F-08a）を落とす。

## 4. 影響・帰結（Consequences）

**良い影響**
- 単一コードベースで現場/オフィス両文脈をカバー。**PWAで賄える範囲は自前ホスト（MIT）に適合**。
- 現場・運用UIの一貫したデータパス（IndexedDB真実源）で、圏外/圏内のコード分岐を排除しバグ面を縮小。分析UIはオンライン・サーバ集計に分離し過剰なローカルミラーを回避。
- スパイクS1で確定した冪等（UUIDv7＋CHECK）とフロントの採番が一致し、同期の芯がぶれない。

**悪い影響・制約**
- **配布の二経路化（A6-H1／R2-H1）**：ネイティブ必須機能が要る運用者には自前ホストPWAだけでは足りず、署名済みネイティブ配布（設定可能backendの汎用アプリ or 運用者の自己署名）が要る。OSSの提供形態が二経路になり、任意backend接続のセキュリティ（ADR-0017）が付随する。
- **安全データの鮮度管理コスト（A6-H2）**：オフライン安全警告にfail-safe・優先同期・版管理が要る（実装/運用の負荷）。ただし安全側に倒すのは必須。
- **未同期保護の運用（A6-H3）**：persist()・優先同期・未同期可視化が要り、エビクション耐性が不足する運用者はネイティブが要る。
- **オフライン同期の複雑性**はADR-0007へ集約されるが、楽観的更新・競合表示（5.1.1）はUX（ADR-0016）と密結合。

### 4.1 受容する原理的限界（オフラインの本質的制約・第4回レビュー）

オフラインファーストには、**設計で消せない・受容すべき本質的限界**がある。緩和策を添えて明記する：

- **安全判定は鮮度に束縛される（R4-L1）**：オフライン安全判定は**最終同期時点の基準**に基づき、**それ以降の登録失効・基準改定は次回同期まで保証対象外**。「最重要チェックは承認でも不可」は**既知の失効にのみ**効く。緩和＝(a)復帰時の**失効/回収の最優先同期**、(b)**オフライン有効期間**、(c)期限内でも**最終同期時刻・基準版を常時表示**。安全critical運用は**有効期間を短めに**設定する。
- **長期オフライン継続 vs 即時失効は二律背反（R4-L2）**：猶予/有効期間を**短く＝安全/失効に強いが遠隔圃場で運用が死ぬ**、**長く＝運用は生きるが失効/鮮度が弱まる**。両取りは不可。**運用者が法域・通信事情・機微度で選ぶ**（国内近接＝短め／海外遠隔＝長め＋端末保護・監査を厚く）。既定は短め、延長は**明示的なリスク受容**。
- **紛失オフライン端末の保護は暗号化のみが砦（R4-L3）**：**リモートワイプ・失効時パージはオフライン端末に届かない**。圏外で紛失/盗難された端末の運用データ＋PIIは**保存時暗号化だけが最後の砦**で、ブラウザPWAの暗号化は弱い。よって**機微データを端末保持する運用者は(b)ネイティブ経路（OSキーストア暗号化＋MDMワイプ）を推奨**、ブラウザPWAは機微度が低い運用に限る（ADR-0017で確定）。
