## 1. 背景・課題（Context）

APIは、(a)現場PWA/ネイティブのオフライン同期、(b)オフィスの分析/管理UI、(c)外部公開（F-90）の**3つの異なる利用**を支える。ADR-0007（オフライン同期）が**同期プロトコルの要件**を確定済みで、本ADRはそれを実装可能にする**API方式**を裁定する。満たすべき要件：

- **オフライン同期を素直に表現できる**（ADR-0007）：**依存束の原子受理（push）**、**シャード別カーソルによる差分pull**、**冪等（UUIDv7＋`(tenant_id,event_uuid)`）**、**優先度クラス（P0安全/失効…）**、**サーバ側で権限再検証**。
- **テナント/権限をサーバで強制**（ADR-0001）：全リクエストでtenant・スコープを注入・RLS。**1DB=1国/シャード**（ADR-0002）へ正しくルーティング。
- **外部公開（F-90／4.10）**：第三者システムが**相互運用しやすい**こと（一般的な規約・認証・バージョニング）。
- **性能**（5.2）：一覧/API 500ms/p95、地図2秒/p95。キャッシュ・ページング。
- **2つのクライアント文脈**（ADR-0006）：現場（固定的・オフライン同期）とオフィス（柔軟な分析クエリ・大量データ）。
- **MIT OSS**：運用者が自前ホスト・拡張しやすい標準的な構成。

## 2. 決定（Decision）

**REST（JSON over HTTPS）を基盤API方式とする。** その上に、**用途別に3つのAPI面**を設ける：**①専用同期API（ADR-0007特化）**、**②アプリ用REST（運用/分析UI）**、**③外部公開REST（F-90）**。GraphQLは基盤には採らず、**必要が実証されれば分析read専用のオプション**として後付けする。

### 2.1 基盤＝REST/JSON/HTTPS

- **リソース指向のREST**（`/fields`, `/worklogs`…）＋**JSON**。HTTPセマンティクス（メソッド・ステータス・キャッシュ・冪等）を活用。
- **バージョニング**：URLパス版（`/api/v1/…`）。破壊的変更はメジャー版で分離。
- **共通規約**：ページング（カーソル方式）、フィルタ/ソート、エラーモデル（RFC 9457 problem+json 準拠）、**冪等キー**（`Idempotency-Key` または本文の `event_uuid`）。
- **認証**：Bearerトークン（詳細はADR-0009）。**権限/tenantはトークンから導出せず、サーバがリクエスト毎に権限を再評価**（ADR-0001/0005・0007の受理時再検証と一致）。

### 2.2 ①専用同期API（ADR-0007を素直に表現）

汎用CRUD RESTではなく、**同期セマンティクスを持つ専用エンドポイント**を設ける（0007の依存束・カーソル・冪等・優先度を1級市民に）：

- **依存束はシャード（tenant）内に閉じる（A8-H1・原子受理の前提）**：0007の依存束は「参照依存の最小単位」で、データモデルの**同一テナントFK**により**必ず単一tenant内**に収まる。受託者が複数テナントを1端末で扱う場合、**アウトボックスをtenant単位に分割**し、**tenant跨ぎの参照依存を作らせない**。これにより束は**単一シャード（DB）で原子受理**でき、分散トランザクションを避ける（ADR-0002 1DB=1国と整合）。
- **tenant跨ぎの業務関連は「独立イベント＋弱参照」で扱う（R2-H1・現場の跨ぎ実態）**：現場では tenant 跨ぎの因果が自然発生し得る（共同倉庫からの出庫が複数tenantの在庫を消費／契約変更で圃場のテナント帰属が変わる／受託者の連続作業がテナントAの圃場→隣接テナントBへ続く）。これらを**参照依存（FK）にせず**：
  - **各tenantに独立の①イベントとして記録**（tenant間にFKを張らない＝同一テナントFK原則を貫く）。共同倉庫は**各tenantの在庫を独立に減算**（按分は上位集計で）。
  - 圃場のテナント変更は**移管イベント**として扱い、記録は各時点のtenantに帰属（跨ぎ参照にしない）。
  - 残る業務的関連は**弱参照（IDのみ・FKなし・整合はアプリ層）**で表現し、**原子受理（束）の対象外**とする（束はあくまでtenant内の強い参照依存のみ）。
  - ADR-0002/0005/データモデルと整合、S7で検証。
- `POST /api/v1/sync/push`：**同一tenantの依存束をバッチで送る**（tenant単位）。サーバは当該tenantのシャードで**束ごとに原子受理**（**全成功 or 全保留のみ・部分成功を返さない**＝A8-M5）、`(tenant_id,event_uuid)` で**冪等**（再送は0件扱い）、受理時に**権限・参照先tenant一致・在庫残高を再検証**。応答は**束単位**の受理/保留（保留は理由コード＋是正アクション、束ごとエラーキューへ＝0007 §2.5.1と1:1）。**複数tenant分は複数バッチ（各シャード独立に成功）**で送る。
- `GET /api/v1/sync/pull?cursor=…&scope=…`：**シャード別の単調カーソル以降の差分**を返す（削除・失効も含む）。**優先度クラス（P0安全/失効）は独立エンドポイント/チャネル**で先行取得可能。スコープ変更時は**追加スコープ分の初回pull**。
  - **読み取り一貫性（R2-M3）**：pull は**スナップショット一貫性**で応答する。**カーソル上限＝取得時点のコミット済み最大 server_seq** に固定し、範囲内は**単一スナップショット**（PostgreSQL MVCC／リピータブルリード）で読む。取得中の新規更新は次回pullに回し、**親は新・子は旧のような部分不整合を返さない**。S7で一貫性を検証。
- 同期APIは**サーバ側でtenant→シャード（DB）へルーティング**（ADR-0002）。カーソルは**シャード単位で単調**、かつ**opaque（不透明）＋サーバ署名**でtenant/スコープ/シャードを内包し改ざんを拒否（A8-M2）。

### 2.3 ②アプリ用REST（運用/分析UI）

- **運用UI**（オフライン）は主に①同期API経由（IndexedDBが真実源）。オンラインの補助取得は②REST。
- **分析UI**（オンライン・サーバ集計）は②RESTの**集計・一覧エンドポイント**（サーバ側集計・カーソルページング）。**GraphQL的な自由クエリは持たせない**（後述の理由）。必要な集計は**用途特化エンドポイント**で提供。
- **特化の増殖を止める判断基準（A8-M4）**：特化エンドポイントが**一定数を超え、かつクライアント要求の多様性が高い分析領域**に限り **read専用GraphQL** を検討する。採る場合も**RLS・コスト制御可能な範囲に限定**（**永続化クエリ・クエリ深さ/コスト上限・N+1対策**必須）。この基準を満たさない限りは特化RESTを維持（無闇に増やさない・移行の手遅れを避ける）。

### 2.4 ③外部公開REST（F-90）＝独立したセキュリティ境界（A8-H2）

外部公開は**越境・情報漏れ・DoSの最大の攻撃面**のため、**独立したセキュリティ境界**として設計する（脅威モデルはADR-0017）：

- **安定版REST**（`/api/v1/public/…`）＋**明示的なバージョニング**。
- **トークン→RLS注入の厳格写像**：外部トークンは **tenant＋スコープ＋許可操作を明示的に保持**し、内部RLSの注入値に**厳格写像**（過剰付与を禁止・内部権限を外部へ拡大しない）。認証フロー（OAuth client credentials 等）は**ADR-0009**で確定。
- **公開範囲の allowlist**：どのリソース/操作を公開するかを**明示的な許可リスト**で管理（既定は非公開）。
- **PII除外・最小フィールドのDTO**：公開DTOは**PIIを除外し最小フィールド**を既定とし、内部で見えるものを外部へそのまま出さない（権限フィルタ）。
- **レート制限は二段**（**APIキー単位＋tenant単位**）で、内部の優先度クラス（0007 P0/P1/P2）を侵食しない。
- Webhook/イベント通知の方式は**ADR-0013**へ委譲（本ADRはRESTの受け口まで）。
- 外部公開は**内部モデルを直接晒さず、公開契約（DTO）を分離**（内部変更から外部を保護）。

### 2.5 単一内部モデルからの投影（A8-M1／R2-M2）

- **単一の内部ドメインモデル（集約）を正**とし、3面は**そこからの一方向の投影（ドメイン集約→各面DTO）**として派生させる。フィールド追加は内部モデルを直し、投影は**1箇所に集約**。**契約テスト（ADR-0021）で3面の整合を担保**。公開DTOのみ意図的に絞る（§2.4 H2）。
- **イベントと状態を無理に一元化しない（R2-M2）**：①同期は**ドメインの変更をイベントとして表現**（追記・不変・event_uuid・順序）、②RESTは**同じ集約の現在状態を表現**（可変・version）。両者は**同じ集約の別ビュー**であり、**状態→イベントの逆写像は行わない**（投影は一方向）。データモデルの不変性3層（ADR-0003：①イベント/②可逆確定）と対応づけ、1つのシリアライズ形式に統一しない。

### 2.6 横断関心を入口層に集約（A8-M3／R2-M1）

- **認証・tenant解決・シャードルーティング・レート制限・カーソル検証・監査**という横断関心は、**単一の入口層（APIゲートウェイ/ミドルウェア）に論理的に集約**する（各エンドポイントに散らさない＝抜けを防ぐ）。
- **単一障害点・特権集中を避ける（R2-M1）**：集約点は**物理的に多重化**（水平スケール・冗長）し、**権限は最小化**する——入口層が担うのは**tenant解決とルーティングまで**で、**実データの権限はDB層のRLSが最終防波堤**（多層防御を維持し、入口層侵害でも越境を許さない）。集約点自体を監査対象に。可用性・冗長化は**ADR-0019**、脅威モデルは**ADR-0017**。

### 2.7 RLS・シャード・性能との接合

- **全API面で、リクエスト毎にサーバがtenant/スコープを注入しRLSを効かせる**（ADR-0001。クライアントの主張を信用しない）。集約点は§2.6。
- **ルーティング**：tenant→シャード（1DB=1国/グループ）へ（ADR-0002）。カーソル・冪等は**シャード内で完結**。
- **性能**：一覧はカーソルページング＋サーバ集計。**キャッシュ（A8-L1）**：認証必須リソースは `Cache-Control: private`/`no-store`＋`Vary: Authorization`（テナント/権限別レスポンスを共有キャッシュ/CDNに載せず越境漏れを防ぐ）、公開リソースのみ共有キャッシュ可（ADR-0002 CDNもデータ経路）。地図データ（ADR-0010）は空間クエリ特化エンドポイント。
- **バージョニングとオフライン版ずれ（A8-L2）**：**Nメジャー版の後方互換期間**を定め、同期APIは**版ネゴシエーション**（古すぎる端末は更新要求）。0006のSW更新と接合。
- **カーソル署名鍵のローテーション（R2-L1）**：opaqueカーソルの署名鍵は**世代管理**（旧鍵で検証可能な猶予期間）。失効時は**スコープ別フルpullへフォールバック**（0007のスコープ拡大pullと同型）。鍵管理はADR-0017と接合。
- **エラーモデルの統一（A8-L3）**：**共通エラーカタログ**（コード・是正アクション・再試行可否）を problem+json で定義し、①同期の差し戻し理由（0007 §2.5.1）と**一本化**する。
- **公開範囲変更とバージョニング（R2-L2）**：公開allowlistの**縮小は破壊的変更（メジャー版＋非推奨期間）**、拡大は互換とし、変更を外部向けチェンジログで告知（§2.4）。

## 3. 検討した選択肢（Options）

| 観点 | 選択肢 | 評価 |
|---|---|---|
| 基盤方式 | **REST（採用）** ／ GraphQL ／ gRPC | ◎ RESTはHTTPキャッシュ・冪等・相互運用（外部F-90）・自前ホストの標準性に強い。GraphQLは分析の柔軟クエリに強いが**キャッシュ/レート制御が難しく、外部公開・オフライン同期と噛み合わない**。gRPCは高速だがブラウザ/外部相互運用で不利 |
| 同期の表現 | **専用同期API（採用）** ／ 汎用CRUD REST ／ GraphQL mutation | ◎ 0007の依存束・カーソル・冪等・優先度は**専用エンドポイントが最も素直**。汎用CRUDだと束の原子性・カーソルを毎回作り込む。GraphQLは束/カーソルの表現が不自然 |
| 分析クエリ | **用途特化REST集計（採用）** ／ GraphQL自由クエリ | ○ 特化エンドポイントは**RLS・性能・キャッシュを制御しやすい**。GraphQL自由クエリは**RLS配下でN+1・コスト爆発・权限漏れ**の温床。必要が実証されたら**read専用GraphQL/BFFを後付け**（オプション） |
| 外部公開 | **バージョン付きREST＋DTO分離（採用）** ／ 内部APIをそのまま公開 | ◎ 公開契約を内部から分離し安定性/セキュリティを確保。内部直結は破壊的変更・情報漏れリスク |

**却下理由**：GraphQLを基盤にすると、(1)**オフライン同期の依存束・カーソル・優先度**が不自然、(2)**外部公開（F-90）**でGraphQLは相互運用性・レート制御・キャッシュが弱い、(3)**RLS配下の自由クエリ**はコスト/権限漏れの危険。gRPCはブラウザ/外部で不利。よってRESTを基盤とし、分析の柔軟性が本当に必要になったら**read専用GraphQLをオプション**で足す（基盤は据え置き）。

## 4. 影響・帰結（Consequences）

**良い影響**
- 0007の同期モデルを**専用APIで1:1に表現**でき、実装・テスト・可観測性が素直。
- 外部公開（F-90）・自前ホスト・相互運用でREST標準の恩恵。HTTPキャッシュ/冪等が効く。
- RLS・シャード・性能の制御点が明示的（自由クエリの闇を避ける）。

**悪い影響・制約**
- **分析UIの柔軟性**は特化エンドポイントの追加で対応するため、**エンドポイント数が増える**（GraphQLなら1本で済む面）。将来read GraphQL追加の判断が要る。
- **専用同期APIの独自性**：標準CRUDでない分、クライアント/サーバ双方に**同期プロトコルの作り込み**が要る（ただし0007で不可避）。
- **API面が3つ**（同期/アプリ/公開）で**契約・バージョニング・DTO変換**の維持コスト。
- gRPC不採用で**内部マイクロサービス間**が高速RPCを使いたい場合は別途検討（現状モノリス寄りなら不要）。

## 5. 未解決事項（設計/実装で詰める）

- **同期APIの詳細契約**（push束の形＝tenant内・**束は原子で部分成功なし**、pullカーソルの opaque 符号化/署名・**pullのスナップショット一貫性**、tenant跨ぎ＝独立イベント＋弱参照）を0007と一体で確定し、**スパイクS7で検証**（A8-H1/M2/M5/R2-H1/R2-M3の実装確認）。
- **外部公開の脅威モデルと認証フロー**（トークン→RLS写像・allowlist・PII除外DTO・二段レート制限）を**ADR-0017/0009/0013**で確定（A8-H2の実装）。
- **横断関心の集約点の実装形態**（APIゲートウェイ別サービス vs アプリ内ミドルウェア）を**ADR-0019**で（A8-M3）。
- read GraphQL/BFF を足す**具体的な閾値**（特化本数・多様性）の運用判断（A8-M4の基準は決定済、数値は運用で）。
- **OpenAPI等のスキーマ定義**とコード生成・契約テスト（3面の投影整合＝A8-M1）（ADR-0021）。
- 共通エラーカタログの具体（コード体系・再試行可否）を0007 §2.5.1と一本化（A8-L3）。
