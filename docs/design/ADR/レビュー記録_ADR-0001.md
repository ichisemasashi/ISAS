## 🟠 High

### A1-H1. セッション変数のリセット漏れ＝プール接続でのテナント文脈リーク
- **該当箇所**：決定「セッション変数方式（`SET app.tenant_id`）」
- **指摘（攻撃）**：接続プールでは1つの物理接続が複数リクエスト（複数テナント）で使い回される。`SET app.tenant_id`（**セッションレベル**）はコミット後も接続に残るため、**次に同じ接続を borrow したリクエストが前のテナントの文脈を引き継ぎ、別テナントのデータを読む/書く**危険がある（RLS＋プーリングの典型事故）。ADRは「設定漏れ＝分離破綻」までは書いたが、**リセット漏れ／使い回しリーク**を扱っていない。
- **要修正**：決定に「**トランザクション境界の `SET LOCAL app.tenant_id`（トランザクション終了で自動失効）を用いる**、または**接続返却時に必ずリセット**する」を明記。全クエリをテナント設定済みトランザクション内で実行する共通機構を必須とする。

### A1-H2. フェイルクローズ／FORCE RLS／非所有者ロールが「未解決」止まり
- **該当箇所**：決定＋未解決事項（BYPASSRLS）
- **指摘（攻撃）**：RLSは以下を満たさないと**サイレントに無効化**される。ADRではこれらが「未解決」に置かれ、決定に含まれていない：
  1. **FORCE ROW LEVEL SECURITY 未設定**だと、**テーブル所有者はRLSをバイパス**する。アプリがテーブル所有者ロールで接続すると分離が効かない。
  2. **`app.tenant_id` 未設定時の挙動**が未定義。ポリシーが `current_setting(..., true)`（missing_ok）でNULL→比較が真になる書き方だと**フェイルオープン（全件見える）**。
  3. アプリ接続ロールが**スーパーユーザー/所有者**だとRLSが効かない。
- **要修正**：決定に格上げして明記：①全業務テーブルに **`FORCE ROW LEVEL SECURITY`**、②**未設定時は全拒否（フェイルクローズ）**のポリシー既定、③**アプリは非所有者・非スーパーユーザー・非BYPASSRLSロール**で接続、マイグレーション等の特権は別ロール。

## 🟡 Medium

### A1-M1. グループ管理者の横断ポリシーの性能
- **該当箇所**：決定「グループ管理者＝tenant_id集合ベースで横断」
- **指摘（攻撃）**：横断許可を「そのユーザーがアクセス可能なtenant_id集合」に基づくRLSポリシーで表すと、**行ごとにメンバーシップ参照のサブクエリ**が走り、大規模テーブル（5万ユーザー規模の作業日誌等）で性能劣化しうる。集計はマテビューに逃がすとあるが、**明細の横断参照**の読み取り経路が未検討。
- **要修正**：許可tenant_id集合をセッション変数（配列）に事前解決して注入する等、行単位サブクエリを避ける方針を検討事項に追記。

### A1-M2. 複数permissiveポリシーのOR結合
- **該当箇所**：決定「テナント分離ポリシー＋本人起点横断（user_id）ポリシー」
- **指摘（攻撃）**：同一テーブル（労務サマリ）に複数のRLSポリシーを付けると、既定で**OR結合（permissive）**され、いずれか1つが真なら許可になる。テナント分離と本人起点横断の**組み合わせが意図せず参照範囲を広げる**恐れ（例：本人ポリシーが他テナント行まで許可し、テナント分離を上書き）。相互作用が未検討。
- **要修正**：ポリシーのpermissive/restrictiveの使い分け、対象テーブルごとの適用ポリシーの明示を検討事項に追記。労務サマリ限定の範囲をポリシーで厳密化。

### A1-M3. tenant_scopedとsystem-globalテーブルの区別
- **該当箇所**：決定「全業務テーブルにtenant_id」
- **指摘（攻撃）**：**すべてのテーブルがtenant_scopedとは限らない**。国レベルで共有し得るマスタ（例：農薬肥料マスタ／作物マスタ／多言語ラベル）は、テナント横断で共有するか、テナント固有かで設計が変わる。「全テーブルtenant_id必須」と国レベル共有データの存在が噛み合わず、区別ルールがない。
- **要修正**：テーブルを「テナント固有／システム共有（tenant_idなし・全員読取）／テナント上書き可能な共有」に分類する規約を追記。

## 🟢 Low

### A1-L1. 「1DB内テナント数＝数百」前提の境界
- **該当箇所**：選択肢比較の前提「1DB内テナント数は数個〜数百」
- **指摘**：要求仕様#13でOSS運用者は**第三者へのサービス提供（SaaS）も許容**。SaaS運用者が1DBに数千テナントを収容する運用も起こりうるため、DB分離却下の前提（数百）が崩れる場面がある。
- **要修正**：前提の境界と、崩れた場合の指針（ハイブリッドD案・スケールアウト）を注記。

### A1-L2. オフライン端末側のデータ分離
- **該当箇所**：決定「オフライン同期APIで tenant_id を通す」
- **指摘**：サーバ側はRLSで守れるが、**端末（オフライン）側にRLSはない**。複数テナントに所属するユーザー（受託作業者）の端末には複数テナントのデータが載るため、端末内の分離・暗号化はADR-0007（オフライン同期）と連携が必要。
- **要修正**：端末側データ分離はADR-0007で扱う旨の相互参照を追記。

## 処置方針（推奨）

1. **A1-H1・A1-H2 は決定本文に格上げして即反映**（RLSが実際に機能するための必須条件。実装の落とし穴を決定で塞ぐ）。
2. **A1-M1〜M3** は決定の補足＋未解決事項へ追記。
3. **A1-L1・L2** は前提の注記・相互参照。

> 総括：方向性（行レベル＋RLS）は妥当だが、**RLSを「実際に効かせる」ための3条件（SET LOCAL/リセット・FORCE RLS・フェイルクローズ・非所有者ロール）が決定に欠けており、このまま実装すると分離がサイレントに破綻**する。High 2件を決定へ反映すれば、ADRとして安全な基盤になる。

## 🟡 Medium（第2回）

### A1b-M1. 許可tenant_id集合のアプリ事前解決が横断経路の防波堤性を弱める
- **該当箇所**：決定「グループ管理者：許可tenant_id集合をセッション変数（配列）に事前解決して注入」
- **指摘（攻撃）**：A1-M1の性能対策として、横断許可を「アプリが計算したtenant_id集合」の注入に依存させた。しかしこれは、A1-H2で掲げた「**RLS＝アプリのバグに対する最後の防波堤**」という性質を**横断経路では弱める**：アプリの集合計算にバグ（本来アクセス不可のテナントを含める）があれば、RLSはその集合を信じてしまい**誤った横断アクセス**を許す。防波堤がアプリ入力に依存する自己矛盾。
- **要修正（案）**：注入する集合の正当性をDB側で検証する（例：注入集合とメンバーシップ表の突合をポリシー内 or トリガで確認）、または集合をアプリ入力ではなく**DB内のメンバーシップ由来で導出**する方式（性能はマテビュー/キャッシュで両立）を検討事項に追加。「防波堤性」と「性能」のトレードオフを明示する。

### A1b-M2. 「共有＋テナント上書き可能」テーブルとフェイルクローズの衝突
- **該当箇所**：決定「テーブル3分類：共有＋テナント上書き可能（tenant_id NULL=共有、非NULL=上書き）」＋「フェイルクローズ：tenant_id未一致は全拒否」
- **指摘（攻撃）**：3番目の分類は tenant_id が **NULL 可**（NULL=全テナント共有の既定行）。しかしフェイルクローズの単純ポリシー（`tenant_id = current`）では、**NULL行（共有）が誰にも見えなくなる**（NULL比較が真にならないため）。共有マスタが全テナントで見えないのは機能破綻。この分類には「**tenant_id IS NULL（共有）OR tenant_id = current（自テナント上書き）**」という別ポリシーが要り、フェイルクローズ規則と個別に整合させる必要がある。
- **要修正（案）**：3番目の分類の専用ポリシー（NULL共有の可視化＋自テナント上書きの優先）を明記し、「共有行は全テナント可視だが書込は特権のみ」という書込側の制御も定義する。

## 🟢 Low（第2回）

### A1b-L1. SET LOCAL のトランザクション前提
- **該当箇所**：決定「SET LOCAL app.tenant_id」
- **指摘**：`SET LOCAL` は**トランザクション内でのみ有効**（自動コミットの単発クエリでは無効＝未設定＝フェイルクローズで全拒否）。つまり**単純な読取も含め全DBアクセスを明示トランザクションで包む**必要がある。またコネクションプーラ（PgBouncer等）は**トランザクションプーリングモード**である必要（セッションプーリングだと SET LOCAL の前提や他の想定が崩れる）。この含意が未明記。
- **要修正（案）**：「全DBアクセスは明示トランザクション内」「プーラはトランザクションプーリング」を前提として明記。

### A1b-L2. フェイルクローズのエッジ（空文字列）
- **該当箇所**：決定「app.tenant_id 未設定/NULLは全拒否」
- **指摘**：未設定は `current_setting(..., true)` で NULL になるが、**空文字列がセットされた場合** `''::uuid` は**エラー**になり、NULLとは異なる挙動（クエリ失敗）。NULL・空文字・不正値の扱いを実装で統一しないと、想定外のエラーやフェイルの穴が生じうる。
- **要修正（案）**：「未設定・空文字・不正値はすべて全拒否として扱う（安全側）」と実装ルールを明記。

## 処置方針（第2回・推奨）

1. **A1b-M1・A1b-M2** は決定の精緻化（防波堤性と性能のトレードオフ明示、3番目分類の専用ポリシー）として反映。
2. **A1b-L1・A1b-L2** は前提・実装ルールの明記。

> 総括：第1回のHigh 2件は解消済み。第2回は「性能対策が防波堤性を弱める」「共有テーブルがフェイルクローズと衝突」という**二次的な設計トレードオフ**が中心で、High相当の破綻はない。これらを精緻化すればADR-0001は安定。RLSは「効かせるのが難しい」機構であり、こうした二次論点が出るのは想定内。

## 🟡 Medium（第3回）

### A1c-M1. DB側検証の実装が行単位サブクエリ性能問題を復活させる循環
- **該当箇所**：決定「注入集合の正当性をDB側で検証する（ポリシー内 EXISTS 参照または SECURITY DEFINER 関数）」
- **指摘（攻撃）**：A1-M1では**行単位サブクエリを避けるため**に許可集合をセッション変数に事前注入した。ところがA1b-M1の是正で「注入集合の正当性を**ポリシー内 EXISTS で検証**」とすると、**その EXISTS が行ごとに評価され、A1-M1で回避したはずの行単位サブクエリ性能問題が復活**する（是正が元の問題に戻る循環）。
- **要修正（案）**：検証は**行単位ではなく「集合注入時に1回」**行う——リクエスト冒頭で `SET LOCAL` する前に、注入しようとするtenant_id集合が当該user_idのメンバーシップに包含されることを**1クエリで検証**し、検証済みの集合のみを注入する。ポリシー本体は**注入済み集合との包含判定のみ**（サブクエリなし）に保つ。これで「防波堤性（注入は検証済み）」と「性能（ポリシーはサブクエリなし）」を両立する。

## 🟢 Low（第3回）

### A1c-L1. ③「上書き優先解決」の責務はRLSではない
- **該当箇所**：③共有＋テナント上書き可能「上書き行を優先して解決」
- **指摘**：RLSは**行の可視性**を制御するだけで、「共有行と上書き行のどちらを採用するか」は決めない。ポリシー適用後は両行とも可視であり、**上書き優先はクエリ/ビュー側のロジック**（自テナント行があればそれ、なければ共有行）。責務が混在している。また、共有行（tenant_id NULL）と上書き行の**一意制約**設計（tenant_idを含む一意キー、NULL重複の扱い）が必要。
- **要修正（案）**：「可視性はRLS、上書き優先の解決はビュー/クエリ」で責務を分離し、一意制約設計を検討事項に追加。

### A1c-L2. ②共有マスタ書込の特権ロール運用
- **該当箇所**：②システム共有「書込は特権ロールのみ」
- **指摘**：アプリの通常接続は非所有者・非BYPASSRLSロール（A1-H2）。共有マスタの書込は「特権ロール」だが、アプリがどのように**ロールを切り替える/別接続を使う**かが未定義。運用複雑性が生じる。
- **要修正（案）**：共有マスタ書込は管理用の別接続/別ロール経由（通常のテナント接続からは書けない）と運用を明記。

### A1c-L3. トランザクションプーリングの既知制約
- **該当箇所**：前提「PgBouncer等トランザクションプーリング」
- **指摘**：トランザクションプーリングでは**セッション単位のprepared statements・LISTEN/NOTIFY・advisory lock**が期待通り動かない既知制約がある。ORM/ドライバがこれらに依存すると不具合になる。
- **要修正（案）**：ドライバ/ORMの設定（prepared statement無効化 or サーバサイド準備の扱い）とLISTEN/NOTIFY非依存を前提として明記。

## 処置方針（第3回・推奨）

1. **A1c-M1** は決定の精緻化（検証は集合注入時に1回・ポリシーはサブクエリなし）として反映。防波堤性と性能の両立を確定させる。
2. **A1c-L1〜L3** は責務分離・ロール運用・プーラ制約の明記。

> 総括：3回のレビューで High は 2→0→0 と解消・維持。第3回は「是正が元の性能問題に循環する」1点（A1c-M1）と実装運用の詰め（Low 3）に収れんした。A1c-M1を反映すればADR-0001は**実装可能な確定版**として十分。以降の詳細（一意制約・ロール運用・ドライバ設定）はデータモデル設計（M3）で具体化するのが自然で、**ADR単体のレビューはこの回で概ね底**。次ADR（0002）へ進んでよい。

## 🟡 Medium（第4回）

### A1d-M1. 書込側RLS（WITH CHECK）が未記載
- **該当箇所**：決定全体（USING＝読取可視性中心で、INSERT/UPDATE/DELETEのWITH CHECKが未記載）
- **指摘（攻撃）**：ADRのRLS議論は一貫して**読取（行の可視性＝USING）**に集中しており、**書込側（WITH CHECK）**が全版で欠落している。RLSはWITH CHECKを併せて定義しないと：
  - **INSERT時にtenant_idを詐称**（他テナントのtenant_idで行を作る）できる。
  - **UPDATEでtenant_idを書き換え**、行を別テナントへ移送できる。
  - ③テーブルで、**一般テナント接続がtenant_id IS NULL（共有）行を書き込む**のを防げない（v4は「共有書込は特権のみ」と意図を書いたが、それを担保するのはWITH CHECK）。
- **影響**：読取は分離できても**書込で越境・詐称・共有汚染**が起きうる。分離の片翼が抜けている。
- **要修正（案）**：決定に「**各RLSポリシーはUSING（読取）とWITH CHECK（書込）の両方を定義**する」を追加。①テナント固有＝`WITH CHECK (tenant_id = current)`（自テナント以外への書込・移送を拒否）、③＝一般接続は`WITH CHECK (tenant_id = current)`（NULL共有行の書込を拒否）、共有行の書込は特権ロールのみ、を明記。

## 🟢 Low（第4回）

### A1d-L1. SECURITY DEFINER関数の安全な実装
- **該当箇所**：決定「注入集合をSECURITY DEFINER関数で検証」
- **指摘**：SECURITY DEFINER関数は定義者権限で動くため、**search_path未固定だと関数注入の攻撃面**になる（PostgreSQLの既知の注意点）。権限も最小化が必要。
- **要修正（案）**：SECURITY DEFINER関数は`search_path`を固定し、最小権限で定義する実装ルールを追記。

### A1d-L2. ③一意制約のsentinel衝突
- **該当箇所**：決定「③一意制約 `COALESCE(tenant_id, 既定値)`」
- **指摘**：COALESCEのsentinel（既定値）が万一**実tenant_idと衝突**すると一意制約が誤動作する。UUIDのnil値等でも運用次第で危うい。
- **要修正（案）**：sentinel方式より**部分一意インデックス**（共有行用 `UNIQUE(key) WHERE tenant_id IS NULL` ＋ テナント行用 `UNIQUE(key, tenant_id) WHERE tenant_id IS NOT NULL`）の方が安全、と代替を検討事項に追記。

## 処置方針（第4回・推奨）

1. **A1d-M1** は決定に反映（USINGとWITH CHECKの両方を定義する原則＝分離の書込側を塞ぐ。重要）。
2. **A1d-L1・L2** は実装安全性の明記／代替検討。

> 総括：4回のレビューで High は 2→0→0→0。第4回は「レビューが読取中心で書込側RLSを見落としていた」というメタな気づき（A1d-M1）が最大の収穫で、これは分離の完全性に関わるため反映価値が高い。反映後はADR-0001の**分離モデル（読取・書込の両側）が閉じ**、確定版として十分。以降の実装詳細はデータモデル設計（M3）へ。**A1d-M1反映をもってADR-0001はクローズし、ADR-0002へ進むのが妥当**。

## 🟡 Medium（第5回）

### A1e-M1. 認証・ブートストラップ読取の鶏卵問題
- **該当箇所**：決定「フェイルクローズ（未設定は全拒否）」＋「横断許可の集合注入時検証」
- **指摘（攻撃）**：フェイルクローズにより、`app.tenant_id` が設定される**前**は何も読めない。ところが「どのテナントを設定すべきか（ユーザーの所属・メンバーシップ・グループ管理者の許可集合）」を知るには、**まずユーザー／メンバーシップ表を読む**必要がある。この**ブートストラップ読取が、テナント設定前でフェイルクローズに自己ブロックされる**（鶏と卵）。設計として明示しないと、**ログイン/セッション確立自体が不能**になる。
- **影響**：認証・セッション確立の経路が塞がれる（実装初日に必ず突き当たる）。
- **要修正（案）**：**ブートストラップ（認証時のテナント/メンバーシップ解決）は、RLS対象外の特権経路で行う**ことを明記する。具体には、認証・所属解決を**SECURITY DEFINER関数**（集合検証関数と同系）または**認証用の専用ロール/スキーマ**で実行し、テナント確定後に `SET LOCAL app.tenant_id` して以降の業務クエリに入る、という二段構えを決定に追記する（ADR-0009 認証とも連携）。

## 🟢 Low（第5回）

- **指摘**：PostgreSQLの**FK制約チェックはRLSをバイパス**して評価される。テナント跨ぎになり得るFKや、FK違反のエラー/タイミングを使うと、**他テナントに特定IDが存在するかを推測**できる情報漏れの余地がある。
- **要修正（案）**：FKは原則同一テナント内に閉じる設計とし、テナント跨ぎFK（共有マスタ参照等）は情報漏れを踏まえたエラーハンドリングを検討事項に追記。

### A1e-L2. PKの非連番化
- **該当箇所**：決定全体（PK方式が未記載）
- **指摘**：連番（serial/bigserial）PKは、値から**行数やクロステナントの規模**を推測でき、URL露出時に列挙も容易。

## 🟠 High（第6回）

### A1f-H1. デフォルト拒否ポリシー＋FORCE RLS で特権経路が自己ブロックする
- **該当箇所**：v8 §2【v8】「**デフォルト拒否のポリシーを置く／通常ロールに権限を与えない**」「**FORCE RLS の対象外にする例外ではなく**、『通常ロールからは何も見えない』ことをテストで担保する枠として扱う」／§2 A1-H2「**全業務テーブルに `FORCE ROW LEVEL SECURITY` を設定**する。これがないとテーブル所有者はRLSをバイパスする」／§2 A1e-M1「認証・所属解決は**SECURITY DEFINER関数**…で実行する。これがないと**ログイン/セッション確立自体がフェイルクローズで自己ブロックされる**」
- **指摘（攻撃・権限軸）**：PostgreSQL の実際の動作と突き合わせると、v8 の記述は**矛盾しているか、実装すると壊れる**。
  1. **自己ブロック**：`ENABLE ROW LEVEL SECURITY` されたテーブルで**マッチするポリシーが無ければ0行**（デフォルト拒否）。テーブル所有者はRLSをバイパスできるが、**`FORCE ROW LEVEL SECURITY` を付けると所有者もバイパスできない**（A1-H2 がまさにその目的で導入した）。SECURITY DEFINER 関数は**関数所有者の権限で実行される**ため、関数所有者＝テーブル所有者であっても **FORCE RLS ＋ デフォルト拒否ポリシー**の下では**0行しか返らない**。つまり**特権経路自身が拒否され、ログインできない**——これは A1e-M1 が「これがないと自己ブロックされる」と警告した、まさにその失敗である。**A1e-M1 と同じ扱いにするつもりで、A1e-M1 が回避した罠を再導入している。**
  2. **FORCE RLS を設定するのか否かが確定していない**：line36 は「**全業務テーブル**に FORCE RLS」であり、v8 の line47 が「上記4分類は**業務テーブル**の分類」と限定したことで、**特権経路専用テーブルは line36 の対象外**と読める。ところが line58 は「**FORCE RLS の対象外にする例外ではなく**」と述べる。**両者は食い違っている**。
  3. **道具の選択が誤っている**：RLSは**行の可視性**を制御する仕組みである。今回やりたいのは「**このテーブル全体を、特権ロール以外には一切見せない**」——これは**テーブル単位の権限**であり、正しい道具は **`REVOKE`/`GRANT`**（`REVOKE ALL ON <索引> FROM <アプリ通常ロール>; GRANT SELECT ON <索引> TO <認証専用ロール>;`）である。RLSで表現しようとすると、上記のとおりFORCE RLSとの相互作用で自己ブロックするか、逆に「特権ロールを許すpermissiveポリシー」を書くことになり**実質GRANTと同じことを二重に書く**。
- **影響**：素直に実装すると**ログインできない**（最も重い形の破綻）。回避しようとした実装者は FORCE RLS を外すが、v8 は「例外ではない」と書いているため**文書と実装が食い違ったまま進む**。あるいは「特権ロールを許すポリシー」を書くが、そのポリシー式を誤ると**通常ロールにも見えてしまう**（RLSポリシーはロール指定を誤りやすい）。
- **要修正（案）**：**守り方を GRANT ベースに書き換える**。
  - **特権経路専用テーブルは `REVOKE ALL FROM アプリ通常ロール`／`GRANT SELECT TO 認証専用ロール（または SECURITY DEFINER 関数の所有者）` で守る**、と明記する。**RLSポリシーは不要**（テーブル単位で遮断するため、行の可視性の問題が存在しない）。
  - **FORCE RLS の要求対象を明確化**：line36 を「**全業務テーブル（①〜④）**に FORCE RLS」と限定し、**特権経路専用テーブルはRLSではなくGRANTで守る枠**であると line58 を書き換える（「例外ではない」という表現を撤回する——**RLSの枠外にあることを正直に認め、代わりにGRANTで担保する**）。
  - **多層防御を保ちたい場合の追加オプション**：RLSも併用するなら「**FORCE RLS は付けず**、`ENABLE RLS`＋特権ロールに `USING (true)` の permissive ポリシー」とし、**所有者バイパスを自己ブロック回避の逃げ道として残す**。ただし**GRANTだけで十分**であり、複雑さの割に得るものが少ないことを注記する。
  - **ポリシーテストの内容も書き換える**：「通常ロールから読めないこと」の期待は **0行ではなく権限エラー（`permission denied`）** である。テストの期待値を明記する（0行を期待するテストは、GRANTを誤って与えたときに合格してしまう）。

## 🟠 High（第7回）

### A1g-H1. GRANTベース化で網羅的な検出手段が失われた
- **該当箇所**：v9 §2【v9】「守り方は `GRANT/REVOKE`。RLSでは守らない」「`REVOKE ALL ON <テーブル> FROM <アプリ通常ロール>`／`GRANT SELECT ON <テーブル> TO <認証専用ロール>`」／v9 §2【v9】テスト「期待するのは0行ではなく `permission denied`」／v9 §5「特権経路専用テーブルの一覧化」／v9 §4「**この枠に限りRLSの防波堤は存在せず、権限付与の誤りが直接漏えいになる**」
- **指摘（攻撃・権限軸／処置の副作用）**：道具の選び直し（RLS→GRANT）は正しかったが、**RLSが持っていた「網羅検査できる」という性質を失ったことが評価されていない**。
  1. **RLSは列挙なしで検査できた**：`pg_class.relrowsecurity` / `relforcerowsecurity` を走査すれば「**RLSが有効でないテーブルは無いか**」を、テーブル一覧を人が維持せずに検査できる。A1-H2 の自動テストはこの性質に立っていた。**GRANT ベースでは「一覧に載っているテーブルを個別に `permission denied` テストする」形になり、一覧から漏れたテーブルは検査されない**。
  2. **「GRANTしない」は能動的に維持しないと守れない**：新規テーブルの権限は既定では所有者のみだが、実運用のマイグレーションでは **`GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_role`** や **`ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO app_role`** が使われるのが通例である。**後者を設定していれば、以後 `public` に作られる特権経路専用テーブルにも自動的に SELECT が付く**——「GRANTしない」という前提が、**運用の一括付与によって静かに上書きされる**。RLSの「デフォルト拒否」とは安全性の向き方が違う（RLSは付け忘れれば拒否側に倒れるが、GRANTは一括付与で許可側に倒れる）。
  3. **§4 でこの枠に防波堤がないと認めた以上、検出が唯一の防御**である。その検出が「人手の一覧」＋「個別テスト」では、**A1f-M1 で申し送った ADR-0017 の脅威モデルに渡せる保証がない**。
- **影響**：索引テーブル（法域内全ユーザーの取引関係グラフ＝ADR-0002 が機密資産と認定）に**誤って SELECT が付き、全テナント利用者が読める**。RLSも防波堤もなく、テストも一覧漏れで走らない——**気づく手段がないまま漏えいし続ける**。ADR-0001 の最も重要な性質（アプリバグへの最後の防波堤）が、最も機密性の高いテーブルで成立しない。
- **要修正（案）**：**個別テーブルのGRANTではなく、スキーマ単位の遮断＋網羅検査**に切り替える（RLSの網羅性と同等の強度を、GRANTの世界で再構成する）。
  1. **特権経路専用テーブルは専用スキーマに置く**（例：`priv`）。**通常ロールにそのスキーマの `USAGE` を与えない**——スキーマ `USAGE` が無ければ、**個別テーブルに誤って `GRANT` が付いていてもアクセスできない**（二重の防御。個別GRANT漏れに耐える）。
  2. **`ALTER DEFAULT PRIVILEGES` は当該スキーマに設定しない**、かつ **`GRANT ... ON ALL TABLES IN SCHEMA` の対象から当該スキーマを除外**することを、マイグレーション規約として明記する。
  3. **網羅検査を自動テスト化**：`information_schema.role_table_grants`（および `has_schema_privilege`）を走査し、**「`priv` スキーマのオブジェクトに対して通常ロールが持つ権限が1件も無いこと」「通常ロールが `priv` スキーマの `USAGE` を持たないこと」**を検査する。**テーブルを列挙しないため、新規テーブルが増えても自動的に検査対象になる**——これでRLSの `relrowsecurity` 走査と同等の網羅性が得られる。
  4. 逆向きの検査も置く：**`priv` 以外のスキーマに、通常ロールから読めない業務テーブルが存在しないこと**（＝分類ミスで業務テーブルを `priv` に置いてしまい業務が動かなくなる事故の検出。A1f-M2 の一覧化基準と対応）。
  5. §5 の「一覧化」は**人手の管理台帳から、スキーマという物理的な区画**へ格下げする（一覧は文書化のためには残すが、**強制力はスキーマとテストに持たせる**）。

## 🟡 Medium（第7回）

### A1g-M1. 書込用 SECURITY DEFINER 関数の検証条件が不十分
- **該当箇所**：v9 §2【v9】「書込も SECURITY DEFINER 関数経由（A1f-L3）」「**自シャードの行しか書けないことを関数内で検証**する」／ADR-0002 v8「索引は**上位集合保証**（漏れは許さず、余りは許す）」「書込＝加入先シャードのローカルTXのみ」
- **指摘（攻撃・権限軸）**：この関数は**通常ロールから EXECUTE できなければ用を為さない**（メンバーシップ付与と同一トランザクションで呼ぶため）。つまり「**通常ロールから呼べる、テーブル所有者権限で動く関数**」が存在する＝権限昇格の踏み台になり得る。v9 の検証条件は「自シャードの行しか書けない」だけで、**引数（`user_id` 等）を信用してよいのかが規定されていない**。
  - **追加（false positive）方向の細工は比較的無害**：他人の `user_id` を自シャードに紐づけても、そのシャードにメンバーシップが無いのでRLSが拒否し**漏洩しない**（上位集合保証の「余りは安全」がここで効く）。ただしファンアウト先が膨らむ**DoS/性能**の面はある。
  - **削除方向の細工が本質的な穴**：**他人の索引行を削除できると、そのユーザーのファンアウト先からシャードが落ち、データが見えなくなる**——**ADR-0002 が「漏れ（false negative）は許さない」と定めた上位集合保証を、外部から意図的に破れる**。RLSは漏洩を防ぐが**欠落は防げない**（ADR-0008 IND-M2 と同じ性質）。労務・給与の権威確定は全シャードファンアウトなので影響しないが、**日常の横断read が静かに欠ける**（気づきにくい）。
  - さらに、「自シャードのみ」という条件は**接続先DBから自明**であり、**本当に検証すべき条件を書いていない**——それは「**引数の `user_id` が、このシャード内のいずれかのテナントに実際にメンバーシップを持つ（追加時）／持たない（削除時）**」である。この条件は同一DB内のメンバーシップテーブルから判定できる。
- **要修正（案）**：**関数に「何を書くか」を渡さず、メンバーシップから導出させる**。
  - `refresh_user_shard_index(user_id)` の形とし、**関数が同一DBのメンバーシップテーブルを見て、当該 `user_id` の索引行を「あるべき状態」に収束させる**（メンバーシップがあれば行を保証、無ければ削除）。**呼び出し側は「どう書くか」を指示できない**ため、引数細工で任意の追加・削除ができない。
  - `user_id` 自体の細工は残るが、**他人の `user_id` を渡してもメンバーシップに従って収束するだけ**なので、状態を誤らせられない（冪等・宣言的）。
  - 関数は `search_path` 固定・最小権限（A1d-L1）。**`EXECUTE` 権限は通常ロールに与えるが、それが安全であることを上記の導出設計で担保する**、と明記する。
  - **監査**：索引の変更（追加/削除）は書込なので**トリガで捕捉できる**（SELECTと違う）。ハッシュチェーン監査の対象に含める。

### A1g-M2. §4に書いた例外が §1背景・§2決定文に届いていない
- **該当箇所**：v9 §4「【v9】特権経路専用テーブルはRLSの防波堤の外にある」（追記あり）／**§1 背景 line21「WHERE句の付け忘れ等でも他テナントのデータが漏れない『最後の防波堤』が欲しい」（追記なし）**／**§2 決定 line30「**RLSポリシー**でDB層のアクセス制御を強制する（アプリ層のWHERE句に依存しない最後の防波堤）」（追記なし）**
- **指摘**：A1f-M1 の処置として §4 に例外を明記したのは正しいが、**§2 の決定文は依然として無条件に「最後の防波堤」と述べている**。ADRで最も読まれるのは決定文（§2 冒頭）であり、**そこに例外がないと、読み手は§4まで読まないと例外に気づけない**。
  - これは **ADR-0002 第5回 A2f-L3（追記が帰結・未解決事項に届いていない）→ ADR-0001 第6回 A1f-M1（§5には届いたが§4に届いていない）→ 今回（§4には届いたが§1/§2に届いていない）**と、**3回連続で同型が再発**している。**「どこまで行き渡らせるか」の基準が定まっていない**ことが根にある。
- **要修正（案）**：
  - §2 line30 に一文加える：「**ただし認証・所属解決が使う特権経路専用テーブルはこの防波堤の外にあり、テーブル権限（GRANT）とスキーマ分離で守る**（下記【v9】・§4）」。
  - §1 line21 の「最後の防波堤が欲しい」に「（**テナント文脈が確定する前に参照が必要な認証経路は原理的に例外となる**）」と注記。
  - **運用ルールとして「追記の行き渡り先」を定義する**：ADRに決定を追記したら、**①§1背景の前提が変わらないか、②§2の総論的な決定文と矛盾しないか、③§3選択肢に記録すべき裁定か、④§4帰結、⑤§5未解決事項、⑥関連する既存決定の射程**——この6箇所を必ず確認する（開発工程の教訓へ追加）。

### A1g-M3. 未認証の参照監査が攻撃者制御下の量に比例する
- **該当箇所**：v9 §2【v9】監査「認証前の参照は actor が確定していない…**主張された `user_id` ＋ 接続元 ＋ リクエストID として記録**」／v9 §5「**ログイン数に比例する量**に耐えるか」／ADR-0004（監査＝トリガ＋**ハッシュチェーン**。単位分割/アンカ署名。**並行性はS5で未検証**）
- **指摘（攻撃・権限軸）**：未認証段階の参照を監査に記録するということは、**攻撃者が任意の `user_id` を主張してログインを試みるだけで監査行を生成できる**——**書き込ませたい相手に書き込ませられる**という、監査ログに対する最も基本的な攻撃である。
  - **量の見積り基準が誤っている**：v9 は「**ログイン数**に比例」と書いたが、正しくは「**ログイン試行数**」＝**攻撃者が制御できる量**。桁が違う。
  - **ハッシュチェーンとの衝突**：ADR-0004 は監査を**ハッシュチェーン**で改ざん耐性を持たせる方針で、**並行挿入時の直列化ボトルネックは S5（未実行）で検証予定**。そこへ未認証の大量書込を流すと、**監査の書込がボトルネックになり、正規のログインまで遅くなる**（可用性）。
  - **汚染**：存在しない `user_id` の主張が大量に残り、**本物の追跡が埋もれる**。改ざん耐性のある領域に、信頼できない入力を無制限に書き込むのは監査の価値を下げる。
- **要修正（案）**：**未認証の参照は監査本体に書かない**。
  - **認証成功した解決のみ**を監査本体（ハッシュチェーン）へ記録する（改ざん耐性が必要なのは「実際に誰が誰の所属を解決したか」）。
  - **未認証の試行は別系統の運用ログ**（改ざん耐性不要・短期保持・レート制限後・集約カウント）に記録する（ADR-0020 可観測性）。存在しない `user_id` の主張は**個別行ではなく集約カウント**で足りる。
  - §5 の見積り基準を「**ログイン試行数（攻撃者制御下）**」に訂正し、レート制限（ADR-0009）との接合を明記する。

## 処置方針（第7回・推奨）

1. **A1g-H1 を最優先**：**専用スキーマ（`priv`）＋通常ロールへの `USAGE` 不付与＋`information_schema.role_table_grants` の網羅検査**へ切り替える。個別GRANTの管理と人手の一覧に強制力を持たせない。`ALTER DEFAULT PRIVILEGES`／`GRANT ON ALL TABLES` の除外もマイグレーション規約として明記。
2. **A1g-M1**：索引書込関数を **`refresh_user_shard_index(user_id)`＝メンバーシップから収束させる宣言的な形**に変え、引数で「どう書くか」を指示させない。索引の変更は書込なのでトリガ監査の対象にする。

5. **A1g-L1/L2/L3**：全シャードへの一律適用、SECURITY DEFINER 関数の一覧化＋`prosecdef` 走査テスト、テストのロール構成要件。

TO app_role`）。`auth_role` にはこの restrictive が適用されない」／v13 §3.2「**(β) が生む新しい前提と代償**：…**新しいロールに permissive だけを付けるとテナント分離が消える**ため、**(テーブル, ロール) の全組合せに対する網羅検査が (β) の安全性の前提**になる。**検査が無いなら (β) を採ってはならない**」／**A1c-L2「共有マスタの書込は管理用の別接続/別ロール（テナント通常接続とは別経路）で行い」**／A1-H2「マイグレーション等の特権操作は**別ロール**で実行し」／A1g-H1「**強制力を人手の一覧からスキーマとテストへ移した**」
- **指摘（攻撃・権限軸／教訓5の型）**：
  1. **業務ロールは1つではない**。ADR-0001 自身が **A1c-L2 で「管理用の別接続/別ロール」**、**A1-H2 で「マイグレーション用の別ロール」**を既に導入している。さらに ADR-0002 A2h-M2 で認証接続と業務接続の分離を決め、データモデル §6 で `audit_writer` を追加した。**`TO app_role` と単数のロールに限定すると、これら以外のロールには restrictive が適用されない**。
  2. **PostgreSQL の挙動として、restrictive が適用されないロールは「そのテーブルに permissive が1本でもあれば全行見える」**（restrictive が無いので絞られない）。②システム共有には全テナント読取の permissive があるため無害だが、**①テナント固有に何らかの permissive（作成者・個人データ等）が付いているテーブルでは、restrictive 適用外ロールがその permissive の範囲で全テナント横断に読める**。
  3. **列挙漏れが穴になる方向**：新しいロールを追加したとき、**restrictive の `TO` に追記し忘れれば分離が消える**（何もしなければ安全側、ではない）。v13 はこれを「検査で守る」としたが、**v13 自身が A1g-H1 で「人手の一覧に強制力を依存させない」「スキーマとテストへ移す」と決めた思想に反している**——同じ版の中で思想が一貫していない。
- **影響**：**管理用ロール・マイグレーションロール・将来のバッチロール等でテナント分離が効かない**。検査があれば検出できるが、**検査の実装可能性自体が未確立**（A1h-M1）。最悪、①テナント固有テーブルを管理ロールで参照した障害対応の一回が、**全テナント横断の参照になっていたことに誰も気づかない**。
- **要修正（案）**：**restrictive を「全ロールに適用（ロール指定なし）」に戻し、`auth_role` の例外を述語の中に埋め込む**。
  - `USING (tenant_id = ANY(current_setting('app.allowed_tenants')::uuid[]) OR (current_user = '<auth_role>' AND user_id = current_setting('app.auth_subject', true)::uuid))` の形（membership の restrictive にのみこの例外を持たせる）。
  - **利点**：**restrictive は全ロールに適用されるという不変条件が保たれる**ため、**新しいロールを追加しても穴が開かない**（安全側に倒れる）。フェイルクローズも維持（`auth_role` でなく `allowed_tenants` 未設定なら全拒否）。
  - **欠点**：述語に `current_user` とロール名が入る（ハードコード）。**この欠点は「列挙漏れで分離が消える」より小さい**——ロール名の変更はマイグレーションで検出可能な破壊的変更であり、静かに穴が開くことはない。
  - **検査も単純化する**：「**restrictive テナント分離ポリシーに `TO` 指定（ロール限定）が付いているものが存在しないこと**」を見ればよい（ロールの列挙が不要になる＝**テーブルもロールも列挙しない検査**）。これは A1g-H1 の「列挙しないカタログ走査」の思想と一致する。
  - **例外を持つテーブルの一覧化**（現時点では membership のみ）＋**一覧外のテーブルの restrictive に `current_user` が現れないこと**を検査する。
  - **もしロール限定を採り続けるなら**、§3.2 に「**(β) はロールの列挙を正しく維持できる運用を前提とする**」と明記し、**(α) BYPASSRLS 案との比較にこの運用リスクを加えて再評価**すること（現在の比較表は (β) の「検査可能性◎」を過大評価している＝教訓8）。

## 🟡 Medium（第8回）

### A1h-M1. 網羅検査の判定方法が未定義——(β) の採否を決める検査なのに実装可能性が示されていない
- **該当箇所**：v13 §5【v13】「**①③分類のテーブルすべてに restrictive テナント分離ポリシーが存在すること**」「**restrictive の述語形が許可された3種＋例外に限ること**」／§5【v13】「**(テーブル, ロール) の全組合せ検査**」／§3.2「**検査が無いなら (β) を採ってはならない**」
- **指摘**：検査の**内容**は書かれたが、**どうやって判定するか**が書かれていない。
  1. **「restrictive テナント分離ポリシー」の同定**：`pg_policies` から RESTRICTIVE は判別できるが、**「それがテナント分離のポリシーである」ことは名前規約か述語の中身でしか判定できない**。名前規約に頼るなら**名前規約を守らせる仕組み**が別途要る（名前を間違えたポリシーは検査をすり抜ける）。
  2. **述語の比較**：`pg_policies.qual` は**PostgreSQL が正規化して再構成したテキスト**であり、**キャスト・括弧・スキーマ修飾・関数呼び出しの書き方の揺れで文字列一致が壊れる**。「述語形が3種に限る」を文字列比較で実装すると、**正しいポリシーが不一致で弾かれる／誤ったポリシーが一致して通る**の両方が起きる。
  3. **①③分類の同定**：「①③分類のテーブル」をカタログからどう判別するか（`tenant_id` 列の有無で近似できるが、④も `user_id` を持ち②は `tenant_id` を持たない——近似の妥当性が未検証）。
- **影響**：**検査が実装できないまま (β) が採用される**（v13 自身の条件「検査が無いなら採ってはならない」を満たさない）。あるいは脆い文字列一致で実装され、**検査が緑なのに穴が開いている**状態になる——A1g-H1 が排除したはずの「偽の安心」。
- **要修正（案）**：**検査を「カタログでの存在確認」と「振る舞いのテスト」の二段**にする。
  - **一段目（カタログ・列挙しない）**：`tenant_id` 列を持つ全テーブルに RESTRICTIVE ポリシーが存在すること／**restrictive に `TO` 指定が無いこと**（A1h-H1 の修正案を採れば、これだけで役割の同定が不要になる）／`current_user` が現れる restrictive が一覧内のテーブルに限ること。**述語の文字列比較はしない。**
  - **二段目（振る舞い・自動生成）**：カタログからテーブル一覧を取り、**各テーブルに2テナント分のダミー行を投入し、各ロールで読んで他テナント行が見えないことを実データで確認**する。**テーブルを人手で列挙しないので新規テーブルも自動的に対象になる**。**「横断が通ること」の逆側テスト**（IND2-H3 由来）も同じ枠組みで生成する。
  - **ポリシー名の規約**（例 `<table>_tenant_isolation`）を定め、**規約違反を CI で検出**する（一段目の補助）。

### A1h-M2. restrictive の述語形の列挙に③が漏れ、③の述語が更新されていない
- **該当箇所**：データモデル v6 §4「**restrictive の述語形は次の4種に限る**…**(a) 標準**（`tenant_id = ANY(allowed_tenants)`）／**(b) 本人起点例外**／**(c) スコープ**／**(d) ④は対象外**」／同 §4 ポリシー表「| **③共有+上書き** | restrictive(帰属)＋読取許容 | **`tenant_id IS NULL OR tenant_id = current`**（上書き優先はビュー側） |」／ADR-0001 A1b-M2「**フェイルクローズの単純ポリシー（`tenant_id = current`）ではNULL共有行が誰にも見えなくなり機能破綻する**」
- **指摘**：**IND2-H3 の処置（restrictive の述語を `allowed_tenants` に統一）が③に行き渡っていない**（教訓6⑥の再発）。
  1. **③の述語は `tenant_id IS NULL OR tenant_id = current` のまま**で、**`allowed_tenants` に更新されていない**。したがって**③テーブル（農薬肥料マスタ・作物マスタ・I18nLabel）でグループ管理者横断が動かない**（配下組織のテナント上書き行が見えない）。
  2. **「述語形は4種に限る」という検査の列挙に③の形が入っていない**。すると③のポリシーは**検査違反として弾かれる**（実装が止まる＝気づけるので相対的に軽い）か、**検査が③を対象外として見逃す**（③に restrictive が無くても検出できない＝重い）。どちらに転ぶかは実装依存。
  3. `NULL = ANY(array)` は NULL（不明）＝偽扱いなので、**③を単純に (a) 標準へ揃えると共有行（`tenant_id IS NULL`）が全員に見えなくなる**——**A1b-M2 が指摘した破綻がそのまま再発する**。したがって③は**独自の形が必要**であり、それを列挙に含めなければならない。
- **要修正（案）**：**述語形を5種に改め、③を明示する**：**(a) 標準**／**(b) 本人起点例外**／**(c) スコープ**／**(e) ③共有＋上書き＝`tenant_id IS NULL OR tenant_id = ANY(app.allowed_tenants)`**（**`NULL` を先に許容**することで A1b-M2 の破綻を回避し、かつ横断も通る）／**(d) ④は対象外**。データモデル §4 のポリシー表の③行も同時に更新する。**横断が通ることのテストに③を含める**。

### A1h-M3. 「並行性はさらに改善する」はテナント間の話——同一テナント内の直列化は残る
- **該当箇所**：ADR-0004 v5「**副次的な利点：テナント間でチェーンが独立するため、A4b-M2 が懸念した直列化ボトルネックが緩和される**（並行挿入がテナント境界で分かれる）」／A4b-M2「ハッシュチェーンは**単一線形だと高並行・パーティション挿入下で直列化ボトルネック**になり**「前レコード」も定まらない**」／ADR-0002 A2c-M1「**単一のグループ/連合そのものが1DB上限（5万人）を超える**」
- **指摘**：チェーン単位を `(tenant_id, 期間)` にすると**テナント間**の直列化は解けるが、**同一テナント内の並行挿入では「前レコード」を決めるための直列化が依然必要**である。本プロジェクトは **単一グループが5万人を超えるケースを明示的に想定**しており、**大規模テナント1つに書込が集中する構成では A4b-M2 の懸念は未解決**のまま。v5 の「さらに改善する」は**改善の方向は正しいが、懸念が解消したとは言えない**（S5 で測る対象が変わっただけ）。
  - 加えて **移送との整合が未定義**：**期間の途中でテナントを移送した場合、その期間のチェーンをどう扱うか**（移出元に前半・移入先に後半では鎖が2つに割れる）。**移送時点でチェーンを閉じて末尾ハッシュをアンカ署名し、移入先で新しいチェーンを開始する**手順が要るが、ADR-0004 v5／ADR-0003 §2.9 のどちらにも書かれていない。
- **要修正（案）**：
  - **同一テナント内の並行度が高い場合の分割**（期間の粒度を細かくする／テナント内でサブチェーン＋Merkle ルート）を選択肢として明記し、**S5 の合格基準を「想定最大テナントの書込レートで直列化がSLOを侵さないこと」**と定める（テナント間の独立性だけでは合格判定にならない）。
  - **移送時のチェーン閉鎖手順**を ADR-0003 §2.9 の不変条件に追加：**移送は期間境界で行うか、期間途中なら移送時点でチェーンを閉じてアンカ署名し、移入先で新チェーンを開始する**（鎖を割らない）。

### A1h-M4. `allowed_tenants` の意味が未定義——複数テナント所属の受託者の扱いが読めない
- **該当箇所**：v13 §2【v13】1「**通常ユーザーの `allowed_tenants` は自テナント1要素のみ**、**グループ管理者は配下組織集合**」／同 5「**通常ユーザー（横断権限なし）では `allowed_tenants` が `{app.tenant_id}` の1要素であることを注入時に検証**」／ADR-0005（**ユーザー↔組織は多対多メンバーシップ**・受託者は複数テナントに所属）／ADR-0005 v5【v5】「未確定期間は各テナント内で導出した参考値」
- **指摘**：**restrictive の床が `allowed_tenants` になった**（IND2-H3 の処置）ため、**この集合の意味が分離の意味を決める**。ところが v13 は「通常ユーザーは1要素」とだけ書いており、**複数テナントに所属する受託者（本プロジェクトの中核ユースケース）でどうなるかが読めない**：
  - 「1要素」＝**リクエストで選択中の1テナント**なら整合する（ADR-0008 §2.6.2 の per-shard/per-tenant 権限注入と接合し、横断は複数リクエストになる）。
  - 「1要素」＝**ユーザーの所属テナント（1つしか持てない）**と読むと、**多対多メンバーシップ（ADR-0005）と矛盾**する。
  - **ADR-0005 v5 が加えた「未確定期間は各テナント内で導出した参考値を各シャードが返す」も、per-tenant コンテキストで注入されることが前提**だが、v13 側にその接合が書かれていない。
- **影響**：実装者が「所属テナント集合」と読むと、**受託者の `allowed_tenants` が全所属テナントになり、restrictive の床が全所属テナントに広がる**——**受託者が任意のテナントの業務データを横断で読める**（要求#18 が「本人の稼働に限る」と定めた例外が、業務データ全体に広がる）。**IND2-H3 の処置が、より広い越境を作る形で誤実装され得る。**
- **要修正（案）**：**`allowed_tenants` の定義を明記する**：「**そのリクエストで許可されるテナント集合**であり、**ユーザーの所属集合ではない**」。通常ユーザーは**選択中の1テナント**、グループ管理者は**配下組織集合（注入時に検証済み）**。**複数テナントに所属する受託者は、テナントごとに別リクエスト（per-tenant コンテキスト）となる**ことを **ADR-0008 §2.6.2 の per-shard 権限注入と明示的に接合**する。**本人起点横断だけが例外**（restrictive の (b) 形で `allowed_tenants` の外を読む）。

### A1h-L2. `app.auth_subject` と `app.user_id` の命名が類似／auth_role 接続の総当たり
- **該当箇所**：v13 §2【v13】2「`user_id = current_setting('app.auth_subject', true)::uuid`」／本人起点例外「`user_id = current_setting('app.user_id')::uuid`」

### A1h-L3. チェーン単位の「期間」の粒度が未定義
- **該当箇所**：ADR-0004 v5／データモデル v6「チェーン単位＝`(tenant_id, 期間)`」「アンカ署名も `(tenant_id, 期間)` 単位」「代償：チェーン数とアンカ署名数が `(テナント数 × 期間数)` に増える」
- **指摘**：**「期間」の粒度が定義されていない**（`audit_log` のパーティション境界＝月と同じか、より細かいか）。**アンカ署名数の見積りは粒度に完全に依存する**のに、粒度が決まらないまま「増える」と書いている。また A1h-M3 の対策（粒度を細かくして並行性を稼ぐ）と**署名数の増加はトレードオフ**であり、両者を同時に決める必要がある。

## 処置方針（第8回・推奨）

1. **A1h-H1 を最優先**：**restrictive を全ロール適用に戻し、`auth_role` の例外を述語に埋め込む**。これで**新ロール追加でも穴が開かず**、検査も「**restrictive に `TO` 指定が付いていないこと**」という**テーブルもロールも列挙しない形**に単純化できる（A1g-H1 の思想と一致）。§3.2 の比較表の「(β) 検査可能性◎」も再評価する（教訓8）。
2. **A1h-M1**：検査を**「カタログでの存在確認（列挙しない）」＋「自動生成された振る舞いテスト」の二段**にする。**述語の文字列比較に依存しない**。ポリシー名規約はCIで担保。
3. **A1h-M2**：**述語形を5種に改め③を明示**（`tenant_id IS NULL OR tenant_id = ANY(allowed_tenants)`）。データモデル §4 の③行も更新。**横断テストに③を含める**。

### A1h-H1 の処置：`TO` の使い分けを原則化した

v13 の「restrictive を `TO app_role` に限定」を撤回し、**例外は `TO` ではなく述語に書く**形に改めた。根拠は**列挙漏れの倒れる方向が逆**であること：

| ポリシー種別 | `TO` の扱い | 列挙漏れが起きたとき |
|---|---|---|
| **restrictive**（絞る） | **`TO` 指定を付けない（全ロール）** | ——（列挙しないので漏れない） |
| **permissive**（経路を開く） | **`TO` でロールを明示列挙** | **そのロールは何も見えない＝フェイルクローズ**（安全側） |

`membership` の restrictive に `(current_user = '<auth_role>' AND user_id = app.bootstrap_claimed_user)` を OR で足すことで、**新しいロールを追加しても restrictive は効き続ける**。副産物として**検査が単純化した**——「restrictive に `TO` 指定が付いていないこと」を見るだけでよく、v13 が要求していた **(テーブル, ロール) の全組合せ列挙が不要**になった（A1g-H1「列挙しないカタログ走査」の思想と一致）。§3.2 の (β) 評価も v14 の形を前提に読み替えるよう注記した（教訓8）。

### 処置中に自ら発見した欠陥：**①③には「基本 permissive」が必須**

**教訓14（列挙対象を機械的に洗い出す）を restrictive/permissive の全組合せに当てて発見した。** PostgreSQL では行が可視になるのは「**すべての restrictive を満たし、かつ少なくとも1つの permissive を満たす**」場合であり、**permissive が1本も無いテーブルは誰にも0行**（permissive の OR が空集合＝偽）。

**v13 までの記述（「①＝restrictive のみ」）では、正しいテナント文脈でも全①テーブルが0行になる。** これは **IND2-H3（restrictive/permissive の結合意味論）と同じ根**であり、**独立レビューが H3 を指摘した後も、同じ意味論の別の帰結が残っていた**。処置：**①③に `FOR ALL TO app_role, auth_role USING (true) WITH CHECK (true)` の基本 permissive を必ず置く**（絞りは restrictive が行う）。**検査に「permissive が1本も無い①③テーブルが存在しないこと」を追加**した。

## 独立レビュアーの所見（要点）

- **最も弱い接合部**＝**ADR-0001 §2/§5（RLSポリシー＋検査）× ADR-0005（業務権限）× 要求仕様 3.2／#21（ロール別・個人データの最小権限）の三者接合**。テナント次元・本人性・スコープは述語形・検査・振る舞いテストまで作り込まれているのに、**ロール次元と個人データ次元がまったく写像されていない**。業務ロールがDB上1つなので `TO` では差別化できず、注入変数にも権限を表す項が無く、**唯一の逃げ道だった permissive は「基本 permissive `USING(true)` 必須」で自ら塞いでいる**。
- **設計者が自分では疑いにくい前提（3つ）**：
  1. **「permissive は絞り込みに使える」**——IND2-H3 で「横断が足せない」方向からは学習済みだが、**同じ性質が「絞り込めない」方向にも効く**ことは検討されていない。
  2. **「検査（カタログ走査）が正しさを担保している」**——検査は `USING` 側と存在有無しか見ておらず、**書込（WITH CHECK）・ビュー経由・ロール次元は視野に入っていない**。
  3. **「決定的であること＝正しいこと」**——`event_ts` を UUIDv7 から導く決定は「再送で値が変わらない」一点で選ばれ、**その決定的な値が端末時計という信用できない入力である**ことが、同じ文書群の ADR-0007 §2.8（時刻の権威はサーバ）と衝突したまま見過ごされている。
- **クローズ可否**：ADR-0001／ADR-0002／ADR-0005／データモデル設計書＝**クローズ不可**。ADR-0003／ADR-0004＝**条件付きクローズ可**（M8 の法的前提の明示／H5 の是正）。
- **着手順序の推奨**：**H2 →（H3・H4 は H2 と同じ「述語形と検査の再設計」で一括）→ H1 → H5 → M1/M2**。**先に「ロール／個人データ権限をどの層で強制するか」を裁定してから**個別の穴を埋めるべき。

## 処置結果（IND3-H2 の裁定＝(a)・2026-07-27）

### 中核：permissive は経路を開くだけ・絞りはすべて restrictive

| ポリシー種別 | 役割 | 述語 | `TO` |
|---|---|---|---|
| **permissive** | **経路を開くだけ** | **`USING (true)` 固定**（条件を書いてはならない） | **`TO` で列挙**（漏れれば見えない＝安全側） |
| **restrictive** | **絞りはすべてここ** | 7形のいずれか | **`TO` なし**（全ロール） |

**これが IND3-H2 の根本解決**である。v14 で「①③には基本 permissive が必須」という**正しい発見**をしながら、その `USING(true)` が最小権限の permissive を吸収することに気づかなかった——**絞りを restrictive に集約すれば、吸収されるものが無くなる**。検査に「**permissive の述語が `true` 以外のものが存在しないこと**」を追加した。

### RLS が守る範囲を正直に限定した（(b) の要素を部分的に併用）

**(a) を採ってもなお RLS が強制できるのは「行の可視性・書込可否」だけ**である。**権限管理・承認・設定変更のような「行の可視性で表せない操作の可否」はアプリ層が唯一の防御**であり、**§2.9.3／§4／ADR-0005 §2.6 に明記**した。**「RLSが最後の防波堤」を無条件には主張しない。**

### IND3-H3（WITH CHECK）：述語形を「USING と WITH CHECK の対」で再定義

**PostgreSQL は `WITH CHECK` を省略すると `USING` を書込検査に流用する**。v14 までは USING だけで定義し検査も USING しか見ていなかったため、**`labor_summary`（「WITH CHECK なし」と明記）で他テナント名義の①-a追記が可能**だった。**7形すべてで両方を明示**し、**`WITH CHECK` に読取用の集合（`AT`／`UID`／`ESU`）や `tenant_id IS NULL` が現れないこと**を検査項目に、**書込側の振る舞いテスト**（他テナント名義の INSERT・行移送・共有行の書込がすべて拒否されること）を追加した。

### IND3-H4（雇用主横断）：`app.employer_subject_users` で解決し、A5-M3 を撤回

ADR-0005 §2 の**同一節内の自己矛盾**（「本人＋雇用主管理者が全メンバーシップ横断」vs「雇用主は自テナント分のみ」）を解消。**要求#18「独立受託先どうしでも本人稼働に限り参照可」が RLS で成立**するようにし、**A5-M3 を撤回**した（受託先間で他社稼働が露見しない懸念は、**参照先が労務サマリという最小化投影に限られること**で担保される＝要求#18 の設計意図そのもの）。**`app.user_id` は「リクエスト主体（不変）」に固定**し、④下書きへの流用を禁じた。

### あわせて処置：PG-H1（セッション変数の正規化）— **設計者が実測で検証**

**`SET LOCAL` を一度使った接続では「未設定」が NULL ではなく `''` になり、素のキャストはプラン時例外**になる。**すべての参照を正規化形に統一**した：

- 配列 `COALESCE(NULLIF(current_setting('app.x', true), ''), '{}')::uuid[]`
- スカラー `NULLIF(current_setting('app.x', true), '')::uuid`

**実測で確認**：正規化形なら `SET LOCAL` 後の2回目も**エラーにならず0行**。**ただし不正値は依然として例外**（`'garbage'::uuid` はエラー）——したがって「**未設定・空は非通過／不正値は例外**」が正しい記述であり「不正は偽」ではない。**例外の握り潰しを禁じる規約**（フェイルオープンへの反転の防止）と、**「`SET LOCAL` を使った接続の2回目のトランザクション」で注入漏れ挙動を確認するテスト**を追加した。**関数にラップしない**ことも明記（qual から `current_setting` が消えて検査が偽陰性になる＝PG-M4）。

**capability 機構も実測で検証**：capability 無し→自分の行のみ／capability 有り→他者の行も可視、を確認。

## 処置結果（v16・2026-07-27）——2つの独立経路が一致した3件を一括処置

**IND3-H1／PG-H5（ブートストラップ）・PG-H6（FORCE RLS の非伝播）・IND3-M6／PG-H4（ビュー）**を処置した。**いずれも設計者が実測で検証**している。あわせて **IND3-M1**（ADR-0002 の撤回済み機構の残存）と **ADR-0004 の最低要求バージョン**も確定した。

### IND3-H1／PG-H5：ブートストラップのキーを `bootstrap_owner` に変更

**自己矛盾の内容**：述語形(f) の `current_user = '<auth_role>'` は **`auth_role` 自身が membership に `SELECT` を持つ場合しか真にならない**が、§2 3b／§5 検査／ADR-0002 A2i-M1 は「**テーブル権限ゼロ・`EXECUTE` のみ**」を要求。SECURITY DEFINER 経由にすると `current_user` が関数所有者になり**第2項が常に偽→0行→自己ブロック**（IND2-H1 の再演）。**どちらを採っても成立しなかった。**

**処置**：述語のキーを **`bootstrap_owner`（NOLOGIN・非BYPASSRLS・非superuser の専用関数所有者ロール）**に変更。

| ロール | 属性 | 権限 |
|---|---|---|
| `auth_role` | LOGIN | **テーブル権限ゼロ。ブートストラップ関数の `EXECUTE` のみ** |
| **`bootstrap_owner`**（新設） | **NOLOGIN・非BYPASSRLS・非superuser** | **membership の `SELECT` のみ**。関数の所有者 |

- membership の permissive の `TO` に **`bootstrap_owner` を含める**（含めないと permissive が無い＝0行＝PG-H3 の型）。`auth_role` は直接読まないので含めない。
- **`bootstrap_owner` をいかなるロールにも `GRANT` しない**（`SET ROLE` で例外を得られないように＝PG-L7）。
- **実測で検証**：`auth_role` が関数経由で**テナント跨ぎ2件を解決**／**`auth_role` の直接参照は `permission denied`**／**主張と引数が一致しない場合は0件**。

### PG-H6：パーティション子を専用スキーマ `part` へ（構造で塞ぐ）

**実測**：子は `relrowsecurity=f`・ポリシー0本。**親経由50件／子直接100件（全テナント）**。データモデル §5 の「S1 で確認」は事実に反し、**S1 は親経由しか試験していなかった**。

**処置**：**子を専用スキーマ `part` に作成し、通常ロールに `USAGE` を与えない**（親は `public`、アクセスは親経由のみ）。**実測で確認**：親経由は通り、**子直接は `permission denied for schema part`**。**スキーマ `USAGE` が無ければ個別 `GRANT` の事故にも耐える**（`priv` と同じ二重防御）。検査＝「`part` に通常ロールの権限が無いこと」「`relispartition` のテーブルが `part` 以外に無いこと」（**列挙しないカタログ走査**）。S1 に「子直接参照の拒否」を合格項目として追加。

### IND3-M6／PG-H4：ビューは `security_invoker` 必須

**通常のビューは基底表の RLS を「ビュー所有者」の文脈で評価する**ため、`TO` で列挙した permissive が適用されず **FORCE RLS 下では誰が読んでも0行**。**しかもビューは `pg_policies` にも `relrowsecurity` にも現れず、検査のどれにも引っかからない**。

**処置**：**`WITH (security_invoker = true)`（PG15+）を必須**とし、**ビュー本文の絞り込みを `app.allowed_tenants`（集合）＋正規化形**に統一（`app.tenant_id` 単一だとグループ管理者の横断がビュー経由で通らない）。**検査に「RLS 有効な表に依存するビューが `security_invoker` であること」（`reloptions`＋`pg_depend`）／振る舞いテストに「主要ビュー経由で正しい行が見えること」を追加**。

### 副産物：ADR-0004 §2.5 で最低要求 PostgreSQL バージョンを確定

**`security_invoker` が PG15 以降**であることが、**本設計の最低要求バージョンを実質 PG15 に固定する**（無いと業務ビューが0行になり、③解決・訂正チェーン有効値・未確定期間導出はすべてビュー前提）。**推奨は PG16**（スパイクの実行環境と一致）。**バージョン依存が成否を分ける箇所の一覧**（UUIDv7 の PG18 組込み・PgBouncer 1.21・PostGIS の leakproof 等）も §2.5 に表として置いた。

### IND3-M1：ADR-0002 の撤回済み機構の残存を是正

ADR-0002 §2 が **ADR-0001 v13 の撤回済み機構**（`TO app_role` 限定・`app.auth_subject`・(テーブル,ロール) 全組合せ検査）をそのまま記述していたため、**v16 の形に更新**した（読んだ実装者が「穴が開く方向」の形を作るのを防ぐ）。

### 新しく設けた原則（§2.10）：RLS が「自動で効かない」3つの境界

PG検証の所見（**単一機能の記述は20項目すべて正確／誤りはすべて包含を跨ぐ場所に集中**）を受け、**親→子／テーブル→ビュー／セッション→トランザクション**の3境界を **§2.10 として明示**し、それぞれに構造的対策と検査を置いた。**「新しい機構を導入するときは、包含の外側でも成立するかを機械的に確認する」**を本ADRの原則として記録した。

## 処置結果（IND3-H5・2026-07-27）——**独立レビューの High 5件がすべて処置完了**

**IND3-H5（`event_ts` が端末時計由来）**を処置し、**副産物として IND3-L3（冪等キー表記）も解消**した。**前提は実測で確認**している。

### 実測で確認した前提

```
-- 範囲外の時刻は INSERT が失敗する（＝時計ずれ端末の記録が受理できない）
INSERT ... '1970-01-01' → ERROR: no partition of relation "ev" found for row
INSERT ... '2031-03-01' → ERROR: no partition of relation "ev" found for row

-- DEFAULT パーティションは安全網にならない（後から当該月を作れなくなる）
CREATE TABLE ev2_202609 PARTITION OF ev2 FOR VALUES FROM ('2026-09-01') ...
  → ERROR: updated partition constraint for default partition "ev2_def"
           would be violated by some row
```

**電池切れで 1970 にリセットされた端末**（Android/組込みで現実的）が14日分の**農薬使用記録（①-a法定）**を溜めて復帰すると、**1件も受理できない**。`event_uuid` を変えない限り永久に受理できず、変えれば冪等キーが変わり二重計上になる。**ADR-0007 §2.5.1「未同期データは消えない」という不変条件と正面衝突**していた。

### 処置：冪等・物理配置・端末申告時刻を3つの別機構に分ける

| 機構 | 担うもの | 実装 |
|---|---|---|
| **① 冪等** | 再送で二重計上しない | **受理台帳 `event_receipt`** が権威。イベント表の一意制約に依存しない |
| **② 物理配置** | パーティション・retention・プルーニング | **`event_ts`＝サーバが検証・クランプした業務時点**（意味を再定義） |
| **③ 端末申告時刻** | 監査・是正・乖離検出 | **`occurred_at`（生・詐称可能）**を保持し、乖離は ADR-0007 §2.8 の枠組みへ |

- **v9 の却下理由が解消した**：「サーバ受理時刻は再送で値が変わり非決定になる」——**受理台帳が記録済みの `event_ts` を返すので、サーバ採番でも決定性が保たれる**。
- **`event_ts` は構造的に範囲外にならない**（クランプ窓を `CHECK (event_ts BETWEEN received_at - INTERVAL '400 days' AND received_at + INTERVAL '1 day')` でDB側でも強制）。**「どんな端末時計でも①-aは受理できる」を不変条件**とした。
- **`CHECK (event_ts = uuidv7_time(event_uuid))` は撤回**（これがサーバ側の補正を禁止していた）。**UUIDv7 固定は維持**（ソート性・診断）だが**パーティションキーの導出には使わない**——**副産物として PG-L4（PG18 の組込み `uuidv7()` へ差し替える際に CHECK の DROP/ADD＝全件再検証が要る）の負担も消えた**。
- **`DEFAULT` パーティションは置かない**（実測で確認した罠。②により不要）。**パーティションは自動作成ジョブで常に先行作成**。
- **retention は二段**：`event_ts` でのパーティションドロップ（粗い）＋ `occurred_at` ベースの精密削除。**起算点は法域別＝E2**。

### 副産物：IND3-L3（冪等キー表記）の解消

ADR-0007 は冪等を `(tenant_id, event_uuid)` 一意と書いてきたが、**宣言的パーティション表ではパーティションキーを含まない一意制約は作れない**ため実装できなかった（`ON CONFLICT (tenant_id, event_uuid)` は一致する制約が無くエラー）。**受理台帳は `event_ts` でパーティション化しないので、`(tenant_id, event_uuid)` の一意をそのまま張れる**——**ADR-0007 の表記がそのまま成立する**ようになった。
