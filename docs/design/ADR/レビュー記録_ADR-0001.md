## 🟠 High

### A1-H1. セッション変数のリセット漏れ＝プール接続でのテナント文脈リーク
- **該当箇所**：決定「セッション変数方式（`SET app.tenant_id`）」
- **指摘（攻撃）**：接続プールでは1つの物理接続が複数リクエスト（複数テナント）で使い回される。`SET app.tenant_id`（**セッションレベル**）はコミット後も接続に残るため、**次に同じ接続を borrow したリクエストが前のテナントの文脈を引き継ぎ、別テナントのデータを読む/書く**危険がある（RLS＋プーリングの典型事故）。ADRは「設定漏れ＝分離破綻」までは書いたが、**リセット漏れ／使い回しリーク**を扱っていない。
- **要修正**：決定に「**トランザクション境界の `SET LOCAL app.tenant_id`（トランザクション終了で自動失効）を用いる**、または**接続返却時に必ずリセット**する」を明記。全クエリをテナント設定済みトランザクション内で実行する共通機構を必須とする。

### A1-H2. フェイルクローズ／FORCE RLS／非所有者ロールが「未解決」止まり
- **該当箇所**：決定＋未解決事項（BYPASSRLS）
- **指摘（攻撃）**：RLSは以下を満たさないと**サイレントに無効化**される。ADRではこれらが「未解決」に置かれ、決定に含まれていない：
  1. **FORCE ROW LEVEL SECURITY 未設定**だと、**テーブル所有者はRLSをバイパス**する。アプリがテーブル所有者ロールで接続すると分離が効かない。
  2. **`app.tenant_id` 未設定時の挙動**が未定義。ポリシーが `current_setting(..., true)`（missing_ok）でNULL→比較が真になる書き方だと**フェイルオープン（全件見える）**。
  3. アプリ接続ロールが**スーパーユーザー/所有者**だとRLSが効かない。
- **要修正**：決定に格上げして明記：①全業務テーブルに **`FORCE ROW LEVEL SECURITY`**、②**未設定時は全拒否（フェイルクローズ）**のポリシー既定、③**アプリは非所有者・非スーパーユーザー・非BYPASSRLSロール**で接続、マイグレーション等の特権は別ロール。

## 🟡 Medium

### A1-M1. グループ管理者の横断ポリシーの性能
- **該当箇所**：決定「グループ管理者＝tenant_id集合ベースで横断」
- **指摘（攻撃）**：横断許可を「そのユーザーがアクセス可能なtenant_id集合」に基づくRLSポリシーで表すと、**行ごとにメンバーシップ参照のサブクエリ**が走り、大規模テーブル（5万ユーザー規模の作業日誌等）で性能劣化しうる。集計はマテビューに逃がすとあるが、**明細の横断参照**の読み取り経路が未検討。
- **要修正**：許可tenant_id集合をセッション変数（配列）に事前解決して注入する等、行単位サブクエリを避ける方針を検討事項に追記。

### A1-M2. 複数permissiveポリシーのOR結合
- **該当箇所**：決定「テナント分離ポリシー＋本人起点横断（user_id）ポリシー」
- **指摘（攻撃）**：同一テーブル（労務サマリ）に複数のRLSポリシーを付けると、既定で**OR結合（permissive）**され、いずれか1つが真なら許可になる。テナント分離と本人起点横断の**組み合わせが意図せず参照範囲を広げる**恐れ（例：本人ポリシーが他テナント行まで許可し、テナント分離を上書き）。相互作用が未検討。
- **要修正**：ポリシーのpermissive/restrictiveの使い分け、対象テーブルごとの適用ポリシーの明示を検討事項に追記。労務サマリ限定の範囲をポリシーで厳密化。

### A1-M3. tenant_scopedとsystem-globalテーブルの区別
- **該当箇所**：決定「全業務テーブルにtenant_id」
- **指摘（攻撃）**：**すべてのテーブルがtenant_scopedとは限らない**。国レベルで共有し得るマスタ（例：農薬肥料マスタ／作物マスタ／多言語ラベル）は、テナント横断で共有するか、テナント固有かで設計が変わる。「全テーブルtenant_id必須」と国レベル共有データの存在が噛み合わず、区別ルールがない。
- **要修正**：テーブルを「テナント固有／システム共有（tenant_idなし・全員読取）／テナント上書き可能な共有」に分類する規約を追記。

## 🟢 Low

### A1-L1. 「1DB内テナント数＝数百」前提の境界
- **該当箇所**：選択肢比較の前提「1DB内テナント数は数個〜数百」
- **指摘**：要求仕様#13でOSS運用者は**第三者へのサービス提供（SaaS）も許容**。SaaS運用者が1DBに数千テナントを収容する運用も起こりうるため、DB分離却下の前提（数百）が崩れる場面がある。
- **要修正**：前提の境界と、崩れた場合の指針（ハイブリッドD案・スケールアウト）を注記。

### A1-L2. オフライン端末側のデータ分離
- **該当箇所**：決定「オフライン同期APIで tenant_id を通す」
- **指摘**：サーバ側はRLSで守れるが、**端末（オフライン）側にRLSはない**。複数テナントに所属するユーザー（受託作業者）の端末には複数テナントのデータが載るため、端末内の分離・暗号化はADR-0007（オフライン同期）と連携が必要。
- **要修正**：端末側データ分離はADR-0007で扱う旨の相互参照を追記。

---

## 処置方針（推奨）

1. **A1-H1・A1-H2 は決定本文に格上げして即反映**（RLSが実際に機能するための必須条件。実装の落とし穴を決定で塞ぐ）。
2. **A1-M1〜M3** は決定の補足＋未解決事項へ追記。
3. **A1-L1・L2** は前提の注記・相互参照。

> 総括：方向性（行レベル＋RLS）は妥当だが、**RLSを「実際に効かせる」ための3条件（SET LOCAL/リセット・FORCE RLS・フェイルクローズ・非所有者ロール）が決定に欠けており、このまま実装すると分離がサイレントに破綻**する。High 2件を決定へ反映すれば、ADRとして安全な基盤になる。

## 🟡 Medium（第2回）

### A1b-M1. 許可tenant_id集合のアプリ事前解決が横断経路の防波堤性を弱める
- **該当箇所**：決定「グループ管理者：許可tenant_id集合をセッション変数（配列）に事前解決して注入」
- **指摘（攻撃）**：A1-M1の性能対策として、横断許可を「アプリが計算したtenant_id集合」の注入に依存させた。しかしこれは、A1-H2で掲げた「**RLS＝アプリのバグに対する最後の防波堤**」という性質を**横断経路では弱める**：アプリの集合計算にバグ（本来アクセス不可のテナントを含める）があれば、RLSはその集合を信じてしまい**誤った横断アクセス**を許す。防波堤がアプリ入力に依存する自己矛盾。
- **要修正（案）**：注入する集合の正当性をDB側で検証する（例：注入集合とメンバーシップ表の突合をポリシー内 or トリガで確認）、または集合をアプリ入力ではなく**DB内のメンバーシップ由来で導出**する方式（性能はマテビュー/キャッシュで両立）を検討事項に追加。「防波堤性」と「性能」のトレードオフを明示する。

### A1b-M2. 「共有＋テナント上書き可能」テーブルとフェイルクローズの衝突
- **該当箇所**：決定「テーブル3分類：共有＋テナント上書き可能（tenant_id NULL=共有、非NULL=上書き）」＋「フェイルクローズ：tenant_id未一致は全拒否」
- **指摘（攻撃）**：3番目の分類は tenant_id が **NULL 可**（NULL=全テナント共有の既定行）。しかしフェイルクローズの単純ポリシー（`tenant_id = current`）では、**NULL行（共有）が誰にも見えなくなる**（NULL比較が真にならないため）。共有マスタが全テナントで見えないのは機能破綻。この分類には「**tenant_id IS NULL（共有）OR tenant_id = current（自テナント上書き）**」という別ポリシーが要り、フェイルクローズ規則と個別に整合させる必要がある。
- **要修正（案）**：3番目の分類の専用ポリシー（NULL共有の可視化＋自テナント上書きの優先）を明記し、「共有行は全テナント可視だが書込は特権のみ」という書込側の制御も定義する。

## 🟢 Low（第2回）

### A1b-L1. SET LOCAL のトランザクション前提
- **該当箇所**：決定「SET LOCAL app.tenant_id」
- **指摘**：`SET LOCAL` は**トランザクション内でのみ有効**（自動コミットの単発クエリでは無効＝未設定＝フェイルクローズで全拒否）。つまり**単純な読取も含め全DBアクセスを明示トランザクションで包む**必要がある。またコネクションプーラ（PgBouncer等）は**トランザクションプーリングモード**である必要（セッションプーリングだと SET LOCAL の前提や他の想定が崩れる）。この含意が未明記。
- **要修正（案）**：「全DBアクセスは明示トランザクション内」「プーラはトランザクションプーリング」を前提として明記。

### A1b-L2. フェイルクローズのエッジ（空文字列）
- **該当箇所**：決定「app.tenant_id 未設定/NULLは全拒否」
- **指摘**：未設定は `current_setting(..., true)` で NULL になるが、**空文字列がセットされた場合** `''::uuid` は**エラー**になり、NULLとは異なる挙動（クエリ失敗）。NULL・空文字・不正値の扱いを実装で統一しないと、想定外のエラーやフェイルの穴が生じうる。
- **要修正（案）**：「未設定・空文字・不正値はすべて全拒否として扱う（安全側）」と実装ルールを明記。

## 処置方針（第2回・推奨）

1. **A1b-M1・A1b-M2** は決定の精緻化（防波堤性と性能のトレードオフ明示、3番目分類の専用ポリシー）として反映。
2. **A1b-L1・A1b-L2** は前提・実装ルールの明記。

> 総括：第1回のHigh 2件は解消済み。第2回は「性能対策が防波堤性を弱める」「共有テーブルがフェイルクローズと衝突」という**二次的な設計トレードオフ**が中心で、High相当の破綻はない。これらを精緻化すればADR-0001は安定。RLSは「効かせるのが難しい」機構であり、こうした二次論点が出るのは想定内。
