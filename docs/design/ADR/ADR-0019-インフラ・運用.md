## 1. 背景・制約

本システムはMIT OSSとして自社運用、グループ運用、SaaS運用のいずれも許す。一方で、配備者の自由度を理由にデータレジデンシー、RLS、RPO/RTO、P0同期を任意にしてはならない。インフラ製品ではなく、どの配備でも満たす**検証可能な運用契約**を定める。

- 1法域デプロイは1以上のDBシャードで、1シャード5万人を性能設計の基準とする。DB、backup、replica、object、log、trace、監視、通知本文を同じ法域境界に置く。
- 管理系オンライン機能は稼働率99.5%以上、RPO 15分以内、RTO 4時間以内を初期目標とする。現場入力はoffline継続するが、未同期データ保全と復帰後同期は別に保証する。
- PostgreSQL 16＋PostGISを権威ストアとし、BFFはRLSを迂回しない。P0安全／失効をP1業務、P2分析の飽和から守る。
- 静的なシャード構成一覧は`complete`判定の権威である。停止ノードからの動的発見を一覧の代わりに使わない。
- バックアップは「取得成功」ではなく、対応鍵・添付・監査アンカを含めて期限内に復元できた時だけ有効とみなす。

PostgreSQLの継続アーカイブ／PITRは[PostgreSQL 16公式文書](https://www.postgresql.org/docs/16/continuous-archiving.html)、standby運用は[Warm Standby公式文書](https://www.postgresql.org/docs/16/warm-standby.html)を基準にする。

## 2. 決定

### 2.1 配備単位と必須プロファイル

本番はOCI imageと宣言的な構成（IaCまたは同等のversion管理されたmanifest）で配備する。特定cloudやorchestratorは必須にしないが、次の**本番HAプロファイル**を満たさない単一ノード構成は開発・実証専用であり、本番承認しない。

| 層 | 本番HAプロファイル |
|---|---|
| TLS入口／BFF | 同一法域内の2 failure domain以上、BFF 2 instance以上、health/readiness、connection drain、水平増減。TLSは入口から内部serviceまで維持 |
| session/context | 法域内の永続・冗長store。TTLだけでなく権限version失効を反映し、再構築可能。BFF local memoryだけを正にしない |
| DB shard | PostgreSQL 16＋対応PostGIS。primaryと法域内standby、継続WAL archive、PITR、connection pooler。P0/P1はprimary、遅延を許すP2のみread replica可 |
| object | 法域内object storage、保存時暗号化、versioning、未完upload掃除、DB参照との孤立照合。private originを既定とし署名付き短期参照 |
| queue | 失効、同期、quarantine、監査anchorを耐久化。冪等consumer、再試行、dead-letter、最古滞留年齢を持つ |
| 鍵／secret | 法域・用途別KMS/HSMまたは同等。平文secretをimage／Git／backupへ含めず、短寿命workload identityを優先 |
| observability | 法域内collector/store。業務PII・token・生tenant/user IDを出さず、ADR-0020のSLIを収集 |

外部IdP、email、地図tile等を使う場合も、送る属性と法域を台帳化する。業務データを法域外へ転送するproviderしか選べない場合、その機能を無効化するか、法的判断を記録した別設計を要する。

### 2.2 法域・シャード構成の権威

- 配備repositoryに法域ごとの**シャード構成manifest**を置き、`deployment_id`、`jurisdiction`、`shard_id`、状態（`active`/`draining`/`long_term_absent`/`retired`）、接続先secret参照、収容組織、schema version、変更ticket、承認者、発効時刻をversion管理する。secret値やPIIは置かない。
- runtimeはmanifestの署名／digestと単調`configuration_version`を検証し、法域内の冗長storeへ配る。`complete`の対象集合はこのmanifestから得る。service discoveryや応答したDBだけから逆算しない。
- 追加は「standby/backup→migration→RLS/owner/trigger/security-invoker検査→routing追加→観測→active」の順。削除は`draining`で新規割当停止、未同期・queue・参照を排出、最終backupと復旧確認、法定保持確認、二人承認後に`retired`とする。
- `long_term_absent`は自動設定しない。業務・法務影響、対象期間、代替手段を運用者が二人承認し監査する。一時障害は`active`のまま`partial`を返す。
- user→shard物理cacheは既定では作らない。ログインp95 2秒を本番相当試験で満たせない時だけ、ADR-0002の保護・複製・masking条件を満たして追加する。

### 2.3 資源分離と容量設計

入口層がendpoint×認証済み主体からP0/P1/P2を決定し、client申告で昇格させない。各shardのDB接続予算は`max_connections`からDB管理・監視・migration用の固定reserveを先に引き、残りを独立poolへ割り当てる。

| クラス | 用途 | 必須制御 |
|---|---|---|
| P0 | 安全マスタ、権限失効の先行pull | 他classが借用できない予約枠を接続予算の10%以上か8接続の大きい方で確保。短いstatement/queue timeout |
| Auth-P1 | 主体確定後の所属導出 | 業務P1とrole・poolを分離。4接続以上、同時実行上限、allowlist関数のみ |
| P1 | 通常同期、日誌、管理操作 | 通常容量の中心。writeはprimaryだけ。transaction単位の`SET LOCAL`を強制 |
| P2 | 分析、公開REST、import | 全poolの20%以下を初期上限とし、timeout／row／cost上限。必要なら法域内replicaへ逃がす |
| Ops | health、監視、failover、migration | 一般trafficから借用されない固定reserve。superuserをアプリhealthに使わない |

絶対値はDB instanceごとに計算し、合計がDB接続予算を超える構成を起動時に拒否する。基準負荷は、(a) 予測ピークの2倍、(b) 同一tenant監査書込500件/秒、の大きい方とする。P2を上限まで飽和させてもP0のerror率とp95がADR-0020のSLO内でなければ、そのshardを本番承認しない。この500件/秒はS5で検証済みの最低認証profileであり、実測ピークが250件/秒を超える配備では常に2倍側を採用する。

shard増設は5万人到達だけでなく、次のいずれかを**30日予測で超える前**に開始する：storage 70%、primary CPU 60%持続、connection予算70%持続、WAL/archive容量70%、P0/P1 error budget消費、GIS/時系列SLO超過、object容量／転送上限。単一groupは原則分割せず、上限超の例外はADR-0002のcomplete/partial契約を守る。

### 2.4 バックアップ、復旧、保持

1. DBは少なくとも日次base backupと継続WAL archiveを法域内の別failure domain／別権限境界へ暗号化保存する。WAL archiveの未転送時間を5分以内に保ち、15分RPOに余裕を持たせる。
2. 日次復旧点30世代、週次復旧点12世代を最低保持する。法定保持は業務レコードの保持であり、全backupを法定期間保持する意味ではない。削除要求／retentionを永久backupで無効化しないよう、期限到来した世代と鍵依存を削除する。
3. objectはversioningとinventoryを有効にし、DB snapshotと同じ`recovery_set_id`で必要version、監査chain anchor、構成manifest、migration digest、鍵version参照をmanifest化する。鍵そのものはbackupと別管理する。
4. session/context/derived cacheは再構築可能にする。未配送revocation/outbox、quarantine、idempotency ledger、監査chainは権威データとしてbackup対象に含める。
5. backup operatorは本番業務read権限を持たず、restore operatorは定常時に復号権限を持たない。復旧は二人承認、期限付き権限、全操作監査とする。
6. 開発・検証への本番dump直接復元を禁止する。必要時は法域内隔離環境にrestoreし、PII、関係graph、token/secret、位置、添付を用途別allowlistで除外・仮名化してから別datasetとして出す。
7. 月次に自動restore、四半期にDB＋object＋鍵＋監査anchorを含むRTO演習、major migration前後に手動restoreを行う。最新四半期演習がRPO 15分／RTO 4時間を満たさなければreleaseを止める。

### 2.5 障害・縮退・変更

- P0/P1のDB failoverでは、新primaryのtimelineと最後に確定した`server_seq`を確認する。未適用WALがあるnodeへ切り替えてカーソル上限を巻き戻してはならない。RPO超過が疑われる時はwriteを止め、offline入力を継続させて復旧判断する。
- object/KMS障害時に平文保存へ縮退しない。写真は再送可能な保留状態、暗号済みoutboxは端末／queueに保持し、本文だけを先に成功扱いしない。
- IdP障害時も既存sessionはpolicy期限まで利用できるが、新規認証・step-upを要する操作はfail closedとする。ローカル権限失効はIdPと独立して継続する。
- DB migrationはexpand→互換期間→contractとし、appは旧新schemaの重ね期間を持つ。破壊的contract後はappだけのrollbackで復旧できないため、ADR-0021の承認とrestore計画を必須にする。
- 構成変更、failover、backup削除、鍵変更、長期離脱、shard追加／退役は監査対象とする。console手変更は緊急時だけ許し、事後に宣言構成へ反映してdriftをゼロへ戻す。

## 3. 検討した選択肢

| 選択肢 | 評価 | 結論 |
|---|---|---|
| 単一VM＋local DB/volume | 安価だがfailure domain、RPO/RTO、水平化、復旧検証を満たせない | 開発・実証のみ |
| 特定cloudのmanaged serviceへ固定 | 運用を軽くできるがOSS配布と多法域／self-host選択を狭める | 製品固定は不採用。満たすべき契約を固定 |
| Kubernetesを全配備へ強制 | rolling／autoscaleは得やすいが小規模運用者へ過大 | 選択肢。OCI＋宣言構成＋HA契約を必須化 |
| tenantごとにDB／鍵／stackを分離 | 分離は強いがtenant数に比例し、横断・migration・復旧が破綻 | 法令・契約tenantだけの例外profile |
| snapshotだけでbackup | 単純だが15分RPO、任意時点復旧、DB/object整合を保証できない | WAL/PITR＋recovery setを採用 |
| 全trafficで単一pool | 利用効率は高いがP2飽和がP0失効・安全を止める | 優先度別poolを採用 |

## 4. 帰結

- providerを変えても、法域、HA、暗号化、pool、backup、restoreのrelease gateは同じになる。
- 小規模配備でも本番HA profileの費用と運用能力が必要になる。満たせない配備は「本番」と表示できない。
- 静的shard manifestが正しさの一部となるため、application codeと同じreview、署名、rollback、監査が必要になる。
- PITRだけでなくobject・鍵・監査anchorを束ねることで復旧手順は増えるが、「DBだけ戻って写真や証跡が欠ける」成功偽装を防げる。
- poolの分割は未使用枠を生む。P0安全性を資源効率より優先し、再配分は負荷試験を伴う構成変更とする。

## 5. 運用化と未解決事項

方式判断は完了した。以下は本ADRを満たすための配備時入力であり、未決の方式ではない。

- 採用provider／region／failure domain、KMS/HSM、IdP、session store、object store、queue、poolerの製品とversion。
- 法域ごとの予測ピーク、接続予算、shard分割閾値、通知先、法定保持期間。
- S6実機、S7 TLS ingress/pooler/object統合、S9端末鍵、四半期DR演習の実測証跡。

これらがrelease manifestとADR-0021のgateに埋まらない限り、本番releaseは未承認とする。
