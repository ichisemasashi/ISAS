# ADR-0020 敵対的レビュー記録票

| 項目 | 内容 |
|---|---|
| 対象 | [ADR-0020 v1](ADR-0020-監視・SLO.md) |
| レビュー日 | 2026-08-15 |
| レビュアー | Codex（自己敵対的レビュー） |
| 指摘件数 | 8件（High 3／Medium 4／Low 1）。v1へ全件反映 |
| 結論 | 残存 **High 0／Medium 0**。法域内telemetry、SLI分母、P0／復旧SLO、error-budget運用の方式判断は収束 |

## 指摘と処置

| ID | 重大度 | 攻撃／破綻 | 処置 |
|---|---|---|---|
| A20-H1 | High | tenant/user IDをmetric label化すると、RLS外に法域内関係graphを複製し、cardinality攻撃で監視も落とせる | 常設label allowlistを固定。tenant別診断は法域内・制限付きqueryだけで行う |
| A20-H2 | High | auditをbest-effort log exporterへ流すと、collector障害やsamplingで法定証跡が欠落する | audit/security権威eventは業務transaction outboxで耐久化し、一般telemetryから分離 |
| A20-H3 | High | availabilityの分母から5xx、server-side 429、maintenanceを除外すれば、障害時にtrafficを拒否して100%を作れる | eligible requestと除外を固定。正常trafficの429、5xx、timeout、maintenanceを失敗に含める |
| A20-M1 | Medium | API latencyだけを測ると、巨大JS、tile、端末描画が遅い地図を合格にできる | UI SLOは利用可能表示までのRUM＋E2E。API SLIと対で判定 |
| A20-M2 | Medium | 成功requestだけのp95は、遅いrequestをtimeoutで失敗させるほど改善する | latencyをavailabilityと対で判定し、失敗率budget超過をrelease blocker化 |
| A20-M3 | Medium | sample不足を0件＝0msと扱うと、未利用／monitor停止が合格になる | 30試行未満とsignal欠落を`no_data`にし、不合格扱い |
| A20-M4 | Medium | 単一閾値pageは瞬間noiseで疲弊する一方、低速なbudget流出を見逃す | 14.4倍／6倍のmulti-window burnと3日ticketを併用。安全不変条件は即page |
| A20-L1 | Low | alert通知にerror本文やIDを載せるとchat/email経由で法域外へ漏れる | 通知は法域・severity・非PII correlationだけ。詳細は法域内consoleで確認 |

## 収束確認

- **要求との一致**：性能7項目、稼働率99.5%、RPO 15分、RTO 4時間、同期60秒／5分をcatalogへ収録した。
- **S7との一致**：P0先行、idempotency、conflict、quarantine、partial、失効versionをqueue depthだけでなく年齢と結果で観測する。
- **ADR-0019との一致**：P2飽和下のP0、WAL 5分、recovery set、pool/shard/config driftをrelease SLIへ接続した。
- **安全性**：監視停止、sample不足、PII redaction失敗を緑として扱わず、auditを一般logの可用性に依存させない。

よって**ADR-0020 v1を採用（クローズ）とする**。製品選定と実測値はrelease manifest／本番候補環境で確定する。
