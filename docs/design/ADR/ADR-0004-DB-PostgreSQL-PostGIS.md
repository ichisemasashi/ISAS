## 1. 背景・課題（Context）

中核となるデータストアを決める。本システムのDBには、これまでのADRが要求する以下を**単一DBで**満たす必要がある（ADR-0002：1システム＝1DB）：

- **行レベルセキュリティ（RLS）**：ADR-0001が前提とする（PostgreSQL RLS）。
- **地理空間データ**：圃場ポリゴン・メッシュ・GPSログの保持と空間検索（要求仕様F-01〜08、5.2の数万圃場規模）。
- **追記型イベント＋論理削除＋版履歴＋監査**：ADR-0003の不変性3層。
- **性能**：1DBあたり最大5万ユーザー、地図/一覧/ガントが実用速度（5.2 SLO）。
- **時系列データ**：位置ログ・打刻・農機稼働ログ・在庫イベント等、追記型で単調増加するデータ（ADR-0003 A3-L1のストレージ肥大）。

これらを、**追加ミドルウェアを増やさず**、運用の複雑さを抑えつつ満たす選択が要る。

## 2. 決定（Decision）

**PostgreSQL を中核RDBとし、地理空間は拡張 PostGIS で実現する**。時系列・稼働ログも当面はPostgreSQL内で扱う（パーティション＋必要に応じ列指向/TimescaleDB拡張を検討）。

- **RDB＝PostgreSQL**：ADR-0001のRLS（USING/WITH CHECK・FORCE RLS・SET LOCAL）、ADR-0003の追記型/論理削除/版履歴/監査を、すべてPostgreSQLの機能（RLS・制約・トリガ・部分一意インデックス・JSONB等）で実装する。
- **地理空間＝PostGIS拡張**：圃場ポリゴン・メッシュ・GPSログを geometry/geography で保持し、**GiST空間インデックス**で空間検索（近傍・包含）を行う（F-08 近傍圃場、F-01 ポリゴン）。数万圃場規模を前提に空間インデックス設計（ADR-0010の地図タイル/クラスタリングと連携）。
  - **空間×RLSの性能（A4-M1）**：空間クエリはRLSが付与する `tenant_id = current` 述語と組み合わさる。プランナが「tenant_idで絞ってから空間検索」を選べるよう、**`tenant_id` を含む空間複合インデックス**（例：`(tenant_id) B-tree ＋ (geom) GiST` の組合せ、または `gist(tenant_id, geom)` を btree_gist で）を設計し、**スパイクでクエリプランを検証**する（5.2 SLO：地図2秒/p95）。
  - **【v9確定】空間×RLS（PG-M1／PG-M2／PG-M8）**：PostGIS `&&`／`<->` は非leakproofであり、危険な`LEAKPROOF` wrapperやRLS迂回を行わない。単一tenant queryは、DBが再導出した`tenant_id`をSQLへ冗長に等値指定する。bboxは`bbox_min_x/max_x/min_y/max_y`の生成列をtenant付きB-treeで事前絞込し、最後に`geom && ST_MakeEnvelope(...)`で厳密判定する。KNNはtenantごとに明示等値で候補取得し、複数tenantは各tenant結果をapplicationでmergeする。RLSだけの全tenant KNNは禁止する。S2は100万ポリゴン、100 tenant、64接続、各200 query/秒でbbox p95 80.71ms、KNN p95 54.41ms、失敗・skip・他tenant漏洩0となりPASSした（[S2本番規模ログ](../../../spikes/results/S2_LOAD_2026-08-14_PG16_PostGIS.log)）。bbox生成列と索引は[`0009_field_bbox_prefilter.sql`](../../../apps/bff/migrations/0009_field_bbox_prefilter.sql)、queryは`postgres-mvp-repository.mjs`へ昇格済みである。
- **時系列・稼働ログ＝PostgreSQL内で追記型＋パーティション**：位置ログ・打刻・農機稼働ログ・在庫イベント等は、**時間（＋tenant_id）でのレンジ/リストパーティション**で管理し、古いパーティションはアーカイブ/物理削除（ADR-0003 A3-L1、ADR-0017保持ポリシー）。**規模・書込頻度が閾値を超えたら TimescaleDB拡張や列指向を段階導入**する（初期は素のPostgreSQLパーティションで足りる想定）。
  - **パーティション×RLS×一意の接合（A4-H1）**：宣言的パーティションでは既知の制約があるため、以下を接合ルールとして定める（**スパイク必須**）：
    - **一意制約はパーティションキーを含む**（`UNIQUE(..., tenant_id, 時間キー)`）。パーティション跨ぎの全体一意はキー包含が必要。ADR-0003のイベント重複排除・ADR-0001の部分一意もこの制約下で設計する。
    - **【v7までの旧前提】冪等重複排除とパーティションの整合（A4b-M1）**：オフライン同期のリトライはクライアント生成イベントUUIDで冪等に重複排除するが、v7までは「同じイベントを同じパーティションへ入れれば冪等になる」と考え、サーバ受理時刻またはUUID埋め込み時刻を候補としていた。**この前提はv8で撤回済み**であり、現行規則は以下の3機構分離である。
    - **【v8】この目的は v7 まで達成されていなかった（IND3-H5 の是正）**：データモデル設計書は `event_ts` を **`event_uuid`（UUIDv7）から抽出**していたが、**UUIDv7 の埋め込み時刻は端末の壁時計**であり、「決定的」は**再送間の決定性しか与えず、クロックずれを打ち消さない**——**A4b-M1 が掲げた「端末クロックずれで別パーティションに入らないように」は実現していなかった**。しかも `CHECK (event_ts = uuidv7_time(event_uuid))` が**サーバ側の補正を禁止**していた。**実測**：範囲外の時刻は `ERROR: no partition ... found for row` で **INSERT が失敗**し、**電池切れで 1970 にリセットされた端末の①-a法定記録が1件も受理できない**。
    - **【v8】是正＝冪等・物理配置・端末申告時刻を3機構に分離**（データモデル設計書 v10 §5）：**冪等は受理台帳 `event_receipt` が権威**（再送は台帳が弾き、記録済みの `event_ts` を返すので**サーバ採番でも決定性が保たれる**＝v7 までの却下理由「サーバ受理時刻は再送で値が変わる」が解消）。**`event_ts` は「サーバが検証・クランプした業務時点」に再定義**し、**クランプ窓を CHECK でDB側でも強制**する（範囲外が構造的に起きない＝**受理は必ず成功**）。**端末申告の生値 `occurred_at` は保持**し、乖離は **ADR-0007 §2.8** の枠組み（`pending`／監査）へ。
    - **【v8】`DEFAULT` パーティションは置かない（実測で確認した罠）**：未来日付の行が DEFAULT に入ると **後から当該月のパーティションを作成できなくなる**（`updated partition constraint for default partition ... would be violated`）。**パーティションは自動作成ジョブで常に先行作成**する。
    - **【v8】`event_uuid` の UUIDv7 固定は維持**（ソート性・時系列局所性・診断）だが **`event_ts` の導出には使わない**。副産物として **PG-L4（PG18 の組込み `uuidv7()` へ差し替える際に CHECK の DROP/ADD＝全件再検証が要る）の負担も消える**。
  - **パーティションキーの目的競合と一本化（A4c-M1）**：パーティションキーは「RLSプルーニング／空間性能／時間retention／冪等dedup」の**4目的を同時に背負い競合**する。**時間retention（古い時系列をパーティションドロップで削除：A3-L1）は外せない**ため、**時間を主軸に据える**。RLS/空間性能/dedupは以下で両立させる（スパイクで検証）：
    - **サブパーティション**（例：第1軸＝時間レンジ、第2軸＝`tenant_id` のハッシュ/リスト）で、時間retention＋テナントプルーニングを両立。
    - 空間性能は各サブパーティション内の空間索引＋`tenant_id`絞り込みで確保（A4-M1）。
    - イベント冪等は非パーティション受理台帳の`(tenant_id,event_uuid)`一意で成立し、パーティション表のPKには依存しない。
    - ※「`tenant_id`＋UUIDハッシュを主キーにする」案は**時間retentionを壊す**（時間で切れず古いデータをドロップできない）ため不採用。
    - **RLSポリシーは親テーブルに定義し全パーティションに適用**、**`FORCE ROW LEVEL SECURITY` も全パーティション（子）に設定**する（子への非伝播に注意）。
    - **パーティションキーに `tenant_id`（＋時間）を含める**（RLSの絞り込み・分離とパーティションプルーニングを両立）。
    - FK（ADR-0001 A1e-L1：同一テナント内）はパーティション親参照の制約を確認する。
- **高頻度書込の扱い（A4-M2／A4b-L1）**：位置ログ・打刻・稼働ログ等の高頻度・大量書込は、**バッチ/COPYでの一括取込・非同期パイプライン**を用い、1件ごとのトランザクション＋SET LOCAL＋RLSチェックの積み上げを避ける。オフライン同期時の一括流入（A3-M3）もバッチ経路で受ける。**位置ログ自体は監査ログの対象外**とする（それ自体が記録であり、監査で二重記録しない）。**バッチ/COPYは行トリガを発火する**ため、**高頻度×監査が両立するテーブルは、監査を軽量化するか、バッチ後にまとめて監査サマリを作る**（1行ごとの監査トリガでバッチ利点を失わない）。**監査の対象外化はコンプライアンス判断であり、対象外は自己記録イベント（位置ログ・打刻等、それ自体が記録）に限る**。責任追跡が必要な変更は高頻度でも監査する（A4c-L1）。
- **版履歴・監査の実装（A4-M3）**：ADR-0003の版履歴（層②）・監査ログは、**DBトリガ（SECURITY DEFINER・search_path固定：ADR-0001）で追記型テーブルへ書き込む**方式を基本とする（アプリ経路の書き漏れを防ぐ）。
  - **監査テーブルのRLS（A4b-L2）**：監査テーブルもFORCE RLS配下では定義者もRLS対象になるため、**INSERTは監査トリガ/専用ロールのみ許可、一般接続は自テナント分の読取のみ**とするRLSポリシーを定義する（トリガの書込が確実に通るよう許可を明示）。
  - **改ざん耐性と並行性の両立（A4b-M2）**：改ざん耐性の**ハッシュチェーンは単一線形だと高並行・パーティション挿入下で直列化ボトルネック**になり「前レコード」も定まらない。したがって**チェーンの単位を分割（テナント単位／パーティション単位／期間バッチ単位）**するか、**Merkle木・定期的なアンカ署名（一定間隔で全体ハッシュに署名）**を用いる。方式はADR-0017で確定し、並行性と両立させる。**パーティション単位チェーンはパーティションドロップ（retention）でその期間のチェーンが消える**ため、**各期間のチェーン末尾ハッシュに定期アンカ署名し、それを外部/長期保存**して、ドロップ後も「その期間は改ざんされていなかった」証明を残す（A4c-L2）。
  - **【v5】チェーン単位を「(tenant_id, 期間)」に確定する（ADR-0002 IND2-H4 の波及・再裁定）**：A4b-M2 は単位の選択肢を3つ挙げて「方式はADR-0017で確定」と委ねていたが、**ADR-0002 が「1国が規模上限を超えたら 1国=複数DB（シャード）にする」と決めた以上、シャード分割＝テナント単位のデータ移送が必ず一度起きる**。**パーティション単位チェーンでは、1テナント分の `audit_log` を別DBへ移した瞬間に鎖が壊れ、外部保存済みのアンカ署名が実データと一致しなくなる**（移出元は鎖の途中が抜けて検証不能、移入先は他テナントの鎖に異物が入る）＝**要求#17 の改ざん耐性が失われる**。よって**単位は「テナント境界で分割可能」でなければならない**：
    - **チェーンは `(tenant_id, 期間)` 単位**、**アンカ署名も `(tenant_id, 期間)` 単位で外部保存**する。**テナント移送はチェーン丸ごとの移送になり、鎖もアンカも無傷**（移送後も検証可能）。
    - **並行性は「テナント間」については改善する**（チェーンが独立し直列化がテナント境界で分かれる）。**【v6】ただし同一テナント内の直列化は残る（A1h-M3）**——本プロジェクトは **単一グループが1DB上限（5万人）を超えるケースを明示的に想定**（ADR-0002 A2c-M1）しており、**大規模テナント1つに書込が集中する構成では A4b-M2 の懸念（「前レコード」を決めるための直列化）は解消していない**。v5 の「さらに改善する」は方向としては正しいが、**懸念が解消したとは言えない**。
      - **S5 の合格基準を定める**：「**想定最大テナントの書込レートで、監査書込の直列化が性能SLOを侵さないこと**」。**テナント間の独立性が確認できただけでは合格としない。**
      - 不足する場合の分割手段：**期間の粒度を細かくする**（月→日/時間）／**テナント内でサブチェーン＋Merkle ルート**。**いずれも署名数とのトレードオフ**（A1h-L3）。
    - **【v6】「期間」の粒度（A1h-L3）**：**既定は `audit_log` のパーティション境界と同一（月）**とする。見積り例＝**テナント1000 × 月12 ＝ 12,000 チェーン/年**（同数のアンカ署名）。**S5 の実測で並行性が不足する場合に細分化**するが、**署名数が比例して増える**。粒度と署名方式（バッチ化・保管先）は **ADR-0017** で確定する。
    - **【v6】移送時のチェーン閉鎖（A1h-M3）**：**移送は期間境界で行うことを原則**とし、**期間途中に移送する場合は移送時点でチェーンを閉じて末尾ハッシュをアンカ署名し、移入先で新しいチェーンを開始する**（**鎖を2つに割らない**）。ADR-0003 §2.9 の不変条件に反映済み。
    - **代償**：チェーン数とアンカ署名数が `(テナント数 × 期間数)` に増える。**署名のバッチ化・保管・検証手順は ADR-0017**、**並行性の実測は S5** で扱う。
    - **配備モデルの決定がストレージ設計を拘束する例**であり、ADR-0002（シャード化）→ ADR-0004（チェーン単位）という依存を明記する。
- **1DB＝1国（ADR-0002）**：各国システムがそれぞれPostgreSQLインスタンス（プライマリ＋レプリカ）を持つ。周辺（バックアップ・レプリカ）も対象国内（ADR-0002 A2-H1）。
- **接続**：トランザクションプーリングを用いる（ADR-0001 A1b-L1のSET LOCAL前提）。日本初期配備はPgBouncer 1.24.xを採用し、P0／Auth-P1／P1／P2／Opsを別service・role・接続予算へ分ける。

### 2.5 【v7】最低要求 PostgreSQL バージョン（PG-H4／PG-L4／PG検証の所見）

**v6 まで、最低要求バージョンがどのADRにも設計書にも書かれていなかった**（言及は「実行環境＝PG16＋PostGIS 3.4」のみで、方針は ADR-0019 へ先送りされていた）。**しかし設計上の成否がバージョンで変わる箇所がある**ため、ここで確定する。

- **最低要求＝PostgreSQL 15 以上**。決定的な理由は **`CREATE VIEW … WITH (security_invoker = true)`（PG15 以降）**——これが無いと**RLS 有効な表を参照する業務ビューが誰にも0行**になる（PG-H4／ADR-0001 v16 §2.10.2）。**回避策は「ビューを使わない」しかないが、③共有＋上書きの解決・訂正チェーンの有効値・未確定期間の導出はいずれもビューを前提としている。**
- **production採用major＝PostgreSQL 16**。日本初期配備はRDS PostgreSQL 16.14R2＋PostGIS 3.4.6とし、検証済み16.4＋3.4.3との差分をstagingで全migration、RLS、S2、S5、S7再試験してから昇格する。
- **バージョン依存が成否を分ける箇所の一覧**（実装時に確認すること）：

  | 機能 | 必要版 | 影響 |
  |---|---|---|
  | `security_invoker` ビュー | **PG15+** | **最低要求を決定**。無いと業務ビューが0行 |
  | 組込み `uuidv7()`／`uuid_extract_timestamp()` | **PG18+**（要確認） | PG15〜17 は**自作関数が必須**。`CHECK` がそれに依存するため、PG18 で組込みへ差し替えるには**制約の DROP/ADD（大規模テーブルの全件再検証）**が要る＝移行計画に書く |
  | パーティション親への BEFORE ROW トリガ | PG13+ | 「BEFORE はルーティング後」という結論の前提 |
  | パーティション表への UNIQUE 索引（キー包含） | PG11+ | 冪等一意の前提 |
  | `gen_random_uuid()` 組込み | PG13+ | `DEFAULT` に使用 |
  | PgBouncer のトランザクションプーリング＋prepared statements | **PgBouncer 1.21+** | 日本初期配備は1.24.x。ただし正しさをprepared statement対応へ依存させず、transaction終了時のGUC消去と接続再利用を統合試験する |
  | PostGIS 関数の volatility／leakproof | PostGIS 版依存 | 生成列（`ST_Area(geography)`）／`gist(tenant_id, geom)` の索引利用（PG-M2） |

- **アップグレード時の注意**：**生成列・CHECK・索引が PostGIS 関数に依存する**ため、PostGIS のメジャーアップグレードで依存関係が問題になり得る（要確認）。**アップグレード手順の検証を ADR-0019 の運用項目に含める。**

### 2.6 【v10】Mac本番相当ローカル統合環境

- `local-integration`はproduction採用majorと同じPostgreSQL 16＋PostGIS 3.4系を使い、empty DBへ正式migrationを適用する。spike用DDLや別schemaだけでPASSにしない。
- P0／Auth-P1／P1／P2／OpsはPgBouncer 1.24系の5独立instance、別login role、別接続上限で構成する。単一Mac上の論理分離であり、failure domain分離とは表示しない。
- local session/context／失効queueは`local_support` schemaへ置くが、業務schemaとowner、role、migration履歴を分離し、business roleの任意queryを許さない。
- S1／S2／S5／S7と、全poolでの`SET LOCAL`消去、ROLLBACK失敗時の接続破棄をlocal acceptanceへ含める。単一Macの性能値をproduction capacity証跡へ転用しない。

## 3. 検討した選択肢（Options）

| 観点 | 選択肢 | 評価 |
|---|---|---|
| RDB | **PostgreSQL（採用）** ／ MySQL/MariaDB | ◎ PostgreSQLは**RLS・PostGIS・JSONB・部分一意インデックス・強力なトリガ**を備え、ADR-0001/0003の要求（RLS・追記型・版履歴）をネイティブに満たす。MySQLはRLS相当が弱く空間機能もPostGISに劣る |
| 空間 | **PostGIS（採用）** ／ アプリ側計算／専用GISエンジン | ◎ PostGISはデファクトで機能・性能・エコシステムが最良。同一DB内で空間検索でき、RLSと統合できる（別GISエンジンだと分離・RLSが困難） |
| 時系列 | **PG内パーティション＋（必要時）TimescaleDB（採用）** ／ 最初から専用TSDB（InfluxDB等）別建て | ◎ 別TSDBを最初から建てると、RLS・トランザクション整合・運用が二重化。まずPG内で扱い、規模に応じ段階導入する方が単純。要求仕様7章「時系列は別途検討」の方針に沿う |

**却下理由**：MySQL系はRLS・空間・追記型サポートがPostgreSQLに劣り、ADR-0001/0003をネイティブに満たせない。別GISエンジン/別TSDBを初期から建てると、RLS・整合・レジデンシー（ADR-0002）・運用が二重化し、1DB=1国の単純さを損なう。

## 4. 帰結（Consequences）

**良い影響**
- ADR-0001（RLS）・ADR-0003（追記型/版履歴/監査）・空間検索を**単一DB（PostgreSQL+PostGIS）でネイティブに**満たせ、ミドルウェアが増えない。
- 空間・業務・時系列が同一トランザクション/RLS配下に置け、整合とレジデンシー（ADR-0002）が保ちやすい。
- エコシステム（バックアップ・レプリカ・監視・ドライバ）が成熟。

**注意すべき影響・制約**
- **時系列の肥大**：位置ログ・稼働ログはパーティション運用が前提（未対応だと肥大・性能劣化：ADR-0003 A3-L1）。段階導入の閾値監視が要る。
- **PostGISの学習/運用**：空間インデックス設計・投影（SRID）・座標系（海外圃場は各地の投影）を要設計（ADR-0010/0002）。
- **1DB=1国でインスタンス数増**（ADR-0002）：国ごとにPostgreSQL運用（バックアップ・アップグレード）。IaCで標準化（ADR-0019）。
- **RLS＋PostGIS**：空間クエリもRLS配下で走るため、空間インデックスと`tenant_id`複合インデックスの両立を設計する（ADR-0001の性能留意点）。
- **機能の相互制約はスパイクで潰す**：PostgreSQL単体で全機能を賄える利点の裏返しとして、**パーティション×RLS×一意（A4-H1）・空間×RLS性能（A4-M1）・高頻度書込（A4-M2）**が相互に干渉する。これらは要求仕様レビューで挙げた技術リスク（オフライン同期・地図性能・RLS×規模）と直結するため、**基本設計初期にPoC（スパイク）で検証**する。

## 5. 実装・運用上の受入条件

方式上の未解決事項はない。次は決定を実装・運用するための受入条件であり、ADRを再オープンせずrelease manifestで追跡する。

- 時系列は月次rangeを主軸、必要な表だけtenant hash/listを第2軸とする。`DEFAULT` partitionを置かず、3か月先まで自動作成する。保持期限のdropは[日本初期配備profile](../../operations/日本初期配備プロファイル.md#4-日本phase-1保持削除profile)とlegal holdを確認する。
- Phase 1はTimescaleDBを**採用しない**。native partitionで、30日予測のstorage／CPU／connection／WAL 70%または対象SLO超過が2回連続する場合だけ、新ADRでRLS、一意、replica、backup、license、移行を再評価する。
- geometryはSRID 4326で格納し、面積・距離は`geography`または国profileで承認した投影へ変換する。日本profileでJGD2011成果を入力する場合も保存境界でWGS84/4326へ正規化し、原座標系metadataを保持する。
- 日本初期配備は東京regionのRDS Multi-AZ DB cluster（writer 1＋reader 2、3 AZ）とする。P0/P1 writeと権威readはwriter、遅延許容P2だけreaderを使う。
- PostgreSQL/PostGIS minor更新はempty DBと前版snapshotで全migration、RLS/FORCE、owner、trigger、`security_invoker`、bbox/KNN plan、S2/S5/S7を再実行する。
- JSONBはversion付き同期payload、外部取込原文、非索引metadataへ限定する。tenant、scope、status、時刻、金額、数量、農薬安全、FK対象は型付きcolumnとconstraintを正とする。
- `local-integration`はADR-0023 §2.4の構成でproduction migration、5 pool、support schema分離を検証する。local backupや単一nodeのPASSをRDS Multi-AZ／PITR受入へ算入しない。
