## 1. 背景・目標

offline端末、追記型監査、RLS、PWA Service Worker、PostGIS、object、複数shardを持つため、「unit testが通ったimageを手でproductionへ置く」方式では安全性を説明できない。特にDB schemaと端末outboxはapplicationだけを戻しても元に戻らない。

目標は、同じsourceと依存から一度だけ成果物をbuildし、identity/digestを変えずに検証環境からproductionへ昇格すること、そしてrelease可否を人の印象ではなく機械的gateと明示承認で決めることである。supply-chain provenanceは[SLSA](https://slsa.dev/spec/v1.2/)、SBOM形式は[SPDX](https://spdx.dev/)または[CycloneDX](https://cyclonedx.org/)に準拠する。

## 2. 決定

### 2.1 Branch、変更、承認

- `main`を常にrelease可能なtrunkとする。作業は短寿命branch（Codexは`codex/` prefix）で行い、原則2営業日以内に小さなPRとして統合する。長期release branchを通常開発に使わない。
- `main`は保護し、必須CI、最新base、署名済みcommitまたは検証可能なactor、1名以上のreviewを要求する。RLS／認証／暗号／migration／backup／release policyはCODEOWNERS相当の担当を含む2名承認とする。
- production incidentのbreak-glass直変更はSev-1だけに限定し、二人承認、期限付き権限、監査、24時間以内のPR追認と宣言構成への復元を必須とする。
- feature flagはcodeと同じreviewを受け、既定off、tenantまたはdeployment scope、owner、期限、削除条件を持つ。RLS、認証、監査、暗号化、農薬安全検査をflagで迂回させない。
- release versionはSemVerを採り、Git tag、OCI image digest、Web asset digest、migration set、config schemaをrelease manifestへ固定する。tagの再利用と既存artifactの上書きを禁止する。
- 通常の`v<version>`はbaseline tagとし、Production承認済みtagは`production/v<version>` namespaceだけを使う。README、UI build情報、release一覧は現在のrelease classと`Production BLOCKED／AUTHORIZED`を常時表示する。

### 2.2 CI test階層と必須gate

| Gate | PR | Release candidate | 合格条件 |
|---|---:|---:|---|
| Format／lint／type／unit | 必須 | 必須 | 0 failure。生成物差分なし |
| Web/BFF domain・同期状態機械 | 必須 | 必須 | 全test pass。P0先行、冪等、競合、差し戻し、失効、quarantineを含む |
| API contract | 必須 | 必須 | REST schema、error、cursor、idempotency、旧client変換。公開DTOはallowlistと完全一致し、新fieldは既定非公開 |
| PostgreSQL integration | 必須 | 必須 | PostgreSQL 16＋対象PostGISでempty DBへの全migrationと前版からupgrade。RLS、FORCE、owner、trigger、security-invoker、FK、監査chainを実挙動確認 |
| E2E／PWA | 主要PR | 必須 | TLS入口、実BFF runtime、pooler、DB、object、queueを接続。online/offline、更新、再読込、rollback、未同期保持を確認 |
| Accessibility | 主要PR | 必須 | automated axe相当0重大違反。keyboard、focus、screen reader、contrast、200% zoom、locale/RTLは手動checklistを全完了 |
| Security | 必須 | 必須 | secret、SAST、dependency/license、container、IaC scan。脅威model差分review。Critical/High 0、未処置Medium 0 |
| Supply chain | build時 | 必須 | lockfile固定、hermeticに近い再現build、SBOM、provenance、署名、malware/secret scan。artifact digest一致 |
| Performance／SLO | 影響PR | 必須 | ADR-0020全catalog。各30試行以上。P2飽和中P0、S2/S5/S7、本番相当data/networkを含み`no_data` 0 |
| DR／migration rehearsal | migration時 | 必須 | 対応recovery setからRPO 15分／RTO 4時間、rollback/roll-forward、object/監査/鍵整合 |
| Device／encryption | client変更時 | 必須 | S6 iOS/Android実機matrix、S9 cache/outbox別鍵・失効・回復。対象外を未測定のまま合格にしない |
| User acceptance | UX/flow変更時 | MVP必須 | 実対象者で成功率90%、日誌30秒、農薬60秒、SUS 75、offline／未同期理解を達成 |

test fixtureはseedとversionを固定し、PIIを含まないsynthetic dataを既定とする。本番dataが不可欠なrehearsalはADR-0019の法域内隔離restore→allowlist maskingを経て、期限付き環境で行う。flaky testは再実行で緑にせず、最初の失敗を記録しownerと期限を付けて隔離する。安全・RLS・migration・PWA data loss・performance gateは隔離不可とする。

### 2.3 Build onceとartifact

1. review済みcommitから隔離runnerがWeb assets、BFF／workerのhost対応artifact、migration bundleをhost profileごとに一度buildする。Linux等ではOCI image、FreeBSDでは署名済みpackage／application artifactを許す。production secretや長寿命credentialをbuildへ渡さない。
2. dependencyはlockfile、base imageとCI actionはimmutable digestで固定する。runner権限はartifact書込だけとし、PR由来codeへproduction credentialを公開しない。
3. release bundleにsource commit、全artifact digest、SBOM、provenance、署名、migration checksum、config schema、対応API/client範囲、test evidence digestを含める。
4. 同一`host_os`のintegration→staging→canary→productionは同じdigestをpromoteする。OS／architectureが異なるartifactを同一digestと偽らず、同じsource commit、migration、contract testに紐付ける。環境ごとの差は署名／review済みconfigとsecret参照だけにし、環境ごとにrebuildしない。
5. deploy先は署名、provenance、法域、許可registry、digest、config compatibilityを検証し、不一致なら起動を拒否する。

### 2.4 Environmentとdata

| 環境 | 用途 | Data／network |
|---|---|---|
| Local/PR | 高速feedback | synthetic、外部依存stub、単一node可 |
| Integration | PG/PostGIS、object、queue、IdP contract。Mac標準はADR-0023の`local-integration` | synthetic、production非到達、共通domain／migration＋local adapter。同じversion matrixを可能な層で維持 |
| Staging | release candidate総合試験 | production相当構成・規模・TLS。法域内synthetic／mask済みdata |
| Canary | production trafficの限定観測 | 同じ法域・同じ権威DB。tenant安全性を壊さずinstance割合で段階化 |
| Production | 承認済みrelease | macOS／Linux／FreeBSDの承認済みhost profile。本番HA契約を満たし、console手変更禁止 |

非本番からproduction network／KMS／DBへ到達させない。productionから非本番へ生dataを複製しない。email、webhook、push等の外部送信は非本番専用sinkへ固定する。

`local-integration`証跡には`evidence_scope`、source commit、Web／BFF digest、component lock digest、migration set、host arch、runtime versionを必須とする。`fast` profile、未測定、`no_data`、production endpoint guard未確認の結果はIntegration合格にしない。local adapterのPASSは選択したProduction host／provider adapter、HA、DR、実端末、法域内保持を置換せず、release manifestのStaging／Production必須証跡欄は`evidence_scope=local-integration`をschemaで拒否する。

### 2.5 DB・API・offline互換性

- migrationは番号・checksum付きforward-only SQLを正とし、transaction可否、lock/statement timeout、必要権限、容量見積、backup point、roll-forwardを記述する。起動時の暗黙migrationを禁止し、専用migration identityが一度だけ実行する。
- schema変更は**expand→migrate/backfill→互換観測→contract**。expand後は現行と直前app versionがread/writeできることをcontract testする。contractはoffline保持最長14日、active client version、queue/quarantineを確認し、互換clientが残る間は実行しない。
- APIは現行majorと直前majorを受理し、変換可能な旧eventを単一domain modelへ変換する。変換不能eventは法域内quarantineへ耐久保存した後だけclient outboxから削除できる。
- cursor／`server_seq`はfailover、rolling deploy、replica切替で単調性を失わない。migration前後の同一idempotency keyは同じ受理結果を返す。
- PWA Service Workerは待機→利用者通知→未同期確認→activateの順にし、cache schema migration失敗時もoutboxを消さない。serverはN-1 Web assets／APIを互換期間中配信可能にする。

### 2.6 Release判定と段階配備

release candidateは次をすべて満たす時だけproduction承認できる。

1. §2.2の必須gateが全てpassし、`no_data`、失効済み例外、期限切れwaiverがない。
2. ADR-0017 threat modelと敵対的reviewの未処置High/Mediumが0。Critical/High脆弱性、RLS越境、未同期data loss、農薬安全誤判定はwaiver不可。
3. 最新のbackup完全性、四半期restore、migration rehearsal、rollback/roll-forward証跡が有効である。
4. ADR-0020 error budgetが25%以上残り、進行中Sev-1/2がなく、on-call／runbook／ownerが割当済みである。
5. release manifestに`host_os`、OS／kernel／architecture、service管理／isolation方式、filesystem／暗号化、法域、shard一覧version、provider/version、pool、SLO dashboard、artifact、config、migration、互換範囲、承認者を記録する。
6. 対象host上の実UT、実CSV移行rehearsal、backup／restore・四半期DR、security／penetration、24時間連続監視の証跡を同じsource commitとartifact digestへ束縛する。別host、local test、mock、設計書を代替にしない。

`local-integration`の全PASSは上記release判定の前提となる回帰証跡にはできるが、§2.6のproduction承認条件を一つも免除しない。特に選択したhost／provider adapter、実TLS／network、S6/S9、recovery set、手動WCAG／penetration、二人承認をlocal結果でpassへ変更してはならない。

配備は`staging → canary 5% → 25% → 100%`のinstance割合で進める。各段階は最低30分か1,000 eligible transactionsの長い方を観測し、25%段階は最低2時間とする。低trafficで必要event数を得られない場合は合成transactionを加えるが、production実traffic実績と区別する。SLO burn、security event、DB pool/WAL、同期queue、PWA data lossのいずれかが閾値を超えたら自動停止し、承認なしに次へ進めない。

tenantごとに別schemaや別security policyをcanaryにしない。同一DB上のrolling appはN/N-1互換を守る。不可逆な業務動作はfeature flagで限定tenantへ明示opt-inし、結果を監査する。

### 2.7 Rollback、roll-forward、hotfix

- application/configは直前の署名済みdigestへ戻す。rollback後も新schemaを旧appが扱えることを事前testする。
- DB migrationは原則roll-forward。expand段階の未使用objectは残してよい。破壊的contract後の問題、データ破損、cursor巻戻りはwriteを停止し、incident commanderがPITR/recovery setか修正migrationを選ぶ。
- PWAはserver rollbackだけで既に配布済みService Workerを消せない。旧新assetを互換期間保持し、kill switchはoffline outboxをpurgeせずnetwork機能だけを停止する。
- hotfixも同じbuild、署名、最低限のsecurity／contract／DB／E2E gateを通す。緊急性を理由にartifact identity、RLS、backup、reviewを省略しない。後続24時間以内に全gateを完走する。

## 3. 検討した選択肢

| 選択肢 | 評価 | 結論 |
|---|---|---|
| GitFlow＋長期release branch | 並行版には向くがmerge差分と修正重複が増える | 通常はtrunk-based。保守版が生じた時だけ限定branch |
| 環境ごとにbuild | config混入は容易だが検証artifactと本番artifactが別物になる | build once/promoteを採用 |
| 全面big-bang deploy | 単純だが影響半径とrollback判断が大きい | instance canaryを採用 |
| 自動testだけでrelease | 再現性は高いが手動WCAG、実端末、UT、DRを代替できない | 自動＋証跡付き手動gate |
| DB down migrationを常備 | 対称に見えるがdata lossと長時間lockを招く | expand/contract＋roll-forward/PITR |
| test失敗をwaiverして日付優先 | 予定は守れるが安全gateを形骸化する | 安全系waiver不可、その他もowner/期限付き |

## 4. 帰結と未解決事項

- build、署名、SBOM、provenance、実環境E2E、DR、手動確認に運用コストがかかるが、何を本番へ出したかを再現できる。
- 14日offline互換のためcontract migrationが遅くなり、旧fieldの保持期間が長くなる。
- production canaryは同一DBを使うため、schema互換とidempotency不変条件が必須になる。
- release日をgateに合わせ、gateを日付に合わせて弱めない。
- Macでproduction mode artifactをbuildしても、それはbuild onceの候補であり署名済みrelease artifactへの昇格ではない。local証跡とartifact promotionのidentityを分離して記録する。

方式判断は完了した。2026-08-16に実装したGitHub Actions、ECR、SPDX SBOM、BuildKit provenance、cosign/KMS署名、staging→5%→25%→100%と自動rollbackはAWS adapterの実装である。3 OS共通のrelease契約を置換せず、各hostのartifact registry／署名方式／Staging証拠はprofile別に受入する。本ADRの採用といずれか一つのpipeline実装は、他hostまたは本番releaseの承認を意味しない。
