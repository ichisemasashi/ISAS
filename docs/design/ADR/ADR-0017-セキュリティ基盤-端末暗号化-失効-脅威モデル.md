## 1. 背景・保護目標

本システムは法定農薬記録、位置／労務、経営情報、写真、未同期イベント、OIDC token、tenant／scope権限を扱う。保護目標は機密性だけでなく、次の優先順位とする。

1. **tenant／scopeの越境を防ぐ**。暗号化はRLS・認可の代替ではない。
2. **未同期の法定／現場記録を失わない**。失効と暗号消去でoutboxを巻き込まない。
3. **失効をオンライン経路へ迅速かつ決定的に反映**し、オフラインの不可避な遅延は期限／段階縮退／復帰時再検証で閉じる。
4. **鍵侵害の爆発半径を法域・用途別に制限**し、ローテーション／破棄／復旧を監査できるようにする。
5. **改ざん・リプレイ・なりすましの証跡を残す**。機密情報自体はログに残さない。

参照指針は [NIST SP 800-111（端末ストレージ暗号化）](https://csrc.nist.gov/pubs/sp/800/111/final)、[NIST SP 800-57 Part 1 Rev.5（鍵管理）](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)、[NIST SP 800-63B-4（認証器・失効）](https://pages.nist.gov/800-63-4/sp800-63b.html)、[OAuth 2.0 Security BCP / RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)、[WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)とする。

## 2. 脅威モデル

### 2.1 保護資産と信頼境界

| 種別 | 対象 |
|---|---|
| 主体／認証 | OIDC token set、BFF session、MFA／回復経路、外部client鍵 |
| 認可 | context ID、AuthContext、membership/role/scope/capability version、Offline Authorization Snapshot |
| 業務データ | tenant固有行、法定記録、位置／労務、写真、輸出物、outbox |
| 証跡／鍵 | 監査ログ、actor仮名マップ、署名鍵、KEK/DEK、バックアップ |
| 可用性 | 認証P1プール、P0同期／失効経路、KMS/HSM、シャード構成一覧 |

信頼境界は①端末OS／ブラウザ／ネイティブ、②ブラウザ→BFF、③BFF→業務コア、④業務コア→PostgreSQL、⑤アプリ／DB／object storage→KMS/HSM、⑥IdP／権限DB→失効配信に分ける。tenant／scopeはADR-0009 v4 §2.5.1の単一経路だけで②〜④を通過する。

### 2.2 攻撃者・前提・非保証

- 外部攻撃者、別tenantの正規ユーザー、権限を失った元ユーザー、端末拾得者、悪意／過失の運用管理者、侵害された依存ライブラリ／IdP／内部serviceを想定する。
- TLS、OS更新、ブラウザsandbox、KMS/HSM、IdP自体は適切に運用される前提だが、単一障害時の爆発半径を分離と監査で縮める。
- **PWAの非抽出WebCrypto鍵は、鍵バイトの持ち出しを難しくするだけ**である。同一originで実行中のXSS／改ざんService Workerは復号APIを呼べるため、ネイティブOSキーストアと同等の強い端末束縛とは扱わない。
- root/jailbreak済み端末、完全なBFF/業務コア侵害、KMS管理者とデータ管理者の共謀を暗号化単独で防ぐことは保証しない。検知・権限分離・インシデント対応で扱う。

| ID | 脅威 | 必須管理策 |
|---|---|---|
| T1 | 端末紛失／共有端末の別ユーザーがcache/outboxを読む | データ分類別暗号化、ロック、同期済みcache鍵の暗号消去、outboxの回復envelope |
| T2 | XSS／改ざんService WorkerがCookie利用や復号済みデータ窃取を行う | HttpOnly BFF Cookie、厳格CSP/Trusted Types、依存固定・SRI可能範囲、ビルド／配備時の成果物署名検証とロールバック、機密データ最小化 |

## 3. 決定

### 3.1 サーバ・バックアップ・添付の保存時暗号化

- DB volume、backup、object storage、スナップショットは各基盤の保存時暗号化を必須とする。TLS終端より後ろの内部通信もTLSとし、平文backup/ダンプを常設しない。
- OIDC token set、外部client secret、TOTP seed、回復鍵秘密部、actor仮名マップ、配備用secretは**アプリケーション層のenvelope暗号化**を追加する。通常業務行はRLS・基盤暗号化を主とし、検索性を壊す無差別な列暗号化はしない。
- KEKは**法域／用途別**（token/session、object/backup、仮名マップ、offline recovery、署名）にKMS/HSMで分離する。tenant分離の権威はRLSであり、初期からtenantごとのKMS鍵を大量生成しない。契約／法令が要求するtenantだけ専用KEKを選べる。
- ciphertextは鍵version、アルゴリズムprofile、法域、用途、関連リソースIDをAADに束縛する。鍵IDをハードコードせず、新規書込はactive version、読取は新旧重ね期間の許可versionに限る。
- 署名鍵と暗号化鍵を共用しない。鍵の生成、有効化、ローテーション、復号／署名、破棄、管理ポリシー変更を監査する。鍵管理者に業務DBの平文参照権限を与えない。

### 3.2 端末暗号化とデータ分離

| 端末データ | 保護と失効時の扱い |
|---|---|
| 同期済み業務cache／位置／写真 | `cache_key`でAEAD暗号化。logout、ユーザー失効、tenant/scope剥奪、保持期限で対象key slotを破棄し**暗号消去**。データ本体は後刻小分け削除 |
| 未同期outbox／未送信法定記録 | イベントごとのcontent keyでAEAD暗号化。content keyを①有効なOffline Snapshot下のlocal keyと②法域の`offline_recovery` public keyの**二経路でwrap**。失効時は①を破棄し、ciphertext＋②は隔離保持。再認証後の送信または監査付き管理者回復だけを許す |
| 農薬安全マスタ／Snapshot | 機密性に加え、署名・version・期限・法域／tenant／installation束縛を検証。SnapshotはAPI Bearerに使わない |
| 下書き | ユーザー所有の端末暗号化領域に保存。tenant未確定の下書きを他tenant鍵で再利用せず、確定時に参照先tenant／権限をサーバ再検証 |

- **PWA**：OSのフルディスク暗号化／ブラウザprofile分離を運用要件とし、WebCryptoで生成した非抽出wrapping keyを利用できる場合は利用する。ただし活性XSS耐性は無いため、機微データの長期offlineと強い端末束縛は保証しない。共有OSアカウントでの保存を禁止する。
- **ネイティブ**：local wrapping keyをOSキーストアの非抽出鍵に束縛し、ハードウェアbackedが利用可能なら優先する。キーストアの利用者認証、デバイスlock／生体認証要件はデータ分類に合わせる。attestationの有無は検証し、未対応を「束縛済み」と表示しない。
- AEADのnonce再利用を禁止し、暗号文レコードに`key_version`/`algorithm`/nonce/tag/AAD schema versionを持つ。独自暗号を作らず、配備crypto profileで承認したAEAD／key-wrapだけを使う。
- 画面ロックは復号済みキャッシュをメモリから解放する。通知、サムネイル、OSバックアップ、クラッシュレポートへ平文を出さない。

### 3.3 失効経路

失効は「キャッシュをできるだけ早く消す」ではなく、**権限トランザクションと同時に永続する単調version付きイベント**とする。

1. membership/role/scope/user/MFA状態/external clientを変更する権威DBで、対象の`authorization_version`を単調に更新し、同一transactionのoutboxに`revocation_event_id`、法域、主体／tenant／scope、新version、理由、発生時刻を追記する。versionは単一の全体値ではなく、`user`／`membership`／`tenant_policy`／`external_client`ごとの`(target_type,target_id)`を単位とする。context/Snapshotは判定に使った**依存version集合**を持ち、どれか1つでも旧ければ再導出する。
2. 法域内配信がsession store、context store、所属キャッシュ、Offline Snapshot registry、外部client cacheを冪等に無効化する。配信中断は再試行し、dead-letterと最古未適用年齢を監視する。
3. BFFはcontext解決時に現在versionを再導出する。機微操作はキャッシュを使わず権威DBを照会する。一般操作は最大60秒、contextは最大5分だが、イベント受信時はTTLを待たず破棄する。
4. IdP back-channel logout／token revocationはローカルsession失効と分離する。IdP停止中もローカル失効を成功させ、上流失効は監視付きで再試行する。MFA回復・認証器削除は当該ユーザーの全session/context/Snapshotを失効させる。
5. オフライン端末への即時失効は保証しない。Snapshotの24h/72h/最長14d段階縮退を守り、次の通信で**P0失効を業務pull/pushより先に取得**する。pushは現在権限と作成時Snapshot/versionを再検証し、失効後の法定記録を破棄せず回復キューへ隔離する。
6. シャード欠落中の横断失効状態は`partial`とし、`complete`と誤認しない。権威確定や機微横断操作は全必要シャードのversion確認までfail closedとする。

### 3.4 鍵ライフサイクル

- 鍵インベントリはowner、法域、用途、algorithm、version、状態（pre-active/active/decrypt-only/revoked/destroyed）、作成／交代／破棄日、依存データを保持する。
- 既定の最長cryptoperiodは、オンライン署名／token/session envelope key=90日、保存用KEK=1年とする。法令／基盤制約で短縮可能とし、侵害疑い、管理者変更、algorithm廃止、誤公開は期間を待たず交代する。
- 交代は「新鍵で書込→旧鍵をdecrypt/verify-only→バックグラウンドrewrap→参照0確認→破棄」とする。署名公開鍵は発行済み成果物の最長有効期間＋時計許容差まで検証用に保持する。
- KMS障害時に新しい平文secretを永続化しない。復号済み値を無期限cacheしない。すでに暗号化されたoutboxは消さず、復旧まで送信保留とする。
- backup復旧試験は対応鍵versionの復号も含める。暗号文だけ復旧できても成功としない。破棄は保持義務・backup参照・監査アンカを確認し二人承認とする。

### 3.5 通信・添付・エクスポート／ログ

- 外部／内部ともTLSを必須とし、リバースプロキシが付与する主体・client certificate情報は信頼済みproxyリストとmTLS経路からのみ受け入れる。公開リクエストの同名ヘッダはedgeで削除する。
- 写真／ファイルはtenant・用途・サイズ・MIME／拡張子allowlistを束縛した短寿命upload権限で隔離領域へ受け、スキャン／再エンコード後に公開可能状態へ昇格する。object keyをクライアントに自由生成させない。
- E2E暗号化を既定にしない。サーバは農薬・在庫・法定日付・tenant・マルウェアを再検証する必要がある。追加のE2E要求は、サーバ検証を失う影響と鍵回復を別ADRで裁定する。
- 構造化ログはイベント種別ごとのallowlistで出力する。token、Cookie、認可コード、PKCE verifier、TOTP seed、回復コード、署名／暗号秘密鍵、平文outbox、写真本体を出力しない。監査actorは仮名IDとし、相関ID／session仮名ID／`authorization_version`／鍵versionを追跡できるようにする。
- 輸出は機微操作としてstep-up、最小scope、件数／頻度制限、監査、短期限download URL、完了後自動削除を必須とする。

## 4. セキュリティゲートと検証

| ゲート | 合格基準 |
|---|---|
| AuthContext | ADR-0009 v4のBFFテスト、S8 12群、主体／書込tenant置換と集合拡張を拒否、ROLLBACK失敗接続を破棄 |
| 端末暗号化（S9） | PWA/ネイティブごとに鍵非抽出性・ロック・暗号消去を確認。同期済みcache消去後もoutbox ciphertext＋recovery wrapが残り、再認証後に回復可能 |
| 失効（S9） | membership/role/scope/MFAの各失効がsession/context/cache/Snapshotへ冪等反映。二重・逆順・欠落後再送で最新versionへ収束し、シャード欠落は`partial` |
| 鍵交代（S9） | 新旧重ね期間に旧ciphertext/署名を読め、rewrap後に旧鍵参照0を確認。backup復旧は対応鍵と監査アンカを含む |
| Web/PWA | CSP・Trusted Types・CSRF・Cookie・Service Worker更新・機密ログ非出力を自動検査。XSSテストで「非抽出鍵でも活性origin侵害は防げない」前提を維持 |
| ファイル／輸出 | tenant差替え、パス、MIME、サイズ、マルウェア、期限URL、step-up、自動削除を結合試験 |

リリース前に脅威T1〜T10と管理策を機能差分ごとに更新し、High/Mediumの未処置を禁止する。依存ライブラリ・container/IaC・secretスキャン、SBOM、署名付き成果物、パッチSLAはADR-0021、監視／アラート数値はADR-0020、KMS/HSM/backup/DRの製品と配置はADR-0019で確定する。

## 5. 影響・残留リスク

**良い影響**

- 端末失効時の機密性と「未同期は失わない」を、cache/outboxの別鍵で両立できる。
- 失効が単調versionと永続イベントで収束し、TTL・メッセージ配信のどちらか一方だけに正しさを預けない。
- tenant／scope注入と鍵／データの境界が接続し、暗号化済みデータの越境復号も監査できる。

**制約／残留リスク**

- PWAは活性XSS／同一OSアカウント共有に対する強い鍵保護を保証できない。高機密／長期offlineはネイティブ端末を推奨する。
- オフライン失効は次回通信まで遅延する。即時失効とオフライン継続は同時に完全達成できないため、残留リスクをSnapshot期限と運用者の延長監査で受容する。
- offline recovery private keyは未同期データを復号できる高価値資産である。HSM、二人承認、tenant/イベント束縛、全復号監査が必須となる。
- KMS/HSM障害時は一部の新規session、secret発行、復号、回復が停止する。平文へ縮退せず、P0の暗号済みoutbox保持を優先する。
