## 1. 決定

- Phase 1の正規入力形式はUTF-8 CSVとする。Excelは利用者がCSVへ保存して取り込み、XLSXの数式・macro・外部linkをserverで解釈しない。旧MITサービス等のsource固有変換は、正規CSVを生成する法域内adapterとして正規pipelineの前に置く。
- 対象は圃場→作業記録→農薬履歴の順とし、列mapping、形式・参照整合、file内／DB内重複、件数・error reportを業務table変更前に行う。最大50,000行、200列とする。
- raw inputはprivate object storageへSSE-KMSで置き、tenant、作成者、SHA-256、size、dataset、mapping version、状態をjob ledgerへ記録する。malware検査完了前にparserへ渡さない。raw inputとerror reportは30日後に削除する。
- 作成は`Idempotency-Key`＋file SHA-256、確定はjob versionの楽観lockを使う。確定transaction内でRLSと参照・重複を再評価し、全行成功か全行rollbackとする。部分成功を正常完了に見せない。
- DB owner、migration role、bypassrlsで取り込まない。BFFが認証主体・tenant・`migration:manage`を確定し、通常業務roleでRLSを通す。確定者、入力hash、mapping、結果、失敗理由を監査する。
- 農薬履歴は初期使用回数と最終使用日だけを移し、存在しない散布明細を生成しない。正本masterを解決できない行はerrorとする。
- exportはRLS後の範囲だけをUTF-8 BOM付きCSVで返し、先頭`= + - @`をformula neutralizationする。上限100,000行、生成物は7日で削除する。
- rehearsalは本番相当件数の匿名化copyで2回行い、件数、hash、重複、参照、時刻、面積、農薬集計、監査、rollbackをsource ownerと業務ownerが承認する。

## 2. 選択肢

| 選択肢 | 結論 |
|---|---|
| staging job→検査→冪等確定 | 採用。再実行・監査・RLSを両立 |
| CSVを直接業務tableへCOPY | 不採用。RLS、重複、参照、監査を迂回しやすい |
| serverでExcelを全面解釈 | Phase 1不採用。macro・式・日付型の攻撃面と曖昧さが大きい |
| 行単位の部分commit | 不採用。再実行時の境界が不明確になる |

## 3. 受入条件

現行MVPのCSV APIとUIは方式を実装済みである。production object storage／malware scan接続、旧source adapter、実データrehearsalは配備・移行作業として残るが、方式判断に未解決事項はない。
