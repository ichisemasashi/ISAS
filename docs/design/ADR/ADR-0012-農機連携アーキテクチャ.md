| 関連 | [ADR-0001 RLS](ADR-0001-マルチテナント分離-行レベル-RLS.md)、[ADR-0003 データライフサイクル](ADR-0003-データライフサイクル-追記型-論理削除-版履歴-監査.md)、[ADR-0007 同期](ADR-0007-オフライン同期方式.md)、[ADR-0008 API](ADR-0008-API方式.md)、[ADR-0013 外部API](ADR-0013-外部API-Webhook.md) |

## 1. 背景

農機データは、媒体、vendor、schema、単位、座標、時刻精度、再送方式が揃わない。vendor APIを中核にすると契約変更や提供停止が業務継続を止め、各adapterが業務tableを直接更新するとRLS、重複、監査、食品安全判定を迂回する。ISOBUS／ISO-XMLとADAPTはそのまま永続schemaにせず、概念と交換境界の参照に使う。

## 2. 決定

### 2.1 接続方式と責務境界

- 中核経路は利用者が明示投入するISOBUS／ISO-XML、CSV等のファイル取込とする。メーカー／農機クラウドAPI、DataConnect等は同じadapter契約へ接続する補助経路であり、停止しても既存データ閲覧とファイル取込は継続する。
- adapterは`detect → parse → canonicalize → validate report`までを担う隔離processとし、業務DB資格情報、tenant決定権、作業日誌確定権を持たない。BFF／import serviceが現在membership、`machinery:import`、tenant、field scopeを確定し、通常roleでRLSを通してcommitする。
- adapter packageは`adapter_id`、SemVer、対応format／version、入力上限、出力schema version、license、SBOM、署名をmanifest化する。未署名、未承認version、外部通信を要求するparserはproductionで実行しない。

### 2.2 共通データモデル

共通modelは次のaggregateを持つ。

| aggregate | 主な属性 | 不変条件 |
|---|---|---|
| `Machine`／`Implement` | vendor namespace、外部ID、機種、serialの暗号化値、capability | tenant内binding。serialを表示・分析用IDにしない |
| `MachineOperation` | 種別、開始／終了UTC、operator参照、machine／implement、source | 開始≦終了。作業日誌の正本とは別 |
| `TrackObservation` | UTC、geometry、精度、速度、heading、品質 | 生軌跡はPII分類。作業中・同意・保持policyを満たす時だけ保存 |
| `HarvestObservation` | geometry／field候補、収量、水分、品質、単位、精度 | 原値・原単位を保持し、正規化値と変換versionを併記 |
| `ApplicationObservation` | 資材候補、rate、面積、時刻、geometry | 農薬使用記録へ自動確定しない。安全masterと人の確認が必要 |
| `Prescription` | grid／polygon、目標rate、単位、対象machine capability、版 | export前に二人承認し、署名・hash・失効日時を付与 |
| `SourceEnvelope` | source、外部record ID／revision、取得時刻、content hash、adapter version | 原入力と正規化結果を追跡可能にする |

識別子は`source_system + external_namespace + external_id`をtenant内で束縛し、vendor ID単体を全体一意とみなさない。値はSI基準のcanonical値へ変換するが、原値、原単位、座標参照系、timezone／offset、変換versionを失わない。曖昧なローカル時刻、未知単位、無効geometryは推測補完せず保留する。

### 2.3 圃場・作業との照合

- 明示されたfield ID、境界との重なり、時刻、machine割当から候補と`match_confidence`／根拠を出す。境界近傍、複数圃場重複、低精度測位は管理queueへ送る。
- 農機観測は非権威の根拠資料であり、作業日誌、打刻、在庫、農薬法定記録を黙って上書きしない。確定操作は元観測へのlink、変更前後、actor、理由を監査する。
- 同一source recordの再送は`tenant + source + external record + revision`、revisionがない形式はcontent hashで冪等化する。異なる内容の同一keyは上書きせず競合とする。

### 2.4 取込・永続化・保持

1. private object storageへserver生成keyでstagingし、size、MIME/signature、malware、archive展開数／展開後容量／path traversalを検査する。
2. 隔離adapterがcanonical batchと行別警告を生成する。raw hash、adapter／mapping version、件数、棄却数をjob ledgerへ記録する。
3. previewでfield／machine／operator mapping、単位、時刻、重複、低confidenceを人が確認する。
4. commit時に権限と参照を再評価し、追記型観測eventを冪等登録する。大量処理は再開可能chunkとし、chunk境界・cursorを監査する。
5. raw fileは既定30日、精細trackは国別profileの短期保持後に削除または必要粒度へ集約する。法定記録へ採用した値は根拠hashを残し、raw削除後も採用経路を説明可能にする。

メーカーAPI tokenは法域内secret storeでtenant／connectorごとに暗号化し、最小scope、rotation、失効、取得cursorを管理する。日次取得は`取得上限時刻`を固定し、page途中失敗を完了扱いにしない。provider由来データの保存・再配布条件をconnectorごとにregistry化し、許可されないDWH／API出力を止める。

### 2.5 送出

可変施肥等の農機向け出力は読取取込と権限を分離し、`machinery:prescription:approve`を持つ異なる二者の承認、対象圃場、machine capability、単位、上限、版、期限を検証する。artifactを署名し、download／export actorとhashを監査する。自動送信、遠隔制御、安全機能の迂回は本ADRの対象外とする。

## 3. 選択肢

| 選択肢 | 結論 |
|---|---|
| 共通model＋隔離adapter、ファイル主軸 | 採用。vendor停止耐性と一貫したRLS／監査を両立 |
| vendor APIを直接業務modelへ写像 | 不採用。契約・schema変更が中核へ波及する |
| 原formatをそのまま業務DBへ保存 | 不採用。検索、単位、重複、圃場照合がadapterごとに分裂する |
| 観測から日誌・農薬記録を自動確定 | 不採用。測位・mapping誤りが法定／食品安全記録へ伝播する |

## 4. Phase 3受入条件

1. 最低2種類の異なるsource fixtureを同じcanonical modelへ変換し、同一入力再送0件、revision更新、途中再開、archive攻撃、未知単位を試験する。
2. 他tenantのmachine／fieldへのmapping、権限失効後のcommit、adapterからのnetwork／DBアクセスを拒否する。
3. 10万観測／jobでP2 poolを飽和させてもP0失効とP1現場APIのSLOを侵害しない。
4. 原値からcanonical値、候補照合、人による確定、業務記録までを監査で往復追跡できる。
5. provider停止を模擬し、ファイル取込と保存済み観測の利用が継続する。

実partner、契約、sample data、adapter SDKの利用条件は実装開始時のconnector台帳で確定する。これらが未取得の間、個別メーカーconnectorを「対応済み」と表示しない。

capability catalogでは本ADRだけの状態を`planned`とする。最初のconnectorを`implemented`以上へ変更するには、契約主体・利用規約・再配布・保持、匿名化した実sample hash、実機・firmware・adapter digest、圃場照合、人による日誌確定、単位変換、再送、失効、provider停止時のfile取込継続を証跡化し、connector ownerと独立確認者が承認する。詳細な入力項目は[初回農機connector受入契約](../../product/初回農機connector受入契約.md)を使う。
