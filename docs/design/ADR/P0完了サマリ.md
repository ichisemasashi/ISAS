## 2. スパイク（PoC）で早期検証すべき項目

要求仕様レビューで挙げた技術リスク（オフライン同期・地図性能・RLS規模）と直結。**基本設計初期に潰す。**

| # | 検証項目 | 出所 | 合格基準 |
|---|---|---|---|
| S1 | **パーティション×RLS×一意×FORCE RLS**の接合（宣言的パーティションで分離・一意が両立するか） | ADR-0004 A4-H1 | テナント分離と一意性が両立、FORCE RLSが全パーティションに効く |
| S2 | **PostGIS空間クエリ×RLS**の性能（tenant_id含む複合索引でプランが崩れないか） | ADR-0004 A4-M1 | 地図初期表示 2秒/p95（5.2.1） |
| S3 | **オフライン同期の冪等重複排除×パーティション**（同一イベントが同一パーティションに入るか） | ADR-0004 A4b-M1／ADR-0003 A3-M3 | リトライ・時刻ずれで重複しない |
| S4 | **RLS×規模**（1DB=5万ユーザーで許可集合注入・毎リクエスト権限導出が性能内か） | ADR-0001／ADR-0005 A5b-M2 | 一覧・API 500ms/p95（5.2.1） |
| S5 | 監査**ハッシュチェーンの並行性**（単位分割/アンカ署名が高並行で成立するか） | ADR-0004 A4b-M2 | 並行挿入で直列化ボトルネックにならない |

## 4. ADR間の波及・相互依存（トレーサビリティ）

P0は密結合で、後発ADRが先行ADRを更新した箇所がある。

- **ADR-0003 → ADR-0001 v7**：下書き（層③）のために ADR-0001 に第4分類「ユーザー所有」を追加。
- **ADR-0002 ↔ ADR-0001**：認証ブートストラップ（A1e-M1）と複数国ID解決（A2-M1）、1DB横断（A2b-M2）。
- **ADR-0004 ↔ ADR-0001/0003**：パーティション×RLS×一意、追記型イベントの物理設計。
- **ADR-0005 ↔ ADR-0001**：RBAC→RLS写像（集合注入・本人起点・個人データ）。
- **ADR-0015 ↔ ADR-0002/0004**：法域・SRID・暦日/瞬間の型区別。

> 教訓：**個別に正しい決定が、組み合わせ・スケールの端で緊張を生む**（振り子）。ADRを1本ずつだけでなく**接合部でレビュー**することが有効だった。クローズ済みADRも、波及時はバージョン注記して更新する運用が機能した。

## 6. 次の一手（推奨）

1. **スパイク（S1〜S5）に着手**：技術リスクを実装前に潰す（特にS1パーティション×RLS、S2空間×RLS）。
2. **M3（データモデル設計）**：P0を土台にスキーマ・ERD・RLSポリシーを起こす。スパイクと並行。
3. **エスカレーション（E1〜E4）を意思決定者へ**：特にE1（受託者エビデンス権）は要求仕様にも関わる。
4. 残りのADR（P1）を優先度順に起票→敵対的レビュー→クローズ。

> P0（土台）が固まったので、**「S（スパイクで検証）」「M3（スキーマに具体化）」「P1（残ADR）」を並行**で進めるのが効率的。エスカレーション事項は早めに意思決定へ上げる。
