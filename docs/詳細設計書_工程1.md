## 1. この工程で実現すること

イチセが置く1つのISASに、招待した人だけが入る。管理者入口と利用者入口は別とする。ログイン後は「入ったことが分かる」入れ物で足りる。

工程1で動かす論理ブロックは、基本設計書 §10 のとおり、入口、認証・アカウント、利用者による招待、管理者による招待の取消しである。関係の切断、作業場所、圃場、塗り、ガント、指示、日誌、言語切替の本機能は作らない。

### 1.1 工程1の部品

- **入れ物。** 処理は Clojure、画面は ClojureScript とする。その間は JSON の API でつなぐ。後工程の地図も、この同じ分け方に足す。置くときは同じオリジンの1つのISASとする（Clojure が API と ClojureScript の成果物を出す）。HTML フォームだけで完結させない。
- **保存。** アカウントは同じマシンの SQLite ファイルに残す。パスは `data/isas.sqlite` とする。SQLite ファイルは Git に入れない。別プロセスのデータベースは工程1では置かない。
- **最初の管理者。** 置くマシン上の設定ファイルのメールとパスワードから作る。管理者が0人のときだけ作る。既に1人以上いれば設定ファイルのパスワードでは上書きしない。画面の初期登録は置かない。
- **再設定メール。** 同じ設定ファイルのSMTP欄で送る。特定の配信サービス名は固定しない。招待メールは送らない。

初期設定は環境変数にしない。置くマシン上のファイル `data/isas.conf` とする。Git にはサンプル値を載せたこのファイルを置く。置くマシンでは値を直す。実パスワードに置き換えた内容はコミットしない。ファイルが無い、または読めないときは起動を止める。

形式は1行1項目の `名前=値` とする。空行と `#` で始まる行は無視する。YAML や TOML の製品は必須にしない。

| 名前 | 用途 |
|---|---|
| `admin_email` | 最初の管理者のメールアドレス |
| `admin_password` | 最初の管理者のパスワード（管理者が0人のときだけ使う） |
| `smtp_host` | SMTP のホスト |
| `smtp_port` | SMTP のポート |
| `smtp_user` | SMTP のユーザ。空なら認証しない |
| `smtp_password` | SMTP のパスワード |
| `smtp_from` | 再設定メールの差出人 |
| `public_url` | 再設定リンクの先頭（例: `https://isas.example`） |
| `smtp_starttls` | `1` なら STARTTLS する。省略時は `1` |

`admin_email` が、すでに利用者として存在するアドレスなら、起動を止める。同じアドレスを両方に置かないためである。

パスワードのハッシュは bcrypt とする。コストは 12 とする。

## 2. 画面と経路

パソコンのブラウザでもスマホのブラウザでも、同じ経路を使う。工程1では画面を端末別に分けない。画面の経路は ClojureScript が扱う。データの読み書きは Clojure の API を呼ぶ。パスワードや取消しを GET の API で受けない。

未ログインで保護された画面を開いたときは、その側のログインへ進む。利用者のログイン状態で管理者の保護画面を開いても入らない。その逆も同じとする。

公開の新規登録の経路は置かない。

### 2.1 ブラウザの経路（ClojureScript）

| 経路 | 誰 | ログイン | 役割 |
|---|---|---|---|
| `/` | 利用者 | 不要 | 利用者ログイン。入済みなら `/home` |
| `/reset/request` | 利用者 | 不要 | パスワード再設定の依頼 |
| `/reset` | 利用者 | 不要 | 案内のリンクから新しいパスワードを決める。トークンはクエリ `token` |
| `/home` | 利用者 | 必要 | 入ったことが分かる。招待とパスワード変更への出口 |
| `/invite` | 利用者 | 必要 | 利用者を招待し、初期パスワードをその場で見せる |
| `/password` | 利用者 | 必要 | 本人のパスワード変更 |
| `/admin` | 管理者 | 不要 | 管理者ログイン。入済みなら `/admin/home` |
| `/admin/reset/request` | 管理者 | 不要 | 管理者の再設定依頼 |
| `/admin/reset` | 管理者 | 不要 | 管理者の新しいパスワード。トークンはクエリ `token` |
| `/admin/home` | 管理者 | 必要 | 入ったことが分かる。招待・取消し・パスワード変更への出口 |
| `/admin/invite` | 管理者 | 必要 | 利用者を招待し、初期パスワードをその場で見せる |
| `/admin/users` | 管理者 | 必要 | 取り消されていない利用者の取消し |
| `/admin/password` | 管理者 | 必要 | 本人のパスワード変更 |

再設定メールのリンクは、設定ファイルの `public_url` に上表の `/reset` または `/admin/reset` と `token` を付けたものとする。API の経路ではない。

### 2.2 API（Clojure）

JSON をやり取りする。`Content-Type` は `application/json` とする。成功は `{ "ok": true, ... }`、失敗は `{ "ok": false, "code": "..." }` とする。画面に出す日本語は §5 のとおり ClojureScript が `code` から付ける。

セッションは Cookie とする（§3.3）。同じオリジンから呼ぶ。別オリジンは工程1の必須としない。

| 経路 | 方法 | 誰 | ログイン | 役割 |
|---|---|---|---|---|
| `/api/user/session` | GET | 利用者 | 任意 | 入っていればメールアドレス。入っていなければ `ok: false`, `code: unauthorized` |
| `/api/user/login` | POST | 利用者 | 不要 | `{ "email", "password" }`。Cookie `isas_user` を付ける |
| `/api/user/logout` | POST | 利用者 | 必要 | 利用者セッションを消す |
| `/api/user/password/reset/request` | POST | 利用者 | 不要 | `{ "email" }`。返事は常に `ok: true` |
| `/api/user/password/reset` | POST | 利用者 | 不要 | `{ "token", "password", "password_confirm" }` |
| `/api/user/password` | POST | 利用者 | 必要 | `{ "current_password", "password", "password_confirm" }` |
| `/api/user/invite` | POST | 利用者 | 必要 | `{ "email" }`。成功時だけ `{ "initial_password" }` を含める |
| `/api/admin/session` | GET | 管理者 | 任意 | 利用者側と同じ。Cookie は `isas_admin` |
| `/api/admin/login` | POST | 管理者 | 不要 | `{ "email", "password" }` |
| `/api/admin/logout` | POST | 管理者 | 必要 | |
| `/api/admin/password/reset/request` | POST | 管理者 | 不要 | `{ "email" }`。返事は常に `ok: true` |
| `/api/admin/password/reset` | POST | 管理者 | 不要 | `{ "token", "password", "password_confirm" }` |
| `/api/admin/password` | POST | 管理者 | 必要 | `{ "current_password", "password", "password_confirm" }` |
| `/api/admin/invite` | POST | 管理者 | 必要 | `{ "email" }`。成功時だけ `{ "initial_password" }` |
| `/api/admin/users` | GET | 管理者 | 必要 | `{ "users": [ { "id", "email" } ] }`。取り消されていない人だけ |
| `/api/admin/users/revoke` | POST | 管理者 | 必要 | `{ "user_id" }` |

失敗の `code` は次とする。

| code | 使うとき |
|---|---|
| `unauthorized` | ログインが必要だが入っていない。または種別が違う Cookie |
| `login_failed` | ログインできない（理由は分けない） |
| `reset_invalid` | 再設定トークンが使えない |
| `invite_invalid_email` | メールアドレスの形式でない |
| `invite_duplicate_user` | すでに利用者として招待されている |
| `invite_duplicate_admin` | 管理者のため招待できない |
| `password_mismatch` | 確認用パスワードが一致しない |
| `password_too_short` | 8文字未満 |
| `password_wrong` | 今のパスワードが違う |

`/signup` に相当する API は置かない。

### 2.3 ログイン画面

| 項目 | 扱い |
|---|---|
| メールアドレス | 必須。1行 |
| パスワード | 必須。入力中は隠す |
| 入る | 利用者は `POST /api/user/login`、管理者は `POST /api/admin/login` |
| パスワードを忘れた | その側の再設定依頼画面へ |

一致しないときは入れない。画面の文句は「メールアドレスまたはパスワードが違います」の1通りとする。存在しないアドレスと、パスワード違いと、取り消された利用者を、文面で分けない。

入ったあとの行き先は、その側のホームとする。

### 2.4 再設定の依頼

| 項目 | 扱い |
|---|---|
| メールアドレス | 必須 |
| 案内を送る | 利用者は `POST /api/user/password/reset/request`、管理者は `POST /api/admin/password/reset/request` |

画面の返事は、送れたときも、そのアドレスのアカウントが無いときも同じとする。「案内を送りました。届かないときは、招待されていないか、入口が違う可能性があります」で足りる。取り消された利用者にはメールを送らない。管理者の依頼で利用者アカウントは変わらない。その逆も同じとする。

SMTP の設定が無くて送れないときも、画面の返事は同じとする。送れなかったことはログに残す。置くマシンの設定ファイルに SMTP を書き、実メールが届くことを工程1の完了で確かめる。

### 2.5 再設定（案内のリンク）

| 項目 | 扱い |
|---|---|
| 新しいパスワード | 必須 |
| 新しいパスワード（確認） | 必須。一致すること |
| 決める | 利用者は `POST /api/user/password/reset`、管理者は `POST /api/admin/password/reset`。`token` は画面のクエリから JSON に載せる |

リンクが無い、使済み、期限切れ、種別が違う、取り消されている、のいずれでも入れない。文句は「この案内は使えません。もう一度やり直してください」の1通りとする。決めたら、その側のログインへ進む。

### 2.6 ホーム（工程1の入れ物）

- 今入っているメールアドレスを出す（`GET /api/user/session` または `GET /api/admin/session`）。
- 管理者ホームには、圃場・地図・ガント・指示を出さない。利用者ホームにも、それら本機能は出さない。
- 出せる操作: 招待、パスワード変更、ログアウト。管理者だけ利用者の取消し。
- 「入っています」が分かれば足りる。

### 2.7 招待

| 項目 | 扱い |
|---|---|
| 相手のメールアドレス | 必須 |
| 招待する | 利用者は `POST /api/user/invite`、管理者は `POST /api/admin/invite` |

成功したら、同じ画面で初期パスワードを1回だけ出す（応答の `initial_password`）。あとから同じ文字列は出さない。案内文として、相手へシステムの外で伝えることを書く。招待メールは送らない。

次のときは招待しない。文句は分けてよい。

- 形式がメールアドレスでない
- 取り消されていない利用者として、すでに同じアドレスがある
- 管理者として同じアドレスがある

利用者の招待画面に、利用者の一覧は出さない。

### 2.8 招待の取消し（管理者 `/admin/users`）

取り消されていない利用者を、メールアドレスの一覧で出す（`GET /api/admin/users`）。各行に「取り消す」を置く。送信は `POST /api/admin/users/revoke`、対象は `user_id` とする。利用者はこの画面を持たない。

取り消すと、その人は以後ログインできない。まだ一度も入っていなくても同じとする。再設定もできない。その利用者のセッション行は無効にする。同じアドレスを、あらためて招待することはできる。そのときは新しい初期パスワードをその場で出す。

### 2.9 パスワード変更（ログイン後）

| 項目 | 扱い |
|---|---|
| 今のパスワード | 必須 |
| 新しいパスワード | 必須 |
| 新しいパスワード（確認） | 必須 |

利用者は `POST /api/user/password`、管理者は `POST /api/admin/password`。今のパスワードが違えば変えない。成功したら、その端末の今のログインは維持してよい。

## 3. 処理の規則

### 3.1 メールアドレス

- 識別子はメールアドレスだけとする。前後の空白は除く。英字の大文字小文字は同一とみなす（保存は小文字）。
- 同じアドレスを、管理者と利用者の両方に置かない。
- 取り消されていない利用者として、同じアドレスを二重に置かない。

### 3.2 パスワード

- 残すのは bcrypt ハッシュだけとする。平文では残さない。初期パスワードも、画面に出したあとはハッシュだけ残す。
- 初期パスワードはシステムが作る。英数字12文字。人が読みやすいよう、紛らわしい文字（0 と O、1 と l と I）は使わない。
- 本人が決めるパスワードは、8文字以上とする。文字種の混在は工程1の必須としない。

### 3.3 ログインとセッション

- 利用者セッションと管理者セッションは別とする。Cookie 名は `isas_user` と `isas_admin` とする。HttpOnly とする。JavaScript から読ませない。SameSite は Lax とする。HTTPS で置くときは Secure を付ける。
- セッションの本体は SQLite のセッション表に残す。Cookie にはセッションIDだけを載せる。ClojureScript は Cookie の値を読まない。API 呼び出しはブラウザに Cookie を付けて送る。
- 一方で入っていても、他方の入口には入れない。
- 同じアカウントで、パソコンとスマホに同時に入れてよい。端末ごとにセッション行を持つ。
- 有効期限は14日とする。明示のログアウト、期限切れ、利用者の取消しで切る。
- 取り消された利用者のセッションは残っていても、保護経路で使えない。取消し時にその利用者の行を無効にする。

### 3.4 招待

1. 招待できるのは、ログイン中の管理者または利用者である。
2. 相手アドレスを正規化し、管理者表と、取り消されていない利用者に無いことを確認する。
3. 取り消済みの同じアドレスがあれば、その行を再利用する。作業場所・下地・圃場・塗りなど利用者が持っていたデータはすべて消してから、新しい初期パスワードを発行し、取消しを解除する。
4. 無ければ利用者として1行足す。初期パスワードを発行する。
5. 招待した人の画面に、初期パスワードをその応答でだけ出す。
6. 増えるのは利用者だけである。この処理で管理者は増やさない。

### 3.5 取消し

- できるのは管理者だけとする。自分（管理者）を利用者一覧には出さない。
- 対象は取り消されていない利用者とする。すでに取り消されていれば何もしない。
- 取消し後はログインも再設定もできない。その利用者のセッションを無効にする。作業場所・下地・圃場・塗りなど利用者が持っていたデータも消す。

### 3.6 パスワード再設定

1. 依頼を受けたら、その側のアカウントを探す。無いか取り消されていればメールは送らず、画面の返事は成功と同じにする。
2. あれば、一度限りのトークンを作り、ハッシュして残す。有効期限は24時間とする。以前の未使用トークンはそのアカウント・その側について無効にする。
3. そのアドレスへ、SMTP で案内メールを送る。本文のリンクは設定ファイルの `public_url` にその側の再設定経路と `token` を付けたものとする。招待の案内は送らない。
4. トークンは平文で残さない。メールに載せる値と、保存するハッシュは別とする。ハッシュは bcrypt でよい。
5. 新しいパスワードを決めたらトークンを使用済みにし、パスワードのハッシュを置き換える。

### 3.7 最初の管理者

起動のたびに次を行う。

1. 管理者表が0行で、設定ファイルに `admin_email` と `admin_password` があるとき、そのメールを正規化して1行作る。パスワードは bcrypt する。
2. そのメールが利用者表にあれば、起動を止める。
3. 管理者表が1行以上なら、設定ファイルでは管理者を足さない・パスワードを変えない。
4. 0行なのに設定ファイルにメールまたはパスワードが無ければ、起動を止める。

2人目以降の管理者を増やす画面は持たない。

## 6. メール本文（再設定のみ）

- 件名: 「ISAS パスワードの再設定」（管理者のときは「ISAS 管理者パスワードの再設定」）
- 本文: 再設定の経路（設定ファイルの `public_url` + 経路 + `token`）と、24時間で使えなくなること。心当たりが無ければ無視してよいこと。
- 招待の案内は送らない。
- 送信は SMTP とする。配信サービスの専用APIは使わない。

## 8. 完了として満たすこと（詳細）

基本仕様書 §1.9 に加え、次を満たす。

- 利用者入口 `/` と管理者入口 `/admin` が別である。
- 画面は ClojureScript、処理は Clojure の JSON API である。
- データは `data/isas.sqlite` に残る。初期設定は `data/isas.conf` から読む。
- 管理者が0人の起動では、設定ファイルの `admin_email` と `admin_password` から1人できる。
- 初期パスワードは招待の応答でだけ見え、保存はハッシュだけである。
- 再設定メールは SMTP で、存在するその側のアカウントにだけ飛ぶ。画面の返事は存在の有無で変えない。
- 取り消したアドレスを再招待すると、新しい初期パスワードで入れる。

## 11. 確定した判断

1. **入れ物。** 処理は Clojure、画面は ClojureScript、その間は JSON の API とする。後工程も同じ分け方とする。以前の「HTML フォーム1本」は改める。
2. **アカウントの保存先。** 同じマシンの SQLite ファイル（`data/isas.sqlite`）とする。
3. **最初の管理者の用意。** 置くマシン上の設定ファイル（`data/isas.conf` の `admin_email` と `admin_password`）から作る。環境変数にはしない。
4. **再設定メールの送信。** 同じ設定ファイルの SMTP 欄で送る。特定の配信サービス名は固定しない。
5. **初期設定の置き方。** 環境変数ではなく、置くマシン上のファイル `data/isas.conf` とする。Git にはサンプル値を置く。実パスワードに置き換えた内容はコミットしない。
