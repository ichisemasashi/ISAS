## 1. この工程で実現すること

イチセが置く1つのISASに、招待した人だけが入る。管理者入口と利用者入口は別とする。ログイン後は「入ったことが分かる」入れ物で足りる。

工程1で動かす論理ブロックは、基本設計書 §10 のとおり、入口、認証・アカウント、利用者による招待、管理者による招待の取消しである。関係の切断、作業場所、圃場、塗り、ガント、指示、日誌、言語切替の本機能は作らない。

## 2. 画面と経路

パソコンのブラウザでもスマホのブラウザでも、同じ経路を使う。工程1では画面を端末別に分けない。

未ログインで保護された経路を開いたときは、その側のログインへ進む。利用者のログイン状態で管理者の保護経路を開いても入らない。その逆も同じとする。

| 経路 | 誰 | ログイン | 役割 |
|---|---|---|---|
| `/` | 利用者 | 不要 | 利用者ログイン。入済みなら利用者ホームへ |
| `/reset/request` | 利用者 | 不要 | パスワード再設定の依頼 |
| `/reset` | 利用者 | 不要 | 案内のリンクから新しいパスワードを決める |
| `/home` | 利用者 | 必要 | 入ったことが分かる。招待とパスワード変更への出口 |
| `/invite` | 利用者 | 必要 | 利用者を招待し、初期パスワードをその場で見せる |
| `/password` | 利用者 | 必要 | 本人のパスワード変更 |
| `/admin` | 管理者 | 不要 | 管理者ログイン。入済みなら管理者ホームへ |
| `/admin/reset/request` | 管理者 | 不要 | 管理者の再設定依頼 |
| `/admin/reset` | 管理者 | 不要 | 管理者の新しいパスワード |
| `/admin/home` | 管理者 | 必要 | 入ったことが分かる。招待・取消し・パスワード変更への出口 |
| `/admin/invite` | 管理者 | 必要 | 利用者を招待し、初期パスワードをその場で見せる |
| `/admin/users` | 管理者 | 必要 | 取り消されていない利用者の取消し |
| `/admin/password` | 管理者 | 必要 | 本人のパスワード変更 |

ログアウトは、今見ている側のセッションだけを消し、その側のログインへ進む。公開の新規登録の経路は置かない。

### 2.1 ログイン（利用者 `/`、管理者 `/admin`）

| 項目 | 扱い |
|---|---|
| メールアドレス | 必須。1行 |
| パスワード | 必須。入力中は隠す |
| 入る | 送信 |
| パスワードを忘れた | その側の再設定依頼へ |

一致しないときは入れない。画面の文句は「メールアドレスまたはパスワードが違います」の1通りとする。存在しないアドレスと、パスワード違いと、取り消された利用者を、文面で分けない。

入ったあとの行き先は、その側のホームとする。

### 2.2 再設定の依頼

| 項目 | 扱い |
|---|---|
| メールアドレス | 必須 |
| 案内を送る | 送信 |

画面の返事は、送れたときも、そのアドレスのアカウントが無いときも同じとする。「案内を送りました。届かないときは、招待されていないか、入口が違う可能性があります」で足りる。取り消された利用者にはメールを送らない。管理者の依頼で利用者アカウントは変わらない。その逆も同じとする。

### 2.3 再設定（案内のリンク）

| 項目 | 扱い |
|---|---|
| 新しいパスワード | 必須 |
| 新しいパスワード（確認） | 必須。一致すること |
| 決める | 送信 |

リンクが無い、使済み、期限切れ、種別が違う、取り消されている、のいずれでも入れない。文句は「この案内は使えません。もう一度やり直してください」の1通りとする。決めたら、その側のログインへ進む。

### 2.4 ホーム（工程1の入れ物）

- 今入っているメールアドレスを出す。
- 管理者ホームには、圃場・地図・ガント・指示を出さない。利用者ホームにも、それら本機能は出さない。
- 出せる操作: 招待、パスワード変更、ログアウト。管理者だけ利用者の取消し。
- 「入っています」が分かれば足りる。

### 2.5 招待

| 項目 | 扱い |
|---|---|
| 相手のメールアドレス | 必須 |
| 招待する | 送信 |

成功したら、同じ画面で初期パスワードを1回だけ出す。あとから同じ文字列は出さない。案内文として、相手へシステムの外で伝えることを書く。招待メールは送らない。

次のときは招待しない。文句は分けてよい。

- 形式がメールアドレスでない
- 取り消されていない利用者として、すでに同じアドレスがある
- 管理者として同じアドレスがある

利用者の招待画面に、利用者の一覧は出さない。

### 2.6 招待の取消し（管理者 `/admin/users`）

取り消されていない利用者を、メールアドレスの一覧で出す。各行に「取り消す」を置く。利用者はこの画面を持たない。

取り消すと、その人は以後ログインできない。まだ一度も入っていなくても同じとする。再設定もできない。同じアドレスを、あらためて招待することはできる。そのときは新しい初期パスワードをその場で出す。

### 2.7 パスワード変更（ログイン後）

| 項目 | 扱い |
|---|---|
| 今のパスワード | 必須 |
| 新しいパスワード | 必須 |
| 新しいパスワード（確認） | 必須 |

今のパスワードが違えば変えない。成功したら、その端末の今のログインは維持してよい。

## 3. 処理の規則

### 3.1 メールアドレス

- 識別子はメールアドレスだけとする。前後の空白は除く。英字の大文字小文字は同一とみなす。
- 同じアドレスを、管理者と利用者の両方に置かない。
- 取り消されていない利用者として、同じアドレスを二重に置かない。

### 3.2 パスワード

- 残すのはハッシュだけとする。平文では残さない。初期パスワードも、画面に出したあとはハッシュだけ残す。
- 初期パスワードはシステムが作る。英数字12文字。人が読みやすいよう、紛らわしい文字（0 と O、1 と l と I）は使わない。
- 本人が決めるパスワードは、8文字以上とする。文字種の混在は工程1の必須としない。
- ハッシュの製品名は、§11 の入れ物に合わせて選ぶ。要件は「元に戻せないこと」とする。

### 3.3 ログインとセッション

- 利用者セッションと管理者セッションは別とする。一方で入っていても、他方の入口には入れない。
- 同じアカウントで、パソコンとスマホに同時に入れてよい。端末ごとにセッションを持つ。
- 有効期限は14日とする。明示のログアウト、または期限切れで切る。
- 取り消された利用者のセッションは、以後の保護経路で使えない。

### 3.4 招待

1. 招待できるのは、ログイン中の管理者または利用者である。
2. 相手アドレスを正規化し、管理者表と、取り消されていない利用者に無いことを確認する。
3. 取り消済みの同じアドレスがあれば、その行を再利用する。新しい初期パスワードを発行し、取消しを解除する。
4. 無ければ利用者として1行足す。初期パスワードを発行する。
5. 招待した人の画面に、初期パスワードをその応答でだけ出す。
6. 増えるのは利用者だけである。この処理で管理者は増やさない。

### 3.5 取消し

- できるのは管理者だけとする。自分（管理者）を利用者一覧には出さない。
- 対象は取り消されていない利用者とする。すでに取り消されていれば何もしない。
- 取消し後はログインも再設定もできない。

### 3.6 パスワード再設定

1. 依頼を受けたら、その側のアカウントを探す。無いか取り消されていればメールは送らず、画面の返事は成功と同じにする。
2. あれば、一度限りのトークンを作り、ハッシュして残す。有効期限は24時間とする。以前の未使用トークンはそのアカウント・その側について無効にする。
3. そのアドレスへ案内メールを送る。本文に再設定の経路とトークンを含む。招待の案内は送らない。
4. トークンは平文で残さない。メールに載せる値と、保存するハッシュは別とする。
5. 新しいパスワードを決めたらトークンを使用済みにし、パスワードのハッシュを置き換える。

メールの送り方の製品は §11 とする。要件は、置く環境の送信設定で、再設定案内だけ送れれば足りる、とする。特定の配信サービスの名前は必須にしない。

### 3.7 最初の管理者

画面から管理者を増やさない。最初の1人の作り方は §11 とする。要件は次とする。

- 利用者の招待フローでは作らない。
- メールアドレスとパスワードを持つ。
- 2人目以降の管理者を増やす画面は持たない。

## 4. 残す情報（工程1）

### 4.2 利用者アカウント

### 4.4 セッション

| 項目 | 内容 |
|---|---|

セッションを表に残すか、署名付きCookieだけにするかは、§11 の入れ物に合わせる。要件は、ログアウトと取消しと期限切れで保護経路に入れなくなることとする。

## 5. 画面に出す文言（工程1）

工程1は日本語だけとする。日英切替の部品は置かない。文面の英語版は工程6とする。

| 場面 | 文言 |
|---|---|
| 利用者ログイン見出し | 利用者ログイン |
| 管理者ログイン見出し | 管理者ログイン |
| ログイン失敗 | メールアドレスまたはパスワードが違います |
| 再設定依頼の返事 | 案内を送りました。届かないときは、招待されていないか、入口が違う可能性があります |

| 招待重複（管理者） | このメールアドレスは管理者のため、利用者として招待できません |
| ホーム（利用者） | 利用者として入っています |
| ホーム（管理者） | 管理者として入っています。圃場は持ちません |

## 6. メール本文（再設定のみ）

- 件名: 「ISAS パスワードの再設定」（管理者のときは「ISAS 管理者パスワードの再設定」）
- 本文: 再設定の経路（トークン付き）と、24時間で使えなくなること。心当たりが無ければ無視してよいこと。
- 招待の案内は送らない。

## 7. 工程1で作らないもの

## 8. 完了として満たすこと（詳細）

基本仕様書 §1.9 に加え、次を満たす。

- 利用者入口 `/` と管理者入口 `/admin` が別である。
- 初期パスワードは招待の応答でだけ見え、保存はハッシュだけである。
- 再設定メールは、存在するその側のアカウントにだけ飛ぶ。画面の返事は存在の有無で変えない。
- 取り消したアドレスを再招待すると、新しい初期パスワードで入れる。

## 9. 後工程への渡し方

- 利用者IDと管理者IDは、後工程が圃場や指示を載せるときの所有者・操作者になる。工程1で表の形を壊さない。
- 工程1の利用者表に、圃場用の空欄を先回りして足さない。
- セッションの種別（管理者／利用者）は、後工程でも入口を混ぜないために残す。

## 11. 判断待ち

次は基本設計が工程着手時に送った How であり、工程1の詳細設計を閉じるために決める。決まったら本書を改訂する。

1. **入れ物。** 画面と処理を1つのWebアプリケーションにするか、画面用とAPI用を分けるか。後工程の地図も同じ入れ物に足す前提で決める。
2. **アカウントの保存先。** 同じマシンで完結するファイル（SQLite 等）か、別プロセスのデータベース（PostgreSQL 等）か。工程1はアカウントだけだが、工程2以降で形と画像を載せる置き場所になる。
3. **最初の管理者の用意。** 起動時の設定値（メールとパスワード）から作るか、コマンドで作るか。画面の初期登録は置かない。
4. **再設定メールの送信。** 置く環境のSMTP設定で送るか、特定の配信サービス名を第1版で固定するか。
