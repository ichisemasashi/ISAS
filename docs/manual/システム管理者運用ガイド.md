## 1. 目的・適用範囲

本書は、ISASを安全に導入し、日々監視し、利用者を管理し、データを保全し、障害・変更・廃止に対応するための運用基準である。provider固有commandや組織固有の連絡先は本書を上書きせず、末尾の運用台帳と法域別adapter runbookへ追記する。

対象範囲は次のとおり。

- React PWA、同一origin BFF、OIDC、session/context、PostgreSQL 16＋PostGIS、object storage、queue、KMS/HSM、法域内telemetry。
- tenant、組織、ユーザー、role、圃場scope、作業指示、日誌、農薬master、在庫、CSV移行／出力。
- backup、PITR、復旧、release、rollback、incident、脆弱性、鍵、privacy、監査。

## 2. 運用責任と権限分離

| 役割 | 主な責任 | 与えてはならない権限 |
|---|---|---|
| Service Owner | SLO、予算、業務継続、release最終判断 | 日常のDB superuser／鍵復号 |
| System Administrator | tenant／利用者、構成、日常点検、問い合わせ | backupと鍵の単独削除、RLS迂回 |
| Release Commander | Go/No-Go、段階配備、rollback判断 | 一人だけのproduction承認 |
| DB Operator | PG/PostGIS、pool、WAL、migration、性能 | 業務上不要なPII閲覧、常設application credential |
| Backup Operator | backup取得、保持、checksum | 定常業務read、restore復号の常設権限 |
| Restore Operator | 隔離restore、DR演習 | 平時の復号権限、旧clusterの即時破棄 |
| Key Custodian | KMS/HSM、rotation、期限付きgrant | 業務DB read、単独のbackup復号 |
| Security/Privacy | alert、incident、保持／削除、監査 | 業務データの目的外利用 |
| Tenant Administrator | 自組織の利用者・scope・master・業務承認 | 他tenant、system infrastructure、RLS無効化 |
| Verifier | 対象、証跡、結果の独立確認 | 自分の実行を自分だけで承認 |

production変更、restore、鍵、backup削除、shard長期離脱は二人承認とする。break-glassはSev-1だけに限定し、期限付き権限、操作監査、24時間以内の追認を要する。

## 3. システム構成とデータ境界

```text
利用端末/PWA
  → TLS入口
  → BFF（Cookie session、CSRF、tenant/context再導出）
  → P0 / Auth-P1 / P1 / P2 接続pool
  → PostgreSQL 16 + PostGIS（FORCE RLS、監査、同期台帳）
  ├→ object storage（写真、私有origin、短期署名参照）
  ├→ queue（失効、同期、quarantine、監査anchor）
  ├→ KMS/HSM（法域・用途別鍵）
  └→ 法域内telemetry（metric/trace/log。監査は別の権威経路）
```

- 1法域デプロイは1以上のDB shardで構成する。DB、replica、backup、object、log、trace、監視、通知本文を同じ法域境界に置く。
- `tenant_id`の分離はPostgreSQL RLSが最終防波堤である。application、運用者、監視、backupがRLSを代替しない。
- shardの`complete`判定は署名／version管理された静的manifestを参照し、応答したnodeだけから対象集合を作らない。
- 端末はoffline outboxを持つ。server障害や権限変更時でも、未同期記録を削除する操作を行わない。

詳細は[ADR-0019](../design/ADR/ADR-0019-インフラ・運用.md)、[ADR-0020](../design/ADR/ADR-0020-監視・SLO.md)、[ADR-0021](../design/ADR/ADR-0021-テスト・リリース方式.md)を参照する。

## 4. 導入前チェック

### 4.1 必須環境

| 項目 | 必須条件 |
|---|---|
| Runtime | OCI imageを扱え、同一digestを段階配備できる宣言的環境。本番BFFは2 instance／2 failure domain以上 |
| Database | PostgreSQL 16、対応PostGIS、primary＋法域内standby、WAL archive、PITR、pooler |
| Identity | allowlist済みOIDC issuer、MFA／step-up、back-channel logoutまたは失効adapter |
| Session/context | 法域内の永続・冗長store。BFF memory storeはtest専用 |
| Object/queue | 暗号化・versioning object、耐久queue、dead-letter、最古滞留監視 |
| Key/secret | KMS/HSMまたは同等。secretをGit、image、平文backupへ入れない |
| Network | 外部から内部までTLS、private DB/object、egress allowlist、法域外転送禁止 |
| Observability | 法域内collector/store、SLO dashboard、on-call、監査とは別経路 |
| Client | HTTPS下の対応browser/PWA。正式なiOS/Android下限はS6実機合格後に台帳へ固定 |

単一VM、local DB、memory session、平文secret、手動consoleだけの構成は開発・実証専用でありproduction承認しない。

### 4.2 法域・配備台帳

導入前に次を埋め、二人で確認する。

| 入力 | 値 |
|---|---|
| Service Owner／24h連絡 | `ISAS-JP-ServiceOwner`／`ISAS-JP-OnCall` IAM Identity Center group、SNS `isas-jp-prod-incident` |
| `deployment_id`／法域 | `isas-jp-prod-01`／日本（`JP`） |
| provider／region／failure domain | AWS／`ap-northeast-1`／相異なる3 AZ（実AZ IDは署名済みdeployment manifestから取得） |
| shard manifest格納先／version | S3 `*-shard-config/shards/manifest-v<N>.json`＋`.sig`／OpenTofu deployment manifest記載version・SHA-256 |
| IdP issuer／MFA policy | Cognito `IsasJpUserPool` issuer／passkey優先、passwordはTOTP、管理操作はstep-up |
| DB／pooler／object／queue／KMS | RDS PostgreSQL 16.14R2＋PostGIS 3.4.6／PgBouncer 1.24.x／S3／SQS／single-region KMS CMK |
| telemetry／alert／status page | ADOT→東京CloudWatch/X-Ray／CloudWatch Alarm＋SNS／dashboard `ISAS-jp-prod-overview` |
| backup格納先／保持／key reference | AWS Backup vault `isas-jp-prod-vault`＋`IsasJpRecoveryBucket`／日次30＋週次12／backup用途KMS CMK |

製品・policyは[日本初期配備プロファイル](../operations/日本初期配備プロファイル.md)を正とする。AWS account ID、AZ ID、ARN、endpointはIaC outputから生成する署名済みdeployment manifestを正とし、手入力しない。manifest未生成、実group未割当、staging未試験の法域をrelease manifestで`READY`にしてはならない。

## 5. 初期セットアップ

### 5.0 最初に確認すること

2026-08-15現在、起動対象は次の3種類に分かれる。**UT／デモ環境やスパイクDBを本番システムとして起動しない。**

| 対象 | 現在の状態 | 用途 | データ |

### 5.2 Production初期化順

1. 法域、network、KMS、secret参照、audit sinkを作る。
2. PG16/PostGIS primary/standby、WAL/PITR、pooler、固定Ops reserveを構成する。
3. schema/migrationをexpand順で適用し、RLS/FORCE、owner、trigger、`security_invoker`、監査chainをverifyする。
4. object versioning、private origin、queue/DLQ、session/context storeを構成する。
5. OIDC issuer、redirect URI、MFA、session期限、CSRF/originを登録する。
6. BFF/Webを署名済みdigestでstagingへ配備し、合成tenantでE2Eする。
7. telemetry、alert、backup、月次restoreを先に有効化する。
8. tenant、管理者、field group、masterを登録し、最小権限で利用者を招待する。
9. `ops/release-manifest.example.json`を実値へ置換し、検査、二人承認、段階配備する。

### 5.3 UT／デモPWAの起動・終了

これは**架空データを使う開発用画面**であり、BFF、PostgreSQL、IdPへ接続しない。実際の農薬散布、法定記録、利用者受入には使わない。

#### 5.3.1 macOSでの初回準備

Finderの「アプリケーション」→「ユーティリティ」→「ターミナル」を開く。Node.js 22以上とpnpmが導入済みか確認する。

```bash
node --version
pnpm --version
```

どちらかが`command not found`の場合、組織でHomebrewの利用が許可されているMacでは次で導入する。管理対象Macでは勝手に導入せず、端末管理者の配布手順に従う。

```bash
brew install node pnpm
```

repository rootへ移動し、対象を確認する。次は現在の標準配置例であり、別の場所へcloneした場合は実際のrepository pathへ読み替える。

```bash
cd /Volumes/SD_ONE/work/dev/ISAS
test -f apps/web/package.json
pwd
```

`test`が無出力で終了し、`pwd`がISAS repositoryを示せばよい。`No such file or directory`の場合は、FinderからISAS folderをターミナルへdragして実pathを確認する。

#### 5.3.2 Mac自身だけで起動する

初回またはlockfile更新後は依存関係を導入する。

```bash
cd /Volumes/SD_ONE/work/dev/ISAS/apps/web
pnpm install --frozen-lockfile
```

起動する。

```bash
pnpm dev
```

terminalに`Local: http://localhost:4173/`相当が表示されたら、browserで次を開く。

```bash
open 'http://127.0.0.1:4173/?ut=1&reset=1'
```

`open`を使わずSafari、Chrome等のaddress欄へ同じURLを入力してもよい。画面上端に「ユーザビリティ試験用・架空データです」と表示されれば正常である。別terminalから疎通だけを確認する場合は次を実行し、終了codeが0であることを確認する。

```bash
curl --fail --silent --show-error http://127.0.0.1:4173/?ut=1 >/dev/null
echo $?
```

終了は、`pnpm dev`を実行したterminalで`Ctrl+C`を1回押す。次のcommandが接続失敗になれば終了済みである。

```bash
curl --fail --silent --show-error http://127.0.0.1:4173/?ut=1 >/dev/null
```

再起動は終了確認後に同じdirectoryで`pnpm dev`を再実行する。`reset=1`を付けて再読込するとbrowser内のUTデータが初期化されるため、試験証跡採取中は付けない。terminalを閉じただけでprocessが残った疑いがある場合は、勝手にprocessをkillせず次でPIDを確認する。

```bash
lsof -nP -iTCP:4173 -sTCP:LISTEN
```

#### 5.3.3 同じLAN内の端末へ一時公開する

通常の`pnpm dev`は`127.0.0.1`だけで待ち受ける。同じ信頼済みLANのiPhone、iPad、Android等から確認するときだけ、起動済みprocessを`Ctrl+C`で終了してから次で起動する。

```bash
cd /Volumes/SD_ONE/work/dev/ISAS/apps/web
pnpm dev --host 0.0.0.0
```

MacのLAN内IPv4 addressを調べる。Wi-Fiが`en0`でないMacでは`networksetup -listallhardwareports`でinterface名を確認する。

```bash

```

例えば`192.168.1.20`と表示された場合、同じLANの端末で次を開く。

```text
http://192.168.1.20:4173/?ut=1&reset=1
```

macOS firewallが確認を表示した場合は、接続先が信頼済みLANであることを確認してNode.jsの受信を許可する。公共Wi-Fi、guest network、VPN越し、internet routerのport転送では公開しない。作業後は起動terminalで`Ctrl+C`を押し、次が無出力であることを確認する。

```bash
lsof -nP -iTCP:4173 -sTCP:LISTEN
```

#### 5.3.4 macOSでよくある起動エラー

| 症状 | 原因 | 確認・処置 |
|---|---|---|
| `ECONNREFUSED 127.0.0.1:3000`、`http proxy error: /api/bff/session` | `?ut=1`なしで開き、未起動のproduction BFFへ接続した | `http://127.0.0.1:4173/?ut=1&reset=1`を開く。デモ確認のためにBFFを無理に起動しない |
| `EADDRINUSE`またはport 4173を使用中 | 別のVite processが残っている | `lsof -nP -iTCP:4173 -sTCP:LISTEN`でPIDとcommandを確認し、元のterminalで`Ctrl+C`。不明なprocessを即時killしない |
| `pnpm: command not found` | pnpm未導入またはPATH未反映 | `brew install pnpm`後にterminalを開き直し、`pnpm --version`を確認 |
| `ERR_PNPM_OUTDATED_LOCKFILE` | `package.json`とlockfileが不一致 | 独断でlockfileを更新せず、正しいbranch／commitか確認して開発責任者へ連絡 |
| LAN端末から接続できない | loopback起動、異なるLAN、firewall | `--host 0.0.0.0`、Macと端末のSSID、`ipconfig`結果、firewall、`lsof`を順に確認 |

デモではない実BFFは、Cognito、DynamoDB、KMS、SQS、object storage、5系統のDB poolとsecret検査を要求する。Mac上の画面確認で`/api/bff/session`を成功させる目的だけでproduction adapterを起動したり、production credentialを設定したりしてはならない。

#### 5.3.5 Mac本番相当ローカル統合環境との区別

デモではなく実BFF、PostgreSQL 16＋PostGIS、OIDC、永続session/context、object、queue、暗号化、監視、PWA offline同期をMacで接続する後続環境の正式名称は**Mac本番相当ローカル統合環境**、profile IDは`local-integration`である。これはADR-0021のIntegration環境であり、Production環境ではない。`Mac本番環境`、`ローカル本番`とは呼ばない。

要求範囲と責任分担は[要求仕様書 v1.1 §5.6](../農業営農支援システム_要求仕様書.md#56-mac本番相当ローカル統合環境)、信頼境界と誤用防止は[責任境界設計](../design/Mac本番相当ローカル環境_責任境界設計.md)を正とする。現時点では用語と境界だけが確定しており、起動command、Compose、local adapterは未実装である。§5.3のViteデモや§5.4の検証DBを組み合わせても、このprofileの合格とはみなさない。実装完了まではproduction credentialを使った代替起動を行わない。

### 5.4 PostgreSQL 16＋PostGIS検証環境の起動・終了

このDBは`spikes/docker-compose.yml`の**破棄可能な検証環境**であり、hostの`55432`番portを使う。本番データを投入しない。

起動する。

```bash
cd spikes
docker compose up -d
docker compose ps
docker compose exec -T db pg_isready -U postgres -d spike
```

`docker compose ps`で`db`が`healthy`、`pg_isready`で`accepting connections`なら正常である。起動しない場合は状態と直近200行を確認する。

```bash
docker compose ps
docker compose logs --tail=200 db
```

containerとDB dataを保持して停止する。

```bash
docker compose stop
docker compose ps
```

再開する。

```bash
docker compose start
docker compose exec -T db pg_isready -U postgres -d spike
```

検証環境そのものを削除する場合だけ、対象が`spikes`であることと必要な試験証跡を退避したことを二人で確認してから次を実行する。

```bash
docker compose down -v
```

`down -v`はcontainer、network、volume内の`spike` DBを削除し、元に戻せない。日常の終了には`docker compose stop`を使う。`./run.sh`も`spike` DBを作り直すため、本番や保存が必要な検証dataに対して実行しない。

### 5.5 Productionの起動・終了

日本初期配備はAWS東京regionに決まり、対象論理名とAWS CLIは[配備別サービス操作手順](../operations/配備別サービス操作手順.md)に確定した。OpenTofu、production HTTP runtime、Cognito／DynamoDB／KMS／SQS adapterは実装済みだが、実resourceと署名済みdeployment manifestはまだ存在しないため、現時点ではproduction起動commandを実行してはならない。`pnpm dev`や`docker compose up`をproduction起動手順として流用しない。BFF単体の構成検査、前景起動、保守端末での起動／停止／再起動は[BFF Production runtimeの操作](../../apps/bff/README.md#production-runtimeの操作)を参照する。

OpenTofu apply後、同手順が要求する署名済みmanifestへaccount ID、ARN、endpoint、digestを生成し、stagingで次をすべて実行してからproduction release gateへ進む。

1. 操作対象を`deployment_id`、法域、cluster、release digestで特定する。
2. DB／queue／object／KMS／IdPを先に状態確認し、依存先を不用意に停止しない。
3. Web/BFFの起動、readiness、合成login、RLS付きread、同期push/pullを実commandで確認する。
4. drain→停止→停止確認、起動→readiness→traffic復帰、rolling restartを別々に試験する。
5. log、metric、監査、rollback、on-call escalationまで証跡を残す。

manifest欠落、論理名との不一致、受入表の未試験項目が1つでもあればproductionは`BLOCKED`である。

## 6. Tenant・利用者・権限管理

### 6.1 Roleの基準

| Role | 許可範囲の概要 |
|---|---|
| Group Administrator | 単一法域内の配下組織。複数shard横断の権威値は`complete`のみ |
| Organization Administrator | 自組織の圃場、指示、記録、経営、利用者、master |
| Field Supervisor | 担当範囲の指示、進捗、記録。経営は閲覧限定、利用者／master管理なし |
| Worker | 自分の担当指示と記録。管理機能なし |
| Contractor | tenantごとに付与された受託範囲。別tenant権限を流用しない |

実装capabilityには`instruction:manage`、`journal:review`、`pesticide:manage`、`pesticide:override`、`inventory:adjust`、`migration:manage`、`export:read`、`conflict:resolve`等がある。role名だけで判断せず、法域profileのRole→capability表をreviewする。

### 6.2 追加・変更・失効

1. 本人確認後、IdP主体`(issuer, subject)`へ内部userを結ぶ。emailだけで既存userへ自動結合しない。
2. tenant、role、field group scope、期限、雇用／受託関係を最小権限で付与する。
3. 管理者・export・migration・農薬overrideはMFA／step-upと別承認を必須にする。
4. 変更時は単調`authorization_version`と失効eventを権威DBで同一transactionに記録し、session/context/offline snapshotを冪等に無効化する。
5. 退職・契約終了・端末紛失は、membership失効→session/context失効→offline snapshot失効→鍵／端末措置→監査確認の順で処理する。
6. 未同期法定記録は失効時に捨てず、回復queueで現在権限と作成時証跡を確認する。

四半期ごとに管理者、休眠user、期限なしmembership、全域scope、export/migration/overrideを棚卸しする。他者の位置履歴は原則閲覧させず、例外は目的、期間、同意、参照者を監査する。

### 6.3 現baselineでの具体操作と制限

現baselineにはCognito OIDC、認証専用DB関数、単調`authorization_version` outbox、DynamoDB/SQSの冪等失効adapterに加え、利用者／membership／break-glass／Privacy requestの管理画面とAuth-P1 APIがある。DB関数は申請者と承認者の同一性を拒否し、変更、version増加、失効event、監査を同一transactionで行う。DBへ直接`INSERT`／`UPDATE`して代用してはならない。

#### 利用者を登録・変更・失効する

1. MFAで再認証し、対象tenantへ切り替えて、下部navigationの「その他」→「管理者向けセキュリティ操作」を開く。
2. 「利用者・tenant権限」で操作を選ぶ。登録時は内部利用者UUID、CognitoのOIDC issuer／subject、表示名を入力する。変更／失効時は「現在の利用者」のUUID、role、scope、状態、期限、`authorization_version`を照合する。
3. role、field-group scope（複数はUUIDをカンマ区切り）、利用開始、利用期限、ticket、10文字以上の理由を入力し「二人承認へ申請」を押す。失効では変更後のfieldを入力しても適用されない。
4. 別の管理者が同じtenantで「二人承認・変更前後の監査」を開き、「変更前後を比較」で差分、対象、ticket、期限を確認する。「判断根拠」を入力して「別管理者として承認」または「却下」を押す。申請者本人のbuttonは無効で、DBも自己承認を拒否する。
5. statusが`executed`となり、利用者表のrole／scope／期限と`authorization_version`が更新されたことを確認する。失効時は別browserのsession/context/offline snapshotが無効となり、旧scopeのAPIが403になることをstagingで確認する。

入力誤りは却下して新しい申請を作る。pending行や監査行をDBから削除しない。画面が403なら、MFAから10分以内か、`security:manage`／`break_glass:approve`／`privacy:manage`の現在権限があるかを確認する。

#### break-glassを期限付き発行する

1. Sev-1 incidentを宣言し、Incident Commanderが対象利用者、必要capability、根拠ticket、終了条件を確定する。
2. 「break-glass権限」で対象UUID、一時capability（カンマ区切り）、現在から5分超かつ最大1時間の失効日時、incident ticket、10文字以上の理由を入力し「期限付き発行を申請」を押す。
3. 別の`break_glass:approve`保持者が変更前後を確認し、判断根拠を入力して承認する。許可list外、1時間超、自己承認はDBで拒否される。
4. 実施中は操作のcorrelation IDをincidentへ記録する。期限到来後にAuthContextから一時capabilityが消え、`authorization_version`と失効eventが更新されたことを確認する。

#### Privacy requestを処理する

1. 本人確認後、「Privacy request」で開示／訂正／削除、本人UUID、法定・契約上の対応期限、対象dataをJSON、受付メモを入力し「本人確認済みとして受付」を押す。
2. 別のPrivacy管理者が対象、第三者data、法的保持を確認し、理由を入力して承認または却下する。自己承認はできない。
3. 承認後「処理開始」を押す。削除対象にlegal holdがあれば「法的保持で停止」を押し、解除までDBやobjectを削除しない。
4. 開示／訂正／削除をRLS適用済み手順で実施し、完了証跡URIと処理メモを入力して「証跡付きで完了」を押す。「処理履歴を表示」で受付から完了までのactorと遷移を確認する。

## 7. 業務masterと日常管理

### 7.1 圃場・作業・割当

- 圃場をtenantとfield groupへ割り当て、geometry、名称、作物、timezone、状態を確認する。
- online背景は許可済みの地理院標準タイルだけをbrowserから直接取得する。offline背景はprivate S3の日本PMTilesからsame-origin BFFを経由し、各Rangeでsession、AuthContext、RLSのfield-group割当を再検証する。外部style URL、地理院タイルのproxy cache、S3署名URLによるPMTiles直接配布を設定しない。
- 作業指示は圃場ID、担当者ID、名称、作業種別、開始／終了、優先度、詳細を設定する。再割当はonline限定で、現在versionが一致しない409を上書きしない。
- 14日timelineとモバイル作業listは同じ指示を使う。表示不一致時に別データを手修正せず、指示IDとversionを調査する。

### 7.2 日誌review

- `submitted`／`corrected`だけを承認する。差し戻しには具体的理由が必須。
- 承認済み日誌を直接更新せず、訂正理由付きrevisionを追記する。
- 競合はサーバ値／端末値と対象fieldを確認し、`conflict:resolve`を持つ現在の管理者が裁定する。静かなLWWをしない。

### 7.3 農薬master

- release version、有効期限、失効日、適用作物、希釈範囲、年間回数、収穫前日数を二人reviewして公開する。
- masterの出典、取得日、法域、reviewer、差分、発効時刻を保存する。古いreleaseを再公開しない。
- client警告は事前支援であり、serverが受理時に再判定する。overrideは理由、確認者、根拠を監査し、常用しない。

### 7.4 在庫

- 残高を直接編集せず、入庫／出庫／棚卸し調整eventから導出する。
- マイナス在庫alertは実棚、未同期event、重複、単位を確認し、`inventory:adjust`で差分eventを追記する。過去eventを削除して合わせない。

### 7.5 管理画面の具体操作

以下は現Webで実装済みの操作である。UT／デモでは§5.3のURLを開いて操作を確認できる。本番ではBFF／IdP接続後、対象capabilityを持つ利用者だけに項目が表示される。

#### 作業指示を発行する

1. 下部navigationの「その他」を押す。
2. 「作業指示を発行」で、圃場ID、担当者ID、指示名、作業種別、開始予定、終了予定を入力する。必要なら優先度と詳細も入力する。
3. 選択中tenant、圃場、担当者、日時、timezoneを復唱する。「オンラインで発行」が無効なら通信を回復し、offlineで迂回しない。
4. 「オンラインで発行」を押す。
5. 「作業指示を発行しました。」を確認し、「予定」画面の14日timelineと担当者の「今日」に同じ指示が表示されることを確認する。

再割当は対象指示の「新しい担当者ID」へIDを入力し、表示中versionが最新であることを確認して「再割当」を押す。「担当者を変更しました。」を確認する。409になったら画面を再読込し、他者の変更を確認してから再判断する。強制上書きしない。

#### 日誌を承認または差し戻す

1. 「その他」→「日誌の承認・差し戻し」を開く。
2. 圃場、作業種別、開始／終了、メモ、写真、農薬記録、訂正理由を原記録と照合する。
3. 問題がなければ「承認する」を押し、「日誌を承認しました。」を確認する。
4. 訂正が必要なら「差し戻し理由」へ、修正箇所と期待値を具体的に入力して「理由を付けて差し戻す」を押す。
5. 「日誌を担当者へ差し戻しました。」と、担当者側の「訂正が必要な日誌」への表示を確認する。

理由なしの差し戻しは画面で拒否される。承認済みrecordをDBで直接更新しない。

#### 同期差し戻し・競合を処理する

1. 「その他」の「差し戻しキュー」「競合キュー」の件数を確認する。
2. 「差し戻し」ではreason、bundle ID、回復操作を記録し、再認証、入力訂正、管理者回復のどれが必要か判断する。outboxを削除しない。
3. 「競合の裁定」では競合field、サーバ値、端末値、各version、業務上の原資料を照合する。
4. 正当な値を判断できた場合だけ「サーバ値を採用」または「端末値を採用」を押す。
5. 「競合の裁定を保存しました。」を確認し、同期後にqueue件数が減ったことと監査eventを確認する。

#### マイナス在庫を裁定する

1. 「今日」→「在庫入出庫」を開く。
2. 「マイナス在庫の裁定」に表示された農薬、同期後残高、単位を確認する。
3. 現物を数え、未同期出庫、重複event、単位違いがないか調べる。
4. 「実棚数量」へ確認値を入力し、「調整イベントを記録」を押す。
5. 調整後残高と追記eventを確認する。既存の入出庫eventを削除しない。

#### 農薬masterをreview・公開する

1. 「その他」→「管理者向けセキュリティ操作」→「農薬master review・公開」を開く。
2. 出典と差分を確認し、公開候補JSONへ`version`、`validUntil`、1件以上の`chemicals`を入力する。各農薬には登録番号、名称、適用作物、希釈下限／上限、最大使用回数、収穫前日数を含める。
3. ticketと10文字以上の理由を入力して「reviewへ回付」を押す。
4. 別の`pesticide:manage`保持者が「公開前後を比較」で全差分と出典を照合し、review所見を入力して「review承認して公開」または「却下」を押す。申請者本人は公開できない。
5. statusが`published`、release IDが記録され、端末の次回priority pullで新versionと有効期限が届くことを確認する。古いversion、空の農薬list、期限不正、同一version競合は修正せず新申請でやり直す。

管理UI／APIは実装済みだが、production利用はAWS stagingでCognito二管理者、Auth-P1、失効consumer、監査検索まで受入してrelease manifestを承認するまで`BLOCKED`である。

#### 写真ストレージを照合する

1. recent MFA後に「その他」→「管理者向けセキュリティ操作」→「写真ストレージ保全」を開く。
2. 日次点検または写真障害のticket番号を運用記録へ先に作り、「写真ストレージを照合」を1回押す。処理中に再押下しない。
3. messageの「走査」「孤立候補」「確定」「隔離」を記録する。`確定`はS3 ready化後にDB確定できなかった再試行、`隔離`はDB参照があるのにobjectが見つからない異常、`孤立候補`はDB参照のないobjectへ30日回収tagを付けた件数である。
4. `隔離 > 0`は写真欠損としてSev-2以上へescalateし、自動削除を待たずS3 version／CloudTrail／upload correlationを調査する。`孤立候補 > 0`は誤tagでないことを二人で確認し、保持・legal holdを確認するまで手動削除しない。
5. S3 lifecycleは`pending`を2日、`orphaned`を30日後に回収し、未完multipartを7日でabortする。法定証跡写真は`supporting`から`statutory`へ分類してから保持判断し、端末未同期写真をS3処理で代替しない。

#### offline map成果物を公開・確認する

1. review済みの`japan.pmtiles`、`OSM-NOTICE.txt`、`sbom.json`を法域内release領域へ置き、PMTilesのSHA-256を`offline_tileset_archive_sha256`へ設定して保存planを二人承認する。
2. OpenTofu apply後、`cd infra/opentofu`で`chmod 0555 scripts/publish-offline-map.sh`を行い、`scripts/publish-offline-map.sh <12桁staging-account> <PMTiles> <NOTICE> <SBOM>`を実行する。account、東京region、version、digest不一致なら修正せず停止する。
3. 成功messageのS3 URIとSHA-256をchange ticketへ記録する。BFF `/health/ready`が200であること、合成利用者の担当圃場だけが取得でき、担当外は403、Rangeなしは416になることを確認する。
4. iOS／AndroidでWi-Fi明示取得、圏外再起動、期限、assignment縮小、250MiB上限、LRU、OSM帰属を確認する。地理院タイルがoffline packへ混入していたら公開を中止する。

## 8. 日次・週次・月次・四半期作業

| 頻度 | 確認内容 | 停止／escalation |
|---|---|---|
| 常時 | Sev-1/2 alert、P0、WAL、失効DLQ、監査chain、法域外export | WAL 15分、失効DLQ 60秒、chain不一致は即Sev-1 |
| 日次 | SLO/error budget、backup、queue最古年齢、object孤立、disk/pool、security event | backup不完全、tenant越境疑い、未同期消失疑い |
| 週次 | capacity 30日予測、quarantine、dependency/security update、admin変更 | quarantine 7日超はSev-2 |
| 月次 | restore test、権限差分、retention削除、feature flag期限、証明書期限 | restore不成功はrelease freeze |
| 四半期 | 全recovery set DR、管理者／全域権限棚卸し、鍵rotation rehearsal、incident訓練 | RPO 15分／RTO 4時間超はrelease blocker |
| 年次／法改正時 | 法域、保持根拠、農薬master出典、vendor、BCP、privacy notice | 根拠不明の法定表示／越境処理を停止 |

点検結果は担当、時刻、対象、evidence、異常、処置、期限を残す。「異常なし」だけの記録にしない。

### 8.1 点検の実行順

1. [配備別サービス操作手順 §1](../operations/配備別サービス操作手順.md#1-対象台帳)を開き、当番対象のdeployment、法域、shard、digestを読み上げる。
2. 同手順§6に記入済みのURL／commandでSLO、instance、DB/WAL/pool、queue/DLQ、object/KMS、監査chainを順に開く。
3. dashboardの期間とtimezoneを確認し、`no_data`と0を区別する。各画面の時刻入りcaptureまたはquery IDをevidenceへ添付する。
4. §8表の停止条件に該当すれば、正常欄へcheckせず[障害対応手順](../operations/障害対応手順.md)を開始する。
5. 異常がなければ、担当、確認時刻、対象digest、各evidence、次回期限を点検記録へ保存する。

配備別手順§6のcommandが0終了しない、またはdashboard／manifestの実URL・ARNが生成されていない状態では点検を実施したことにできず、production開始を承認しない。

定期保守では、次も法域別台帳で管理する。

- PostgreSQL autovacuumを無効化せず、dead tuple、long transaction、index bloat、統計鮮度、replication slot、WAL容量を確認する。大量backfill後は対象tableの`ANALYZE`とplanを確認する。
- 時系列partitionは作成を先行し、retentionで古いpartitionをdropする時は端末時刻clamp窓、法的保持、backup、監査anchorを同時に確認する。
- objectの未完upload、孤立object／DB参照、version retention、lifecycle、quotaを日次照合する。管理画面の「写真ストレージを照合」で件数を記録し、自動削除で未同期／法定添付を消さない。offline mapはversion prefix、PMTiles SHA-256／MIME／ODbL metadata、NOTICE、SBOM、期限を照合する。
- session/context期限切れ、revocation consumer、DLQ、quarantine、idempotency ledgerの保持と容量を確認する。
- TLS証明書、domain、OIDC client secret、signing key、KMS key、backup key依存、外部API credentialの所有者と期限を管理し、失効前に重ね期間付きで更新する。
- OS、runtime、PostgreSQL/PostGIS、browser対象、dependency、container base、CI actionのsupport終了日を管理する。安全gateを省略した自動major updateをしない。
- maintenance告知は影響、開始／終了、offline継続、未同期を消さないこと、問い合わせ先を事前に伝え、終了後に同期とSLOを確認する。

## 9. 監視とSLO

| 対象 | 目標 |
|---|---|
| 管理系online | 99.5%以上／rolling 30日 |
| P0安全・失効pull | 99.9%以上、500ms以内 |
| 一般GET | p95 500ms以内 |
| Login | p95 2秒以内 |
| 圃場一覧／地図／ガント | p95 1.5秒／2秒／3秒以内 |
| 日誌保存 | 写真1枚込みp95 1秒以内 |
| 同期 | 回線復帰後60秒以内開始、規定1日分5分以内 |
| DR | RPO 15分、RTO 4時間 |

必須dashboardは利用者体験、同期／安全、DB/shard、権限／監査、object/PWA、DR/deployの6面である。tenant/user IDをmetric labelへ載せず、診断時だけ法域内の制限queryを使う。`no_data`、collector drop、alert配送失敗を緑と解釈しない。

dashboard、alarm、GitHub Environment、SBOM／署名、staging→5%→25%→100%、自動rollbackの具体的な画面・CLI操作は[監視・セキュリティ・CI/CD自動化](../operations/監視・セキュリティ・CI-CD自動化.md)を正とする。手作業でALB weightを変更せず、workflow run IDとS3 delivery stateを証跡に残す。

14.4倍burn（1h＋5m）はSev-1、6倍（6h＋30m）はSev-2。30日error budget残25%未満では高risk releaseを凍結する。

## 10. Backup・復旧・事業継続

- 日次base backup＋継続WAL archive、日次30世代＋週次12世代を最低とする。WAL未転送は5分以内。
- DB、object version、権威queue、idempotency、監査anchor、構成、migration、鍵version参照を同じ`recovery_set_id`へ束ねる。
- 月次restore、四半期DR、major migration前後のrestoreを実施する。job成功だけをbackup成功としない。
- 本番dumpを開発環境へ直接復元しない。法域内隔離restore後、用途allowlistでPII、関係graph、secret、位置、添付を除外／仮名化する。
- 障害時は旧clusterを上書きせず新clusterへrestoreし、RLS、監査、object、queue、cursor、idempotencyを検証して切替える。

実行順は[バックアップ・復旧手順](../operations/バックアップ・復旧手順.md)を参照する。

### 10.1 具体的な実施方法

1. [配備別サービス操作手順 §7](../operations/配備別サービス操作手順.md#7-backuprestoredeployrollback)の「recovery set作成」を実行する。
2. 返された`recovery_set_id`を記録し、同表の完全性確認commandでDB、WAL、object、queue、監査、構成、鍵versionが同じIDに含まれることを確認する。
3. size、checksum、法域、暗号化key reference、保持期限を取得し、前回値との異常差を確認する。
4. Backup OperatorとVerifierが別々に証跡を確認し、backup台帳を完了する。
5. 月次は同表の「隔離restore」を新しい隔離環境へ実行し、restore検証commandと合成transactionを実施する。既存clusterへ復元しない。

stagingで使う具体commandは次のとおりである。出力をGitへ保存せず、アクセス制限された作業領域を使う。

```bash
ops/recovery/create-recovery-set.sh 123456789012 deployment-manifest.json /secure/recovery/recovery-set.json
ops/recovery/start-isolated-restore.sh 123456789012 deployment-manifest.json approved-recovery-set.json approved-restore-request.json /secure/recovery/restore.json
node ops/recovery/check-operational-acceptance.mjs /secure/recovery/operational-acceptance.json
```

最後のcommandが`BACKUP / OPERATIONS ACCEPTANCE: PASS`を出すまでは復旧受入未完了である。開始job IDだけ、DBだけのrestore、dashboardの緑だけを合格にしない。

providerはAWS東京region、backupはAWS Backup＋RDS PITR＋S3 version inventoryに決定し、OpenTofu resourceと検証手順を実装済みである。ただし実AWS recovery point、隔離restore、RPO／RTO証跡は未取得なので、現時点の本番受入は`BLOCKED`である。`pg_dump`だけをrecovery setの代替にしない。

## 11. Release・変更・rollback

1. `main`のreview済みcommitから一度だけbuildし、SBOM、provenance、署名、digestを作る。
2. unit/contract、PG16/PostGIS、RLS、E2E/PWA、WCAG、security、SLO、DR、S6/S9、UT gateを埋める。
3. `node ops/check-release-readiness.mjs <実manifest>`が0終了し、RCとVerifierが別人で承認する。
4. 同じdigestをstaging→5%→25%→100%へ昇格し、各段階でSLOと安全signalを観測する。
5. application/configだけなら直前digestへrollback。DBはexpand/contractとroll-forwardを原則とし、data破損はwrite freeze＋PITRを判断する。
6. PWA rollbackでcache/outboxをpurgeしない。旧新assetを互換期間保持する。

詳細は[デプロイ・ロールバック手順](../operations/デプロイ・ロールバック手順.md)を参照する。

### 11.1 Repositoryでのrelease検査操作

リポジトリrootで、実manifestをGit管理外の安全な場所に用意して次を実行する。

```bash
node ops/check-release-readiness.mjs /absolute/path/to/release-manifest.json
echo $?
```

`READY`と表示され終了codeが0の場合だけ次へ進む。exampleは意図的に`BLOCKED`なので本番判定に使わない。検査tool自体の回帰testは次で実行する。

```bash
node --test ops/test/check-release-readiness.test.mjs
```

実配備は[配備別サービス操作手順 §7](../operations/配備別サービス操作手順.md#7-backuprestoredeployrollback)のdigest配備、pause、rollback commandを使う。署名済みdeployment manifest、GitHub workflow、AWS resource、staging証跡のいずれかが欠ければreleaseを中止する。Git tag作成やWebの`pnpm build`だけではproductionへのdeployにならない。

## 12. CSV移行・出力

- 取込はonline限定、`migration:manage`必須。圃場→作業記録→農薬履歴の順に、列mapping→行検査→重複確認→確定する。
- エラー行が1件でもあれば元CSVを直し、新jobとして再検査する。検査済みjobだけを楽観lock付きで確定する。
- 出力は`export:read`とRLS適用後の範囲だけ。目的、期間、受取人、保存期限を記録し、表計算式注入対策を外さない。
- export fileをemailへ直接添付せず、法域内の期限付き安全な経路を使う。不要になったlocal copyを削除する。

列定義、上限、重複keyは[CSVデータ移行・出力ガイド](../CSVデータ移行・出力ガイド.md)を参照する。

### 12.1 CSV取込の画面操作

1. 原本を変更不可で保管し、別copyをUTF-8 CSVとして準備する。数式、macro、password付きfileは持ち込まない。
2. onlineで対象tenantを確認し、「その他」→「CSVデータ取込」を開く。
3. 「取込対象」で「圃場」「作業記録」「農薬履歴」のいずれかを選び、「CSVファイル」でfileを選ぶ。
4. 「列のマッピング」で検出列を各項目へ割り当てる。「必須」がすべて対応済みであることを確認する。
5. 「重複と入力内容を検査」を押す。
6. 全件数、取込候補、重複、エラーと、表示された行番号・理由を確認する。エラーがあれば元copyを修正し、新しいjobで手順3からやり直す。
7. statusが「取込可能」の場合だけ、別の確認者が対象tenant、dataset、件数、mappingを照合し、「検査済みN件の取込を確定」を押す。
8. 「N件の取込を確定しました。」と「直近の取込」の「取込済み」を確認し、業務画面からsampleを照合する。

初回移行は参照関係のため圃場→作業記録→農薬履歴の順で行う。browserの戻る操作や連打で再実行せず、job履歴を先に確認する。

### 12.2 CSV出力の画面操作

1. onlineで対象tenantとscope、出力目的、受取人、保存期限を確認する。
2. 「その他」→「CSVデータ出力」を開く。
3. 作業日誌または農薬記録は必要最小限の開始日・終了日を入力する。開始日が終了日より後ならbuttonは無効になる。
4. 「作業日誌を出力」「圃場台帳を出力」「農薬記録を出力」のいずれかを1回押す。
5. 「<file名>を出力しました。」を確認し、download fileのheader、件数、期間、tenant範囲を別の確認者が照合する。
6. 承認済みの法域内経路で受け渡し、期限到来後にlocal copyを削除して証跡を残す。

## 13. Security・privacy・鍵

- TLS、HttpOnly/Secure/SameSite Cookie、Origin/CSRF、CSP/Trusted Types、rate limit、dependency固定を維持する。
- token/session、object/backup、仮名map、offline recovery、署名を法域／用途別KEKで分離する。署名鍵と暗号鍵を共用しない。
- 鍵rotationは新旧重ね、復号試験、backup依存、二人承認、監査を伴う。参照0と保持義務を確認するまで旧鍵を破棄しない。
- Critical/High脆弱性、未処置Medium、RLS越境、未同期data loss、農薬安全誤判定はrelease waiver不可。
- operational logへtoken、Cookie、自由入力、写真、位置、SQL bind、生tenant/user IDを記録しない。監査は一般logで代替しない。
- retentionは種別と法域根拠に従う。法的保持対象を勝手に削除せず、根拠のない無期限保持もしない。
- 本人開示・訂正・削除・exportはprivacy担当が本人確認、対象、法的保持例外、実施証跡を記録する。

### 13.1 Securityと鍵の具体操作

#### 脆弱性対応

1. alertでartifact digest、dependency名、CVE、severity、到達可能性、影響法域を確認する。
2. source commitを固定し、修正branchでBFFとWebの品質testを実行する。

```bash
cd apps/bff
npm test
npm run check

cd ../web
pnpm test:quality
```

3. Critical／High、RLS越境、農薬安全、未同期消失に該当すればreleaseを凍結し、§14のincident手順を開始する。
4. 修正artifactのSBOM、署名、digestとtest evidenceをrelease manifestへ登録し、§11の段階配備を行う。
5. 配備後に対象digestが0 instanceになったこと、alertが再検査で解消したことを確認する。alertを単にdismissしない。

#### 鍵rotation

AWS KMSの用途別single-region customer managed key resourceはOpenTofu実装済みで、対称鍵は自動rotationを有効化している。非対称署名鍵の交代、既存ciphertextの再暗号化、依存inventoryを含む`kms-rotation` workflowは未実装のため、手動でproduction鍵を置換してはならない。workflow実装時はmanifestのkey ARNを対象に、次をstagingで検証する。

1. 新key version作成→encrypt/sign先だけを新versionへ切替える。
2. 旧新両versionで復号／署名検証し、backup、object、session、offline recoveryの依存数を取得する。
3. chunk単位で再暗号化し、失敗時に再開できることを確認する。
4. 旧version参照0、保持期限、legal hold、restore test、二人承認を確認する。
5. 旧versionをdisableし、監視期間後にのみdestroyする。即時削除しない。

各段階のcommand、期待件数、abort、旧version再有効化手順が空欄ならrotationを開始しない。

#### Privacy request

1. Privacy窓口で本人確認とrequest種別（開示、訂正、削除、移転）を記録し、ticket IDを発行する。
2. 対象tenant、期間、data種別、第三者data、法的保持／係争holdをPrivacy担当と確認する。
3. 開示は§12.2のRLS適用済み出力を使い、第三者dataと内部security情報を除外する。
4. 訂正／削除は§6.3の専用workflowと監査eventで行う。legal hold中の削除完了は拒否されるため、法務担当の解除証跡なしに迂回しない。
5. 実施項目、除外理由、受領確認、local copy削除、完了時刻をticketへ残す。

## 14. Incident対応

| Severity | 代表例 | 初動 |
|---|---|---|
| Sev-1 | tenant越境、農薬安全誤判定、未同期data loss、chain不一致、WAL 15分、法域外流出、広範停止 | 5分ack、Incident Commander、promotion停止、必要ならwrite freeze |
| Sev-2 | 主要劣化、6倍burn、quarantine 7日、pool/storage逼迫 | 15分ack、ownerと復旧予定 |
| Sev-3 | 回避策のある限定不具合 | 営業時間内triage |

初動で法域、deployment、shard、release digest、開始時刻を固定する。安全性が不明なら機能を止め、平文、RLS無効、古い権限cacheへ縮退しない。連絡文へPIIや脆弱性詳細を載せない。復旧後24時間以内にtimelineを作り、5営業日以内にreviewしてtest/alert/runbookへ反映する。

実行順は[障害対応手順](../operations/障害対応手順.md)を参照する。

### 14.1 初動の具体操作

1. alertをackし、時刻、deployment、法域、shard、release digest、correlation IDをincident記録へ転記する。
2. [配備別サービス操作手順 §6](../operations/配備別サービス操作手順.md#6-状態log監視)の状態・log commandを実行し、秘密情報を除いたquery IDと時刻を添付する。
3. deploy中なら同手順§7の「rollout pause」を実行する。commandが空欄なら手動推測せずRelease Commanderへescalateする。
4. tenant越境、data破損、農薬安全、監査chain、未同期消失の疑いでは「write freeze」を二人確認で実行し、利用者へoffline保存と未同期dataを消さないことを案内する。
5. 5分または15分のack期限内にSeverity、Incident Commander、次回更新時刻を確定する。

障害時にRLS無効化、DB直接修正、平文退避、outbox削除、未承認の古いimage起動を行わない。

## 15. Troubleshooting

どの症状でも、まず次の共通手順を行う。

1. 利用者から時刻、選択tenant、画面名、表示message、同期件数を聞く。password、MFA code、写真、自由記述本文をchatへ貼らせない。
2. §8.1の順でdeployment、digest、SLO、依存先を確認し、correlation IDで非PII logを検索する。
3. 再現操作は合成tenantで1回だけ行い、同じ登録buttonを連打しない。
4. 下表の確認・処置を行い、RLS無効化、scope全域化、outbox削除、DB直接修正を回避策にしない。
5. 停止条件または15分以内に切り分け不能なら§14へescalateし、担当、次回更新時刻、証跡を記録する。

| 症状 | 確認 | 処置 |
|---|---|---|
| Loginできない | IdP、issuer/audience、MFA、Auth-P1 pool、shard partial、membership version | user存在を外部へ列挙せず、法域内correlationで調査。権限を広げて回避しない |
| 利用者に圃場が出ない | 選択tenant、field group scope、assignment、RLS、bbox、cache | 正しいmembership/scopeを修正。RLS無効化や全域付与をしない |
| 未同期が減らない | online、再認証、P0、push、DLQ、rejection/conflict、quota | outboxを削除せず、reason/recovery actionに従う |
| 差し戻しが増える | authorization version、旧snapshot、API version、quarantine | 法定記録を捨てず、再認証／管理者回復／変換を選ぶ |
| 日誌写真だけ失敗 | 10MB、signature/MIME、object/KMS、署名URL、quota | 本文だけを完全成功扱いせず再送。平文一時保管しない |
| 農薬警告 | master期限／失効、作物、倍率、回数、収穫日、server再判定 | 無条件overrideしない。責任者が根拠確認 |
| 在庫がマイナス | 未同期出庫、重複、単位、実棚 | eventを削除せず調整eventを追記 |
| 地図が遅い／空白 | 地理院tile到達、PMTiles version／metadata、BFF Rangeの206／403／416、assignment version、250MiB、bbox＋2km、PostGIS plan、RUM | 背景がなくても担当polygonを確認。S3 URL公開、担当外range許可、RLSを弱めるindex workaroundは禁止 |
| `partial`表示 | shard manifestと各shard応答 | `complete`へ手変更せず、復旧または監査付き長期離脱判断 |
| Backup失敗 | WAL、checksum、object inventory、key reference、容量 | release freeze。別世代があるだけで成功扱いしない |
| Monitorが無データ | collector、export、cardinality、credential、network | `no_data`として停止。0件／100%に変換しない |

## 16. 廃止・tenant退出・データ返却

1. 法的保持、契約、未同期、係争、legal holdを確認する。
2. RLS適用済みexportを作成し、checksum、項目、除外した第三者data、受領者を記録する。
3. 新規writeを停止し、queue、outbox、object、監査anchorを確定する。
4. 最終recovery setを作り、保持期限と鍵依存を台帳化する。
5. membership/session/context/offline snapshot、API client、送信先を失効する。
6. 保持満了後、DB/object/backup/key参照を二人承認で削除し、削除証跡を残す。

## 17. Baseline 1.0の既知制限

- Web logout、Cognito front-channel logout、refresh token revoke、global sign-out、SQS back-channel失効、DynamoDB session/context/offline snapshotの冪等失効は実装済み。ただし実Cognito user、複数browser、queue障害を含むAWS staging受入前は共有端末で運用しない。
- Cognito／DynamoDB／KMS／SQS adapterは実装済みだが、実AWS apply、Secrets Managerへのactor pseudonym key投入、署名済みimage、staging証跡は未完である。
- 写真private S3、短期参照URL、未完／孤立回収、offline map private S3／BFF Range／端末cache、法域内OTel、scan／署名build-once、段階配備workflowは実装済みだが、実AWS apply、実PMTiles公開、custom verifier、GitHub保護設定、実環境DR受入が必要。
- 日本語／英語切替基盤はあるが全文言の英訳reviewとRTL実表示は未完。
- S9 PWA暗号vaultと自動試験は実装済み。S6/S9のiOS/Android実機8プロファイル、実KMS回復、実Cognito logout、実network S7、実利用者UTは未完。

これらをmanual上の注意だけで受容せず、以下の受入checklistで実装・検証する。

## 18. 運用開始／release受入checklist

- [ ] 法域台帳に空欄・placeholderがない。
- [ ] 本番HA profile、OIDC/MFA、永続store、TLS、KMS、object、queueが実装済み。
- [ ] production logout、全session/context失効、共有端末の終了手順が実機でPASS。
- [ ] 全shardでRLS/FORCE、owner、trigger、security-invoker検査がPASS。
- [ ] P0/Auth-P1/P1/P2/Ops poolとP2飽和試験がPASS。
- [ ] SLO dashboard、burn alert、監査／WAL／失効即時alert、on-callが有効。
- [ ] 月次restoreと四半期DRがRPO 15分／RTO 4時間内。
- [ ] S6実機、S9鍵、実network S7、手動WCAG、実UTがPASS。
- [ ] release manifest、SBOM、provenance、署名、二人承認が揃う。
- [ ] 利用者向けguide、privacy notice、問い合わせ窓口、障害連絡方法を周知済み。

1つでも未完ならrelease statusは`BLOCKED`とする。

### 18.1 端末鍵・紛失・共有端末の操作

1. 配備前に法域`offline_recovery` RSA-2048以上のKMS非対称鍵を作り、private keyの`Decrypt`を通常BFF roleへ付与しない。`GetPublicKey`結果をJWKへ変換し、`apps/web/public/device-security-config.json`形式のruntime configとして同一originへmountする。空の同梱fileのままならoutbox保存はfail-closedする。
2. stagingで`cd apps/web && pnpm test:device-security`を実行する。続けて実機証跡JSONを作成し、repository rootで`node ops/check-device-acceptance.mjs <証跡JSON>`を実行する。exit 0と二人承認を確認するまで`device_encryption` release gateを`pass`にしない。
3. 通常終了は利用者に未同期0件を確認させ、右上利用者アイコン→「その他」→「ログアウト」を押させる。cache鍵消去、BFF session失効、Cognito logoutの監査相関IDを確認する。browser data削除をlogoutの代用にしない。
4. 未同期ありではlogoutが拒否される。通信復旧して冪等pushするか、端末紛失なら暗号化recovery packageを隔離する。packageの`tenantId`、`eventId`、`recoveryKeyId`を二人で照合し、HSM内private keyによる回復と再pushを監査する。平文やprivate keyをticket、端末、共有driveへ保存しない。
5. 紛失時は管理画面でmembership/session/context/offline snapshotを失効し、端末管理がある場合はlock/wipeする。次回onlineのcache暗号消去を待たずに権威API側で旧authorization versionを拒否する。遠隔wipe後は端末上の未同期outboxを回収できないため、recovery packageの耐久upload確認前にwipeしない。
6. rotationは新公開鍵配布→新規wrap切替→旧package回復rehearsal→旧key ID参照0→保持義務確認→旧private key無効化の順で行う。端末local cache鍵は再暗号化、outbox鍵はcontent key rewrapを完了してから旧versionを削除する。
