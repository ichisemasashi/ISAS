# ISAS 配備別サービス操作手順

| 項目 | 値 |
|---|---|
| 文書版 | 1.2 任意AWS adapter初期配備（2026-08-17） |
| 状態 | **製品・論理名・操作確定**。IaC applyとstaging受入が完了するまでproduction実行は`BLOCKED` |
| 目的 | production配備後に、当番者が推測せず起動・終了・状態確認できる実commandを固定する |
| 承認 | 実行者と確認者の二人承認。staging実行証跡がないcommandをproductionで初実行しない |

この文書は[Productionホスト共通契約](Productionホスト共通契約.md)に従い、`provider=aws`を選んだ[日本初期配備プロファイル](日本初期配備プロファイル.md)だけの実行台帳である。AWSは必須providerでもmacOS／Linux／FreeBSDの代替でもない。他hostでは各host専用runbookを使用し、未実装ならProductionを開始しない。固定論理名は本書、account ID、ARN、endpoint、image digest等の生成値はOpenTofuが出力する署名済み`ops/runtime/isas-jp-prod-01/deployment-manifest.json`を正とする。manifestが存在しない間はこのAWS production commandを実行しない。UT／デモと検証DBは[システム管理者運用ガイド §5](../manual/システム管理者運用ガイド.md#5-初期セットアップ)を参照する。

## 1. 対象台帳

| 項目 | 実値 |
|---|---|

| provider／account／region | AWS Commercial／account alias `isas-jp-prod`／`ap-northeast-1` |
| cluster／service | ECS cluster `isas-jp-prod-01`／`isas-jp-prod-web`、`isas-jp-prod-bff`、`isas-jp-prod-worker`、`isas-jp-prod-pool-{p0,auth-p1,p1,p2,ops}` |
| Web/BFF image | ECR private `isas/web`、`isas/bff`。tagではなくmanifestの`ecs.image_digests.*`を配備 |

| queue | SQS Standard `isas-jp-prod-{authorization-revocation,offline-sync,quarantine,audit-anchor}`＋各`-dlq` |

## 2. Command記入規則

各操作へ次の5点を必ず記入する。

1. copy&pasteできる非対話command。暗黙のcurrent contextに依存させない。
2. 正常時の終了codeと、確認できる出力例。
3. timeoutと失敗判定。無限に待たない。
4. data、session、outbox、trafficへの影響。
5. 失敗時の停止位置、rollback、連絡先。

secretはcommand line、shell履歴、証跡へ直接書かず、承認済みsecret参照を使う。

各作業shellの最初に次を実行する。以降のcommandはこの変数と署名検証済みmanifestを前提にする。

```bash
ISAS_DEPLOYMENT_MANIFEST=ops/runtime/isas-jp-prod-01/deployment-manifest.json
test -r "$ISAS_DEPLOYMENT_MANIFEST" && jq -e '.deployment_id == "isas-jp-prod-01" and .region == "ap-northeast-1"' "$ISAS_DEPLOYMENT_MANIFEST"
ISAS_AWS_REGION=ap-northeast-1
ISAS_ECS_CLUSTER=isas-jp-prod-01
ISAS_ECS_SERVICE=isas-jp-prod-bff
case "$ISAS_ECS_SERVICE" in isas-jp-prod-web|isas-jp-prod-bff|isas-jp-prod-worker|isas-jp-prod-pool-p0|isas-jp-prod-pool-auth-p1|isas-jp-prod-pool-p1|isas-jp-prod-pool-p2|isas-jp-prod-pool-ops) ;; *) exit 64 ;; esac
aws sts get-caller-identity
aws configure get region
```

最後の2行が承認対象account IDと`ap-northeast-1`を返さなければ停止する。manifestのKMS署名検証commandと期待key ARNはrelease manifestに記録する。

## 3. 通常起動

| 手順 | 実command／期待結果 |
|---|---|
| 1. 対象context | §2の4 commandを実行。account ID、region、clusterが台帳・manifestと一致 |
| 2. DB | `aws rds describe-db-clusters --region "$ISAS_AWS_REGION" --db-cluster-identifier isas-jp-prod-db --query 'DBClusters[0].[Status,EngineVersion,Endpoint]' --output table`／`available`、`16.14-R2`相当、writer endpoint 1件 |
| 3. queue/object/KMS/session | `aws sqs list-queues --region "$ISAS_AWS_REGION" --queue-name-prefix isas-jp-prod-`; `aws s3api head-bucket --bucket "$(jq -r '.storage.private_object_bucket' "$ISAS_DEPLOYMENT_MANIFEST")"`; `aws kms describe-key --key-id "$(jq -r '.kms_key_arns.object' "$ISAS_DEPLOYMENT_MANIFEST")"`; `aws dynamodb describe-table --table-name "$(jq -r '.storage.session_table' "$ISAS_DEPLOYMENT_MANIFEST")"`／全件存在しKMS有効 |
| 4. migration | production GitHub Environmentの`deploy` workflowを承認し、migration taskの終了code 0、schema digestがrelease manifestと一致することをActions証跡で確認。ECS service起動時にmigrationしない |
| 5. service起動 | `aws ecs update-service --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --service isas-jp-prod-bff --desired-count 3`; `web`、`worker`、5 pool serviceにもmanifest記載数で同じcommandを実行 |
| 6. 安定待ち | 各serviceを`ISAS_ECS_SERVICE`へ明示設定し、`aws ecs wait services-stable --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --services "$ISAS_ECS_SERVICE"`／10分以内に終了code 0 |
| 7. readiness／合成 | `curl --fail --silent --show-error --max-time 10 "$(jq -r '.application_url' "$ISAS_DEPLOYMENT_MANIFEST")/health/ready"`; staging用synthetic principalでlogin、RLS read、push、pull workflowを実行／全件0終了 |
| 8. traffic復帰 | GitHub `deploy` workflowの`enable-production-traffic`承認jobを実行。ALB weighted targetを10%→50%→100%、各10分でerror budget・P0 SLIを確認 |

## 4. 通常終了

利用者影響を承認したmaintenance時だけ実行する。DB、object、queue、KMSはWeb/BFFと同時に停止しない。

| 手順 | 実command／期待結果 |
|---|---|
| 1. 凍結・告知 | GitHub `operations` workflowの`maintenance-on`を二人承認。管理writeは503＋`Retry-After`、端末にはoffline保存継続を表示 |
| 2. traffic drain | 同workflowの`drain-alb`を実行し、CloudWatch `ActiveConnectionCount`とBFF in-flightが15分以内に0 |
| 3. queue証跡 | queue名をmanifestの`queues`から照合し、`aws sqs get-queue-attributes --queue-url "$(jq -r '.queues["offline-sync"].url' "$ISAS_DEPLOYMENT_MANIFEST")" --attribute-names ApproximateNumberOfMessages ApproximateNumberOfMessagesNotVisible`を4用途＋DLQへ実行。最古ageはCloudWatch `ApproximateAgeOfOldestMessage`を同時刻で取得し、operation evidenceへ保存 |
| 4. service停止 | web、bff、workerを順に`ISAS_ECS_SERVICE`へ設定し、`aws ecs update-service --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --service "$ISAS_ECS_SERVICE" --desired-count 0`。pooler、DB、queue、object、KMSは停止しない |
| 5. 停止確認 | `aws ecs describe-services --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --services isas-jp-prod-web isas-jp-prod-bff isas-jp-prod-worker --query 'services[].{name:serviceName,running:runningCount}'`／全0。入口はmaintenance応答 |
| 6. 保全確認 | RDSの`LatestRestorableTime`が15分以内、監査anchor queueが0、当日recovery pointが`COMPLETED`であることをAWS CLIとdashboardで確認 |

端末側outboxは削除しない。DB停止が必要な保守は別のDB provider手順とbackup／restore手順で、standby、WAL、RPOを確認して行う。

## 5. 再起動・rolling restart

| 手順 | 実command／期待結果 |
|---|---|
| precheck | CloudWatch dashboard `ISAS-jp-prod-overview`でP0/P1 SLO、error budget、各AZ task数を確認。3 AZすべてreadyでない時は中止 |
| rolling restart | `aws ecs update-service --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --service "$ISAS_ECS_SERVICE" --force-new-deployment --deployment-configuration maximumPercent=133,minimumHealthyPercent=66`／3 task中2 task以上を維持 |
| 進行確認 | `aws ecs wait services-stable --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --services "$ISAS_ECS_SERVICE"`／10分以内に0終了 |
| postcheck | §3手順7とdashboardのlogin、RLS read、push/pull、P0を確認 |
| abort | `aws ecs update-service --region "$ISAS_AWS_REGION" --cluster "$ISAS_ECS_CLUSTER" --service "$ISAS_ECS_SERVICE" --task-definition "$(jq -r --arg service "$ISAS_ECS_SERVICE" '.previous.taskDefinitions[$service]' "$ISAS_DEPLOYMENT_MANIFEST")"`。新規deploymentの停止はGitHub `rollback` workflowで実施 |

## 6. 状態・log・監視

| 操作 | 実command／URL |
|---|---|
| instance／digest | `aws ecs describe-services --region ap-northeast-1 --cluster isas-jp-prod-01 --services "$ISAS_ECS_SERVICE"`; task definition image digestをmanifestと照合 |
| readiness／liveness | `curl --fail --max-time 10 "$(jq -r '.application_url' "$ISAS_DEPLOYMENT_MANIFEST")/health/ready"`、同`/health/live` |
| 直近200行の非PII log | `aws logs tail /isas/production/bff --region ap-northeast-1 --since 30m --format short`。出力前にPII redaction alarmが0であることを確認 |
| correlation ID検索 | CloudWatch Logs Insightsで`fields @timestamp,@message | filter correlation_id="ID" | sort @timestamp desc | limit 200`。tenant/userの生IDで検索しない |
| SLO／error budget | CloudWatch dashboard `ISAS-jp-prod-overview`、Alarm prefix `ISAS-JP-P0-`／`ISAS-JP-P1-` |
| DB／WAL／pool | `aws rds describe-db-clusters --db-cluster-identifier isas-jp-prod-db --region ap-northeast-1`; dashboard widgets `DB-LatestRestorableTime`、`PgBouncer-*` |
| queue／DLQ／失効遅延 | `aws sqs list-queues --queue-name-prefix isas-jp-prod- --region ap-northeast-1`後、各URLの全attributes。DLQ>0またはP0最古>60秒でincident |
| object／KMS | manifest記載bucketへ`aws s3api get-bucket-versioning`／`get-public-access-block`、keyへ`aws kms describe-key`。`Enabled=true`かつsingle-region |
| 監査chain／anchor | CloudWatch widget `AuditChainVerification`とSQS `isas-jp-prod-audit-anchor`。chain gapまたは未anchor>5分でwrite freeze |

## 7. Backup・restore・deploy・rollback

次のcommandを[バックアップ・復旧手順](バックアップ・復旧手順.md)と[デプロイ・ロールバック手順](デプロイ・ロールバック手順.md)から参照する。復旧は必ず隔離staging accountで行う。

| 操作 | 実command／期待結果 |
|---|---|
| recovery set作成 | `ops/recovery/create-recovery-set.sh <staging-account-id> "$ISAS_DEPLOYMENT_MANIFEST" /secure/recovery/recovery-set.json`。6 backup job、PITR、4 inventory、queue、監査、構成、鍵を同じIDへ記録。production manifestは拒否 |
| WAL／object／queue／監査 | 出力のPITR lagを900秒以内、6 jobを`COMPLETED`、4 inventoryを最新、queue／監査／digest／KMS参照を欠落なしで照合し、二人承認後だけstatusを`APPROVED`へ変更 |
| 隔離restore | `ops/recovery/start-isolated-restore.sh <staging-account-id> "$ISAS_DEPLOYMENT_MANIFEST" approved-recovery-set.json approved-restore-request.json /secure/recovery/restore.json`。application VPCと同一、sink以外のegress、二者承認なしを拒否 |
| restore検証 | schema、RLS/FORCE/owner、trigger/security-invoker、audit chain、object hash、queue/cursor、idempotency、revocation、tenant越境、合成transactionを検査し、`node ops/recovery/check-operational-acceptance.mjs <evidence.json>`で判定 |
| release digest配備 | GitHub Actions `deploy` workflowへrelease manifest digestを指定。OIDC role、cosign/KMS署名、SBOM、provenance、ECR scanを検証後、task definitionを登録 |
| rollout pause | GitHub production Environmentの次段承認を拒否し、現在のALB traffic weightを維持する。異常taskは増やさず、必要なら次行のrollbackを実行 |
| 直前digest rollback | GitHub `rollback` workflowへdeployment IDとmanifestの`previous.releaseDigest`を指定。DB contract migration後はappだけを戻さずwrite freeze＋restore判断 |
| write freeze／解除 | GitHub `operations` workflowの`write-freeze-on`／`write-freeze-off`。解除は原因解消、queue/cursor/監査検証、Incident Commander＋Verifier承認後だけ |
