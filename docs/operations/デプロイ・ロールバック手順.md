# デプロイ・ロールバック手順

## 1. 適用範囲と役割

ADR-0021のrelease candidateを、ADR-0019の本番HA profileへ同一digestのまま段階配備する。Release Commander（RC）が判断し、Operatorが実行、Verifierが別端末で対象と証跡を照合する。DB migration、security、法域判断の担当を必要に応じ追加する。

## 2. 事前確認（Go/No-Go）

1. change ticketにrelease version、source commit、全artifact digest、法域、shard manifest version、変更概要、影響、owner、作業時刻を記録する。
2. `node ops/check-release-readiness.mjs <manifest>`を実行し0終了を保存する。example、`no_data`、期限切れwaiver、High/Medium、error budget 25%未満、最新DR 93日超はNo-Go。
3. stagingで同じdigestのE2E、PG16/PostGIS migration、RLS/owner/trigger/security-invoker、SLO 30試行以上、PWA未同期保持、manual WCAG、security、S6/S9、UT証跡を照合する。
4. 進行中Sev-1/2が0、on-callとincident channelが有効、dashboard/alert/runbookがrelease digestを表示できることを確認する。
5. WAL archive age 5分以内、最新recovery set完全、四半期restoreがRPO 15分／RTO 4時間以内、object/KMS/queueを含むことを確認する。
6. shard manifestをruntime値と照合する。応答nodeだけから一覧を作らず、`active`、`draining`、`long_term_absent`の二人承認を確認する。
7. migrationのexpand/contract段階、lock/statement timeout、容量、backfill、N/N-1互換、14日offline client、roll-forwardとwrite-freeze条件を復唱する。

## 3. 実施

### 3.1 Backup pointとmigration

1. 配備直前の`recovery_set_id`を作成し、[バックアップ手順](バックアップ・復旧手順.md#2-backup取得)で完全性を確認する。取得中にWAL/object/鍵参照が欠けたら停止する。
2. dedicated migration identityでchecksum済みbundleを一度だけ実行する。application起動時migrationは禁止する。
3. expand migration後、schema version、RLS/FORCE、owner非bypass、trigger、security-invoker、監査chain、index、replica/WAL lagを確認する。想定外lock、archive 15分超、`server_seq`不整合でwriteを止める。
4. backfillはchunk化・再開可能・冪等にし、P0予約枠を使わない。P0 burnまたはreplica/WAL/storage閾値で自動pauseする。

### 3.2 Application段階配備

1. 署名、provenance、registry、法域、digest、config compatibilityをdeploy先で検証する。環境別rebuildはしない。
2. canary 5%へ配備し、最低30分か1,000 eligible transactionsの長い方を観測する。
3. gateが緑なら25%へ進め、最低2時間か1,000 eligible transactionsの長い方を観測する。
4. RCとVerifierが明示承認して100%へ進める。旧instanceはconnection drain後に停止し、rollback窓が閉じるまで直前digestを保持する。
5. 各段階でavailability/error budget、P0、login、pool待ち、WAL、queue最古年齢、revocation、quarantine、監査chain、object、client RUM、PWA更新を確認する。signal欠落は緑ではない。

## 4. 自動停止と判断

次のいずれかでpromotionを止める。

- ADR-0020の14.4倍／6倍burn、WAL 15分超、P0失効DLQ 60秒超、監査chain不一致。
- RLS越境、認証context拡張、農薬安全誤判定、未同期outbox消失、cursor巻戻り、idempotency結果変化。
- artifact/config/shard manifest digest不一致、法域外telemetry/export、署名検証失敗。
- DB lock／storage／poolが設定閾値超、object/KMS障害で平文縮退が必要になる状態。

RCは次から選ぶ。

| 状態 | 処置 |
|---|---|
| application/configだけ、schemaは互換 | 直前の署名済みdigestへrollback |
| expand migrationの新objectが原因 | app rollback。新objectは削除せず無効化し、後日roll-forward |
| backfill／contractに問題、dataは健全 | writeまたはjob停止、修正migrationをroll-forward |
| data破損、cursor巻戻り、誤った不可逆event | write freeze、incident宣言、復旧手順でPITR/recovery setを判断 |
| PWAのみ | serverで旧新assetを維持し、network kill switch。cache/outboxをpurgeしない |

## 5. 完了

1. 100%後24時間は強化監視し、release digestとSLOをmanifestへ追記する。
2. contract migrationは14日offline窓、active client、queue/quarantine、rollback窓を再確認した別changeとして実行する。
3. ticketへ開始／終了、実行者／確認者、manifest digest、test/monitor/backup evidence、判断、incident、残taskを記録する。
4. console手変更があれば宣言構成へ戻しdrift 0を確認する。feature flagにowner／期限がない状態を残さない。
