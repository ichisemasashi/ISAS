# 障害対応手順

## 1. Severity

| Severity | 例 | 初動 |
|---|---|---|
| Sev-1 | tenant越境、農薬安全誤判定、未同期data loss、監査chain不一致、WAL 15分超、法域外流出、広範停止 | 5分以内ack、Incident Commander設置、promotion停止 |
| Sev-2 | 6倍burn、主要機能劣化、quarantine 7日超、replica/pool継続逼迫 | 15分以内ack、ownerと復旧予定 |
| Sev-3 | SLO未侵害の限定不具合、回避策あり | 営業時間内にtriage |

## 2. 初動

1. alertの法域、deployment、shard、release digest、開始時刻、症状を復唱する。通知本文にPIIを追加しない。
2. Incident Commander、Operations、Application/DB/Security、Communications、Scribeを割り当てる。一人が複数役を兼ねても、実行と確認は分ける。
3. deploy中ならpromotionを停止する。security／data整合性が不明ならwriteをfreezeし、offline入力の継続とoutbox保持を優先する。
4. shard manifest、error budget、P0、WAL、pool、queue、object/KMS、監査chain、直近changeを確認する。monitor欠落を正常とみなさない。
5. 公開statusには影響と回避策だけを記載し、tenant/user/field、脆弱性詳細、credentialを載せない。法域・契約ごとの通知期限を法務担当が判断する。

## 3. 復旧と終了

- application/configだけなら署名済みdigestへrollbackする。data破損やcursor疑義なら[復旧手順](バックアップ・復旧手順.md#4-実障害からの復旧)へ移る。
- 平文保存、RLS無効化、古い権限cache、監査停止を回避策にしない。安全を保てない機能だけを停止する。
- 復旧判定はSLO signal、synthetic transaction、業務不変条件を別のVerifierが確認する。dashboardが緑になっただけで終了しない。
- 24時間以内にtimeline、影響、data loss、検知／判断／復旧、再発防止owner/dateを記録する。5営業日以内に非難を目的としないreviewを行い、ADR/runbook/test/alertへ反映する。
