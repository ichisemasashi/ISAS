# ISAS 日本初期配備プロファイル

| 項目 | 決定値 |
|---|---|
| profile ID | `jp-prod-aws-tokyo-v1` |
| 状態 | **採用**。OpenTofu・migration・受入gateは実装済み。AWS staging apply／実環境25項目受入は未実行のためproduction releaseは引き続き`BLOCKED` |
| 法域 | 日本（`JP`）。1法域デプロイ、法域外への業務データ複製なし |
| cloud／account | AWS Commercial Cloud。AWS Organizations配下の専用production account alias `isas-jp-prod` |
| region | Asia Pacific (Tokyo) `ap-northeast-1`のみ |
| failure domain | 同region内の相異なる3 Availability Zone。IaCが利用可能な3 AZ IDを選び、release manifestへ固定 |
| deployment ID | `isas-jp-prod-01` |
| data classification | 業務DB、写真、session、queue、log、trace、backup、鍵を東京region内へ保持 |

このprofileはOSS全体をAWSへ固定するものではない。初期の日本production配備だけを具体化し、他法域・self-hostはADR-0019の同じ契約を満たす別profileとする。

## 1. 採用製品

| 領域 | 採用 | 構成・禁止事項 |
|---|---|---|
| DNS／証明書／入口 | Amazon Route 53、AWS Certificate Manager、AWS WAF、Application Load Balancer | ALBは3 AZ subnet。HTTPSのみ、HTTPはHTTPSへredirect。application配信のCloudFrontはPhase 1で不採用。Cognito custom managed loginが内部利用するCloudFront distributionと`us-east-1`証明書だけを認証endpointの例外とし、業務data／application assetを載せない |
| Web／BFF／worker | Amazon ECS on AWS Fargate | private subnetの3 AZを使用。Web／BFFはdesired 3、最低2 task、実受入で各2 AZ以上への分散を必須化。Web assetも同一originから配信 |
| database | Amazon RDS for PostgreSQL Multi-AZ DB cluster、PostgreSQL `16.14R2`、PostGIS `3.4.6` | writer 1＋reader 2を3 AZ。RDS管理WAL archiveと自動backupで30日PITR。public access禁止。minor／PostGIS更新はstaging migration・plan再試験後だけ |
| pooler | PgBouncer `1.24.x`をECS serviceとして配備 | P0／Auth-P1／P1／P2／Opsを別service・role・予算へ分離。transaction pooling、`SET LOCAL`契約を維持 |
| OIDC IdP | Amazon Cognito User Pools Plus（東京region、resource logical ID `IsasJpUserPool`） | authorization code＋PKCE、managed login custom domain。WebAuthnは`MULTI_FACTOR_WITH_USER_VERIFICATION`でuser verification付きpasskeyをMFA要件として扱い、password経路はTOTP MFA。SMSは回復用にも既定不採用 |
| session/context | Amazon DynamoDB Standard、single-region table `isas-jp-prod-session-context` | 3 AZ自動複製、PITR、KMS暗号化、strongly consistent read。global table禁止。期限判定と失効はBFFが同期実施し、TTLは後処理だけ |
| object storage | Amazon S3 Standard、private bucket＋VPC-only access point | Block Public Access、ACL無効、versioning、SSE-KMS。添付はALB/BFF同一originから認可後に配信し、bucketを公開しない。CRR／Transfer Acceleration／public website禁止 |
| offline map | private S3の日本PMTiles＋same-origin BFF Range proxy | OSM／Planetiler成果物のversion、SHA-256、ODbL、NOTICE、SBOMを固定。端末へS3 URLや日本全体を公開せず、各RangeでRLS担当scopeを再検証。地理院タイルはonline直読だけ |
| queue | Amazon SQS Standard＋用途別DLQ＋S3 quarantine archive | P0失効、同期、quarantine、監査anchorを分離。mainごとにDLQとredrive allowを限定し、quarantine原文はObject Lock archiveへ退避。at-least-once前提の冪等consumer。cross-region転送禁止 |
| key／secret | AWS KMSのsingle-region customer managed key＋AWS Secrets Manager | AWS KMSのFIPS検証済みHSMで保護。DB、object、session/token、queue、backup、ECDSA署名を用途別keyに分離。CloudHSM custom key store／multi-Region key禁止。ECS task roleの短期credentialを使用 |
| CI/CD | GitHub Actions、GitHub Environments、AWS IAM OIDC federation | long-lived AWS key禁止。actionはcommit SHA固定。PRとproduction environmentを分離し、productionは二人承認 |
| artifact registry | Amazon ECR private repositories | tag immutable、digest deploy、Amazon Inspector enhanced scanning。SBOMはSPDX JSON、BuildKit provenanceとcosign/KMS署名・attestationを同digestへ保存 |
| artifact signing | `cosign`＋AWS KMS asymmetric signing key | build jobだけに署名権限、deploy roleは検証のみ。署名・SBOM・provenance不一致は起動拒否 |
| IaC | OpenTofu、remote stateは東京regionのS3＋DynamoDB lock | production console変更はSev-1だけ。stateはSSE-KMS、versioning、別権限。plan二人review |
| telemetry | OpenTelemetry SDK＋ADOT Collector、Amazon CloudWatch Metrics/Logs/Application Signals、AWS X-Ray | 全export先を`ap-northeast-1`へ固定。cross-region Logs centralization禁止。PII、token、生tenant/user IDを送らない |
| audit／cloud control | 業務監査chainはRDS＋S3 Object Lock、AWS操作はCloudTrail | 一般logと監査を統合しない。audit anchor用bucketは別account相当の別権限境界、同region |
| alert／on-call | CloudWatch Alarm＋Amazon SNS topic `isas-jp-prod-incident` | 通知本文は法域、severity、非PII correlation、runbook URLだけ。担当はIAM Identity Center group `ISAS-JP-OnCall` |

AWSは、選択したregionのcustomer contentを顧客の同意なく別regionへ移動・複製しない方針を示している。ただし一部global／edge serviceは転送を伴い得るため、このprofileはregional resourceをallowlistし、CloudFront、DynamoDB Global Tables、S3 CRR、multi-Region KMS、cross-region log集約を禁止する。参考：[AWS data privacy](https://aws.amazon.com/jp/compliance/data-privacy-faq/)、[S3 region](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)。

RDS PostgreSQL 16はPostGISを提供し、Multi-AZ DB clusterはwriter 1＋reader 2を3 AZへ配置する。参考：[RDS extension matrix](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html)、[RDS Multi-AZ DB cluster](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/create-multi-az-db-cluster.html)。実装前に東京region／対象accountでengine versionが選択可能かIaC planとAWS APIで再確認する。

CognitoはWebAuthn passkeyをサポートし、user verification付きpasskeyをMFA相当へ構成できる。参考：[Cognito authentication flows](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html)。BFFはtokenをbrowserへ返さず、logout時にlocal session/contextを即時失効してCognitoのtoken revoke／global sign-out adapterを呼ぶ。

## 2. Network・account境界

1. AWS Organizationsで`security/log-archive`と`production` accountを分離する。業務データをsecurity accountへ複製せず、CloudTrail等のAWS control-plane記録だけを送る。
2. production VPCは3 AZにpublic ingress subnet、private application subnet、isolated DB subnetを持つ。NAT／egressはallowlistし、DB、DynamoDB、S3、SQS、KMS、CloudWatch、ECRへVPC endpointを優先する。
3. ALBだけをinternet-facingにし、ECS task、RDS、poolerへpublic IPを付けない。
4. DNS名、Cognito custom domain、WebAuthn RP IDは同一の運用domainへ固定し、IaC outputをrelease manifestへ記録する。
5. backup、object version、log、traceは東京region外へ複製しない。region全損時のRTOは初期profileの保証外とし、法域内3 AZのRPO 15分／RTO 4時間をrelease gateとする。

## 3. 認証・session policy

| 項目 | 決定値 |
|---|---|
| 一般利用者 | passkeyを推奨。password利用時はTOTP MFAを登録 |
| 管理・export・migration・農薬override | user verification付きpasskeyまたはpassword＋TOTP。操作時step-up、有効10分 |
| BFF idle session | 30分 |
| BFF absolute session | 一般12時間、管理者8時間 |
| tab context | 15分。権限version変更時は期限前でも失効 |
| refresh token | 30日以下。BFFでKMS envelope encryption、browserへ非公開 |
| Cookie | `Secure; HttpOnly; SameSite=Lax`、host-only、session IDは256-bit以上の不透明値 |
| DynamoDB TTL | 期限切れitemの物理掃除専用。認可時は必ず`expires_at`と`authorization_version`を検証 |
| logout | BFF session/context即時削除＋Cognito revoke/global sign-out。失敗はDLQへ記録しlocal失効を戻さない |

DynamoDB TTLの削除はbest effortで期限後も残り得るため、認可の期限判定には使わない。参考：[DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_UpdateTimeToLive.html)。DynamoDBは既定で3 AZへ複製される。参考：[DynamoDB resilience](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html)。

## 4. 日本Phase 1保持・削除profile

これは日本初期配備の**運用既定**であり、すべてが法定最低期間という意味ではない。tenantの業種、認証、契約、係争、補助事業、税務上の位置付けにより延長する場合は、根拠ID、対象、起算日、期限、承認者を保持policyへ登録する。legal hold中は自動削除せず、解除を二人承認する。

| データ種別 | 既定保持／起算 | 根拠区分 | 期限時処理 |
|---|---|---|---|
| 農薬使用記録、作業日誌、収穫・出荷trace、添付写真 | 作付終了日の属する年度末から3年 | 農水省GAP資料の1〜3年目安を上限側で採用。農薬使用者一般に一律3年の法定義務があるとの表現はしない | 監査付き削除。法定・認証対象は訂正recordを維持し、保持終了後に物理削除 |
| 農薬仕入・販売帳簿に該当する在庫event | 帳簿閉鎖／事業年度基準で7年。欠損金・災害損失等はtenant税務profileで10年 | 法人税帳簿・棚卸・取引書類として扱う安全側既定。農薬販売者の帳簿は別途最低3年 | partition単位削除前に税務profileとlegal holdを照合 |
| 打刻、労働者名簿、賃金計算根拠に採用した日誌 | 対象記録の起算日から5年 | 労基法本則5年を採用（経過措置の当分3年より長く保持） | 雇用主tenantの承認後に削除または法定recordの非必須PIIを仮名化 |
| 監査log／anchor／管理者操作 | eventから7年 | security・説明責任の運用既定。税務／労務recordと結合する証跡は対応recordの長い方 | 仮名mapを切断し、chain／anchorは期間単位で保持後削除 |
| 圃場、作付、各種masterの論理削除版 | active中＋削除後90日、版履歴3年 | 誤操作回復の運用既定 | 90日後に現行rowを物理削除、版履歴は3年後削除。参照・holdがあれば延期 |
| 利用者account／membership | 契約・所属終了後30日 | 本人請求・誤失効回復の運用既定 | 法定record上の主体は仮名IDへ置換し、IdP属性・任意PII・sessionを削除 |
| session／context／login state | §3の絶対期限＋失効後7日以内に物理掃除 | security運用 | 論理上は期限／失効時点で即無効。DynamoDB TTLと日次sweeperで物理削除 |
| CSV取込原文／error行 | job完了または中止から30日 | 移行検証・再現の運用既定 | job台帳・checksum・件数を残し、原文とPII error detailを削除 |
| CSV export／署名URL | export 24時間、object 7日以内 | data minimization | download URL失効、object lifecycle削除、受領者のlocal copyは目的終了時削除 |
| raw位置log（Phase 2） | 90日 | 目的限定・data minimizationの既定 | 90日で削除。必要な業務実績は圃場・日単位の非軌跡集計へ変換し3年 |
| operational/security log | 90日 | ADR-0020既定 | lifecycle削除 |
| trace | 30日 | ADR-0020既定 | lifecycle削除 |
| metric | 90日 | ADR-0020既定 | retention expiry |
| backup recovery point | 日次30世代＋週次12世代 | ADR-0019／要求SLO | 世代期限、legal hold、鍵依存を確認して削除。業務recordの法定期間をbackupで代替しない |
| quarantine／同期回復原文 | 解消後30日、未解消は最長1年で必須escalation | data loss防止とdata minimization | 解消証跡・変換結果を残して削除。30日未解消はrelease blocker |

公的根拠：法人の帳簿・取引書類は原則7年で、一定の欠損金等は10年となる（[国税庁 No.5930](https://www.nta.go.jp/taxes/shiraberu/taxanswer/hojin/5930.htm)）。労働関係書類は本則5年、経過措置として当分3年である（[厚生労働省Q&A](https://www.startup-roudou.mhlw.go.jp/qa/zigyonushi/syuugyoukisoku/q6.html)）。農水省のGAP資料は農薬等の記録について作付終了後1〜3年程度を目安としている。個人情報保護法は一律の保存期間を定めず、不要となった個人データを遅滞なく消去する努力義務を示す（[個人情報保護委員会Q&A](https://www.ppc.go.jp/all_faq_index/faq1-q5-2/)）。

## 5. CI/CD・監視policy

1. GitHub ActionsはOIDCで環境別IAM roleを引き受け、長寿命access keyを置かない。trust policyはrepositoryとGitHub Environmentの`sub`を完全一致させる。参考：[GitHub OIDC for AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)。
2. review済みcommitから本repositoryが所有するWeb、BFF、migrationを一度だけbuildし、ECRへimmutable digestでpushする。platform image（worker、PgBouncer、ADOT）は承認済みupstream／別build pipelineのdigest、SBOM、scan evidenceをrelease manifestへ固定する。
3. ECR enhanced scanningでOSと言語packageを継続scanする。参考：[ECR enhanced scanning](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-scanning-enhanced.html)。
4. SPDX JSON SBOM、BuildKit SLSA provenance、cosign/KMS署名とSBOM attestationを同digestへ束ねる。署名公開鍵のSHA-256もbuild manifestへ固定し、production境界で再検証する。
5. ADOT sidecarから東京regionのCloudWatch／X-Rayへ送る。参考：[ADOT and X-Ray](https://docs.aws.amazon.com/xray/latest/devguide/xray-services-adot.html)。X-Ray SDK／daemonは新規採用しない。
6. `main`、staging、production GitHub Environmentに保護ruleを設定し、productionはRelease CommanderとVerifierの二人承認にする。

## 6. 配備時に生成する実値

AWS account ID、AZ ID、resource ARN、endpoint、Cognito issuer、dashboard URL、SNS subscription、KMS key IDは秘密ではないものも含め、手入力で文書へ複製しない。OpenTofu outputから署名済み`deployment-manifest.json`を生成し、release manifestへdigestを記録する。次の論理名は固定する。

| 種別 | 固定論理名／参照 |
|---|---|
| Service Owner | IAM Identity Center group `ISAS-JP-ServiceOwner` |
| on-call | IAM Identity Center group `ISAS-JP-OnCall`、SNS `isas-jp-prod-incident` |
| security／privacy／法務 | groups `ISAS-JP-Security`、`ISAS-JP-Privacy`、`ISAS-JP-Legal` |
| shard manifest | versioning＋Object Lock＋SSE-KMSのS3 `*-shard-config/shards/manifest-v<N>.json`と`.sig`。SHA-256とKMS ECDSA署名をrelease manifestへ固定 |
| offline map | versioning＋SSE-KMSのS3 `*-offline-maps/tilesets/<version>/`。`japan.pmtiles`、`manifest.json`、`OSM-NOTICE.txt`、`sbom.json`を同versionへ固定 |
| dashboard | CloudWatch dashboard `ISAS-jp-prod-overview` |
| backup | AWS Backup vault `isas-jp-prod-vault`＋S3 `IsasJpRecoveryBucket`、東京region |
| operation evidence | S3 Object Lock bucket `IsasJpOpsEvidenceBucket`、東京region |

実ARN等が生成されていないことは「方式未決」ではなく「AWS staging未適用」である。[OpenTofu実装](../../infra/opentofu/README.md)のapply、[staging 25項目受入](AWS-staging受入手順.md)、DRが完了するまでproduction releaseは`BLOCKED`のままとする。
