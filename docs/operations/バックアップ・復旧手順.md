# バックアップ・復旧手順

## 1. 前提

対象はDBだけでなく、object version、権威outbox／revocation／quarantine／idempotency、監査chain/anchor、shard/config manifest、migration digest、鍵version参照を含む`recovery_set`である。backupは法域内の別failure domain・別権限境界へ暗号化し、鍵自体はbackupと分ける。

役割はBackup Operator、Restore Operator、Security/Key Custodian、Verifierに分ける。Restore Operatorへ常設復号権限を与えず、実復旧はIncident Commanderの二人承認と期限付き権限を要する。

## 2. Backup取得

1. 対象の`deployment_id/jurisdiction/shard_id`、primary timeline、`server_seq`上限、schema/release/config/shard manifest versionを記録する。
2. WAL archive ageが5分以内、archive/checksum error 0、object inventoryと権威queueが観測可能であることを確認する。15分超ならSev-1とし、通常backup成功にしない。
3. 隔離stagingでは`ops/recovery/create-recovery-set.sh <account-id> <deployment-manifest> <output>`を実行する。productionでは同じsource commitと署名済みimageから昇格した承認済みworkflowだけを使う。日次復旧点30世代、週次12世代を最低保持し、平文`pg_dump`を共有volumeへ常設しない。
4. 同じ`recovery_set_id`で、必要なWAL範囲、object version inventory、queue/checkpoint、監査anchor、構成／migration／artifact digest、鍵ID/version参照をmanifestへ記録する。
5. 各artifactのsize、checksum、暗号化key reference、法域、retention expiry、immutability/versioning、作成時刻を検証する。鍵versionがrestore時まで保持されることをkey inventoryで確認する。
6. backupのread/list/delete権限を分離し、削除は保持期限・legal hold・鍵依存0を二人確認する。backupを永久保持して本人削除やretentionを無効化しない。

「job succeeded」だけでは完了ではない。月次restoreで読めることを確認し、四半期に全recovery setでRPO/RTOを測る。

SQSは配送路であり、queue message自体を権威backupにしない。復旧時はPostgreSQLの永続outbox／idempotency、quarantine archive、監査anchorから未完配送を再構築し、取得時のSQS概算件数とcursorを欠落検出に使う。S3 inventoryは24時間以内を要求するが、復旧本体は同じsetのAWS Backup recovery pointとversioningを使う。

## 3. 月次restore test

1. production networkから分離した**同一法域内**の一時環境を新規作成する。既存clusterへ上書きしない。外部email/webhook/pushはsinkへ固定する。
2. 無作為に選んだ日次／週次世代からbase＋WALを指定時点へrestoreする。timelineとrecovery pointがmanifestに一致するまで一般接続を許可しない。
3. 対応するobject version、権威queue、監査anchor、構成をrestoreし、期限付きkey grantで復号する。不足要素を「対象外」にしてDBだけの成功へ縮小しない。
4. applicationをmanifest記載digestで起動し、migrationを勝手に最新化しない。restore schemaに対応するversionで検査する。
5. 次を検証する。
   - row/count/hashの期待値、外部参照、object checksum、未完upload／孤立参照。
   - RLS/FORCE、owner非bypass、trigger、security-invoker、tenant/scope拒否、認証bootstrap allowlist。
   - 監査chain/anchor、`server_seq`単調性、idempotency ledger、revocation version、quarantine原文。
   - synthetic tenantでread/write/syncし、他tenant 0行、P0先行、同一key同一結果。
6. data loss時間、開始から利用可能までの時間を記録する。RPO 15分またはRTO 4時間を超えたらrelease blockerとしてowner/date付き是正を登録する。
7. 証跡を残した後、一時環境と期限付きkey grantを承認済み手順で破棄する。平文dump、log、shell history、外部sinkにdataが残っていないことを確認する。

実行開始には`ops/recovery/start-isolated-restore.sh`を使い、復旧後の最終判定には`ops/recovery/check-operational-acceptance.mjs`を使う。月次restoreは前回実施から35日を超える前に行い、日次／週次世代を交互に選ぶ。四半期DRは100日を超える前に、実行担当へ予告しない世代選択で同じ検証を行う。data lossは復旧点と障害基準時刻の差、RTOは障害宣言からreadiness・合成transaction・独立確認完了までを単調時計で測る。

本番dataを開発／一般stagingへ直接復元しない。試験fixtureが必要なら隔離restore後に用途allowlistでPII、関係graph、token/secret、位置、添付を除外・仮名化し、新しいdatasetとして承認する。

## 4. 実障害からの復旧

1. [障害対応手順](障害対応手順.md)に従いIncident Commanderを置き、影響法域／shard／tenant、最終正常時点、最終確定`server_seq`、端末offline継続可否を確定する。
2. data破損またはRPO超過疑いではwriteをfreezeする。clientへoffline保存継続と未同期を消さない案内を出す。古いprimaryへ再接続させない。
3. 復旧目標時点を選び、失われる可能性のある期間とeventを明記して二人承認する。最新backupではなく、破損前の整合した時点を選ぶ。
4. 新clusterへ§3と同じ順でrecovery setをrestoreする。旧clusterを上書きせず、forensic保全と戻し先を残す。
5. RLS、監査、object、queue、cursor、idempotency、business invariantを検証する。shard manifest上の対象集合を使い、応答nodeだけで`complete`にしない。
6. TTLを短縮し、新入口を新clusterへ切替える。最初は内部synthetic→限定traffic→全trafficの順にし、P0、WAL、pool、error budgetを監視する。
7. RPO窓で失われたserver eventと端末outboxを照合する。同じidempotency keyは再送し、受理済みは重複作成しない。失効後記録や変換不能eventを捨てず回復／quarantineへ送る。
8. 24時間強化監視後にwrite freeze、DNS/route、旧cluster、key grantを整理する。data loss、RPO/RTO、判断、再送、法令通知要否をincident記録へ残す。

## 5. 四半期DRの合格条件

- 予告なしに選んだ世代とshardで、DB＋object＋queue＋audit＋鍵＋構成を復元できる。
- data loss 15分以内、利用可能まで4時間以内。
- tenant越境0、監査chain不一致0、object欠損0、cursor巻戻り0、同一idempotency重複0。
- 実行者とは別のVerifierがevidenceを確認し、release manifestの`dr`を更新する。

## 6. staging運用演習

同じ四半期枠で[配備別サービス操作手順](配備別サービス操作手順.md)の通常起動、通常終了、rolling restartを実行する。依存障害はP2 pool停止、queue配送停止、readiness依存失敗を一つずつ注入し、P0保護、alert、runbook、rollbackを確認する。最後に[障害対応手順](障害対応手順.md)でSev-1机上＋実操作演習を行い、ack 5分、役割割当、write freeze、offline案内、復旧、24時間監視への引継ぎを記録する。

```sh
node ops/recovery/check-runbook-placeholders.mjs \
  docs/operations/配備別サービス操作手順.md \
  docs/manual/システム管理者運用ガイド.md \
  docs/manual/システム利用者ガイド.md
node ops/recovery/check-operational-acceptance.mjs /secure/recovery/operational-acceptance.json
```

両commandが0終了し、Service Owner、Restore Verifier、Security On-callの異なる三者が承認するまでproductionへ昇格しない。
