## 2. 評価の前提（日々の農作業タスク管理に必要な能力）

本レビューでは、日々の農作業のタスク管理として次の能力を必要とみなし、各指摘をこれに照らして評価した。

| 記号 | 必要な能力 | 説明 |
| --- | --- | --- |
| A | 当日・今週の把握 | 今日やること、今週これからやることが一覧で分かる |
| B | 遅れの把握 | 予定日を過ぎても終わっていない作業に気づける |
| C | 実行記録 | 着手・完了、作業時間、確認項目を記録できる |
| D | 現場での記録 | 畑にいる間（スマホ）に記録できる |
| E | 記録の正しさ | 操作の順番や複数画面で記録が壊れない |
| F | 複数人での運用 | 誰がやるか、依頼した作業がどうなったかが分かる |
| G | 定型作業・注意喚起 | 繰り返し作業の登録、期限前の知らせ |
| H | 継続運用 | 一シーズン分のデータでも使え、データを失っても戻せる |

重大度は次のとおりとする。

| 重大度 | 定義 |
| --- | --- |
| 重大 | 日々の運用で作業漏れ、または記録の破損・消失に直結する |
| 中 | 運用は可能だが、手作業での補完や別手段の併用が常に必要になる |
| 軽微 | 手間や分かりにくさはあるが、作業漏れや破損には至らない |

指摘の分類は次のとおりとする。

| 分類 | 定義 |
| --- | --- |
| 欠陥 | 要求仕様書または一般的な正しさに反する動作 |
| 要求の問題 | 要求仕様書そのものに矛盾・不足がある |
| 改善 | 要求どおりだが、日々の運用に対して不十分 |
| 要求外 | 要求仕様書で第2版の対象外と明記されている。運用上のリスクとして記録する |

## 3. 総合判定

**判定: 条件付きで不十分（現状のままでは、日々の農作業のタスク管理を本システム単独で漏れなく行うことはできない）**

- 一人の利用者がパソコンの前で「今日の作業」を未着手／着手中／完了で回し、作業時間とチェック項目を付ける、という最小限の使い方は成立している（能力 C）。
- 一方で、次の 3 点は日々の運用で作業漏れや記録の破損に直結するため、重大と判定した。
  1. 要求の「今週」が実装では「直近7日（過去方向）」になっており、今週これからの作業が日次一覧の「今日」「直近7日」に出ない（R-01）。
  2. 予定日を過ぎた未完了の作業が「今日」から消え、8日以上前のものは「直近7日」からも消える。遅れの表示もない（R-02）。
  3. 日次一覧で実行状態を保存すると、画面を開いた時点の古い内容で作業全体を上書きし、作業画面で行った時刻・題名の変更が黙って元に戻る（R-03）。
- さらに、スマホで完了を付けられない、担当・依頼が日次一覧につながらない、繰り返し・通知がない、という要求外の制約（R-05〜R-07）により、畑での記録や複数人での運用は本システムの外（紙・口頭・別アプリ）で補う必要がある。
- 以上から、重大指摘 R-01〜R-03 を処置し、要求外の制約を運用手順（使い方）で明示することを、日々のタスク管理に使う条件とする。
- **1.1 追記（2026-09-25）:** 重大指摘 R-01〜R-03 は処置し、回帰試験で確認した（§10）。日々のタスク管理に使う条件のうち残るのは、中程度以下の指摘（R-04〜R-12）への対応と、要求外の制約（R-05〜R-07）を運用手順として明示することである。
- **1.2 追記（2026-09-25）:** 中程度の指摘 R-04〜R-08 を処置した（§10.4〜§10.6）。R-04 は要求から圃場0枚の日次一覧を削り、画面を合わせた。R-08 は完了時のチェック残りを知らせるようにした。R-05〜R-07 は要求外のまま機能は作らず、運用手順を `使い方_利用者.md` に明記した。これで §3 冒頭の条件（重大指摘の処置と、要求外の制約の運用手順での明示）は満たした。残るのは軽微な指摘 R-09〜R-12 である。

## 5. 指摘詳細

### R-01 要求「今週」と実装「直近7日」の不一致（重大・要求の問題）

- **分類の訂正（1.1）:** 初版では「欠陥（実装が要求に反する）」としたが、「直近7日」は `docs/基本仕様書.md` V2-1.6 で意図して定めた仕様であり、実装は基本仕様書と一致していた。問題は、要求仕様書の「今週」が基本仕様に合わせて改訂されていなかったこと（トレーサビリティの欠落）と、今週これからの作業が見えないという運用上の不足である。分類を「要求の問題」に改める。重大度は変えない。

- **事象:** 要求仕様書は日次一覧の期間を「今日」「今週」と定めている。実装の期間は「今日」「直近7日」「すべて」で、「直近7日」は今日から6日前までの過去方向の7日間である。今週これから予定している作業（例: 金曜に見た時の日曜の作業）は「すべて」を選ばないと見えない。
- **根拠:**
  - 要求: `docs/要求仕様書_第2版.md` §1（16行）、§5.2（69行）、§8（155行）、§10-1（179行）で「今日／今週」。
  - 実装: `src/clj/isas/time.clj` 82〜88行 `tokyo-days7-window` は `[(今日-6日)0:00, 翌日0:00)`。90〜99行 `tokyo-week-window` は「日次一覧では使わない」と明記。
  - 設計書は「直近7日」で書かれているが、要求仕様書は改訂されておらず、要求と設計のトレーサビリティが切れている。
- **再現結果:** 現在時刻 2026-09-25（金）09:00 で、2026-09-27（日）の作業を登録した。「今日」「直近7日」には出ず、「すべて」にだけ出た。
- **影響:** 週の段取り（週末の防除、来週頭の資材手配など）を日次一覧で確認できず、見落としにつながる。「すべて」は過去の作業も全部並ぶため、代わりにならない。
- **推奨対応:** 次のどちらかを決める。(1) 要求どおり「今週（月曜始まり）」を追加し、`tokyo-week-window` を日次一覧に使う。(2) 「直近7日」を採用するなら、要求仕様書を改訂し、あわせて「これから7日」を追加する。

### R-02 期限切れの未完了作業が見えなくなる（重大・改善）

- **事象:** 日次一覧の期間判定は作業の開始〜終了が期間と重なるかだけで決まる。予定日を過ぎて終わっていない作業は「今日」から消え、終了が8日以上前なら「直近7日」からも消える。遅れを示す表示もない。
- **根拠:** `src/clj/isas/gantt.clj` 127〜129行 `overlaps-window?`、131〜149行 `list-daily`。実行状態が未着手・着手中かどうかは期間判定に使われていない。
- **再現結果:**
  - 5日前（2026-09-20）の未着手作業: 「今日」に出ない、「直近7日」に出る。
  - 8日前（2026-09-17）の未着手作業: 「今日」「直近7日」とも出ず、「すべて」にだけ出る。
- **影響:** 雨で延びた作業、手が回らなかった作業ほど一覧から消える。毎朝「今日」だけを見る運用では、遅れている作業に気づけない。農作業では適期を逃すと損失が大きく、最も避けたい漏れ方である。
- **推奨対応:** 未着手・着手中で終了が今日より前の作業を「今日」「直近7日」にも含め、「遅れ」と表示する。少なくとも件数を一覧の先頭に出す。

### R-03 日次一覧の状態保存が他画面の変更を巻き戻す（重大・欠陥）

- **事象:** 日次一覧で実行状態を保存すると、日次一覧を読み込んだ時点の題名・開始・終了・作業名・圃場を添えて作業全体を上書き（PUT）する。保存時に版の確認（楽観ロック）がないため、別タブや作業画面で先に変えた内容が、エラーも出ずに古い内容へ戻る。
- **根拠:**
  - `src/cljc/isas/ui.cljc` 2306行 `daily-row-put-body`（日次一覧の行データから全項目を組み立てる）、4535〜4547行 `set-daily-row-status`（その内容で `PUT /api/user/gantt/{id}`）。
  - `src/clj/isas/gantt.clj` 337行 `update-row` に更新日時や版の照合がない。
- **再現結果:** 今日 08:00〜17:00 の作業「今日の作業」を日次一覧で読み込んだ後、作業画面相当の操作で題名を「今日の作業(時刻変更)」、時刻を 13:00〜18:00 に変更した。その後、日次一覧の古い内容で状態を「着手中」にして保存したところ、応答は 200（成功）で、題名と時刻が「今日の作業」08:00〜17:00 に戻った。
- **影響:** 朝に日次一覧を開いたまま、作業画面で予定を直し、あとで日次一覧から「完了」を付ける、という普通の使い方で予定が消える。本人は気づかず、記録の正しさが失われる。
- **推奨対応:** (1) 実行状態だけを変える専用の更新（例: `PATCH /api/user/gantt/{id}/status`）を用意し、日次一覧はそれだけを送る。(2) 作業の更新全般に `updated_at` などの版照合を入れ、不一致なら「他で変更されています」と返す。

### R-04 圃場0枚の利用者の日次一覧が必ず空になる（中・要求の問題）

- **事象:** 圃場を1枚も持たない利用者は、作業も作業の題名も作れない（`no_fields`）。一方、要求仕様書はスマホ日次一覧で「圃場0枚の利用者: 自分の作業」を閲覧できるとしている。作れない作業を閲覧する要求になっており、この利用者の日次一覧は常に空である。
- **根拠:** 要求 `docs/要求仕様書_第2版.md` §5.2（72〜74行）、§10-6（184行）。実装 `src/clj/isas/gantt.clj` 16行 `require-fields`。
- **再現結果:** 圃場0枚の利用者で題名の作成・作業の作成とも失敗（作業は `no_fields`）。スマホ日次一覧（今日）は空。
- **影響:** 書類・資材手配など圃場に紐づかない作業だけを担当する人（事務担当、手伝いの家族など）は、タスク管理に参加できない。要求 §5.3「面積で測れない作業も同じ実行状態で回せる」の趣旨とも合わない。
- **推奨対応:** 圃場0枚でも圃場なしの作業は作れるようにするか、要求仕様書から当該記述を削る。どちらにするかを要求として決める。

### R-05 スマホで記録できない（中・要求外）

- **事象:** スマホの日次一覧は閲覧のみで、実行状態・作業時間・チェックを変えられない。
- **根拠:** 要求 §2（28行）、§5.2（70行）、§5.5（94行）で対象外と明記。`src/cljc/isas/ui.cljc` 2560〜2591行 `daily-row-html` は閲覧専用のとき状態の文字だけを出す。
- **影響:** 畑で作業を終えても、その場で完了を付けられない。帰宅後にパソコンでまとめて付けることになり、付け忘れや時刻の記憶違いが起きる。作業時間の記録（能力 C）も後追いになり、精度が落ちる。
- **推奨対応:** 次版で少なくとも「完了にする」だけはスマホで可能にする。それまでは、使い方に「現場での完了は紙などに控え、当日中にパソコンで反映する」と運用手順を明記する。

### R-06 担当・依頼が日次一覧とつながらない（中・要求外）

- **事象:** 作業に担当者を割り当てられない。指示（他の利用者への依頼）は別機能で、`src/clj/isas/orders.clj` には作業（ガント）への参照が一切ない。依頼を受けた人の日次一覧に、その依頼は出ない。
- **根拠:** 要求 §2（25行）、§5.3（85行）で担当割当は対象外。`orders.clj` にガント関連の処理なし（机上確認）。
- **影響:** 複数人の農場では「今日は誰が何をやるか」を日次一覧で共有できない。受け手は日次一覧と指示一覧の二か所を見る必要があり、依頼の見落としが起きうる。
- **推奨対応:** 次版で、受け手の日次一覧に「今日の指示」を並べて表示する（担当割当を作らなくても、指示の作業日で表示するだけで効果がある）。

### R-07 繰り返し作業・通知がない（中・要求外）

- **事象:** 毎週の防除や毎朝の見回りなどを繰り返しとして登録できず、毎回手入力が必要。期限前や遅れの通知もない。
- **根拠:** 要求 §2（26〜27行）、§5.5（94行）で対象外。
- **影響:** 定型作業の登録漏れ・日付の打ち間違いが起きやすい。R-02 と重なると、遅れた作業に気づく手段がなくなる。
- **推奨対応:** 次版で「作業を複製して日付をずらす」操作を最低限用意する。通知は R-02 の遅れ表示で代替効果が大きいため、R-02 を先に処置する。

### R-08 チェック項目と実行状態が連動しない（中・改善）

- **事象:** チェック項目が未完了のままでも作業を「完了」にでき、警告も出ない。逆に、全チェックが済んでも状態は未着手のまま。
- **根拠:** 詳細設計どおりの仕様（状態非連動）。`src/clj/isas/gantt.clj` 337行 `update-row` にチェック項目の確認がない。
- **再現結果:** チェック項目「燃料確認」を未完了のまま、作業を「完了」に更新でき、応答は成功だった。
- **影響:** 確認漏れ（例: 防除後の器具洗浄、燃料確認）が「完了」の陰に隠れる。日次一覧の要約「チェック 0/1」を見れば分かるが、完了で絞り込むと目に入らない。
- **推奨対応:** 自動連動はしないとしても、未完了のチェックが残るまま「完了」にするときは確認ダイアログを出す。日次一覧で「完了だがチェック未完了」を目立たせる。

### R-09 複数日作業の進み具合を日ごとに残せない（軽微・改善）

- **事象:** 実行状態は作業（行）に1つだけ。3日かける稲刈りなどは、毎日「今日」に同じ作業が出て、状態は「着手中」のまま変わらない。
- **影響:** 「今日の分は終わった」を記録できない。作業時間で代用はできるが、日次一覧からは分からない。
- **推奨対応:** 運用として「日ごとに作業を分けて登録する」ことを使い方に明記する。または日次一覧に「今日の作業時間あり」を表示する。

### R-10 日次一覧からの操作導線が弱い（軽微・改善）

- **事象:**
  - 日次一覧の「作業を開く」は作業画面（`/works`）へ移るだけで、その作業を選んだ状態にならない（`src/cljc/isas/ui.cljc` 2577行）。
  - 日次一覧から作業を追加できない。
  - 開始・終了はテキスト入力（`YYYY-MM-DDTHH:MM`）で、日付選択の部品がない。
- **影響:** 朝の段取りで「今日の作業を足す・直す」たびに作業画面で探し直す必要がある。日時の打ち間違い（例: 月と日の取り違え）が R-01・R-02 の見落としを増やす。
- **推奨対応:** 「作業を開く」で該当作業を選択状態にする（`/works?id=…` など）。日時入力に日付・時刻の選択部品を使う。

### R-11 作業一覧が全期間表示（軽微・改善）

- **事象:** 作業画面の一覧は、削除していない作業を期間の区別なく全部並べる（`src/cljc/isas/ui.cljc` 2625行 `works-view`）。絞り込み・検索・ページ分けがない。

### R-12 性能とデータ保全（軽微・改善）

- **推奨対応:** 日次一覧の要約をまとめて取得する。管理者向けに日次のバックアップ手順（ファイルのコピーまたは SQLite の `.backup`）を定め、`使い方_管理者.md` に書く。

## 7. 良好と判断した点

敵対的な立場で確認したうえで、次の点は日々のタスク管理の土台として妥当と判断した。

- タスクの本体を既存のガント作業に一本化しており、予定と実行記録が二重管理になっていない。
- 実行状態・作業時間・チェック項目の入力検証（不正な状態値、時刻の前後、空の項目名、文字数上限）が API 側で行われ、不正な値が保存されない。
- 期間の判定が東京時間の暦日で統一されており、日付の境目で一覧がずれない。
- 日次一覧に作業時間の有無とチェック進捗の要約が出るため、作業を開かなくても進み具合の目安が分かる。
- 自動試験とカバレッジ 100% の維持により、既存の動作が壊れたときに検出できる体制がある。

### 10.2 R-02 遅れ

- **決定:** 遅れ＝終了日時が現在時刻以前で、完了でない作業。現在を含む期間（今日・今週・前後7日）では、期間より前に終わった遅れも一覧に含める。先週には足さない。遡る期間の上限は置かない。状態フィルタは遅れにも効く。
- **実装:** `gantt.clj` に `overdue?`・`in-daily-window?` を追加し、利用者の日次一覧と管理者の横断一覧（スマホ）で同じ判定を使う。応答の各行に `overdue` を付け、画面は表示名の前に赤地の「遅れ」を出す。並びは開始日時の昇順のままで、遅れは先頭側に来る。
- **確認:** 5日前・8日前・先月の未完了が「今日」「今週」に遅れとして出ること、完了済みの過去作業は遅れにならないこと、終了ちょうどの時刻で遅れになること、管理者の横断一覧でも同じになることを試験した。

### 10.3 R-03 状態保存による巻き戻り

- **第1段階（状態専用 API）:** `PUT /api/user/gantt/{id}/status`（本文は `execution_status` だけ）を追加した。日次一覧はこれだけを送る。`src/cljc/isas/ui.cljc` の `daily-row-put-body`（一覧の古い内容で全項目を組み立てていた関数）は削除した。
- **第2段階（版照合）:** `gantt_rows.version`（既定 1）を追加し、行更新・状態変更のたびに 1 進める。行更新 API は `version` が送られたとき、保存時の版と一致する場合だけ更新し（`UPDATE ... WHERE id = ? AND version = ?`）、一致しなければ `gantt_conflict` を返す。作業画面・ガント画面は読み込んだ `version` を送り、衝突時は案内を出して最新を読み込み直す。`version` を省略した呼び出しは互換のため照合しない。
- **確認:** 付録 9.3 の再現手順（日次一覧を読み込んだ後に作業画面で題名・時刻を変更し、日次一覧から状態を保存）で、題名・時刻・対象圃場が保たれ、状態だけが変わることを試験した。あわせて、古い版・整数でない版での保存が `gantt_conflict` になり内容が変わらないこと、状態 API の入力エラー・権限（他人・削除済み・圃場0・未ログイン）を試験した。
- **残る注意:** 版照合は `version` を送る呼び出しにだけ効く。画面はすべて送るが、API を直接使う場合は `version` を添えること。
